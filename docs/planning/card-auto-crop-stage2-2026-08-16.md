# 자르기 2단계 — 두 경로를 나란히 잰다

**작성**: 2026-08-16 PM 세션 · **상태**: 착수 대기(담당 세션 배정 필요)
**앞 단계**: 1단계 완료 — PR #256(추가 266·269)

---

## 0. 왜 2단계가 따로 있나

사용자가 1단계를 실제로 써 보고 이렇게 말했다.

> **"모두 잘 잘리고 더 안정적으로 명함을 잘 가이드해서 자동으로 잘 찍힘"**

⚠️ **좋은 신호이지만 이것은 관찰이지 실측이 아니다.** 이 저장소는 2026-08-16
하루에만 **재보지 않고 단정한 것이 여섯 번** 뒤집혔다(추가 250·269). 그래서
**기본값을 바꾸기 전에 숫자로 재는 단계**를 따로 둔다.

**지면 되돌린다.** 기존 촬영 화면을 안 지운 것이 그것을 가능하게 한다.

---

## 1. ⚠️ 이번에 반드시 함께 잴 것 — **필드별 정확도** (사용자 지시)

사용자가 1단계를 쓰고 짚었다.

> **"각 필드에 넣는 것은 아직… 부족해 보이네."**

**지금 있는 숫자로는 이 말에 답할 수 없다.**

| 지금 아는 것 | 알아야 하는 것 |
|---|---|
| **전체 94%**(140칸 중 132칸, 2026-08-14) | **이름 몇 %, 회사 몇 %, 전화 몃 %** |
| **옛 촬영 경로**로 찍은 사진 기준 | **새 스캐너로 찍으면 어떻게 되나** |

⚠️ **94%가 좋아 보이는 것은 평균이라서다.** 8칸이 틀리는데, **이름이나 회사가
틀리면 그 명함은 한 칸만 틀려도 못 쓴다.** 사용자 체감과 평균이 어긋나는
이유가 여기 있다.

### 도구는 이미 있다 — 새로 만들지 마라

| | |
|---|---|
| 정답지 만들기 | `tool/ocr_review/index.html` (로컬 전용, 네트워크 없음) |
| 채점 | `test/ocr_accuracy_score_test.dart` |

```bash
TSV=~/Downloads/scan_result.tsv \
TRUTH=~/Downloads/ocr_truth.tsv \
flutter test test/ocr_accuracy_score_test.dart
```

⚠️ **이 테스트는 "통과"가 목적이 아니라 숫자를 뽑는 것이 목적이다.** 두 파일이
없으면 조용히 건너뛴다(CI에 개인정보를 안 두므로). **출력을 봐야 한다.**

판정은 다섯이다 — **일치 / 틀림 / 미검출 / 오검출 / 둘 다 빔(분모 제외)**.
*"둘 다 빔"*을 빼는 이유: 명함에 원래 전화가 없는 경우까지 *"맞혔다"*고 세면
**정확도가 부풀려진다.**

## 2. 무엇을 재나

같은 명함을 **두 경로에 각각** 넣고 잰다. debug 스위치가 그것을 위해 있다.

| | 재는 값 | 왜 |
|---|---|---|
| **A** | **검출 성공률** — 명함 테두리를 제대로 잡았나 | 1단계의 목적 그 자체 |
| **B** | **필드별 정확도** — 이름·회사·직책·전화·이메일·주소 | ⚠️ **사용자가 지목한 것** |
| **C** | **크롭 긴 변 픽셀** — 접은 화면·편 화면 각각 | 축소 임계(1,600)와 저장 비용 |
| **D** | **재촬영 횟수** — 한 장을 얻는 데 몇 번 찍었나 | 체감 품질은 여기서 갈린다 |

### C는 1단계에서 일부 나왔다

```
2,039 · 3,315 · 3,277px   (실측, 편 화면)
```

⚠️ **접은 화면(커버)은 아직 안 쟀다.** 기존 경로에서 커버가 1,805px로 임계에
**여유 13%뿐**이었으므로(추가 246), **커버를 반드시 따로 잰다.**

## 3. 표본

**명함 20~30장.** 이미 정답지가 있는 **17장을 그대로 쓰는 것을 권한다** — 새로
만들면 정답지 작성에만 시간이 다 간다.

⚠️ **제3자 개인정보다.** 검수 도구는 로컬 전용이고, **TSV·정답지 파일을 저장소에
넣지 않는다.** 결과는 **숫자만** 문서에 남긴다.

---

## 4. 판단 기준 — 미리 정해 둔다

**재고 나서 기준을 정하면 결과에 맞춰 기준이 움직인다.**

| 결과 | 판단 |
|---|---|
| 검출·필드 **둘 다 새 경로가 나음** | 3단계로 — 기본값 교체 |
| 검출은 나은데 **필드가 나빠짐** | ⚠️ **멈춘다.** 원인부터 — 자른 뒤 글자가 잘렸을 수 있다 |
| 검출도 **비슷** | 교체하지 않는다. **의존성만 늘어난다** |
| 새 경로가 **더 나쁨** | 되돌린다. 1단계 코드는 남기고 스위치만 끈다 |

⚠️ **"조금 나음"으로 교체하지 않는다.** 새 경로는 **0.0.x가 아닌 3.0.1이라도
외부 의존성**이고, 촬영은 이 앱의 핵심 경로다.

---

## 5. 이 측정이 함께 답하는 것

**필드별 숫자가 나오면 다음 작업이 자동으로 정해진다.**

| 어디가 나쁜가 | 다음에 할 것 |
|---|---|
| **글자 자체가 틀림**(`길`→`킬`) | **R-03** 다중 OCR 패스 → **E-04**가 닫힌다 |
| 글자는 맞는데 **엉뚱한 칸에 들어감** | **R-05** 좌표 기반 분류 |
| 특정 형식만 틀림(전화·우편번호) | **R-04** 규칙 보강 — 가장 싸다 |

📌 **지금 이 중에 고르면 찍는 것이다.** 8월 14일 숫자는 **전체 평균 하나**뿐이라
어디가 나쁜지 모른다.

### ⚠️ 그리고 자르기가 R-05를 더 쓸모 있게 만들었다

```
전: 기울고 여백 있는 사진 → 좌표가 흔들린다
후: 반듯하게 펴고 딱 맞게 자름 → 좌표가 안정적이다
```

지금 파서는 **글자 줄만 순서대로** 받고 *"이 줄이 어디에 있었나"*를 모른다.
실제로 OCR이 주소를 **순서를 뒤집어** 읽어, 고치려다 **이름이 사라진** 일이
있었다(추가 213) — **위치를 알면 안 생길 문제다.**

## 6. 절차 (인계 문서와 동일)

⚠️ **검증 시작 전에 먼저 적는다.**

```
커밋 해시 / 플래그 값 / APK 빌드 시각 / 설치 시각 / PID
설치 뒤 force-stop → 재실행 → PID가 바뀐 것을 눈으로 확인
```

📌 **`Success`는 "파일이 바뀌었다"이지 "그 코드가 돈다"가 아니다.**

- ⚠️ **개수로 판정하지 않는다** — 파일명·크기·시각을 본다(기기에 명함 20장)
- ⚠️ **폴더가 둘이다** — `code_cache`와 `cache`. 어느 쪽을 보는지부터 정한다
- **검증 종류는 사용자에게 표로 물어 고르게 한다**(CLAUDE.md 4절).
  ⚠️ 이번 것은 **부분 테스트보다 크고 전체 테스트는 아니다** — 표에 **무엇을
  볼지(명함 20~30장 · 두 경로 · 접은/편 화면 · 필드별 채점)**를 구체적으로 적어야
  사용자가 규모를 알고 고른다
