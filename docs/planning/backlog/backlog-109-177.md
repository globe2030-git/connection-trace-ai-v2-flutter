### 2026-08-12 (추가 177) — 주소 검색에 입력칸 주소가 자동으로 안 들어가던 문제

**증상(사용자)**: 주소 검색을 열면 입력칸 내용이 검색에 반영되던 것이
**안드로이드·아이폰 모두** 안 된다.

**원인(코드가 깨진 게 아님)**: 원래 방식이 **클립보드 복사**였다. "검색창에
자동 입력하는 공식 API가 없다"고 보고 검색어를 클립보드에 넣은 뒤 "검색창을
탭하고 붙여넣기 하세요"라고 안내했는데, **웹뷰 안에서는 붙여넣기 메뉴가 잘 뜨지
않아** 사실상 쓸 수 없는 안내였다. 즉 "되던 게 깨진" 게 아니라 처음부터
작동하기 어려운 우회책이었다.

**해결(PR #138)**: 다음 우편번호 서비스는 `embed(el, {q: '검색어'})`로 **초기
검색을 지원한다.** HTML에 자리표시자를 두고 로드 직전 검색어를 주입해, 화면을
열면 곧바로 그 주소로 검색된 상태가 되게 했다. 클립보드 복사·붙여넣기 안내는
제거하고 "무엇으로 검색했는지 + 결과 없으면 검색어를 줄여 보라"는 안내로 교체.
`autoClose: false`로 결과가 하나여도 사용자가 확인하고 고르게 한다.

⚠️ **검색어에 사용자 입력·OCR 결과가 들어와** 따옴표·역슬래시·줄바꿈이 섞일 수
있다. 그대로 끼워 넣으면 자바스크립트 문자열이 깨져 **검색 화면 자체가 안 뜬다**
— `jsonEncode`로 감싼다. 주입을 순수 함수 `injectInitialQuery`로 빼고 테스트
4건 추가(**실제 HTML 자산에 자리표시자가 남아 있는지**까지 검사 — 자산에서 지우면
주입이 조용히 실패한다).

### 2026-08-12 (추가 176) — E-07: 주변 검색이 "안 되는 것"처럼 보이던 문제

**증상(테스터)**: "'주변' 탭의 검색 기능이 작동하지 않는다."

**조사 결과 검색은 구현돼 있었다.** TextField → `setSearchTerm` →
`filteredContacts`에서 이름·회사·직함으로 정상 필터링된다. 문제는 **검색 대상의
범위**였다. 이 검색은 명함 전체가 아니라 "지금 주변 목록에 있는 사람"만
걸러내는데, 그 목록에 들어가려면 ① 내 현재 위치를 알아야 하고 ② 명함에 좌표가
있어야 하고 ③ 반경 안이어야 한다. 테스터는 위치를 대부분 못 잡는 상태(E-10)라
목록이 늘 비어 있었고, 그래서 무엇을 입력해도 0건이었다.

**왜 QA도 못 걸렀나**: 안내가 오해를 키웠다(힌트가 '이름, 회사명, 키워드로
검색해 보세요'라 명함 전체를 찾는다고 읽힌다). 게다가 **빈 화면은 정상과 고장이
똑같이 생겨서** 검증하는 쪽에서도 통과로 넘길 수밖에 없었다.

**해결(PR #136)**:
- 힌트를 **'주변 인맥 중에서 검색'**으로 바꿔 범위를 밝힘.
- 빈 상태를 원인별로 나눔(`_NearbyEmptyState`): 위치 없음(권한/획득 실패) /
  검색어 불일치 / 주변에 없음(반경 넓히기) / 반경이 이미 전체면 좌표 없음 안내.
  검색어가 있을 때는 **'명함 지갑에서 전체 검색' 버튼**으로 실제로 보낸다.
- 탭을 바꿀 통로가 없어 `MainTabScreen.openTab()` 추가(요청을 반영한 뒤 곧바로
  비운다 — 남겨 두면 다음에 화면이 다시 만들어질 때 탭이 튄다).
- 덤: **지갑 검색의 대소문자 구분 버그** 수정. 주변 검색은 소문자로 바꿔
  비교하는데 지갑만 원문 그대로라 'SAMSUNG'이 'samsung'으로 안 찾혔다. 테스트 4건.

⚠️ **"반경을 전체로 하면 전체 검색"은 사실이 아니다** — 위치·좌표 조건은 그대로다.
그래서 그렇게 안내하지 않고 명함 지갑(전체 검색)으로 보낸다.

### 2026-08-12 (추가 175) — 지도 화면에서 감지 반경 변경(부분 테스트 통과)

사용자 요청: 지도에서 반경 원을 보다가 **거기서 바로** 반경을 바꾸고 싶다.
기존에는 지도 제목에 "· 반경 3km"라고 **글자로만** 적혀 있어, 여기서 바꿀 수
있다는 것도 바꿀 방법도 없었다.

- `_RadiusSelector` → **`RadiusSelector`로 공개**해 주변 화면과 지도 화면이 같은
  칩을 공유한다. 옵션(500m·1km·3km·5km·전체)·라벨·선택 시트가 갈라지면 두 화면이
  서로 다른 반경 목록을 보여주게 되므로 한 곳에 둔다.
- 지도 앱바 제목은 "주변 인맥 지도"로 되돌리고 오른쪽에 선택 칩 배치.
- 반경이 바뀌면 **지도 배율을 다시 맞춘다**. 안 그러면 원 크기만 바뀌고 배율은
  그대로라 원이 화면 밖으로 나가거나 점처럼 작아져 무엇이 바뀌었는지 눈으로 알
  수 없다. 빌드 중에는 지도를 움직일 수 없어 다음 프레임으로 미룬다.

**주변 화면과의 동기화는 코드가 필요 없었다**: 두 화면이 같은 `RadarViewModel`
하나를 보고 `updateRadius`가 기기 저장까지 하므로(추가 139) 자동으로 유지된다.

**검증**: analyze 19(baseline)·test 192, 안드로이드 실기기 **부분 테스트 통과**
(반경 변경 → 원·배율 반영, 주변 화면 복귀 시 값 유지, 재실행 후에도 유지,
지도 표시 인원 수 갱신). PR #134.

### 2026-08-12 (추가 174) — E-10 수정: 위치 갱신이 대부분 실패하던 문제(측위 시간 + 최근 위치 폴백)

**증상(테스터, Galaxy S24+/Android 16, 빌드 7)**: '주변'에서 지도를 눌러 위치를
갱신하면 대부분 "현재 위치를 확인하지 못했어요"가 뜨고 간헐적으로만 성공.

**원인**: `LocationService.getCurrentPosition`의 제한 시간이 **6초**였다.
`Geolocator.getCurrentPosition`은 캐시가 아니라 **새 측위를 강제**하므로
실내·콜드 스타트에서는 6초 안에 못 끝나는 일이 흔하고, 그때마다
TimeoutException → catch → `null` → "확인하지 못했어요"로 떨어졌다. 게다가 OS가
들고 있는 **마지막으로 알려진 위치를 전혀 쓰지 않았다**(geolocator 문서도 이
상황에 `getLastKnownPosition` 사용을 권한다). "대부분 실패, 간헐 성공"이라는
관찰과 정확히 맞는다.

**해결(PR #132)**:
- 제한 시간 6초 → **15초**(`LocationService.fixTimeout`). 화면에 이미 진행
  표시가 있어 실패로 끝내는 것보다 기다리는 편이 낫다.
- 실패 시 `getLastKnownPosition()` **폴백**. 단 **10분 이내**
  (`maxLastKnownAge`)만 받아들인다 — 무제한이면 한참 전 동네를 현재 위치로 삼아
  거리 계산이 틀리고 **E-06(정확도)를 오히려 키운다**. 기기 시계가 미래로 틀어진
  경우도 배제.
- 쓸 수 있는 위치가 없으면 여전히 `null`. **가짜 좌표는 만들지 않는다**(대원칙).
- 판정을 순수 함수 `isLastKnownUsable`로 분리해 테스트 5건 추가(총 192).

**상태**: 코드 병합 완료, 두 기기에 설치(커밋 `7363e48`) → **부분 테스트 대기**.
`LocationService`는 정적 Geolocator를 부르는 얇은 어댑터라 자동 테스트로는
타임아웃·폴백의 실제 동작을 증명할 수 없다 — 실기기 확인이 판정 기준이다.

### 2026-08-12 (추가 173) — E-05 수정: 지도 연속 터치 시 앱 멈춤(위치 흐름 재진입 차단)

**증상(테스터)**: "지도를 연속으로 여러 번 터치하면 앱이 멈춘다" → 강제종료.

**원인(증상≠원인)**: 크래시가 아니라 **화면이 시트로 겹겹이 덮인 것**이었다.
주변 탭의 지도 카드·위치 버튼이 부르는 `handleLocationAccessAction`에 재진입
가드가 없어, 탭할 때마다 위치 동의 시트가 새로 열리고 OS 설정도 거듭 호출됐다.
GPS 요청 자체는 `_resolveLocationAccess`의 `_isRefreshingLocation`으로 이미
단일화돼 있었지만 **시트·설정 열기 같은 UI 경로는 무방비**였다.

**해결(PR #130)**: `handleLocationAccessAction`을 단일 실행으로(진행 중이면 즉시
반환, try/finally로 반드시 해제). 레이더·설정이 같은 흐름을 공유하므로 가드는
화면이 아니라 **흐름 단위(파일 스코프)**. `NearbyMapView.show`도 중복 push 차단
(지도는 열 때마다 타일을 새로 받아 여러 장 쌓이면 메모리·네트워크 급증).
테스트용 `resetLocationAccessActionGuard()` 추가.

**⚠️ 테스트에 대한 교훈**: 처음 쓴 "연속 탭" 재현 테스트는 **가드를 꺼도
통과**했다 — 모달 배리어에 막혀 재현이 안 됐다. 즉 **결함을 못 잡는 테스트**였다.
불변식(진행 중 재호출 시 시트가 겹치지 않는다)을 직접 검증하도록 고쳐, 가드를
끄면 시트 2장이 잡혀 실패하는 것까지 확인했다. 테스트 2건 추가(총 187).

**네 경로의 성격이 서로 다르고, 그 차이를 숨기지 않았다.**

| 카톡 | 문장을 **복사**하고 카카오톡을 열어 줌 → 사용자가 붙여넣기 |
| 더보기 | OS 공유 시트(`share_plus`) |

  가려진다. OS가 제3자 앱을 전화 화면 위에 띄우지 못하게 하므로 화면 유지는

- **카톡만 다른 이유**: 카카오톡에는 "특정 상대에게 미리 채운 메시지"를 여는
  공개 경로가 없다. 링크 공유용 스킴은 있지만 여기서 보내려는 것은 링크가
  아니라 문장이다. 그래서 복사 + 앱 열기로 만들고 **안내 문구에도 "붙여넣어
  주세요"라고 사실대로** 적었다. 되는 척하는 문구를 쓰지 않는다는 것이 이
  프로젝트의 원칙이다(가짜 데이터 금지와 같은 결).
- **문자는 앱이 대신 발송하지 않는다** — 사용자가 보내기 전에 고칠 수 있다.

- **문자 본문의 공백이 `+`로 나왔다.** `Uri(queryParameters: ...)`는 웹 폼

  브라우저는 되돌려 읽지만 문자 앱은 받은 문자열을 그대로 본문에 넣는다.
  `Uri.encodeComponent`(공백 → `%20`)로 URL을 직접 조립하게 바꿨다.
  **구분자도 플랫폼마다 다르다** — Android는 `sms:번호?body=`, iOS는
  `sms:번호&body=`다. 반대로 쓰면 본문이 통째로 무시되고 빈 문자 화면만
  열린다. 기존 코드는 양쪽 다 `?`였으므로 **iOS에서는 애초에 본문이 채워지지
  않았을 것**이다(사용자가 본 `+`는 Android 쪽 증상).
- **카카오톡이 깔려 있는데 "설치돼 있지 않아요"라고 안내했다.**

  바꿨다(여는 것 자체는 조회 권한과 무관하다). 선언이 또 빠져도 같은 오안내가
  재발하지 않는다. 안내 문구도 "설치돼 있지 않아요" → "열지 못했어요"로
  고쳤다 — 원인을 확실히 알 수 없는데 단정하면 사용자를 엉뚱하게 스토어로

더보기(공유 시트)로 메일 앱을 고르면 본문만 넘어가고 **받는 사람이 비어

### 2026-08-10 (추가 141) — 주변 화면 상단 한 줄로 + 입력 폼 플로팅 라벨

**PR #79.** 사용자가 실기기 캡처(`다운로드/IMG_4025.jpeg`)에 빨간 표시를
남겨 요청했다. 공통된 지적은 **"사용성이 비슷한 것들이 각각 한 줄씩 차지해
화면을 낭비한다"**.

#### ① 반경 + 지도 + 위치 갱신을 한 줄로

```
전:                    [⊙ 반경 제한 없음 ⌄]
                       [⛶ 지도에서 크게 보기]
     ...
     [ⓘ 위치는 사용 중에만 확인해요.        ◉]

후:          [◉] [⊙ 반경 제한 없음 ⌄] [⛶ 지도 보기]
```

**두 줄을 벌었다.** 반경과 지도는 "주변을 어디까지, 어떻게 볼 것인가"라는
같은 결정에 속하는데 각각 한 줄씩 차지하고 있었다.

- **`Row`가 아니라 `Wrap`을 썼다.** 반경이 "제한 없음"일 때 라벨이 가장
  길어지는데, 좁은 화면이나 시스템 글자 크기를 키운 기기에서는 세 요소가 한
  줄에 안 들어갈 수 있다. `Row`면 그 상황에서 오버플로 줄무늬가 뜨지만
  `Wrap`은 조용히 아랫줄로 내려 준다. 같은 이유로 버튼 문구를 "지도에서 크게
  보기" → **"지도 보기"** 로 줄였다(아이콘이 함께 있어 뜻은 유지된다).
- 위치 갱신 아이콘은 상태에 따라 하는 일이 달라(갱신 / 위치 설정하러 가기)
  툴팁과 `Semantics` 라벨을 상태별로 나눴다.

#### ② "위치는 사용 중에만 확인해요" 줄 제거

### 2026-08-10 (추가 137) — P1-41 닫힘: 동의 화면에 제한된 범위가 애초에 없었다

추가 136으로 UI를 정리한 뒤 "CASA를 정말 안 받아도 되는가"를 확인하는 과정에서
**P1-41 ②(콘솔에서 `gmail.readonly` 제거)가 처음부터 할 일이 없었다는 사실**이
드러났다. 추가 128 이래 "베타 배포 전에 반드시 끝낼 것"으로 붙들고 있던
항목이라, 왜 착각이 생겼는지까지 남긴다.

**콘솔 실물 확인**(프로젝트 `connection-sense`, Google 인증 플랫폼 → 데이터
액세스):

- 민감하지 않은 범위 / 민감한 범위 / **제한된 범위** — 세 표가 **전부 비어
  있음**. `gmail.readonly`는 코드에만 있었고 동의 화면에 등록된 적이 없다.
- "범위 추가 또는 삭제" 대화상자에 Gmail 범위들이 보이지만 **전부 체크 해제**
  상태다. 이 목록은 등록된 범위가 아니라 *사용 설정된 API의 선택 후보*이며,
  Gmail API가 프로젝트에 enable돼 있어서 후보로 뜨는 것이다. **API를 켜 둔
  것만으로는 CASA 대상이 되지 않는다** — 이 구분을 모르면 이 화면을 보고
  "아직 등록돼 있다"고 오판하기 쉽다.
- 대상(Audience): 게시 상태 **프로덕션**, 사용자 유형 **외부**, OAuth 사용자
  한도 100명 중 2명.

**왜 착각했나.** 추가 128 시점에 "코드가 `gmail.readonly`를 요청한다"는
사실에서 "동의 화면에 등록돼 있을 것"을 추론했고, 콘솔을 열어 확인하지
않았다. CLAUDE.md의 "코드는 맞는데 실물이 틀린다" 유형과 방향만 반대인 같은
함정이다 — 이번엔 **실물이 이미 맞는데 코드를 보고 틀렸다고 단정**했다.
외부 콘솔 상태를 근거로 P1 항목을 세울 때는 캡처든 CLI든 실물을 붙일 것.

**Google 공식 문서로 확인한 기준**(2026-08-10):

- `gmail.readonly`는 restricted(제한된) 범위 — Gmail API 문서 "Restricted
  scopes" 표에 있음.
- restricted를 쓰면 연 1회 CASA 보안평가가 **강제**. 데이터가 서버로 나가면
  상위 등급(AL2).
- **비민감 범위만 쓰면 앱 검증 자체가 의무가 아니다** — "If your app utilizes
  only non-sensitive scopes, it is not mandatory for your app to complete the
  app verification process."
- 판정 기준은 소스코드가 아니라 **동의 화면에 등록된 범위**다. 콘솔이 범위마다
  등급을 자동 표시한다.
- 단 **브랜드 확인(brand verification)** 은 남는다 — 동의 화면에 앱 이름·로고를
  띄우려면 필요한 가벼운 절차이고 CASA와 무관하다.

**결과**: P1-41 **닫힘**. P1-31(CASA 비용)은 **현재 미발생**(대상 자체가 아님)으로
갱신 — 사라진 게 아니라 Gmail을 다시 켜면 되살아나는 조건부 비용이다.

**Gmail API 사용 설정은 켠 채로 둔다(2026-08-10 결정).** 처음엔 "안 쓰는 API니
꺼 두면 후보 목록에서 빠져 깔끔하다"고 제안했으나, 사용자가 "그러면 앱
로그인도 막히는 것 아니냐"고 물어 이득과 위험을 다시 비교한 결과 **끄지 않기로
했다.**

- **로그인은 안 막힌다.** 로그인은 `accounts.google.com`(Google Identity)과
  Identity Toolkit API를 쓰고, `gmail.googleapis.com`을 부르는 코드는
  `email_sync_service.dart` 두 곳뿐인데 그마저 추가 136으로 호출 경로가
  끊겼다. `openid`/`email`/`profile`은 어떤 API도 켜지 않아도 동작한다.
- **그런데도 끄지 않는 이유는 이득이 없어서다.** 얻는 건 "범위 후보 목록이
  깔끔해진다" 뿐이고 검증·CASA·비용 어디에도 영향이 없다. 반면 콘솔에서
  옆줄의 Identity Toolkit·Firestore·Generative Language를 잘못 누르면
  **앱이 즉시 멈춘다.** 이득 대비 오조작 위험이 맞지 않는다.

즉 **차단은 UI 레벨에서만 한다**가 최종 형태다. 다음 세션이 "안 쓰는 API가
켜져 있다"를 정리 대상으로 오해하지 않도록 여기에 못 박아 둔다.

   → 83.3 → 76.9로 단조 감소가 되고 추가 원가는 월 ₩66뿐이다.
2. **무료 5회를 매월 리셋하느냐가 월 순이익을 3.2배 가른다.** 매월 주면
   유료 사용자도 매달 5회를 공짜로 받아 ₩1,000(10회) 상품이 스스로 무너진다
   (+$1,061 vs +$3,349, 손익분기 인원 609명 vs 161명). **가입 시 1회 지급**을
   권고.
3. **충전형은 이 문서에서 유일하게 다운사이드가 없는 구조다.** 사용이 곧
   매출이라 많이 쓸수록 이익이 **는다**(+$3,349 → +$6,017). 반대로 구독은
   많이 쓸수록 **준다**(+$5,136 → +$3,286). 대신 충전형은 매출 예측이 어렵다.
4. **공헌이익률이 네 티어 모두 80~81%대로 사실상 같다.** AI 원가가 판매가의
   3~5%뿐이고 실질 원가는 스토어 수수료 15% 하나다 → **회차를 얹는 건 거의
   공짜, 가격을 깎는 건 그대로 손실**. 프로모션은 할인이 아니라 회차 증정으로.

**주 단위 한도 검토(13-5, 사용자 제안)** — **권하지 않는 것으로 결론**.
사용량을 18% 눌러도 1인당 이득이 **월 ₩10**인데, 해지율이 0.5%p만 올라도
상쇄된다(순매출 ₩1,997.5 기준 1%p = ₩20). 더 큰 문제는 제약의 위치다 —
이 앱의 핵심 사용 장면은 **행사·모임 다음 날 명함을 몰아서 등록하는 것**인데
주 한도는 정확히 그 순간에만 걸린다. 회차제는 이미 회차가 상한이라(₩1,000 =
10회, 잠식폭 3.9%) 막을 대상도 없다. 대안으로 **이미 구현된 `DAILY_LIMIT`을
티어별로 재사용**할 것을 권고 — 목적은 원가가 아니라 어뷰징·동시성 사고
방어이며, 정상 사용자가 평생 안 만날 높이(₩1,000 티어 5회/일)로 잡는다.

**개발·법무 부담(14-1)**: 충전형은 소비형 인앱결제라 **결제 5건 중 가장 무거운

### 2026-08-09 (추가 120) — P1-39 A안: 경합 발견 → 결정적 양방향 동기화로 재작성

**QA가 잡은 진짜 결함**: 시나리오 3(편집)·4(삭제)를 돌리니 편집·삭제가 B로
전파됐다 — 그런데 추가형 병합(mergeFromServer)은 이미 있는 id를 안 건드리므로
그럴 수 없다. 원인은 **경합(race)**: 로그인 시 `auth_gate`가 `setCurrentUid`
(암호화 로컬 복호화 재로드)를 **기다리지 않고** `restoreFromServerIfEmpty`를
불러서, 복호화가 끝나기 전 로컬을 "비었다"고 오판 → 서버 전체를 다시 받아
로컬을 통째로 덮어쓰고 있었다. 그래서 편집·삭제가 "우연히" 전파됐고, 추가
119의 "검증 완료"는 사실 병합이 아니라 이 경합 덕분이었다. **비결정적**(기기·
타이밍에 따라 다름)이고 **오프라인 로컬 데이터 손실 위험**이 있는 버그다.

**A안 — 결정적·안전한 양방향 동기화로 재작성**:
- **경합 수정**: `setCurrentUid`가 반환하는 Future를 붙잡아 동기화 전에 await
  (복호화 로드 완료 보장). `context.mounted`로 가드.
- **편집 전파(LWW)**: `ContactModel.updatedAt`(nullable) 추가. add/update 시
  지금 시각을 찍고, 병합에서 updatedAt이 더 최신인 쪽을 채택. null은 epoch 취급.
- **삭제 전파(tombstone)**: 삭제 시 `users/{uid}/deletedContacts/{id}`에 삭제
  시각 기록. 병합에서 tombstone이 채택본보다 최신이면 제거. 삭제 후 편집한
  건(부활)은 살아남음.
- **손실 방지**: 로컬에만 있거나 로컬이 더 최신인 명함은 서버로 올림(push).
- `computeServerAdditions`/`mergeFromServer` → **순수 함수 `mergeSync`
  + `syncWithServer`**로 대체. `firestore.rules`에 deletedContacts 추가.
- `auth_gate` 정상 로그인 경로만 `syncWithServer`(계정 전환 "유지"·prefs 실패
  경로는 안전하게 `restoreFromServerIfEmpty` 유지).

**검증**: mergeSync 순수 함수 테스트 7건(추가·편집 LWW 양방향·삭제·부활·
손실방지·null), flutter analyze 0, flutter test 100건. **실기기 2대 재검증 예정**
(rebuild + QA 시나리오 재실행). ⚠️ tombstone 정리(오래된 것 prune)·프로필 동기화·
크로스기기 전화번호 중복은 별도로 남음.

**원인**: Google Sign-In(Android)은 **(패키지명 + 서명 키 SHA-1)** 조합을 서버에서
검증하는데, Firebase에는 **debug 키 SHA-1(`5482f3fa…`)만** 등록돼 있었다. P1-19에서
업로드 키 서명으로 바꾸면서 APK의 SHA-1이 `419aee69…`로 달라졌고, 그게 등록돼
있지 않아 거부됐다. iOS는 SHA-1이 아니라 번들 ID로 검증해서 영향이 없었다.

**해결**: Firebase Console → 프로젝트 설정 → Android 앱 → **디지털 지문 추가**로
업로드 키 SHA-1(`41:9A:EE:69:81:62:A4:4C:1F:8F:2A:10:8F:0F:F7:E8:10:39:EA:D7`)과
SHA-256을 등록. **서버 측 검증이라 APK 재빌드·재설치 없이** 1~2분 뒤 로그인됨.

**얻은 것/주의**:
- keytool로 지문 뽑을 때 **한글 로케일 버그**(`IllegalFormatConversionException`)가
  터진다 → `keytool -J-Duser.language=en -J-Duser.country=US ...`로 우회.
- 이 맥의 debug 키 = `5482f3fa…`(등록돼 있어 debug 빌드는 Google 로그인이 됨).
  즉 급하면 **debug 빌드가 테스트 우회로**가 된다.
- 콘솔에 `c392262a…`라는 정체불명 SHA-1이 "충돌"로 떠 있었다(우리 키 아님 —
  같은 패키지가 든 **옛 중복 프로젝트** 흔적으로 추정). 우리 동작엔 무관하나
  정리 대상.
- ⚠️ **다음 단계**: Play로 배포하면 Play가 **앱 서명 키**로 재서명하므로, 그
  **Play 앱 서명 키의 SHA-1도 Firebase에 추가 등록**해야 Google 로그인이 된다
  (Play Console → 앱 무결성/앱 서명에서 확인). P1-19의 남은 후속 작업.

### 2026-08-09 (추가 109) — Android 릴리스 서명 키 설정 (P1-19 완료)

**배경**: 그동안 Android 릴리스 빌드가 debug 키스토어로 서명돼 있어(`build.gradle.kts`

   실수 방지용 안전망이지 보관 위치가 아니다).
2. **`android/key.properties` 작성** — `storePassword`/`keyPassword`/`keyAlias`/
   `storeFile` 4줄. gitignore로 무시됨(`git check-ignore`로 확인) — 비밀번호는
   커밋되지 않는다.
3. **`android/app/build.gradle.kts` 수정** — 상단에서 `key.properties`를 읽고,
   `signingConfigs.release`를 만들어 릴리스 빌드에 연결. **파일이 없으면 debug 키로

성공. **`apksigner`(APK)·`jarsigner`(AAB)로 서명자 인증서가 debug가 아닌 업로드
키(`CN=…CreamHouse…, C=KR`)임을 확인**했다.

- `key.properties`의 비밀번호는 **키스토어를 만들 때 입력한 그 비밀번호**여야 한다.
