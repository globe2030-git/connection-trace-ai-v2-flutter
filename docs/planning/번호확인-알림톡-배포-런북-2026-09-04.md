### 0단계 — TTL 정책 🔒 ⚠️ **2026-09-05에 다시 쟀다 — 「먼저」가 아니었다**

```bash
gcloud firestore fields ttls update expiresAt \
  --collection-group=phoneSendLedger --enable-ttl \
  --project=connection-sense
```

> 🚨 **이 절의 예전 문장은 틀렸다. 지운 것이 아니라 무엇이 틀렸는지 남긴다.**
>
> 예전에 이렇게 적혀 있었다 — *"순서를 바꾸지 마라 — TTL 은 소급되지 않는다.
> 함수를 먼저 배포하면 그 사이 쌓인 장부 문서는 `expiresAt` 이 있어도 **정책이
> 없어 영영 안 지워진다.**"*
>
> **공식 문서 두 곳이 정반대를 말한다**(2026-09-05 확인, 원문 인용):
>
> - Firebase — *"Applying a TTL policy on an existing collection group results
>   in a bulk deletion of all expired data according to the new TTL policy."*
> - Cloud — *"If a document has an expiration time in the past and you add a
>   new TTL policy to the collection, the document will be deleted within 24
>   hours of when the TTL policy finishes setup and becomes active."*
>
> 즉 **필드를 갖고 있는 문서는 정책을 나중에 켜도 지워진다.**

#### 그러면 진짜로 안 지워지는 것은 무엇인가

```
정책을 켜기 전에 쓰인 문서
  ├ expiresAt 이 있다   →  정책을 켜면 지워진다 ✅   (위 인용 둘)
  └ expiresAt 이 없다   →  영영 안 지워진다 🚨      ← 진짜 사각지대
```

⭐ **`expiresAt` 이 없는 문서 = 필드를 심는 코드가 배포되기 「전」에 쓰인 것**이다.
그러므로 **위험한 경계는 「정책을 켜기 전」이 아니라 「코드를 배포하기 전」**이다.
*"Leaving the field absent … disables the TTL for the individual document."*

#### 🚨 그래서 순서 제약이 오히려 풀린다 — 그리고 그래야 켤 수 있다

**2026-09-05 실측**: 두 장부가 **둘 다 0건**이었다.

```
phoneSendLedger   0 건
deviceLedger      0 건
cardSources       0 건 · ocrStats 12 건 (같이 잰 값)
잰 법   globe2030님 콘솔(컬렉션 그룹 드롭다운) + PM 의 Firestore REST 카운트 교차 확인
```

globe2030님이 콘솔에서 드롭다운을 열었을 때 **두 장부가 목록에 없었다** — 문서가
한 건도 없어서다. **즉 「정책을 먼저」는 콘솔에서 물리적으로 안 된다.**

⭐ **그런데 위 인용대로라면 먼저 켤 필요가 없다.** 실제로 가능한 순서는 이것이다.

```
① 함수를 배포한다              expiresAt 을 심는 코드가 올라간다
② 장부에 첫 문서가 생긴다        그때부터 모든 새 문서가 필드를 갖는다
③ 그다음 TTL 정책을 켠다        ②의 문서들도 함께 대상이 된다(위 인용)
```

📌 **①과 ③ 사이에 쌓인 것은 잃지 않는다** — 전부 `expiresAt` 을 갖고 있기 때문이다.
⚠️ 다만 **즉시는 아니다** — *"this bulk deletion is also not instantaneous and
depends on how much data exists for that collection group."* 그리고 정책이
켜지는 데만 *"a minimum of ten minutes or more"* 가 걸린다.

⭐ **지금 이 순간의 손실 가능량은 0이다** — 배포 이전에 쌓인 문서가 0건이므로,
**지금 배포하면 필드 없는 문서가 하나도 안 생긴다.** 이 창은 **오늘만** 열려 있다.

#### ⚠️ 확인하지 못한 것 — 추정을 결론으로 쓰지 않는다

**`gcloud` 가 「문서가 하나도 없는 컬렉션 그룹」에 TTL 정책을 만들어 주는지는
확인하지 못했다.**

| 물음 | 문서가 말하는 것 |
|---|---|
| TTL **필드**가 미리 있어야 하나 | ❌ 아니다 — *"You can select a field that already exists or you can designate a field that you plan to add later."* |
| **컬렉션 그룹**이 미리 있어야 하나 | **적혀 있지 않다** — 된다고도 안 된다고도 안 나온다 |
| 콘솔은 어떻게 고르나 | 문서는 *"Enter a collection group name"* — **입력**이라고 적혀 있다 |

🚨 **문서와 실제 콘솔 UI가 다르다.** 문서는 「이름을 입력」인데 실제로 본 것은
**드롭다운**이었다. **「드롭다운에 없다」는 「API 가 거부한다」가 아니다** — UI 의
한계일 수 있다. 확실히 아는 길은 **실제로 `gcloud` 를 돌려 보는 것 하나뿐**이고,
그것은 globe2030님 권한이라 이 문서를 쓴 세션은 돌리지 않았다.

📌 **그런데 위 ①②③ 순서를 쓰면 이 물음에 답하지 않아도 된다** — ③ 시점에는
컬렉션 그룹이 이미 존재한다. **모르는 것을 몰라도 되게 순서를 바꾼 것이다.**

📌 **`deviceLedger` 도 같은 순서다**(추가 699 · PR #861). 그쪽은 문서가
`config/billing.model` 을 켠 뒤에야 생기므로 **배포 → 과금 ON → 첫 문서 → TTL**
이 되고, 과금을 켜기 전까지는 쌓이는 것이 없다.

📌 **`phoneSendLedger` 는 탈퇴해도 남는다 — 결함이 아니라 결정이다**(추가 642).
지우면 **탈퇴 → 재가입으로 하루 5통 상한이 초기화**된다

### 3단계 — testMode 로 실기기 확인 📖

앱에서 번호를 넣고 **알리고 콘솔의 발송 내역**에 testMode 건이 찍히는지 본다.
**이때는 실제 문자가 오지 않는다.**

⚠️ **게이트가 아직 없으므로 인증 화면이 자동으로 뜨지는 않는다.** 3단계를 보려면
게이트를 잠깐 켜야 하는데, 그 방법은 아래 「게이트를 안전하게 보는 법」에 있다.

### 4단계 — 실제 발송을 연다 🔒

```bash
firebase functions:secrets:set ALIGO_TEST_MODE --project connection-sense   # 값: N
firebase deploy --only functions:phoneOtpRequest,functions:phoneOtpConfirm \
  --project connection-sense
```

⚠️ **시크릿만 바꾸면 반영되지 않는다 — 함수를 다시 배포해야 한다.**

#### 🚨 이 채널로는 **광고를 보내지 않는다** (2026-09-06 결정)

여기서 발송이 열리면 **카카오톡 채널이 실제로 도는 창구**가 된다. 친구가 쌓이면
광고 생각이 나는 자리이므로 못 박아 둔다.

```
쓰는 것    인증번호 알림톡 — 이용자가 직접 요청했을 때만
안 쓰는 것  광고 · 홍보 · 이벤트 · 재방문 유도 — 전부
```

**이유**: 방침 `privacy-policy.html:607`·`:922` 가 광고 전송 매체를
**"(이메일 · 앱 알림)"** 으로 **닫아 놨다.** 카카오톡으로 광고를 한 번 보내면
**그 문장이 거짓**이 되고, 그때는 방침을 고쳐야 한다.

📌 **이유까지 적는 이유**: 금지만 있으면 다음 사람이 *"왜 안 되지?"* 하고
풀어 버린다. ⭐ 정말 보내려면 **방침 개정 → 고지 기간 → 광고 동의 화면에 매체
추가 → 동의 재취득** 순서다(동의는 **매체별**이다 — 2026-08-25 법무 회신).

⚠️ **방침에는 이 금지를 쓰지 않는다** — 방침은 「하는 일」을 적는 문서다
(법무 2026-09-06 회신). 같은 결정이 `docs/marketing/marketing-plan-2026-08-14.md`
§6-5 에도 있다.

### 5단계 — 게이트를 켠다 🔒 **← 여기서부터 사람이 겪는 것이 바뀐다**

🚨 **이 단계 전에 방침 v2.7 이 게시돼 있어야 한다.** 아래 §4 참고.

## 3. 게이트를 안전하게 보는 법 — 아무도 안 걸린 채로

```
enforce = true · enforceFrom = 2030-01-01   →  전원 통과. 스위치가 도는지만 본다
enforceFrom 을 잠깐 과거로                   →  본인 계정으로 인증 화면 확인
다시 미래로                                  →  원복
```

🚨 **`config/phoneVerification` 문서를 잘못 만들면 테스터 전원이 인증 화면에
갇히고 나갈 길이 없다**(추가 645). **문서를 만드는 것 자체가 스위치다** —
값을 바꾸는 게 아니라 **없는 것을 만드는 것**이 켜는 동작이다
(`config/billing.model` 과 같은 성질).

## 4. 🚨 방침과의 순서 — 5단계 앞에 걸린다

```
지금            발송이 안 돈다 → 게시본 v2.6 의 「현재 재위탁은 없습니다」가 참이다
게이트를 켜면    카카오 재위탁이 실제로 생긴다 → 그 문장이 거짓이 된다
```

**v2.7(재위탁을 적은 판)은 아직 게시 전이다.** 초안은
[`../legal-drafts/privacy-policy-v2.7-draft.html`](../legal-drafts/privacy-policy-v2.7-draft.html)
에 있고 **파일 머리에 게시 절차 5단계**가 적혀 있다.

⭐ **2~4단계까지는 방침과 무관하다** — 발송 경로가 열려도 **게이트가 없으면
아무도 그 경로를 안 탄다.** 📌 **그러니 경계는 「배포」가 아니라 「게이트」다.**

⚠️ **게이트를 켜는 날과 v2.7 게시일이 벌어지면 그 사이에 방침이 거짓이 된다.**
붙여서 진행하거나, v2.7 을 먼저 게시한다.

## 5. 되돌리기(롤백)

| 무엇이 문제인가 | 되돌리는 법 | 되돌아가나 |
|---|---|---|
| 발송이 잘못된다 | `ALIGO_TEST_MODE` 를 `Y` 로 되돌리고 재배포 | ✅ 즉시 |
| 사람들이 인증 화면에 갇힌다 | `config/phoneVerification` 의 `enforceFrom` 을 먼 미래로 | ✅ 즉시 |
| 함수 자체가 문제다 | 이전 판으로 재배포 | ✅ |
| **장부가 쌓였다** | TTL 이 30일 뒤 지운다 | ⚠️ **즉시는 아니다** |

🚨 **되돌릴 수 없는 것 하나** — **필드를 심는 코드가 배포되기 「전」에 쌓인 장부**는
`expiresAt` 이 없어 정책이 못 읽는다. 영영 남으므로 **손으로 지워야 한다.**

⚠️ **예전에는 이 문장이 *"TTL 을 켜기 전에 쌓인 장부"* 였는데 틀렸다**(2026-09-05
정정, 0단계 참고). **정책을 나중에 켜도 필드가 있는 문서는 지워진다.** 경계는
**정책이 아니라 배포**다. ⭐ 2026-09-05 실측으로 **배포 이전 문서가 0건**이라,
지금 배포하면 이 위험 자체가 안 생긴다.

## 6. 켠 직후 스모크 체크

```
□ 번호를 넣으면 알림톡이 온다 (안 오면 대체문자가 오는지도 본다)
□ 인증번호를 넣으면 통과한다
□ 틀린 번호를 넣으면 막힌다
□ 같은 번호로 6번째 발송이 막힌다 (하루 5통 상한)
□ Firestore users/{uid} 에 phoneVerifiedAt · phoneHash 만 있고 원문이 없다
□ phoneSendLedger 문서에 expiresAt 이 찍혀 있다
```

⚠️ **마지막 둘은 콘솔 실물로 본다** — 이 저장소는 *"코드는 맞는데 실물이 틀린"*
결함을 반복해서 겪었다(CLAUDE.md 4절).

⭐ **대체문자는 우리가 두 번 부르지 않는다** — 알림톡이 실패하면 **알리고가 같은
호출 안에서** 문자로 떨어뜨린다(`phoneOtpSender.ts:82`).

## 7. 리스크 & 주의

- 🚨 **`--only functions` 로 넓게 배포하지 마라** — 과금·지갑 코드가 함께 나간다.
- ⚠️ **~~TTL 을 나중에 켜지 마라 — 소급이 안 된다~~** → **2026-09-05 정정.**
  필드가 있는 문서는 **나중에 켜도 지워진다**(0단계의 원문 인용 둘). 지켜야 할 것은
  **「필드를 심는 코드를 먼저 배포한다」**이지 정책 순서가 아니다.
- 🚨 **게이트를 시험 삼아 켜지 마라** — 테스터 전원이 갇힐 수 있다. §3 방식으로.
- ⚠️ **시크릿 값을 문서·대화·커밋에 남기지 마라.**
- ⚠️ **번호 원문은 서버에 저장되지 않는다**(`phoneHash` HMAC-SHA256 + 시각만).
  이 사실이 방침 v2.7 문안의 근거이므로 **구현을 바꿀 때 방침도 함께 본다.**
- 📌 **「3분」이나 앱 이름이 바뀌면 템플릿 재심사 영업일 2일**이다. ⭐ 법인명은
  템플릿 문안에 안 들어가므로 표기 통일(추가 673)은 재심사 대상이 아니다.

## 9. ⭐ 이 정정에서 남길 것은 결론이 아니라 **방법**이다

2026-09-05에 여기서 막혔던 순서를 되짚어 둔다. **결론(「배포가 먼저」)만 적으면
다음 사람이 다른 물음 앞에서 똑같이 막힌다.**

```
막힌 자리   "빈 컬렉션 그룹에 TTL 을 만들 수 있는가?"
            → 콘솔 드롭다운에 안 뜬다. gcloud 는? **문서에 안 적혀 있다**
            → 확실히 알려면 실제로 돌려 봐야 하는데 그것은 사용자 권한이다
```

**그때 한 것은 「알아내기」가 아니라 「안 알아도 되게 만들기」였다.**

```
① 왜 그 물음이 생겼나를 거슬러 올라간다
     → "정책을 먼저 켜야 한다" 는 제약 때문이다
② 그 제약의 근거를 원문으로 확인한다
     → "TTL 은 소급되지 않는다" 였는데 **공식 문서 두 곳이 정반대를 말했다**
③ 근거가 무너지면 제약이 사라지고, 물음도 함께 사라진다
     → 배포를 먼저 하면 ③ 시점에 컬렉션 그룹이 이미 있다. **물을 필요가 없다**
```

⭐ **모르는 것을 몰라도 되게 순서를 바꾼 것이다.** 그래서 *"gcloud 가 빈 컬렉션
그룹을 받아 주는지"* 는 **지금도 모르고, 모르는 채로 적어 두었다.**

🚨 **「확인 못 했다」를 지우지 마라.** 지우면 다음 사람이 「확인한 것」으로 읽는다.

📌 **그리고 근거를 뒤집을 때는 원문을 인용해 남긴다.** 이 런북의 틀린 문장은
**지우지 않고** 「무엇이 틀렸는지」로 0단계에 남겨 뒀다 — 결론만 고치면 다음
사람이 같은 자리에서 같은 추정을 한다(규약 4절).

⚠️ **그런데 이 방법에도 조건이 있다** — ②에서 **원문에 닿을 수 있어야** 한다.
이번에는 공식 문서가 있었다. 없으면 ③으로 못 가고, 그때는 **「실제로 돌려 본다」
말고 길이 없다** — 그것이 사용자 권한이면 **그대로 올린다.**
