## 3. ③ 로직이 순수 함수로 빠져 있나 — **전부 (가)다**

PM 이 준 세 갈래로 갈라 보면:

```
(가) 빠져 있고 테스트도 있다 — 호출부만 안 잠김     ← 16개 전부
(나) 빠져 있는데 테스트가 없다                      0개
(다) 아예 index.ts 안에 박혀 있다                   0개  ※ 아래 ⚠️
```

⭐ **좋은 소식이다.** 이 저장소는 **이미 로직을 빼 놓았고 그것을 촘촘히 잠갔다.**

| 모듈 | 테스트 | 모듈 | 테스트 |
|---|---|---|---|
| `socialAuth` | 36 | `deviceLedger` | 15 |
| `phoneOtp` | 29 | `purchases` | 14 |
| `adminAuth` | 24 | `pilotEvents` | 11 |
| `briefingPrompt` | 22 | `walletCredits` | 11 |
| `creditGrant` | 17 | `referralCode` | 9 |
| `phoneOtpSender` | 17 | `usageReset` · `cardPhotoCleanup` | 8 · 8 |
| `kakaoUnlink` | 15 | 나머지 5개 | 6씩 |

**19개 모듈 전부 짝 테스트가 있다.** 없는 것은 `index.ts` 와 `adminEmails.ts`
(상수 목록) 둘뿐이다.

⚠️ **그런데 (다)가 0개라는 것은 「모듈을 쓰는가」로만 판정한 결과다.** 핸들러
본문이 249·364·261줄인데 **그 안에서 모듈 호출은 몇 줄뿐**이다. **나머지 수백 줄
— 권한 검사, 트랜잭션 순서, 오류 분기, Firestore 쓰기 — 은 여전히 `index.ts`
안에 박혀 있다.** 즉 실제로는 **(가)와 (다)가 한 핸들러 안에 섞여 있다.**

> **모듈을 부른다고 그 핸들러가 잠긴 것이 아니다.
> 잠긴 것은 「모듈이 옳게 계산하는가」이고,
> 안 잠긴 것은 「그 계산을 옳은 때에 옳은 순서로 쓰는가」다.**

📌 오늘 이 저장소에서 나온 결함들이 정확히 뒤쪽이었다 — [추가 79] *"재시도 로직이
죽어 있음: 서비스는 정상, 부르는 쪽이 없음"*, [추가 687] *"`deleteCardImage` 호출이
0건"*. **둘 다 순수 함수는 멀쩡했다.**

### 무엇으로 이걸 알았나 — 깨뜨려 보기

개발C 가 `#861` 에서 이렇게 확인했다:

```
expiresAt 을 심는 줄 + import 를 index.ts 에서 지운다
→ npm test 272건 전부 통과 · 0건 잡힘
```

⭐ **커버리지 숫자보다 이 방법이 낫다.** 커버리지는 **그 줄이 실행됐는지**만 보고,
**그 줄이 틀렸을 때 실패하는지**는 안 본다.

> **줄을 지우고 테스트가 여전히 통과하면, 그 줄은 안 잠긴 것이다.**

⚠️ **다만 「실패했다」를 바로 「잡았다」로 읽으면 안 된다.** 오늘 겪었다 — 호출을
없앤 자리에 없는 함수를 넣었더니 **컴파일이 깨져 테스트가 아예 안 돌았다.**
그건 잡은 것이 아니다. **컴파일은 되는 채로** 깨뜨려야 한다.

## 4. ④ 가장 위험한 다섯 — 그리고 왜 그 다섯인가

고른 기준은 **「틀렸을 때 되돌릴 수 없는가」 × 「본문이 큰가」 × 「조용히
틀리는가」** 셋이다.

### 1위 · `onUserDeletedCleanup` (227줄, `onDocumentDeleted`)

**탈퇴하면 데이터를 지운다.** 여기가 틀리면 **안 지워진 개인정보가 서버에 남는데
아무도 모른다** — 실패해도 화면이 없다. 방침은 *"탈퇴 시 파기"* 라고 적고 있어
**어긋나는 것 자체가 법적 리스크**다.

🚨 **방법 A(`onCall` 만 grep)로 세면 이 핸들러가 목록에 아예 안 나온다.** 오늘
개발A 가 *"탈퇴해도 서버에 남는 것 둘"* 을 [추가 690] 으로 찾은 자리이기도 하다.

### 2위 · `verifyAndGrantPurchase` (261줄)

**결제**다. 영수증 검증 → 지급이 한 흐름인데, **중복 지급**이나 **검증 실패인데
지급**이 나면 돈이 오간다. 규약 6장이 *"과금은 검증 없이 나가면 안 된다"* 고
못 박은 자리다.

### 3위 · `bootstrapAccount` (**364줄 — 가장 크다**)

가입 직후 **무료 회차 지급 + 기기 대장 + 추천 코드**가 한 덩어리로 돈다.
`config/billing.model` 을 켜는 순간 **전 테스터에게 지급이 시작된다**. 켜기 전에
잠가 둬야 하는데, **지금은 켜는 스위치만 있고 그 경로를 잠근 것이 없다.**

### 4위 · `generateBriefing` (249줄)

**차감 + 외부 LLM 호출**. 차감과 호출의 **순서**가 틀리면 *"돈은 빠졌는데 결과가
없다"* 또는 그 반대가 된다. 순수 함수(`walletCredits`)는 **얼마를 뺄지**만 알고,
**언제 빼는지**는 여기 있다.

### 5위 · `kakaoUnlinkWebhook` (93줄, **`onRequest`**)

**외부에서 들어오는 유일한 HTTP 진입점**이다. 다른 열다섯은 인증된 앱이 부르지만
이것은 **카카오 서버가 부른다** — 즉 **인증 검사가 이 함수 안에 있다.** 그게
틀리면 남이 부를 수 있고, 그 결과가 **삭제**다.

📌 **줄 수만 보면 93줄로 작아 5위지만, 「누가 부를 수 있는가」로 보면 1위여도
이상하지 않다.**

### 왜 이 다섯인가 — 한 줄로

> **되돌릴 수 없고(돈·파기), 본문이 크고(순서와 분기가 많고),
> 틀려도 화면이 없다.** 셋이 겹치는 자리다.

⚠️ **`socialSignIn`(234줄)과 `phoneOtpConfirm`(177줄)을 뺐다.** 크고 중요하지만
**틀리면 이용자가 즉시 안다**(로그인이 안 된다). 위 다섯은 **조용히 틀린다.**

## 5. ⑤ 하나만 골라 — `onUserDeletedCleanup` 을 어떻게 잠글 것인가

**1위를 고른다.** 개인정보 파기이고, 오늘 [추가 690]에서 실제로 누락이 나왔다.

🚨 **아래 셋 중 하나로 단정하지 않는다. 대가가 다르고, 고르는 것은 globe2030님
또는 PM 이다.**

### 갑 · `firebase-functions-test` 를 들인다

핸들러를 **실제로 호출**해 본다. 공식 도구이고 `onDocumentDeleted` 같은 트리거도
모의할 수 있다.

```
얻는 것   호출부를 그대로 잠근다 — 순서·분기·오류 처리까지
대가      · 개발 의존성이 하나 늘고, Firestore 모의가 필요하다
          · **`index.ts` 를 import 하는 순간 파일 전체가 로드된다** — 지금
            0건인 이유가 이것일 수 있다. 초기화 부수효과가 있으면 테스트가
            무거워지거나 아예 안 돈다
          · 러닝커브가 이 저장소에서 가장 크다
⚠️ 확인 필요  이 저장소가 `firebase-admin` 을 어떻게 초기화하는지 먼저 봐야 한다.
             안 보고 시작하면 「해 보니 크더라」가 된다
```

### 을 · 로직을 **더** 빼낸다 (이 저장소가 이미 하던 방식)

핸들러 안의 **순서와 분기**를 순수 함수로 한 겹 더 빼고, 핸들러는 **엮기만** 한다.

```
얻는 것   · 기존 방식과 같아 러닝커브가 0이다
          · 19개 모듈이 이미 그렇게 잠겨 있다 — **증명된 길**이다
          · 「무엇을 어떤 순서로 지우는가」를 자료(계획)로 만들면 그것을 잴 수 있다
대가      · 핸들러가 얇아지는 만큼 **호출부는 여전히 안 잠긴다** —
            "계획은 맞는데 그 계획을 안 부른다"가 다시 가능하다
          · 즉 **[추가 79]·[추가 687]의 결함 유형은 이 방식으로 못 막는다**
⭐ 보완    「부르는가」는 **소스 스캔 테스트**로 따로 못 박을 수 있다
          (오늘 `AccountPaths`·`profileCardPhotoDeletionFor` 에서 쓴 방법)
```

### 병 · 배포 뒤 **실물로 본다**

지금처럼 두고, 탈퇴를 실제로 해 보고 Firestore·Storage 를 조회한다.

```
얻는 것   · 가장 정확하다 — 이 저장소가 반복해서 겪은 "코드는 맞는데 실물이 틀린"
            결함은 **오직 이 방법만 잡았다**
대가      · 되돌릴 수 없다(진짜 계정이 지워진다)
          · 매번 사람이 해야 한다 — 회귀를 못 막는다
          · **배포 뒤**라 이미 나간 다음이다
```

### 제 의견 (결정 아님)

**을 + 소스 스캔**을 먼저 하고, **갑은 그다음에 판단**하는 쪽이 이 저장소에
맞아 보인다.

📌 이유는 **비용이 아니라 순서**다. 갑은 `index.ts` 를 import 할 수 있는지부터
확인해야 하는데(초기화 부수효과), **그 확인 자체가 을의 첫 단계와 같다** — 핸들러를
얇게 만들면 import 부담도 줄어든다. **을을 하고 나면 갑이 쉬워지지만, 반대는
아니다.**

⚠️ **병은 어느 쪽을 골라도 필요하다.** 자동 테스트는 *"Cloud Storage 에서 실제로
사라지는가"* 를 **절대 못 본다.**

```
① 테스트 건수를 실측 못 했다
   새 워크트리라 node_modules 가 없어 `npm test` 가 `tsc: command not found` 로 죽었다.

      놓친 것일 수도 있다. **차이를 못 밝힌 채로 적는다.**

② 「(다) 아예 박혀 있다」를 0개로 적었지만 정확하지 않다
   모듈을 **부르는가**로만 판정했다. 핸들러 본문 수백 줄 안에서 모듈 호출은 몇
   줄뿐이고 나머지는 여전히 index.ts 안에 있다. **한 핸들러 안에 (가)와 (다)가
   섞여 있다** — 3절에 적었지만 표는 그것을 못 보여 준다.

③ 「위험한 다섯」은 **읽어서 매긴 순위**다
   실제 장애 이력이나 로그로 잰 것이 아니다. `kakaoUnlinkWebhook` 을 5위로 둔 것도
   줄 수 기준이고, **「누가 부를 수 있는가」로 보면 더 위여야 한다**고 본문에 적었다.

④ `index.ts` 를 import 할 수 있는지 **확인 안 했다**
   ⑤의 갑이 가능한지가 여기 달려 있는데, 초기화 부수효과를 재려면 실제로
   import 해 봐야 한다. **안 해 봤다.**

⑤ 커버리지 도구를 안 돌렸다
   일부러다 — 커버리지는 「실행됐는지」만 보고 「틀렸을 때 실패하는지」는 안 본다.
   ⚠️ 다만 **안 돌린 것도 사실이므로 적는다.** 숫자가 필요하면 돌려야 한다.
```
