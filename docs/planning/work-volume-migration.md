## 왜 스크립트를 쓰나 — 손으로 끌어다 놓으면 조용히 깨지는 것들

세 가지가 **옮긴 직후에는 티가 안 나고 며칠 뒤 엉뚱한 증상으로** 나타난다.
CLAUDE.md 4장의 *"코드는 맞는데 실물이 틀린"* 유형이다.

| 무엇이 | 왜 깨지나 | 안 고치면 |
|---|---|---|
| `git worktree` | `.git` 파일과 `.git/worktrees/*/gitdir` 에 **절대경로**가 박혀 있다 | Work 에서 일하는데 git 은 **X31 에 쓴다.** X31 을 빼면 죽는다 |
| `.dart_tool` | `package_config.json` 이 패키지 경로를 절대경로로 적는다 | `flutter` 가 옛 경로를 계속 찾는다 |
| `명함데이터` 권한 | 제3자 개인정보라 700 이어야 한다 | 복사 방식에 따라 755 로 풀린다 |

그리고 **git 에 없는 것**이 있다 — `android/key.properties`(서명), `.env`,
`scan_result*.tsv`(제3자 개인정보), `stash`, push 안 된 브랜치. 이것들은
**원격에서 다시 받을 수 없다.** 그게 ① 조사 단계가 있는 이유다.

## 절차 — 순서대로

```bash
tool/migrate_to_work_volume.sh survey        # ① 읽기만. 무엇이 있는지 조사
tool/migrate_to_work_volume.sh copy --yes    # ② 복사 (X31 은 그대로 둔다)
tool/migrate_to_work_volume.sh repair        # ③ 옮겨서 깨진 절대경로 고치기
tool/migrate_to_work_volume.sh verify        # ④ 원본과 대조
tool/migrate_to_work_volume.sh sync          # ⑤ GitHub 과 맞춘다(계획만)

# 나중에 **같은 볼륨 안에서** 폴더를 옮겼다면(예: Work/* → Work/Claude/*)
tool/migrate_to_work_volume.sh relocate --root=/Volumes/Work/Claude
```

🚨 **이 스크립트는 아무것도 지우지 않는다.** X31 은 손대지 않는다. 정리는
④가 통과하고, 새 경로에서 `flutter test` 와 실기기 빌드까지 한 번 돌려 본
뒤에 **사람이 직접** 한다.

### ① survey — 원격에서 복구 안 되는 것을 먼저 센다

저장소마다 원격(GitHub/GitLab/기타), 미커밋, stash, 업스트림 없는 브랜치,
비추적 비밀 파일, 딸린 워크트리를 뽑는다. 아무것도 바꾸지 않는다.

- 베어 저장소(`upstream.git` 처럼 이름에 `.git` 이 붙은 폴더)는 **이름이 아니라
  구조**(`objects/` + `HEAD` + `refs/`)로 찾는다 — 이름으로 찾으면 통째로 놓친다.
- `--fetch` 를 붙이면 원격을 먼저 받아 비교한다. 안 붙이면 **마지막으로 받아 둔
  상태 기준**이고, 화면에도 그렇게 적힌다.

### ② copy — `ditto` 로 복사한다

`cp -R` 은 확장속성을, 구버전 `rsync` 는 ACL 을 흘린다. **명함데이터의 700
권한이 풀리면 제3자 개인정보가 노출된다.** `--yes` 없이 돌리면 계획만 보여준다.
대상에 같은 이름이 이미 있으면 **덮어쓰지 않고 건너뛴다.**

### ③ repair — 절대경로를 고친다

🚨 **`git worktree repair <새 경로>` 를 쓰지 않는다.** git 은 넘긴 경로의 `.git`
을 읽어 **거기 적힌 옛 본체**를 찾아가 고친다. 그래서 「옛 본체 ↔ 새 워크트리」로
짝이 맞춰지고 **원본 X31 쪽 파일이 바뀐다.** 2026-09-03 시험에서 실제로 그렇게
됐다 — 원본 두 파일이 새 볼륨을 가리키게 바뀌고, 정작 복사본은 그대로 깨져
있었다(즉 **정확히 반대로** 됐다).

그래서 문자열은 스크립트가 직접 고치고, git 은 **확인에만** 쓴다. 그리고
단계 끝에 **원본 쪽 git 연결 파일의 체크섬을 전후 비교해** 원본이 그대로인지
잰다 — *"X31 은 손대지 않는다"* 를 말로만 두지 않는다.

이어서 `.dart_tool` 삭제 후 `flutter pub get`, `명함데이터` 700 재적용,
`~/Downloads/커넥션센스` 심볼릭 링크 갱신, 그리고 문서에 남은 옛 절대경로
목록(사람이 판단해서 고친다)을 낸다. iOS `Pods/` 는 빌드 전에 `pod install`
을 직접 돌린다.

### ④ verify — 개수만 보지 않는다

|  판정 근거 |  이유 |
|---|---|
| **파일 개수** | 🚨 다르면 실패 |
| **원본에만 있는 파일 목록** | 🚨 있으면 실패 — **그 줄을 그대로 보여 준다** |
| 바이트 합 | ⚠️ 참고만 — repair 가 경로 문자열을 바꿔 **길이가 달라진다** |

세 값은 **같은 목록**을 쓴다(`.dart_tool`·`build`·`Pods`·`node_modules`·
`.gradle`·`.DS_Store` 제외). 시험 중에 표는 `.dart_tool` 을 세고 유실 목록은
빼서 **유실 0건인데 「다르다」가 뜨는** 헛경보가 났다 — 세는 법이 둘이면 두 번
어긋난다(CLAUDE.md 「세는 도구가 못 보는 것」).

⚠️ `rsync` 를 쓰지 않는다. `rsync` 가 없는 기계에서 이 단계가 **조용히 「유실
0건」** 을 내면 그것이 가장 나쁜 결과다 — 틀린 답이 아니라 **잴 것이 없었던
것**인데 통과로 읽힌다.

### ⑤ sync — GitHub 과 맞춘다

🚨 **push 는 밖으로 나가는 동작이다.** 기본은 계획만 보여주고, `--yes` 를
붙일 때만 올린다. **절대 force 하지 않는다.**

- 기본은 **GitHub 으로 분류된 원격**만. GitLab 쪽은 `--remote=<이름>` 으로 지정한다.
- 업스트림 없는 브랜치는 `push -u`, 앞선 브랜치는 `push`.
- **원격이 앞서 있으면(뒤짐 > 0) 손대지 않는다.** merge 인지 rebase 인지는
  그 저장소의 규약대로 사람이 정한다.
- 미커밋·stash 는 **push 되지 않는다.** 화면에 경고로 남는다.
- ⚠️ **「검사한 저장소 0개」와 「올릴 것이 0개」를 구분한다.** GitHub 원격이 없어
  전부 건너뛴 것을 「✅ 올릴 것이 없다」로 끝내면 안 된다 — 시험에서 실제로
  그렇게 나와 고쳤다.

## 🚨 실물에서 결함이 다섯 건 나왔다 — 시험 트리에서는 안 나온 것들

전 단계가 흉내낸 시험 트리를 통과한 뒤에 실물을 돌렸는데, **거기서 다섯 건이
더 나왔다.** 다섯 건의 뿌리가 전부 같다.

> **잴 것이 없어진 것을 「통과」로 읽었다.**

| # | 무엇이 | 어떻게 드러났나 |
|---|---|---|
| 1 | `copy` 의 「이미 있다 — 건너뛴다」가 **긴 로그 중간의 노란 줄 하나**였다 | 대상에 옛 클론이 있어 19.3GB 가 통째로 안 옮겨졌는데 「복사됐다」로 읽고 다음 단계로 갔다. **repair 에서 워크트리 5개가 안 보여서야** 드러났다 |
| 2 | 보고서 파일 이름이 `<날짜>_<단계>` 라 **나중 실행이 앞 기록을 덮었다** | 전체 copy 로그가 뒤이은 `--only` 실행에 덮여 **되짚을 수 없게 됐다** |
| 3 | `verify` 가 **「복사본에 더 있는 것」을 유실로 판정**했다 | 🚨 7건이 떴는데 같은 출력의 판정선은 「유실 0건」이었다 |
| 4 | `repair` 의 `pub get` 이 **추적 파일 `analysis_options.yaml` 을 고치고 말하지 않았다** | 나중에 `analyze` 가 warning 을 내자 **이전 탓인가부터 의심**하게 됐다(아니었다) |
| 5 | `repair` 가 **같은 볼륨 안 이동에는 못 쓴다** | 이전을 마친 뒤 `Work/*` 를 `Work/Claude/` 로 옮기자 절대경로가 전부 다시 틀어졌다 |

⭐ **1·2·3 은 「틀린 값」이 아니라 「없어진 정보」다.** 틀린 값은 눈에 띄는데,
없어진 정보는 **통과처럼 보인다.** verify·sync 에는 그 안전장치를 미리 넣어
두었는데 **copy 에만 빠져 있었다** — 규약을 아는 것과 빠짐없이 적용하는 것은
다른 일이다.

### 5번은 결이 다르다 — 같은 명령이 조건에 따라 갈린다

`repair` 는 「옛 경로 → 새 경로」 **문자열 치환**이라 한 번만 맞다. 같은 볼륨
안에서 옮기면 **새 경로가 옛 경로를 품어서**(`/Volumes/Work` →
`/Volumes/Work/Claude`) 치환이 두 번 먹고 `Claude/Claude` 가 된다. 그래서
`relocate` 를 따로 두었다 — **치환하지 않고 지금 있는 자리를 읽어 다시 잇는다.**

🚨 그리고 옮긴 직후의 워크트리는 `git worktree list` 에 **`prunable`** 로 보인다.
`repair` 는 마지막에 `worktree prune` 을 돌리므로 **그냥 돌리면 등록이 지워진다.**

⭐ **`git worktree repair <새 경로>` 는 여기서는 정답이다.** ③에서 「쓰면 안 된다」고
크게 적어 둔 바로 그 명령이다. 갈리는 조건은 하나뿐이다.

```
옛 본체가 아직 살아 있다   → 위험. git 이 그리로 찾아가 **원본을 고친다**
                             (git 메시지: ".git file incorrect")
옛 본체가 없어졌다         → 안전. git 이 갈 곳이 없어 제자리를 고친다
                             (git 메시지: ".git file broken")
```

📌 **그래서 「쓰지 마라」가 아니라 「언제 위험한지」를 적는다.** 금지 목록은
언제나 뒤늦다 — 오늘 위험했던 명령이 내일 정답이다.

## 아직 안 한 것

- **⑤ `sync` 를 안 돌렸다.** push 안 된 브랜치가 **12개**(그중 2개는 업스트림조차
  없음) 있어서, 어느 것을 올릴지 정하는 것이 먼저다. 파일은 이미 옮겨져 있으므로
  급하지 않다.
- **X31 을 안 지웠다.** 그리고 당분간 지우지 않는다 — 새 볼륨에서 며칠 써 본 뒤에
  사람이 직접 정리한다. 스크립트는 어느 단계에서도 X31 을 건드리지 않았고,
  `repair` 가 매번 **원본 무개변을 체크섬으로 재서** ✅ 를 찍었다.
- **GitLab 쪽은 확인하지 않았다.** `--remote=<이름>` 으로 같은 절차를 쓸 수 있지만,
  자체 호스팅 GitLab 의 인증 방식은 확인이 필요하다.
- `backlog.md` 「추가 N」은 **PM 이 번호를 배정한 뒤**에 적는다(CLAUDE.md 4-2).
