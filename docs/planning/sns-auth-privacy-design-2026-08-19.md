# 네이버·카카오 로그인 — 구현 전에 정할 것 (2026-08-19)

> 배경: 사용자가 *"네이버 카카오도 할 거야"*, *"성별과 연령대 마케팅을 위해서"*라고
> 밝혔다. 기존 인수인계서([`SNS_AUTH_HANDOFF.md`](./SNS_AUTH_HANDOFF.md))는 **어떻게
> 붙이나**를 적었고, 이 문서는 **무엇을 받고 무엇을 저장할지**를 적는다. backlog 추가 337.

⚠️ **이 문서는 법률 자문이 아니다.** 마케팅 동의와 광고 전송은 실제로 과태료가
나오는 영역이라, 구현 전 검토를 권한다([`legal-review-request-2026-08-15.md`](./legal-review-request-2026-08-15.md)에
얹으면 된다).

📌 **성격**: 현재 코드·방침 확인은 **실물**(직접 열어 봤다), 법 해석은 **조사**다.

## 1. ⚠️ 인수인계서의 요구가 방침·법과 부딪친다

인수인계서 4장:

> 🚨 **로그인 성공 시 4대 SNS에서 수신된 전체 응답 데이터(`rawPayload`)를
> `users/{uid}.authProfile`에 통째로 누락 없이 저장**

현재 개인정보처리방침 1장 총칙:

> 서비스 제공에 필요한 **최소한의 정보만** 처리합니다.

**두 문장이 같이 설 수 없다.** 최소수집은 방침의 문구이기 전에 **개인정보 보호법
제3조 제1항**이다.

> **받는 것과 저장하는 것은 다르다.** SNS가 줘도 안 쓰면 저장하지 않으면 된다.
> *"나중에 쓸지 몰라서 다 담아 둔다"*는 개인정보에서 **위험을 담아 두는 것**이다.

이 저장소는 **서버에 명함 개인정보가 평문으로 남아 있던 일**을 이미 겪었다.

## 2. 항목별로 정할 것

네이버가 주는 것(인수인계서 3-3)과 카카오의 동의 항목을 합쳐 정리한다.

| 항목 | 이 앱에 필요한가 | 법적 근거 | 권고 |
|---|---|---|---|
| `id` (계정 식별자) | **필요** — 회원 식별 | 계약의 이행 | ✅ 저장 |
| `email` | **필요** — 회원 식별·중복 방지 | 계약의 이행 | ✅ 저장 |
| `name` / `nickname` | 필요 — 화면 표시 | 계약의 이행 | ✅ 저장 |
| `profile_image` | 필요 — 아바타 | 계약의 이행 | ✅ 저장(URL) |
| **`gender`** | 서비스엔 불필요 · **마케팅에 필요** | **정보주체의 동의** | ⚠️ 3장 참고 |
| **연령대** | 서비스엔 불필요 · **마케팅에 필요** | **정보주체의 동의** | ⚠️ 3장 참고 |
| `birthday`/`birthyear` | ❓ | 동의 | ❌ **권고: 안 받음** |
| `mobile` / `mobile_e164` | ❓ | 동의 | ❌ **권고: 안 받음** |
| 본인확인 연계정보(CI/DI) | ❌ | — | ❌ **권고: 안 감** |

### 2-1. 생년월일 대신 **연령대**

인수인계서는 `birthday`·`birthyear`를 받는다고 적었다. 그런데 마케팅에 필요한
것은 **연령대**이지 생년월일이 아니다.

```
생년월일 (1987-03-14)   개인 식별력이 높다. 유출되면 피해가 크다
연령대   (30대)         같은 목적을 이루면서 식별력이 낮다
```

**카카오는 `age_range`를 구간으로 준다.** 네이버는 `birthyear`를 주므로, **받은
즉시 구간으로 바꿔 저장하고 원본은 버리는** 방식을 권한다.

> 목적을 이루는 가장 약한 형태를 고르는 것이 최소수집이다.

### 2-2. 휴대전화번호를 권하지 않는 이유

인수인계서는 *"내 명함 연락처 자동 채움"*을 이유로 든다. 그런데 **내 프로필의
전화번호는 이미 이용자 직접 입력 항목으로 있다**(방침 2-1). 자동 채움은 편의일
뿐이고, 그 편의를 위해 **전 이용자의 휴대전화번호를 서버에 쌓는다.**

자동 채움이 정말 필요하면 **받아서 화면에 채워 주고 저장은 이용자가 저장을
누를 때** 하면 된다 — 그러면 기존 "이용자 직접 입력" 근거 안에 머문다.

### 2-3. CI/DI로 가면 문서 전체가 바뀐다

현재 방침 2-3:

> 고유식별정보(주민등록번호, 여권번호, 운전면허번호, 외국인등록번호)를
> **일절 처리하지 않습니다.**

본인확인 연계정보로 가면 이 문장을 **통째로 고쳐야 하고**, 본인확인기관 계약도
필요하다. **이 앱은 실명확인이 법으로 요구되는 서비스가 아니다.**

## 3. 마케팅 목적은 **자리가 다르다**

```
방침 2-1  동의 없이 처리   ← 계약의 이행 (제15조 제1항 제4호)
방침 2-2  동의를 받아 처리 ← 정보주체의 동의 (제1호)   ★ 성별·연령대는 여기
```

**회원 식별에 성별·연령대는 필요 없다.** 그러니 "계약의 이행"으로는 못 받는다.

### 3-1. 동의를 묶으면 안 된다

개인정보 보호법 제22조 — 선택 동의를 거부했다고 **서비스 제공을 거부할 수 없다.**
방침 2-2가 이미 그렇게 약속하고 있다:

> 동의하지 않아도 명함 관리 등 서비스의 기본 기능을 **그대로 이용할 수 있습니다.**

**구현에 그대로 걸린다**: 네이버·카카오 동의 화면에서 성별·연령대를 **선택 항목**
으로 요청하고, **거부해도 로그인이 끝까지 되어야 한다.**

### 3-2. 실제로 광고를 보내면 법이 하나 더 붙는다

정보통신망법 제50조 — 광고성 정보 전송은 **사전 동의(옵트인)**, 제목에 `(광고)`
표기, **2년마다 수신동의 확인**, 야간(21시~08시) 전송은 **별도 동의**.

⚠️ **"성별·연령대 수집 동의"와 "광고 수신 동의"는 다른 동의다.** 세그먼트를
나누는 것과 메시지를 보내는 것은 별개다.

### 3-3. 커버리지가 100%가 아니다 — 마케팅 쪽에서 먼저 알아야 한다

성별·연령대는 **선택 제공 항목**이라 이용자가 거부할 수 있다. 그리고 구글·애플은
이 항목을 주지 않는다.

```
구글·애플로 가입한 이용자   성별·연령대 없음
네이버·카카오 + 동의        있음
네이버·카카오 + 거부        없음
```

**세그먼트가 반쪽이 된다는 것을 전제로 기획해야 한다.** 없는 사람을 어떻게 다룰지
(제외할지, 기본 세그먼트에 넣을지) 정해 두지 않으면 나중에 숫자가 안 맞는다.

## 4. 함께 걸리는 것 — **"마지막에 무엇으로 로그인했나"**

제공자가 넷이 되면 이용자는 **어느 걸로 가입했는지 잊는다.**

```
구글로 가입 → 몇 달 뒤 재설치 → 카카오로 로그인
  → 다른 계정이 생긴다 → 명함이 하나도 안 보인다
  → "데이터가 다 날아갔다"로 접수된다
```

⚠️ **되돌리기 어렵다.** 두 계정이 생기면 합칠 방법이 없고, 이용자는 **앱이
데이터를 잃었다고 믿는다.** 제공자가 둘일 때는 견디지만 넷에서는 결함이 된다.

**재료는 이미 있다.** `AuthRepository`가 `provider`를 보안 저장소에 넣고 있다.
다만 **로그아웃할 때 지운다** — *"마지막에 무엇으로"*는 로그아웃 뒤에도 남아야
쓸모가 있다.

📌 **제공자 이름만 남긴다.**

```
남겨도 되는 것    provider ("google" / "kakao")   ← 개인정보가 아니다
남기면 안 되는 것  이메일 원문                     ← CLAUDE.md 4절
```

가린 이메일(`ho***@gmail.com`)을 보여 주는 방법도 있으나 **가린 것도 개인정보**라
보안 저장소에 넣어야 한다. **제공자 이름만으로 중복 가입은 막힌다.**

## 6. 사용자가 정할 것

1. **5장 권고안대로 갈지** — 특히 휴대전화번호·생년월일을 안 받는 것
2. **`authProfile` 전체 저장을 접을지** — 인수인계서 4장의 🚨 항목
3. **광고 수신 동의를 함께 받을지** — 받으면 정보통신망법 제50조가 붙는다
4. **법률 검토를 받을지** — 마케팅 동의·광고 전송은 과태료 영역이다

## 8. "마지막에 사용" 표시 — 설계

4장에서 **왜 필요한지**를 적었다. 여기는 **어떻게 만들지**다.

### 8-1. 무엇을 남기나

```
키       last_auth_provider
값       "google" | "apple" | "kakao" | "naver"
저장소   flutter_secure_storage (기존 것 재사용)
지우기   로그아웃해도 **안 지운다**  ← 이게 핵심
         계정 삭제(탈퇴) 시에는 지운다
```

⚠️ **로그아웃과 탈퇴를 갈라야 한다.** 지금 코드는 둘 다 `_sessionKey`를 지운다.
*"마지막에 무엇으로"*는 **로그아웃 뒤에 쓰는 값**이므로 세션과 수명이 다르다.
같은 키에 넣으면 로그아웃하는 순간 사라져 아무 쓸모가 없다.

```
로그아웃   세션 지움 · last_auth_provider 남김
탈퇴       세션 지움 · last_auth_provider 지움   ← 남기면 "지웠는데 남아 있다"
```

📌 탈퇴 때 지우는 것은 **이 저장소가 겪은 일** 때문이다 — *"앱 삭제 후 로그인
정보 잔존(iOS)"*이 실사용에서 발견된 적이 있다(CLAUDE.md 4절 표).

### 8-2. 개인정보 판단

```
provider 이름만    "google" 은 개인정보가 아니다        ✅ 이것만 남긴다
이메일 원문        ❌ CLAUDE.md 4절 — 평문 저장 금지
가린 이메일        ho***@gmail.com 도 개인정보다 —
                   보안 저장소에 넣어야 하고, 이득은 배지와 같다
```

**제공자 이름만으로 중복 가입은 막힌다.** 더 담을 이유가 없다.

### 8-3. 화면

```
  ┌────────────────────────────┐
  │  [G] Google로 계속하기      │  ← 마지막에 사용
  │  [] Apple로 계속하기       │
  │  [K] 카카오로 계속하기      │
  │  [N] 네이버로 계속하기      │
  └────────────────────────────┘
```

배지는 **버튼 순서를 바꾸지 않는다.** 순서가 바뀌면 손이 기억하는 자리가 흔들려
오히려 잘못 누른다. **표시만 얹는다.**

⚠️ **값이 없으면 아무것도 그리지 않는다**(첫 설치·탈퇴 후). 이 저장소는 화면을
채우려고 없는 것을 만들지 않는다(CLAUDE.md 4절).

### 8-4. 검증

저장소를 건드리므로 **재설치 후 동작**을 실기기로 봐야 한다.

```
1. 구글로 로그인 → 로그아웃 → 로그인 화면에 배지가 구글에 붙나
2. 앱 삭제 → 재설치 → 배지가 없나        ← iOS Keychain은 앱을 지워도 남을 수 있다
3. 탈퇴 → 배지가 없나
```

📌 2번이 이 저장소가 실제로 데인 자리다. **iOS는 앱을 지워도 Keychain이 남는다.**
