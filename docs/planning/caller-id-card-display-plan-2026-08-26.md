# 전화 수신 시 명함 정보 표시 — 별건 기록과 구현 계획 (2026-08-26)

> **지금 하지 않는다.** 스토어 등록 전에는 손대지 않기로 했다(사용자 결정
> 2026-08-26). 이 문서는 **나중에 착수할 때 처음부터 다시 조사하지 않기 위한
> 기록**이다.

## 0. 무엇을 하려는 것인가

모르는 번호로 전화가 왔을 때 **"이 번호는 명함첩의 ○○○ 부장"** 을 화면에
띄우는 것. 리멤버 설정의 `전화 수신 시 상대방 명함정보 표시`(켜짐)가 이것이다
(2026-08-26 실물 확인 → [`remember-settings-analysis-2026-08-26.md`](remember-settings-analysis-2026-08-26.md)).

📌 **명함을 모으는 이유가 여기서 회수된다.** 지금 우리 앱은 명함 주인이 전화를
걸어와도 아무 말을 못 한다.

## 1. 🚨 이건 "기능 추가"가 아니라 **결정 되돌리기**다

`android/app/src/main/AndroidManifest.xml`이 관련 권한을 **명시적으로 지우고
있다**(실측 2026-08-26):

```xml
READ_CALL_LOG      tools:node="remove"
WRITE_CALL_LOG     tools:node="remove"
READ_PHONE_STATE   tools:node="remove"   ← 이게 없으면 전화 온 것을 모른다
READ_PHONE_NUMBERS tools:node="remove"
READ_SMS           tools:node="remove"
```

`tools:node="remove"`는 **어떤 라이브러리가 끌고 들어와도 지우라**는 뜻이다.
빠뜨린 것이 아니라 **일부러 뺀 것**이고, 배경은 추가 312(2026-08-18, 통화·문자
자동 기록 조사 후 현상 유지 결정)다.

⚠️ **그러므로 착수는 그 결정을 뒤집는 것에서 시작한다.** 조용히 권한만 되살리면
왜 뺐는지가 사라진다.

## 2. 두 OS가 완전히 다른 방식으로 한다

⚠️ **이 절은 원문 문서를 열어 확인하지 않고 적었다.** 착수 전에 Apple·Google
문서를 직접 보고 고칠 것 — 이 저장소는 기억으로 적은 절차가 여러 번 틀린 전례가
있다.

### iOS — 앱이 전화를 못 본다. 목록을 미리 넘겨 둔다

```
CallKit Call Directory Extension (앱 확장)
  앱이 OS에 (전화번호 → 표시할 이름) 쌍의 정렬된 목록을 미리 등록
  전화가 올 때 앱·확장은 호출되지 않는다 — OS가 자기 목록에서 찾아 띄운다
  명함이 늘거나 바뀌면 앱이 목록 갱신을 요청해야 한다
```

📌 **장점**: 통화 관련 권한이 필요 없다. 앱은 전화를 관찰하지 않는다.
🚨 **대가**: 명함첩 **전체의 번호와 이름**을 OS 확장이 읽을 수 있는 자리에
미리 복사해 두어야 한다.

### Android — 앱이 전화를 직접 안다

```
READ_PHONE_STATE          전화가 온 것과 번호를 앱이 받는다
+ SYSTEM_ALERT_WINDOW     통화 화면 위에 우리 창을 그린다(이용자가 설정에서 직접 켜야 함)
```

국내 발신자 표시 앱들이 쓰는 방식이 이것이다.

⚠️ **Play 정책**: 통화기록 권한군(`READ_CALL_LOG`)은 *"기본 전화·문자 앱만"*
원칙으로 강하게 막힌다. `READ_PHONE_STATE`는 그보다 약하지만 여전히 민감
권한이고 **소명이 필요할 수 있다.** 2026-08-26에 확인한 연락처 권한 정책
(`READ_CONTACTS` 제한, 2027-01-27 시행)과 **같은 방향의 흐름**이다 — 구글은
권한 범위를 계속 좁히고 있다.

## 3. 🚨 진짜 어려운 곳은 권한이 아니라 **암호화와 부딪히는 지점**이다

우리 명함 데이터는 기기에서도 서버에서도 **AES-256-GCM으로 암호화**돼 있고,
키는 기기 보안 저장소(iOS Keychain / Android Keystore)에 있다.

그런데 발신자 표시는 본질적으로 **"전화가 울리는 그 순간의 빠른 조회"**를
요구한다. 그러려면 번호와 이름이 **빠르게 읽히는 형태**로 어딘가에 있어야 한다.

```
번호는 해시로 둘 수 있다        조회는 "이 번호가 있나"이므로 해시 비교로 된다
이름은 해시로 둘 수 없다        화면에 띄워야 하므로 평문이 필요하다
```

⚠️ **즉 "누구인지 띄운다"는 요구가 곧 "이름을 평문으로 둔다"를 부른다.**
이 앱의 암호화 원칙과 정면으로 만난다.

### 완화 방향 (착수 시 결정할 것)

| 안 | 내용 | 대가 |
|---|---|---|
| **가** | 확장/서비스가 키를 공유받아 그때그때 복호화 | iOS는 Keychain 공유 그룹, Android는 같은 앱이라 가능. **복잡하고 느릴 수 있다** |
| **나** | 표시용 최소 인덱스(번호 해시 + 이름)만 따로 암호화해 둔다 | 조회가 빨라지지만 **인덱스가 또 하나의 사본**이다 |
| **다** | 이름 대신 **"명함첩에 있는 사람입니다"**만 띄운다 | 평문 이름이 필요 없다. 🚨 **효용이 크게 준다** |

📌 **다安은 버리기 아깝다.** 이름을 못 띄워도 *"모르는 번호가 아니다"*만
알려 줘도 스팸과 갈린다. **가장 싸고 가장 안전한 첫 단계**가 될 수 있다.

## 4. 방침·법무에 걸리는 것

- **제3자(명함 주인)의 번호와 이름을 OS 확장·오버레이로 넘긴다** — 앱 밖으로
  한 벌 더 나가는 것이라 `docs/legal/privacy-policy.html`에 항목이 생긴다
- 이용 목적이 늘어난다(발신자 식별)
- iOS는 목록을 **미리** 넘겨 두므로, 전화가 오지 않아도 그 사본이 상시 존재한다

⚠️ **법무 질문으로 뽑아 둘 것**

```
① 명함 주인의 번호·이름을 OS 발신자 표시 기능에 제공하는 것이 기존 수집 근거로
   덮이는가, 별도 고지·동의가 필요한가
② iOS 확장 컨테이너에 상시 사본을 두는 것이 보관·안전조치 서술에 어떻게 잡히는가
③ 이용자가 이 기능을 끄면 사본도 즉시 지워야 하는가
```

## 5. 착수 순서 (하기로 정해졌을 때)

```
1  결정 되돌리기 기록      추가 312 를 왜 뒤집는지 backlog 에 남긴다
2  법무 질문 셋            위 ①②③ — 답이 오기 전에는 코드 금지
3  원문 확인               Apple CallKit · Google 권한 정책을 직접 연다(2절 경고)
4  실측 프로토타입          Android 오버레이가 실제 통화 화면 위에 뜨는지
                          iOS 확장에 명함 100건을 넣어 실제로 이름이 뜨는지
5  암호화 설계 결정         3절의 가/나/다 중 하나. 다안(이름 없이)부터 재 볼 것
6  구현 · 방침 개정 · 심사 소명
```

🚨 **4번(실측)을 3번(원문 확인)보다 먼저 하지 않는다.** 되는 줄 알고 만들었다가
정책에서 막히면 만든 것이 통째로 버려진다.

출시를 앞두고 손댈 것이 아니다.

⭐ **함께 봐 둘 것**: 같은 "연락처" 묶음의 다른 항목과 **방향이 반대**다.

늘리는** 기능이다. 한 화면에 나란히 두면 이용자가 헷갈린다.
