# 통계 지표 — 제안과 실물 대조 (2026-08-20)

> 배경: 사용자 질문 *"앱을 통해서 얻을 수 있는 통계가 뭐가 있지?"* →
> *"그 문서를 열어 실물과 대조해서 정리하자."* backlog **추가 347**.
>
> 대조 대상: [`HANDOFF.md`](./HANDOFF.md) 6장 "화면별 통계 지표 제안".

⚠️ **6장은 "제안"이지 "있는 것"이 아니다.** 문서 스스로 그렇게 적고 있는데,
목록이 길어서 **읽는 사람이 이미 있는 줄 오해하기 쉽다.** 이 문서가 그 오해를
막는다.

📌 **성격**: 전부 **실물**이다 — 코드·`firestore.rules`·`pubspec.yaml`을 직접
열어 확인했다. 추정은 그렇다고 표시했다.

## 1. ① 지금 실제로 쌓이는 것

| 무엇 | 어디에 | 누가 쌓나 | 볼 수 있나 |
|---|---|---|---|
| **명함 인식 품질** | 기기(`shared_preferences`) | `OcrStatsService` ← `add_card_modal_view` | ✅ 설정 → 명함 인식 진단 |
| **좌표 변환 실패 형태** | 기기 | `GeoBackfillService` | ✅ 같은 화면(추가 342·344) |
| **AI 브리핑 반응·전달 채널** | **서버** `pilotEvents/{uid}/events` | `PilotEventsService` ← `briefing_overlay_view` | ❌ **보는 화면이 없다** |
| **크래시** | **서버** Firebase Crashlytics | SDK 자동 | ✅ Firebase 콘솔 |

그 밖에 **서버가 스스로 쌓는 것**(앱이 아니라 Cloud Functions가 쓴다):

```
users/{uid}.aiUsage          AI 이용 횟수·기준 시각
users/{uid}.cardPhotoQuota   명함 사진 할당량
creditGrantAudits            회차 지급 감사(행위자·사유·전후 잔액)
AI 호출 운영 로그             호출 시각·성공 여부·오류 유형·토큰량
inquiries                    1:1 문의
```

### ⚠️ 오늘 이 모양이 **네 번째**다 — `pilotEvents`

```
grantSupportCredits   서버만 있고 앱에 통로 없음        (추가 338)
좌표 칸               앱은 내보내는데 하네스가 안 읽음  (추가 334)
좌표 실패 집계        쌓는데 보여주는 화면 없음          (추가 342)
pilotEvents           **서버에 쌓이는데 보는 화면이 없다**  ← 새로 발견
```

**AI 브리핑을 쓴 사람이 👍/👎를 누르고 어느 채널로 보냈는지가 서버에 쌓이고
있는데, 그걸 볼 방법이 없다.** Firebase 콘솔에서 문서를 직접 뒤지는 것 말고는.

## 2. ③ 제안만 있고 아무것도 없는 것

6장이 화면 9개에 걸쳐 지표를 적어 뒀다. **아래는 전부 미구현이다.**

| 화면 | 제안된 지표 | 상태 |
|---|---|---|
| 로그인/회원가입 | 시도 수, 제공사별 비율, 성공/실패율, 온보딩 소요 시간 | ❌ |
| 레이더 | DAU/WAU, 체류시간, 근접 알림 전환율, 위치 동의 퍼널 | ❌ |
| 명함 지갑 | 사용자당 명함 수 분포, 검색·필터 사용률, 목록→상세 진입율 | ❌ |
| 명함 등록/스캔 | 촬영 성공률, 자동/수동 비율, **필드별 수정률** | ⚠️ 아래 |
| 내 프로필 | 항목별 채움 비율, QR 공유 횟수 | ❌ |
| AI 브리핑 | 제공사별 사용량 | ⚠️ 반응·채널만 있음 |
| 소통기록 | 채널별 입력 수 | ❌ |
| 설정 | 반경 변경 분포, 위치 동의율·철회율 | ❌ |
| 공통 | 화면별 로딩 실패율, 세션당 체류시간 | ❌ (크래시율만 ✅) |

📌 **"필드별 수정률"만은 이미 있다** — `OcrStatsService`가 사용자가 어느 칸을
고쳤는지 센다. 실사용에서 **주소 21건**으로 1위였다(추가 343).

## 3. 왜 대부분이 비어 있나 — 의도된 것이다

6장 머리말:

> 서버 자체 집계 대신 Firebase Analytics/Amplitude 같은 SaaS를 붙이면 서버 없이도
> … 사용자는 *"서버 구축은 해야 할 일로 남겨 달라"*고 했으므로, 여기서는 지표
> 설계만 하고 SDK/서버 연동은 하지 않았다.

**`firebase_analytics` 의존성이 없다**(실물 확인). 붙이는 순간 대부분이 자동으로
채워지지만, 그건 **새 수집**이다.

## 4. ⚠️ 통계를 붙이는 것은 **새 수집**이다

```
방침(개인정보처리방침)을 함께 고쳐야 한다
```

CLAUDE.md 4절이 못박아 둔 자리이고, **오늘 부서 필드에서 실제로 놓쳤다**(추가 337).

그리고 6장이 제안하는 것 중 성격이 다른 것이 있다:

| 제안 | 성격 |
|---|---|
| DAU/WAU, 체류시간, 화면 진입율 | 이용자 본인의 행동 |
| **"사용자당 등록 명함 수 분포"** | **제3자 개인정보의 집계** |
| **"소통기록 채널별 입력 수"** | 이용자가 **누구와 어떻게** 연락하는지 |

⚠️ 뒤 둘은 *"익명 통계"*라고 불러도 **성격이 다르다.** 명함 수는 인맥 규모이고,
소통 채널은 관계의 밀도다. 붙일지 말지를 **한 덩어리로 결정하면 안 된다.**

## 5. 지금 상태에서 답할 수 있는 것 / 없는 것

**답할 수 있다** (진단 화면 또는 콘솔에서):

```
· 명함 인식이 얼마나 잘 되나        칸별 채움률·수정 횟수
· 어느 칸을 사람이 제일 많이 고치나  주소 21건 (추가 343)
· 주소 → 좌표 변환이 얼마나 실패하나 11건, 73%가 지번
· 앱이 얼마나 죽나                  Crashlytics
· AI를 얼마나 쓰나                  users/{uid}.aiUsage (관리자 화면)
```

**답할 수 없다**:

```
· 이용자가 며칠에 한 번 여나 (DAU/WAU)
· 어느 화면에서 이탈하나
· 로그인이 얼마나 실패하나          ← 오늘 S6에서 실제로 겪은 문제다
· 명함 등록을 시작하고 몇 %가 저장까지 가나
· AI 브리핑 반응이 어떤가            서버에 쌓이는데 **볼 화면이 없다**
```

## 5-2. `pilotEvents` 보기 — **둘 다 필요하다** (사용자 확정 2026-08-20)

사용자 결정: *"한 사람씩 조회와 전 이용자 집계 둘 다 필요해."*

### ⚠️ 먼저 — 내가 크기를 잘못 말했다

*"방침 무관 · 1시간"*이라고 했는데 **틀렸다.** 읽기 권한을 확인하지 않고 말했다.

```
match /pilotEvents/{uid}/events/{eventId}
  allow read: if isAdmin()      ← 관리자만 읽는다
```

**본인도 자기 것을 못 읽는다.** 그래서 *"앱 안에 화면 하나"*로 끝나지 않는다.

### ⓐ 한 사람씩 조회 — 관리자 문의 화면에 붙이기

문의에 답하면서 **그 사람의 AI 브리핑 반응**을 함께 보는 것. `getUserUsage`와
같은 모양이다.

```
필요한 것
  · Cloud Functions 함수 하나 (관리자가 남의 문서를 읽어야 한다)
  · 관리자 문의 시트에 묶음 추가
  ⚠️ firebase deploy --only functions  → **사용자 결정**
```

📌 규칙은 **안 바꿔도 된다** — Admin SDK는 규칙을 우회한다. `getUserUsage`가
이미 그렇게 하고 있고, **사용량만 돌려주고 명함은 안 건드리는** 그 설계를 그대로
따르면 된다.

### ⓑ 전 이용자 집계 — 규칙·색인이 함께 필요

```
필요한 것
  · collectionGroup 읽기 규칙        ❌ 지금 없다 → 전체 조회가 막힌다
  · Firestore 색인                   ❌ 지금 없다
  · 집계 함수 또는 관리자 화면
  ⚠️ firebase deploy --only firestore:rules,firestore:indexes  → **사용자 결정**
```

⚠️ **ⓑ를 서버 집계로 하면 규칙을 열 필요가 없다.** Cloud Functions가 Admin
SDK로 읽어 **집계값만** 돌려주면, 클라이언트에 `collectionGroup` 권한을 주지
않아도 된다. **권한을 여는 것보다 이쪽이 안전하다** — 규칙을 열면 관리자
계정이 털렸을 때 전 이용자 이벤트가 통째로 나간다.

### 무엇을 볼 수 있게 되나

```
copy_send   채널별 전달 수      call · sms · kakao · email
feedback    👍/👎 · 1~5 척도
```

**AI 브리핑이 실제로 쓸모 있었는지**를 처음으로 알 수 있다. 지금은 쌓이기만 하고
아무도 안 본다.

### 순서 권고

**ⓐ를 먼저.** 문의 대응에서 바로 쓸모가 있고, 함수 하나만 배포하면 된다.
ⓑ는 표본이 쌓인 뒤에 해도 늦지 않다 — 지금 집계해 봐야 몇 건 안 된다.

## 6. 권고 — 싼 것부터

1. **`pilotEvents`를 보는 화면** — 이미 쌓이는데 못 본다. 새 수집이 아니라
   **방침을 안 건드린다.** 가장 싸다.
2. **로그인 실패 계측** — 오늘 S6에서 겪은 유형(Play 서비스 버전)을 테스터
   기기에서 알아채려면 필요하다. ⚠️ 새 수집이라 방침을 봐야 한다.
3. **Firebase Analytics** — 붙이면 대부분이 채워지지만 **가장 큰 결정**이다.
   방침 개정 + 국외 이전 + 위탁 현황이 함께 걸린다.

⚠️ **3을 먼저 하지 않기를 권한다.** 무엇이 필요한지 모르는 채로 다 켜면, 나중에
*"이건 왜 모으나"*에 답하기 어려워진다 — 최소수집 원칙과도 부딪친다.
