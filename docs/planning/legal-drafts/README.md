# 법적 고지 문서 — **게시 전 초안** 보관소

여기 있는 HTML 4개는 **아직 게시하지 않은 초안**이다. `docs/legal/`에는
**지금 실제로 서비스 중인 게시본만** 둔다.

| 폴더 | 무엇 | 배포되나 |
|---|---|---|
| `docs/legal/` | **게시본** (현재 v2.0 / 시행일 2026-08-12) | ✅ Firebase Hosting `legal` 타겟 |
| `docs/planning/legal-drafts/` ← 여기 | **초안** (v2.1 + v2.2) | ❌ |

---

## 왜 나눠 뒀나

**`firebase.json`의 `legal` 타겟이 `docs/legal`을 통째로 배포한다.** 초안을 그
폴더에 두면 **`firebase deploy` 한 번에 미고지 초안이 그대로 공개된다.**

실제로 그 직전까지 갔었다. 2026-08-15에 확인해 보니

- 저장소의 `privacy-policy.html`은 **본문이 v2.2인데 헤더만 2.0**이었다
- 라이브 사이트(<https://connection-sense.web.app/privacy-policy>)는 **v2.0**이었다
- 즉 **관리자 콘솔 배포 같은 다른 이유로 hosting을 한 번만 건드려도** 초안이
  나갈 수 있는 상태였다

개인정보처리방침은 **바꾸기 전에 알리고 기간을 두는 것**이 원칙이다. 알리기
전에 새 방침이 게시되면 그 절차가 무너진다.

같은 종류의 문제를 관리자 콘솔에서도 겪었다(ADMIN-VULN-008 — 내부 보고서가
공개 경로에 있었다). **"배포 폴더에는 배포할 것만 둔다"**가 규칙이다.

⚠️ **법무 산출물(`legal-review-*.md`, `policy-code-gap-*.md`)도 같은 이유로
`docs/planning/`으로 옮겼다.** 내부 검토 문서이고 공개 대상이 아니다.

## 게시할 때 — 이 순서로

### 1. 게이트가 다 닫혔는지 확인

방침 v2.2가 약속하는 것이 **실제로 동작해야** 한다. 하나라도 깨지면 7일 고지의
근거가 무너진다.

| 게이트 | 무엇 | 상태(2026-08-15) |
|---|---|---|
| ① | **기존 사진 일괄 업로드(백필)를 만들지 않았을 것** — 새로 저장할 때만 올린다 | ✅ |
| ② | *"그 밖의 목적에 이용하지 않는다"* 문장이 문안에 있을 것 | ✅ |
| ③ | **탈퇴 시 서버 사진이 실제로 지워질 것** | ✅ 배포 완료 |
| ④ | **탈퇴 시 삭제 기록(묘비)도 지워질 것** | ✅ 배포 완료 |

①이 특히 중요하다. **소급 업로드가 없다**는 사실이 "고지 기간 30일"을 **7일로
줄인 근거**다(법무 검토 2026-08-15). 나중에라도 백필을 넣으면 그 근거가
사라진다 — 꼭 필요하면 **이용자가 직접 누르는 버튼**으로 만든다.

### 2. 헤더의 날짜·버전을 **게시일 기준으로** 고친다

⚠️ **이 단계를 빼먹으면 안 된다.** 지금 초안 헤더는 옛 값이다.

```
공고일  = 실제 게시하는 날
시행일  = 공고일 + 7일
버전    = 2.2
```

변경 이력 표의 `(게시 시 확정)`도 같은 날짜로 채운다.

**시행일이 게시일에 걸리므로 이 값은 게시하는 사람이 정한다.**

### 3. 초안을 `docs/legal/`로 되돌린다

```
git mv docs/planning/legal-drafts/*.html docs/legal/
```

### 4. 배포

```
firebase deploy --only hosting:legal
```

⚠️ **`--only hosting`처럼 타겟 없이 쓰지 마라.** `legal`과 `admin`이 **둘 다**
나간다. 관리자 콘솔만 배포할 때도 마찬가지로 `--only hosting:admin`으로 좁힌다.

### 5. 실물을 열어 확인한다

배포됐다는 메시지가 아니라 **브라우저로 직접 본다.**
<https://connection-sense.web.app/privacy-policy> 에서 헤더의 버전·시행일이
의도한 값인지 확인한다. 이 저장소는 **"배포했다"와 "실제로 그렇게 보인다"가
달랐던 전례**가 여러 번 있다.

### 6. 시행일이 지난 뒤에야 플래그를 켠다

`kCardPhotoBackupEnabled = true`는 **공고일이 아니라 시행일 이후**다.
`test/card_photo_backup_gate_test.dart`가 플래그를 고정하고 있어, 켜려면 그
테스트도 함께 고쳐야 한다(실수 방지 장치다).

## 여기 있는 초안에 담긴 변경

**v2.1** — 명함 수집 항목에 **직통전화·팩스·웹사이트** 추가

**v2.2** — 주요 변경 셋

1. **명함 원본 사진을 서버에 저장**한다(종전: 기기에만 보관). 목적은
   **저장·조회·관리 / 기기 변경 시 복원 / 이용자 본인 명함의 확인·보정** 셋으로
   한정하고, **그 밖의 목적에 이용하지 않는다**고 명시
2. 명함(인맥) 정보 처리 근거에 **제15조 제1항 제6호(정당한 이익) 병기** —
   명함 주인은 이용계약 당사자가 아니라 제4호만으로는 부족하다는 판단
3. **관계 법령에 따른 보존 항목(4번) 신설** — 전자상거래법상 계약·청약철회
   기록 5년, 대금결제·재화 공급 기록 5년. **각 거래일부터** 기산

**빠진 것 둘** (2026-08-15 사용자 결정)

- **1:1 문의·답변 3년 보존** — 유료 결제 전에는 거래가 없어 "소비자 불만·
  분쟁처리 기록"이 성립하지 않는다. 실제 코드도 탈퇴 시 즉시 삭제다
  (`089949e`, ADMIN-VULN-007에서 **의도적으로** 그렇게 고쳤다)
- **AI 이용 일별 집계** — 구현이 어느 브랜치에도 없다. 없는 처리를 고지할 수
  없다

⚠️ **결제를 켜면 위 둘 중 첫 번째가 되살아난다.** 전자상거래법상 소비자
불만·분쟁처리 기록 **3년** 보존이 의무가 된다. **과금 관문 체크리스트**에
넣어 뒀다.
