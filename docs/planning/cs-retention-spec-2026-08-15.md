## 1. 법적 근거

**전자상거래법 §6(거래기록의 보존) + 시행령 §6**

| 기록 | 기간 |
|---|---|
| 표시·광고에 관한 기록 | 6개월 |
| 계약 또는 청약철회 등에 관한 기록 | **5년** |

**개인정보 보호법 §21③** — 법령에 따라 보존하는 경우 **다른 개인정보와
분리하여 저장·관리**해야 한다. 이 조항이 "분리 보관" 설계의 직접 근거다.

**⚠️ 법무 검토가 필요한 지점**: 우리 결제는 IAP(스토어 결제 대행)라 회사가

여지가 있다. 보수적으로 보존하는 것이 업계 관행이나(리멤버 방침도 동일한
4개 항목을 명시), **방침 게시 전 법무 최종 검토를 거친다.**

**참고 — 리멤버 개인정보처리방침 원문 확인 결과**(2026-08-15):
명함 이미지를 포함해 대부분 "회원 탈퇴 시 즉시 파기"로 규정하되, 위 4개

## 2. 설계 — 3층

### 층 1. 결제·충전 원장 — 5년 보존 (코드 변경 최소)

`purchases`·`creditGrants`는 **이미 서버 전용이고 탈퇴 트리거가 건드리지
않는다.** 즉 보존 자체는 지금도 되고 있다. 필요한 것은 세 가지다.

1. **방침 고지 추가**(4절 문안).
2. **`retainedUntil` 필드 신설** — 파기 시점을 데이터에 박아 둔다.
   - `purchases`: `purchasedAt + 5년`
   - `creditGrants`: `grantedAt + 5년` (결제 파생 이력이므로 동일 기간)
   - ⚠️ 기존 문서에는 없으므로 **백필 1회** 필요(2-4절).
3. **분리 보관 형태 유지** — 이미 `allow read, write: if false`(Admin SDK
   전용)라 일반 관리자 콘솔이 직접 못 읽는다. 이 상태를 그대로 둔다.

`creditGrants.balanceAfter`가 이미 "이 사건 직후 두 버킷 값"을 담고 있어
(`ai-credit-wallet-spec.md` 2-3절) **CS 문의 시 잔액 변동을 그대로
재구성**할 수 있다 — 원래 그 목적으로 설계된 필드다.

### 층 2. 1:1 문의·답변 — 3년 분리 보관 (신규 구현)

**삭제 → 이동으로 바꾼다.** `onUserDeletedCleanup`에서:

```
현재: inquiries/{id} + replies 삭제
변경: archivedInquiries/{id}로 복사 후 원본 삭제
```

**`archivedInquiries/{inquiryId}` 스키마**

```
originalId: string          // 원래 inquiries 문서 ID
userId: string              // 탈퇴한 uid (누구의 문의였는지 특정용 — 보존 목적상 필수)
email: string | null        // 문의 당시 연락처
title: string
body: string
status: string              // 종결 상태
createdAt: Timestamp
closedAt: Timestamp | null  // 마지막 답변 시각(없으면 null)
replies: [{ from, body, at }]   // 서브컬렉션을 배열로 접어 넣는다 (2-1절 이유)
archivedAt: Timestamp       // 탈퇴로 이관된 시각
retainedUntil: Timestamp    // 아래 기준으로 계산
```

**`retainedUntil` 계산**: `(closedAt ?? archivedAt) + 3년`.
법문은 "분쟁처리에 관한 기록"의 보존이므로 **처리 완료일 기준**이 자연스럽다.
아직 종결되지 않은 문의는 탈퇴 시각을 처리 완료로 본다.

**보안 규칙**: `match /archivedInquiries/{id} { allow read, write: if false; }`
— 클라이언트·관리자 콘솔 **양쪽 다 직접 접근 불가**. 이것이 ADMIN-VULN-007을
되살리지 않는 핵심이다. 평시 관리자 화면에는 **아무것도 안 보인다.**

**열람 경로**: 신규 Callable `lookupArchivedInquiries`
- 입력: `{ uid?: string, email?: string, reason: string }`
- 관리자 인증 필수(기존 `isAdmin` 경로 재사용).
- **`reason` 필수** — 비면 거부. `creditGrants`의 `support_free` 지급에
  사유를 강제한 것과 같은 방식(`ai-credit-wallet-spec.md` 3-5절).
- 열람 사실을 `archiveAccessAudits/{id}`에 기록: `by`(관리자 이메일),
  `at`, `reason`, `targetUid`, `hitCount`. **불변**(서버만 쓰기).
- 한 번에 반환 상한 50건(ADMIN-VULN-006의 대량 조회 교훈).

#### 2-1. 왜 `replies`를 배열로 접는가

서브컬렉션인 채로 두면 (a) 이관에 문서 수만큼 쓰기가 필요하고 (b) 파기
때도 재귀 삭제가 필요하며 (c) `archivedInquiries` 문서 하나만 읽어서는
전체 맥락을 못 본다. 보관본은 **읽기 전용 스냅샷**이라 정규화할 이유가
없다. 답변이 극단적으로 많아 1MB 문서 한도에 닿을 위험은, 문의 1건당
답변 수가 관리자-사용자 왕복이라 현실적으로 없다(상한 100개로 자르고
잘렸음을 `repliesTruncated: true`로 표시).

#### 2-2. 탈퇴 트리거의 순서

```
1. archivedInquiries에 복사 (batch)
2. 복사 성공 확인 후 원본 inquiries + replies 삭제
3. 실패 시 원본을 지우지 않는다 — 재시도로 복구 가능해야 한다
```

⚠️ 지금 트리거는 삭제만 하므로 실패해도 잃을 게 없었지만, 이동은 **복사가
실패한 채 삭제되면 영구 소멸**이다. 순서를 반드시 지킨다.

### 층 3. AI 호출 로그 — 현행 유지 + uid 없는 일별 집계 (신규)

**`aiAuditLogs`는 지금대로 탈퇴 시 파기한다.** 방침 8번·13번에 "회원 탈퇴 시
함께 파기"로 이미 고지돼 있고, CS 대응에 꼭 필요한 정보(결제·잔액·문의)는
층 1·2가 커버한다. 이 층을 건드리면 방침 개정 범위가 불필요하게 커진다.

대신 **개인을 식별하지 않는 일별 집계**를 따로 쌓는다.

**`costStats/{YYYY-MM-DD}`** (KST 기준 날짜, 서버 전용)

```
date: string              // 'YYYY-MM-DD' (KST)
calls: number             // 전체 호출
okCalls: number           // 성공
promptTokens: number      // 합계
outputTokens: number      // candidates + thoughts 합계
costKrwSum: number        // 원가 합계
costKrwMax: number        // 그날 최댓값 (P90 대용 — 튀는 건을 놓치지 않기 위해)
distinctUsers: number     // 그날 호출한 고유 이용자 수 (아래 방식)
```

**`distinctUsers`를 uid 저장 없이 세는 방법**: `users/{uid}`에
`lastCostStatDate` 필드를 두고, AI 호출 시 그 값이 오늘과 다르면
`distinctUsers`를 1 올리고 오늘로 갱신한다. **uid 목록도, uid 해시도
저장하지 않는다** — 카운터만 증가한다. `users/{uid}`는 탈퇴 시 삭제되지만
카운터는 `costStats`에 이미 반영돼 있어 **탈퇴와 무관하게 남는다.**

이 집계는 개인정보가 아니므로 **파기 대상이 아니고, 방침 수집 항목도 늘지
않는다.** 다만 방침 8번의 "명함 인식 형태 통계"와 나란히 **"AI 기능 이용
집계(개인을 식별하지 않는 수치)"** 한 줄을 넣어 두는 것이 정직하다(4절).

#### 3-1. 이게 푸는 두 번째 문제 — 원가 표본

2026-08-15 실측: 최근 32일 성공 호출 **2건**(표본 요건 150건). 2026-08-12
측정 때는 같은 기간 25건이었다. 계정 삭제가 `aiAuditLogs`를 지우기 때문에
**테스트 중 계정삭제·재가입을 반복하면 표본이 쌓이는 속도보다 지워지는
속도가 빠르다.** 집계가 별도로 남으면 이 문제가 사라진다 —
**충전 티어별 회수 확정(HANDOFF 2-0의 8번)의 전제**다.

`tool/analyze_ai_cost.py`는 `costStats`가 생기면 그쪽을 우선 읽고,
없으면 기존 `aiAuditLogs` 경로로 떨어지게 고친다(양쪽 병행 기간 필요).

### 2-4. 공통 — 만료 파기

**`purgeExpiredRetention`** (Cloud Scheduler, 하루 1회)
- `purchases`·`creditGrants`·`archivedInquiries`에서 `retainedUntil < now`인
  문서를 삭제.
- 로그에는 **컬렉션별 삭제 건수만** 남긴다(개인정보 원문 금지 — CLAUDE.md 4절).
- ⚠️ Cloud Scheduler는 **Blaze 필요**(이미 전환됨).

**백필 1회**: 기존 `purchases`·`creditGrants` 문서에 `retainedUntil`이 없다.
없는 문서는 파기 대상에서 제외되므로 영구 보존이 된다 → 관리자 콘솔의
일회성 작업(기존 태그 정리와 같은 패턴, backlog 추가 204)으로 백필한다.

⚠️ **층 2는 시급하다.** 게이트를 기다리는 동안에도 탈퇴마다 문의가 영구
소멸한다. 두 가지 선택지가 있다:
- **(가) 지금 트리거를 "삭제 보류"로 바꾼다** — 이관 코드가 준비될 때까지
  탈퇴 시 문의를 지우지 않고 `pendingArchive: true`만 찍는다. ADMIN-VULN-007이

- **(나) 그대로 두고 소실을 감수한다** — 테스터 단계라 실제 CS 이력의 가치가
  낮다면 합리적이다.

**(나)를 권장한다.** 지금 쌓이는 문의는 직원 테스터 것이고, (가)는 보안 수정을
일시적으로 되돌리는 변경이라 실수 여지가 크다. 다만 **테스터에게 "탈퇴하면
문의 이력이 사라진다"를 알려** 중요한 제보는 탈퇴 전에 처리한다.

## 6. 검증 계획

**자동 테스트**
- `firestore.rules`: `archivedInquiries` 읽기·쓰기 전면 거부(관리자 토큰
  포함) — `tool/verify_rules.py`에 케이스 추가.
- functions 단위: 이관 성공/실패 시 원본 보존 여부, `retainedUntil` 계산,
  `reason` 없는 열람 거부, 상한 50건.
- `costStats`: 같은 uid가 하루에 두 번 호출해도 `distinctUsers`가 1만
  오르는지, 날짜 경계가 KST인지(추가 176의 TZ 함정).

**부분 테스트**(실기기·실서버)
- 탈퇴 → 관리자 콘솔 문의 목록에 **0건**(007 유지 확인) → `lookupArchivedInquiries`로
  사유를 넣어 조회하면 **나옴** → `archiveAccessAudits`에 기록됨.
- 충전 1건 → 탈퇴 → `creditGrants`로 "언제 얼마" 재구성 가능.
- `costStats` 문서가 날짜별로 생기고, 계정 삭제 후에도 그 값이 남아 있음.

**⚠️ "테스트 통과 = 동작함"이 아니다**(CLAUDE.md 4절). 이 변경은 저장·삭제·
마이그레이션에 해당하므로 **배포 후 Firestore 실물을 직접 열어** 확인한다
(`tool/verify_server_privacy.py` 패턴 재사용).
