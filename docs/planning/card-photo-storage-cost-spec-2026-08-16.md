## 1. 문제 — 수익 구조와 비용 구조가 어긋난다

**충전형은 "AI를 쓸 때" 받는데, 사진 저장은 "안 써도 계속 나가는" 비용이다.**

무료 이용자가 명함 1,000장을 넣고 AI를 한 번도 쓰지 않아도 **매달 저장 요금이
영원히** 나간다. 유료 전환율이 낮으면 **가입자가 늘수록 적자가 커지는 구조**다.

AI 호출은 쓴 만큼만 나가고(회당 $0.0014~0.0023, 추가 100 실측) 충전으로 회수
되지만, **저장은 회수 경로가 없다.**

## 2. 지금 설계로 계산하면 얼마인가

### 실측 — 명함 사진 한 장

**실기기에 실제로 저장된 암호문 16장 전수**(손익 세션 측정, SM F966N,
`adb run-as`, `contact_card_*.enc`):

```
평균 1.67MB · 중앙 1.63MB · P90 2.18MB · 범위 1.17~2.28MB
```

분포가 좁은 이유는 크롭 결과물의 픽셀 수가 명함이 아니라 **가이드 프레임**으로
정해지기 때문이다 — 기기 화소와 무관하게 일정하다. `storage.rules`의 5MB
상한 대비 최대가 46%라 여유는 있다.

⚠️ **PM이 처음 잰 0.92~1.10MB는 임시 파일**(`card_scan_*.jpg`)이었다.
**서버에 올라가는 것은 암호화된 저장본이고 그게 1.67MB**다. 위 값이 맞다.

**축소도 압축도 하지 않는다.** `camera_scan_modal_view.dart`가
`img.encodeJpg(…, quality: 100)`로 **원본 해상도(2934×1636) 그대로** 굽는다.
OCR 인식률을 위한 값인데, **서버 사본은 인식이 끝난 뒤의 복원용**이라 같은
품질일 이유가 없다.

### ⚠️ 먼저 — 아래 "1인 1,000장"은 **계획치가 아니라 상한 스트레스값**이다

명함 3장/월로 쌓으면 1,000장은 **약 28년**이다. 손익 모델의 상단은 **1인
150장**(약 50개월)이다. **이 숫자를 계획 전제로 읽으면 원가를 6.7배 부풀려
의사결정이 왜곡된다.**

**현실 구간은 이쪽이다**(손익 세션, 축소 전 실측 기준):

| 1인 누적 | 무료 5만 명 | E안 25.5만 명 |
|---|---|---|
| **50장** | 월 $94 | 월 $478 |
| **150장** | 월 $281 | 월 $1,435 |

⚠️ **1인 누적 장수가 이 계산의 가장 큰 미지수**다. 장당 용량은 실측으로
닫혔지만(1.67MB), 누적 장수는 **표본이 없다.** 테스터 사용이 쌓이면 재야 한다.

아래는 **"최악이어도 여기까지"**를 보는 스트레스 계산이다.

### [스트레스] 10,000명 × 1,000장 = 1,000만 장 ≈ **16.7TB**

공시가 기준 개략치, 서울 리전(`asia-northeast3`), 환율 1,380원.

| 보관 등급 | GB당/월 | 16.7TB 월 |
|---|---|---|
| **Standard(지금 설계)** | $0.025 | **약 58만원** |
| Nearline | $0.010 | 약 23만원 |
| Coldline | $0.004 | 약 9만원 |

**누적된다.** 이듬해에도 같은 사람이 계속 쌓는다.

⚠️ **다운로드가 더 위험하다.** 기기 변경 복원 시 서울→인터넷 약 $0.12/GB.
1,000장 = 1GB이므로 **1인이 기기 한 번 바꿀 때마다 약 165원**, 1만 명이 한
번씩이면 **약 165만원이 한 번에** 나간다.

## 3. 대책 셋을 합치면 비용 문제가 사실상 사라진다

### ① 이미지 축소 — **확정**(사용자, 2026-08-16)

서버 사본은 **복원해서 보는 용도**다. 인식은 이미 끝났다.

| | 값 |
|---|---|
| 긴 변 | **1,600px** |
| 품질 | **80** |
| 실측 크기 | **평균 236KB** (표본 103장 재인코딩, 손익 세션) — **약 82% 절감** |

**1,600px이 충분한 근거**: 명함 긴 변 90mm가 약 1,390px = **약 390dpi**로,
문서 스캔 표준 300dpi를 넘는다.

⚠️ **기기 로컬 사본은 건드리지 않는다.** 축소는 **업로드 직전에만** 한다 —
로컬 원본까지 줄이면 나중에 재인식·확대 보기에서 손해다.

#### ⚠️ 그래서 기기를 바꾸면 원본이 사라진다 — **안내한다**(사용자 확정 2026-08-16)

```
지금 기기:  원본 (2934×1636)
서버:       축소본 (1600px·q80)
기기 변경 → 서버에서 축소본을 내려받음
새 기기:    축소본만 남는다        ← 원본은 어디에도 없다
```

서버에 원본을 두면 이런 일이 없지만 **비용이 약 4배**다.

**방침에는 "기기 변경 시 복원"이라고만 적혀 있고 화질이 달라진다는 말이 없다.**
사용자 결정으로 **알리기로 했다** — 알려서 손해 볼 것이 없고, 나중에 *"화질이 왜
떨어졌냐"*는 문의가 오면 **설명할 근거가 남는다.**

| | |
|---|---|
| 어디에 | 복원이 끝난 뒤 안내 한 줄 |
| 무엇을 | *"사진은 보관용 화질로 복원됩니다"* 정도(문구 확정은 UI 몫) |
| 언제 넣나 | **플래그 켜기 전** — 복원 경로가 살아나는 시점 |

⚠️ **방침 개정이 필요한가**: 필요 없다고 본다. 방침은 *"복원할 수 있도록
저장한다"*고 고지했고 **화질은 고지 항목이 아니다.** 다만 **법무 확인 대상**으로
남긴다.

#### 복원 안내 — **"화질이 낮음"과 "아예 없음"을 나눈다**(사용자 확정 2026-08-16)

**둘을 뭉뚱그리면 안 된다.** 화질 저하는 감수할 수 있지만, **없는 것은 없는
것**이다. 각각 다른 안내가 필요하다.

| 상황 | 사용자에게 |
|---|---|
| 백업된 사진 | **보관용 화질로 복원됨** |
| **백업 켜기 전 등록** | *"이전에 등록한 사진은 백업 전이라 복원되지 않습니다"* |
| **한도 초과분**(무료 300·충전 2,000) | *"한도를 넘어 백업되지 않았습니다"* |
| **업로드 실패분** | ⚠️ 아래 참고 |

**표현 원칙**: 손실만 말하면 불안만 남는다. **무엇이 되는지**를 말한다.

> 명함 사진은 **글자를 읽을 수 있는 화질**로 서버에 보관됩니다.
> 지금 쓰는 기기에는 **촬영한 원본 그대로** 남아 있습니다.

⚠️ **"지금 기기에는 원본이 있다"를 함께 말한다.** 빼면 *"내 사진이 다
열화됐구나"*로 읽힌다. 실제로는 **기기를 바꾸기 전까지 원본**이다.

⚠️ **"확대해도 또렷하다"는 아직 쓸 수 없다.** 1,600px·품질 80으로 줄인 실제
명함을 **본 적이 없다.** 수치(긴 변 1,600px = 명함 90mm 기준 약 390dpi,
문서 스캔 표준 300dpi 상회)는 계산으로 나오는 사실이지만, **판독 가능성은 빌드
후 실물로 확인한 뒤** 문구를 확정한다(CLAUDE.md 과장 금지).

### ⚠️ 그런데 안내를 하려면 먼저 알아야 한다 — 지금은 모른다

**명함별 백업 여부를 아무 데도 들고 있지 않다.** `ContactModel`에 그런 필드가
없다(2026-08-16 확인).

게다가 **업로드가 fire-and-forget이고 실패가 조용히 삼켜진다**
(`contact_image_service.dart`의 `unawaited(_photoBackup.upload(...))`). 즉
**네트워크가 끊긴 채 저장하면 백업이 안 됐는데 아무도 모른다.**

한도 초과와 **같은 유형의 조용한 실패**다. 그리고 이 저장소가 반복해 다친
자리이기도 하다 — *"의도한 실패도 사용자 눈에는 결함이다"*(`sessions/2026-08.md` 0-21).

**→ 한도 구현과 함께 "명함별 백업 상태"를 만들어야 한다.**

| | |
|---|---|
| 무엇을 | 백업됨 / 안 됨(사유: 한도 초과·업로드 실패·백업 이전) |
| 어디에 | 명함별. 서버 대조 없이 **기기에서 답할 수 있어야** 지갑 목록에 표시된다 |
| 왜 | 이게 없으면 **복원 안내도, 지갑의 "백업 안 됨" 표시도 못 만든다** |

⚠️ 업로드 실패분은 **개별 삭제 재시도(A안)와 같은 구조**다 — 실패를 큐에 적어
두었다가 다시 시도한다. **삭제 큐와 업로드 큐를 함께 설계하는 편이 낫다.**

#### ⬜ 검토했다가 보류한 안 — "이사 때만 원본을 잠깐 올린다"

사용자 제안(2026-08-16): *"일시적으로 자료를 서버에 올려서 새 기기에서
다운받을 때 함께 받도록 하면 어떨까."*

평소엔 축소본만 두고, **기기를 바꾸는 순간에만 원본을 임시 업로드 → 새 기기가
받으면 삭제**하는 방식이다.

**비용은 문제가 아니다.** 1,000장(원본 1.67GB) 기준 **1인 1회 이사당 약 ₩300**
이다(업로드 무료 · 다운로드 ₩276 · 임시 저장 7일 ₩15). 기기 변경은 2~3년에
한 번이다.

**그런데 셋이 걸려 보류한다.**

**① ⚠️ 가장 필요한 순간에 안 된다.** 원본은 옛 기기에만 있으므로 **옛 기기가
살아 있어야** 동작한다.

| | 되나 |
|---|---|
| 새 폰 사고 옛 폰 아직 있음 | ✅ |
| **폰을 잃어버림** | ❌ 올릴 기기가 없다 |
| 이미 초기화·반납 | ❌ |
| 앱만 지웠다 다시 깖 | ❌ |

**사진 백업을 만든 이유가 바로 "잃어버렸을 때"다.** 방침에도 *"기기를 바꾸거나
앱을 다시 설치했을 때 복원"*이라고 고지했다.

**② 방침의 보유기간과 어긋난다.** 파기 사유를 **"명함 삭제 시"·"탈퇴 시" 둘**로
못박아 게시했는데, **"이사 후 N일 뒤 자동 삭제"**라는 제3의 보유기간이 생긴다.
→ **방침 개정 + 7일 고지 재시작**이 필요할 수 있다(법무 확인 대상).

**③ 복잡도.** 이사 모드 UI · 옛 기기 일괄 업로드 · 새 기기 감지 · 완료 후 삭제 ·
**중간에 끊기면?** · 두 기기가 동시에 안 켜져 있으면? **축소본 복원(지금 설계)은
이 전부가 필요 없다.**

**그리고 근본 질문**: 1,600px는 명함 긴 변 기준 **약 390dpi**로 문서 스캔
표준(300dpi)을 넘는다. 원본이 필요한 경우는 **재인식(OCR)** 정도인데 **인식은
이미 끝났고 텍스트가 저장돼 있다.**

→ **"화질이 떨어져 못 쓰겠다"는 말이 실제로 나오는지 먼저 본다.** 지금은 아무도
겪어 본 적이 없다(플래그가 꺼져 있어 복원이 일어난 적 없음). 이 저장소가 반복해
다친 유형이다 — *"있어야 할 것 같아서" 만든 기능이 실제로는 안 쓰였다.*

📌 참고: 리멤버는 **PC 웹에서 흐리고 모바일에서는 정상**이라는 관찰이 있었다
(사용자, 2026-08-16). **웹이 작은 사본을 내려주는 것일 수 있어, 저장 원본이
작다는 증거는 아니다.** 앞서 PM이 "업계도 줄여 저장한다"고 추론했으나 **근거가
약해 철회한다.**

### ② 보관 등급 — ⚠️ **Standard 유지. Nearline 권고를 철회한다**(2026-08-16)

**처음에 PM이 Nearline을 권했으나 가격 근거가 틀렸다.** 쓴 값이 서울이 아니라
일반(미국) 기준이었다.

| | PM이 쓴 값 | 서울 공시가(손익 세션) |
|---|---|---|
| Standard | $0.025 | **$0.023** |
| Nearline | $0.010 | **$0.016** |

절감이 **60%가 아니라 30%**다. 그리고 Nearline에는 **최소 보관 30일 + 조회
과금 + 작업 단가 2배**가 붙는데, **이 앱에서는 복원(기기 변경)이 곧 조회**라
그 추가 과금이 실제로 발생한다.

**축소가 이미 −85%를 해결했다.** 남은 30%는 부작용을 감수할 만큼이 아니다.
손익 16-8에서도 **4순위**다.

→ **수명 주기 규칙을 걸지 않는다.** 아래 표는 처음 판단의 기록으로 남긴다.

복원용이라 평소에 읽지 않는다.

| | 최소 보관 | 검색 비용 | 판단 |
|---|---|---|---|
| Standard | 없음 | 없음 | 자주 읽지 않으므로 과하다 |
| **Nearline** | **30일** | $0.01/GB | ~~권고~~ → **철회**(위 참고) |
| Coldline | **90일** | $0.02/GB | 더 싸지만 아래 이유로 위험 |

⚠️ **Coldline을 권하지 않는 이유**: 최소 보관 기간이 **90일**이라, 명함을
넣었다 지우면 **쓰지 않은 기간까지 요금이 붙는다.** 명함 정리는 생각보다 자주
일어난다. Nearline과 차이는 월 3,000원 수준이라 감수할 이유가 약하다.

| 초과 시 | **신규 업로드만 중단. 기존은 그대로 둔다** |
| 시점 | **플래그 켜기 전** |

권고안·근거: [`card-photo-quota-recommendation-2026-08-16.md`](./card-photo-quota-recommendation-2026-08-16.md)

**300 → 200으로 조정**(사용자, 2026-08-16). 월 3장이면 **200장은 약 5.6년**이다.
버렸던 100장(2.8년)과 달리 **핵심 타겟이 1년 안에 닿지 않는다.**

⚠️ **이 조정은 비용에 실제로 영향이 있다.** 무료 이용자 1인당 100장이 줄어드는데,
무료가 25.5만 명이면 **2,550만 장**이다. 0.3MB·Standard 기준 **월 약 $172**이
빠진다(E안 상한 $606 → 약 $434, **−28%**). 무료 한도는 **인원수에 곱해지므로**
충전 상한보다 훨씬 민감하다.

⚠️ **되돌리기 어려운 방향이라는 것도 함께 본다.** 한도는 **올리기는 쉽고 내리기는
어렵다**(초과분을 지울 근거가 방침에 없다). 200 → 300으로 올리는 것은 언제든
되지만, 켠 뒤 300 → 200으로 내리는 것은 못 한다. **낮게 시작해 필요하면 올리는
방향**이 안전한 쪽이다.

⚠️ **다만 이탈 위험이 커지는 방향이기도 하다.** 사진 백업은 **충전 유도 지렛대가
아니라 보험**이다 — 한도에 걸린 사용자는 충전하는 것이 아니라 *"내 사진이
없어졌다"*로 이탈할 수 있다(손익 세션 판단). **5.6년이 충분히 먼가**는 실사용
데이터로 다시 봐야 한다. **1인 누적 장수 표본이 아직 1명·16장뿐이다.**

#### 충전 상한을 3,000 → 2,000으로 내린 경위

같은 날 사용자가 *"2,000장으로 낮추고 2,000~5,000장 구간은 1회성 ₩2,000"*을
제안했다. **한도 인하는 채택하고 유료 확장은 보류**했다.

**인하가 지금은 공짜다.** Storage에 사진이 **0장**이라 "내리는" 것이 아니라
**처음부터 정하는** 것이다. 켠 뒤에 내리면 초과분을 지울 근거가 없다
(방침의 파기 사유는 "명함 삭제 시"·"탈퇴 시" 둘뿐). **축소와 똑같은 구조다 —
지금 정하면 공짜, 켜고 나면 비싸다.**

**인하로 아끼는 돈은 거의 0이다.** 월 3장이면 2,000장은 55년이라 걸리는
사람이 사실상 없다. 그래도 정해 두는 이유는 **나중에 못 바꾸기 때문**이다.

#### ⬜ 유료 저장 확장(₩2,000) — **보류**

손익 세션 대조 결과 **팔릴 수 없다.**

⚠️ **2,000장에 도달할 방법이 없다.** 코드로 확인했다 — 일괄 스캔 화면은
**명함을 저장하지 않고**(파싱 결과 표시만) **진입 경로도 없다**. CSV·연락처
가져오기도 없다. 일반 사용자는 **한 장씩** 찍거나 고르는 것뿐이라, 2,000장은
**하루 1장씩 5.5년**이다.

손익 영향도 없다 — E안 기준 확장 0명이면 **−1.0%p**, 전원 구매해도 **+2.0%p**로
손익표에서 안 보인다.

**순서가 뒤집혀 있었다. 매출을 만들려면 상품이 아니라 대량 등록 기능이 먼저다**
(별건: `bulk-card-import-idea-2026-08-16.md`).

### ⚠️ 축소와 한도는 **둘 다 있어야** 성립한다

| | E안(무료 25만) 상한 |
|---|---|
| 축소 + 한도 | 월 $606 — **이익 −18.1%** |
| **한도만** (축소 없이) | 월 **$3,376** — **이익 −101%, 적자** |

**한도는 장수를 막고, 축소는 장당 단가를 낮춘다.** 나중에 둘 중 하나를
되돌리자는 논의가 나오면 이 표가 근거다.

## 4. 셋을 합친 계산

⚠️ 아래는 한도 확정 **전**의 계산이다(충전 사용자 1,000장 가정).
확정값(무료 300·충전 3,000) 기준 상한은 §3-③의 표를 보라. 현실 구간(1인 50~150장)
에서는 이보다 훨씬 작다.

가정: 10,000명 / 축소 후 **236KB**(실측) / 무료 한도 **100장** / 충전 사용자
1,000장 / 무료 9,000명·충전 1,000명

→ 무료 90만 장 + 충전 100만 장 = **190만 장 ≈ 448GB**

| 보관 등급 | 448GB 월 |
|---|---|
| Standard | 약 15,000원 |
| **Nearline** | **약 6,200원** |
| Coldline | 약 2,500원 |

**축소 없이 한도만 뒀을 때(3.2TB, 월 11만원)의 1/18**, 아무것도 안 했을 때
(16.7TB, 월 58만원)의 **1/94**다. 복원 다운로드도 1인당 **39원** 수준이다.

손익 세션 계산으로도 같은 결론이다 — E안(무료 25.5만) 기준 **1인 50장이면
스토리지 원가가 이익의 14%, 150장이면 43%**를 먹는데, **축소하면 어느
구간에서도 8% 안**이다.

## 5. ⚠️ 무료 한도에서 반드시 지킬 것

### 조용히 안 올라가면 안 된다

한도를 넘겼는데 아무 말이 없으면, **기기를 바꾼 뒤에야 "사진이 없어졌다"**고
알게 된다. 그건 결함으로 접수된다.

- 한도 도달 시 **명확히 알린다**
- 명함 지갑에서 **"백업 안 됨"을 구분해 보여준다**
- ⚠️ 이 저장소 원칙: **"의도한 실패"도 사용자 눈에는 결함이다**(`sessions/2026-08.md` 0-21).
  rules 미배포 상태에서 동의 토글이 조용히 실패했던 것과 같은 유형이다

### 어떤 100장인가

| 방식 | 문제 |
|---|---|
| **오래된 것부터 밀어내기**(최근 N장 유지) | ⚠️ **있던 게 사라진다.** 백업된 줄 알았던 사진이 조용히 없어진다 |
| **먼저 등록한 N장 유지** | ✅ **권고.** 이미 백업된 것은 그대로 남고, 새 것이 안 올라갈 뿐이다 |

**"이미 있던 것을 잃는" 쪽을 피한다.**

### 방침과의 관계

**요금제에 따른 기능 차등은 개인정보처리방침 사항이 아니다**(약관·요금 안내
사항). v2.2를 다시 고칠 필요는 없다.

⚠️ 다만 방침은 *"사진을 서버에 저장한다"*고 고지했다. **고지보다 덜 하는 것은
문제가 되지 않는다** — 한도를 두거나 아예 켜지 않아도 방침 위반이 아니다.

## 7. 구현 메모 (결정 후)

- 축소는 **업로드 직전** `CardPhotoBackupService`에서. 로컬 원본은 그대로
- 한도 판정은 **서버가 진실**이어야 한다 — 클라이언트만 세면 우회된다.
  `storage.rules`로는 개수를 못 센다(경로 규칙만 가능) → **Firestore에 카운터**를
  두거나 Callable을 거친다
- 보관 등급은 **버킷 수명 주기 정책**으로 건다(업로드 시 Standard → 30일 후
  Nearline). 처음부터 Nearline으로 쓰면 방금 올린 것을 바로 복원할 때 검색
  비용이 붙는다
- ⚠️ `storage.rules`의 업로드 상한이 **5MB**다(`_maxDownloadBytes`와 같은 값).
  축소 후엔 **1MB로 낮추는 것**을 검토한다 — 상한이 느슨하면 축소를 우회한
  업로드를 막지 못한다

무료 할당량(5GB)을 포기하고 `asia-northeast3`로 간다. 근거 셋:

1. **방침 v2.2에 "Cloud Storage, 서울 리전"이라고 이미 게시했다**(2026-08-16).

3. **위치는 한 번 정하면 못 바꾼다**

⚠️ **무료 할당량은 어차피 의미가 없다.** 5GB는 1인 50장 기준 **약 60명분**이고,

| **0-2** | **한도 구현**(무료 300·충전 2,000) | ⚠️ **컴파일 상수 금지 — 서버 전용 사용자별 필드로** |

| 3 | 실기기 확인 — 업로드·복원·탈퇴 삭제 | 전체 테스트 |

### ⚠️ "시행일 이후"는 "그날 켠다"가 아니다

방침 v2.2의 **시행일은 2026-08-23**이다. 이것은 *"이때부터 이 방침이 적용된다"*는
뜻이지 **"이날 반드시 기능을 켜야 한다"가 아니다.**

- **8/23 이전에는 못 켠다** — 고지 기간이 안 지났다
- **8/23 이후로는 아무 때나 켤 수 있다.** 현재 목표는 **8월 말**(사용자, 2026-08-16)
- **늦게 켜는 것은 방침 위반이 아니다.** 고지보다 덜 하는 것은 문제가 되지 않는다.
  준비가 안 됐는데 켜는 쪽이 위험하다

**시행일 자체는 이미 게시돼 못 바꾼다.** 바꾸려면 방침을 다시 고쳐 7일 고지를
처음부터 다시 해야 한다.

### ⚠️ 0번을 앞에 두는 이유 — 소급 적용이 안 된다

지금은 **서버 사진이 0장**이라 0번을 먼저 넣으면 **전량이 축소본**이다.
플래그를 켠 뒤에 넣으면 **그 사이 올라간 것은 영구히 원본으로 남는다.**

되돌리려면 전량 다운로드 → 재인코딩 → 재업로드인데, **암호문이라 서버에서 못
한다.** 각 이용자의 기기에서만 복호화할 수 있으므로 **사실상 되돌릴 수 없다.**

### ⚠️ 함께 처리해야 할 별건 — 촬영 원본이 평문으로 남는다

손익 세션이 점검 중 발견했다. **앱 캐시에 촬영 원본(`CAP*.jpg`)이 평문으로

전부**).

- **저장본을 암호화하는 이유 자체를 무력화한다**
- 명함을 지워도 남아 **"명함 삭제 시 즉시 파기"와도 어긋난다**
- CLAUDE.md 개인정보 원칙: *암호화되지 않는 저장소에 개인정보 원문을 넣지
  않는다*

**별도 세션이 착수했다**(2026-08-16). 브랜치·PR은 아직 없다. 사진 백업을 켜기
전에 정리하는 것이 맞다 — 서버에 올리는 것을 축소·암호화해 놓고 기기에 평문
원본이 쌓이면 앞뒤가 맞지 않는다.

(`camera_scan_modal_view.dart`, `contact_image_service.dart`). **담당이 정해지면
