# 명함 사진 서버 저장 — 비용 설계 스펙

**작성**: 2026-08-16 (PM 세션)
**상태**: **초안 — 사용자·과금 담당 결정 대기.** §6의 세 가지를 정해야 착수한다.
**계기**: 사용자 지적 — *"서버에 사진을 저장하는 순간 사용자가 늘고 유료 충전
인원이 적으면 적자가 될 수 있다."*

⚠️ **플래그를 켜기 전에 정해야 한다.** 켠 뒤에 바꾸면 이미 올라간 원본을
일괄 변환·정리하는 일이 생긴다.

---

## 1. 문제 — 수익 구조와 비용 구조가 어긋난다

**충전형은 "AI를 쓸 때" 받는데, 사진 저장은 "안 써도 계속 나가는" 비용이다.**

무료 이용자가 명함 1,000장을 넣고 AI를 한 번도 쓰지 않아도 **매달 저장 요금이
영원히** 나간다. 유료 전환율이 낮으면 **가입자가 늘수록 적자가 커지는 구조**다.

AI 호출은 쓴 만큼만 나가고(회당 $0.0014~0.0023, 추가 100 실측) 충전으로 회수
되지만, **저장은 회수 경로가 없다.**

## 2. 지금 설계로 계산하면 얼마인가

### 실측 — 명함 사진 한 장

```
card_scan_….jpg   0.92 MB
card_rot_….jpg    1.10 MB
```

**축소도 압축도 하지 않는다.** `camera_scan_modal_view.dart`가
`img.encodeJpg(…, quality: 100)`로 **원본 해상도(2934×1636) 그대로** 굽는다.
OCR 인식률을 위한 값인데, **서버 사본은 인식이 끝난 뒤의 복원용**이라 같은
품질일 이유가 없다.

### 10,000명 × 1,000장(영업직군 상정) = 1,000만 장 ≈ **10TB**

공시가 기준 개략치, 서울 리전(`asia-northeast3`), 환율 1,380원.

| 보관 등급 | GB당/월 | 10TB 월 |
|---|---|---|
| **Standard(지금 설계)** | $0.025 | **약 35만원** |
| Nearline | $0.010 | 약 14만원 |
| Coldline | $0.004 | 약 5.5만원 |

**누적된다.** 이듬해에도 같은 사람이 계속 쌓는다.

⚠️ **다운로드가 더 위험하다.** 기기 변경 복원 시 서울→인터넷 약 $0.12/GB.
1,000장 = 1GB이므로 **1인이 기기 한 번 바꿀 때마다 약 165원**, 1만 명이 한
번씩이면 **약 165만원이 한 번에** 나간다.

---

## 3. 대책 셋을 합치면 비용 문제가 사실상 사라진다

### ① 이미지 축소 — **확정**(사용자, 2026-08-16)

서버 사본은 **복원해서 보는 용도**다. 인식은 이미 끝났다.

| | 값 |
|---|---|
| 긴 변 | **1,600px** |
| 품질 | **80** |
| 예상 크기 | **150~250KB** (지금의 **1/4~1/6**) |

⚠️ **기기 로컬 사본은 건드리지 않는다.** 축소는 **업로드 직전에만** 한다 —
로컬 원본까지 줄이면 나중에 재인식·확대 보기에서 손해다.

### ② 보관 등급 — **Nearline 권고**

복원용이라 평소에 읽지 않는다.

| | 최소 보관 | 검색 비용 | 판단 |
|---|---|---|---|
| Standard | 없음 | 없음 | 자주 읽지 않으므로 과하다 |
| **Nearline** | **30일** | $0.01/GB | ✅ **권고** |
| Coldline | **90일** | $0.02/GB | 더 싸지만 아래 이유로 위험 |

⚠️ **Coldline을 권하지 않는 이유**: 최소 보관 기간이 **90일**이라, 명함을
넣었다 지우면 **쓰지 않은 기간까지 요금이 붙는다.** 명함 정리는 생각보다 자주
일어난다. Nearline과 차이는 월 3,000원 수준이라 감수할 이유가 약하다.

### ③ 무료 한도 — **숫자와 동작을 정해야 한다**(§6)

비용을 수익에 붙이는 유일한 방법이다.

---

## 4. 셋을 합친 계산

가정: 10,000명 / 축소 후 **200KB** / 무료 한도 **100장** / 충전 사용자 1,000장 /
무료 9,000명·충전 1,000명

→ 무료 90만 장 + 충전 100만 장 = **190만 장 ≈ 380GB**

| 보관 등급 | 380GB 월 |
|---|---|
| Standard | 약 13,000원 |
| **Nearline** | **약 5,200원** |
| Coldline | 약 2,100원 |

**처음 계산(35만원)의 1/70.** 복원 다운로드도 1인당 **33원** 수준이다.

---

## 5. ⚠️ 무료 한도에서 반드시 지킬 것

### 조용히 안 올라가면 안 된다

한도를 넘겼는데 아무 말이 없으면, **기기를 바꾼 뒤에야 "사진이 없어졌다"**고
알게 된다. 그건 결함으로 접수된다.

- 한도 도달 시 **명확히 알린다**
- 명함 지갑에서 **"백업 안 됨"을 구분해 보여준다**
- ⚠️ 이 저장소 원칙: **"의도한 실패"도 사용자 눈에는 결함이다**(HANDOFF 0-21).
  rules 미배포 상태에서 동의 토글이 조용히 실패했던 것과 같은 유형이다

### 어떤 100장인가

| 방식 | 문제 |
|---|---|
| **오래된 것부터 밀어내기**(최근 N장 유지) | ⚠️ **있던 게 사라진다.** 백업된 줄 알았던 사진이 조용히 없어진다 |
| **먼저 등록한 N장 유지** | ✅ **권고.** 이미 백업된 것은 그대로 남고, 새 것이 안 올라갈 뿐이다 |

**"이미 있던 것을 잃는" 쪽을 피한다.**

### 방침과의 관계

**요금제에 따른 기능 차등은 개인정보처리방침 사항이 아니다**(약관·요금 안내
사항). v2.2를 다시 고칠 필요는 없다.

⚠️ 다만 방침은 *"사진을 서버에 저장한다"*고 고지했다. **고지보다 덜 하는 것은
문제가 되지 않는다** — 한도를 두거나 아예 켜지 않아도 방침 위반이 아니다.

## 6. 결정해야 할 것 — 사용자·과금 담당

### (1) 무료 한도 장수

**100장?** 영업직군이 1,000장을 든다면 100장은 체감상 적다. **300장**도 후보다.
숫자가 바뀌어도 §4의 비용은 크게 변하지 않는다(300장이면 380GB → 760GB,
Nearline 월 1만원대).

→ **비용보다 "무료 이용자가 얼마나 아쉬워야 충전하는가"의 문제**다. 과금 설계와
함께 봐야 한다.

### (2) 충전 사용자 한도

무제한인가, 상한이 있나. **무제한이면 극단적 사용자 한 명이 비용을 끌어올릴 수
있다** — 상한 + 초과 시 안내가 안전하다.

### (3) 언제 만들 것인가

| | |
|---|---|
| **켜기 전에 넣는다** | ✅ **권고.** 한도 로직이 나중에 붙으면 **이미 올라간 것을 어떻게 할지**가 문제가 된다 |
| 켜고 나서 붙인다 | 초과분 일괄 정리가 필요해진다 |

## 7. 구현 메모 (결정 후)

- 축소는 **업로드 직전** `CardPhotoBackupService`에서. 로컬 원본은 그대로
- 한도 판정은 **서버가 진실**이어야 한다 — 클라이언트만 세면 우회된다.
  `storage.rules`로는 개수를 못 센다(경로 규칙만 가능) → **Firestore에 카운터**를
  두거나 Callable을 거친다
- 보관 등급은 **버킷 수명 주기 정책**으로 건다(업로드 시 Standard → 30일 후
  Nearline). 처음부터 Nearline으로 쓰면 방금 올린 것을 바로 복원할 때 검색
  비용이 붙는다
- ⚠️ `storage.rules`의 업로드 상한이 **5MB**다(`_maxDownloadBytes`와 같은 값).
  축소 후엔 **1MB로 낮추는 것**을 검토한다 — 상한이 느슨하면 축소를 우회한
  업로드를 막지 못한다
