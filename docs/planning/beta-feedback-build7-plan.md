### 그룹 A — OCR 필드 추출 (E-01, E-02, E-03, E-08, F-01, O-01)

"완벽한 명함 파싱 모델 없이 키워드·정규식·글자크기 휴리스틱으로 추론"하는
구조라는 게 코드 주석에 이미 명시돼 있고, 지금까지도 실제 명함 샘플이 나올

위험이 크다.**

#### E-01 — 앞·뒷면 OCR 결과 덮어쓰기

- **증상**: 앞면 스캔 후 뒷면을 스캔하면 앞면 정보가 사라짐.
- **원인(코드 확인)**: `add_card_modal_view.dart`는 이미 "빈 칸만 채운다"는
  안전한 기본 동작(`_fillIfEmpty`, HANDOFF "5. 설계 패턴"에도 명시된 원칙)을
  갖고 있다. 문제는 332~348행의 분기 로직이다 — 새로 스캔한 결과의 **이름**이
  기존 이름과 다르면(`looksLikeDifferentCard`) "다른 명함을 스캔하셨나요?"
  다이얼로그(483~532행)를 띄워 "새 명함으로 시작"(전체 덮어쓰기, 416~429행
  `_setTextFromStart`)과 "뒷면 이어서"(빈 칸만 채움) 중 고르게 한다. **뒷면에는
  보통 이름이 없거나, OCR이 로고·주소 텍스트를 이름으로 잘못 뽑아** 그 값이
  기존 이름과 다르면 이 다이얼로그가 뜬다. 사용자가 "새 명함으로 시작"을
  고르면(문구가 "뒷면 이어서"와 나란히 있어 헷갈리기 쉬움) 뒷면 결과가 비어
  있는 필드까지 포함해 폼 전체를 덮어써서 앞면 정보가 날아간다.
- **처리 방안**: 근본 해결은 F-01(필드별 선택)이다. 다만 F-01이 나오기 전까지
  최소 방어책 2가지를 우선 넣을 수 있다 — ① 다이얼로그 문구에 "새 명함으로
  시작하면 지금까지 입력한 내용이 모두 지워집니다"처럼 결과를 명확히 경고.
  ② 뒷면 스캔(이미 앞면에서 이름이 채워진 상태에서의 재스캔)일 때는 새로
  뽑힌 이름이 "약한 폴백"(`OcrNameSource.leftoverFallback`/`fontSizePreferred`)
  경로로 나온 경우 다른 명함 판정에서 제외 — 즉 파서가 이름을 확신하지 못한
  결과로는 "다른 명함이다"라고 단정하지 않는다.
- **화면 흐름 (현재, 버그)**:
  ```
  ① 명함 지갑 → "명함 추가" → 카메라로 앞면 촬영 → 인식 결과가 폼에 채워짐
  ② 안내 배너 "뒷면 스캔" 버튼 탭 → 뒷면 촬영
  ③ 뒷면 OCR이 이름을 다르게(또는 노이즈로) 인식 → "다른 명함을 스캔하셨나요?"
     다이얼로그 (이름만 비교해서 뜸)
  ④-A "새 명함으로 시작" 선택 → 폼 전체가 뒷면 결과로 덮어써짐
       → 뒷면엔 이름/회사가 없는 경우가 많아 그 칸들이 빈칸이 됨 (버그)
  ④-B "뒷면 이어서" 선택 → 빈 칸만 채워짐 (의도한 동작, 문제 없음)
  ```
- **화면 흐름 (①번 방어책 적용 후)**: 위 흐름과 동일하되 ③의 다이얼로그
  문구에 결과 경고 문장이 추가되고, 뒷면 재스캔 상황에서 이름이 약한 폴백으로
  나온 경우 다이얼로그 자체가 뜨지 않고 곧장 빈 칸만 채우는 병합으로 진행됨.
  **새 화면 없음, 기존 다이얼로그 문구/조건만 수정.**

#### F-01 — 필드별 충돌 선택(E-01의 정공법)

- E-01의 "다른 명함이냐 아니냐" 이분법 자체가 문제의 뿌리라, 필드 단위로
  선택하게 하는 게 구조적으로 맞다. **E-01은 우선 방어책으로 막고, F-01은
  별도 작업으로 이어간다.**
- **화면 흐름 (신규 시트 1개 추가 — `OcrFieldConflictSheet` 가칭)**:
  ```
  ① 명함 스캔 → 앞면 촬영 → 인식 결과 편집 화면(값 채워짐)
  ② "뒷면도 스캔" 탭 → 뒷면 촬영
  ③ 기존 값과 새 값이 다르고 **둘 다 비어있지 않은** 필드가 1개 이상이면
     → 신규 "필드 충돌 확인" 바텀시트가 뜸
       - 필드별로 [기존: 홍길동] / [새로 인식: 기업] 두 줄 + 선택 라디오
         (기본 선택값 = 기존 유지 — 안전한 쪽을 기본으로)
       - 하단에 "전부 기존 값 유지" / "전부 새 값으로" 일괄 버튼
       - 충돌이 없으면(다른 점이 없거나 새 값이 비어 있으면) 시트 없이
         바로 기존 fill-if-empty 병합 → ④로
  ④ 확인 → 편집 화면으로 복귀(선택한 값이 반영된 상태)
  ⑤ 저장
  ※ 빈 필드는 항상 새 값으로 채운다(충돌 아님, 묻지 않음)
  ```
- 기존 "다른 명함을 스캔하셨나요?" 다이얼로그는 이 흐름에 흡수하거나
  (이름이 완전히 다른 확신 경로로 인식된 경우에만 남기는 등) 개발 단계에서
  구체화한다.

#### E-02 / E-03 / E-08 / O-01 — 파싱 정확도 (이름/직함/회사, 전화 라벨, 상세주소)

- **E-02**(이름이 '기업'으로 인식), **E-08**(이름·직함·회사명 혼동, 양
  플랫폼 반복 확인)은 재현할 실제 명함 이미지 없이는 정확한 원인을 코드
  추론만으로 단정하기 어렵다 — 다만 코드 구조상 명확한 후보 지점은
  `_pickCompanyFromLeftover`(455~466행, "더 나은 후보가 없으면 그래도 맨 앞
  줄을 쓴다")와 `leftoverFallback`/`fontSizePreferred` 이름 결정 경로
  (880~917행)다. 둘 다 "확신 없이 찍는" 최후 수단이라 이 경로 사용 빈도가
  실제 오류의 대부분을 설명할 가능성이 높다.
- **E-03**(휴대폰 `H.`가 사무실 전화로 오분류)은 **원인이 코드로 확정된다**:
  `mobileRegExp`/`officeRegExp`(509~514행)는 **숫자 패턴만으로** 분류한다
  (01x = 휴대폰, 02/0xx/070 = 사무실). `H.`/`T.` 같은 라벨은 전혀 보지 않는다.
  `070`으로 시작하는 번호는 인터넷전화 대표번호로도, 휴대폰 가상번호로도 쓰이는데
  지금은 무조건 사무실로 분류된다. **처리 방안**: 번호 앞뒤 토큰에서
  `H.`/`M.`/`HP`/`휴대폰`(모바일) vs `T.`/`Tel`/`전화`(사무실) 라벨을 먼저
  확인하고, 라벨이 있으면 숫자 패턴보다 라벨을 우선하도록 분류 규칙에 한
  단계 추가한다. 이 항목은 세 항목 중 **유일하게 명확한 버그 수정**이다.
- **O-01**(상세주소까지 회사 주소에 포함)은 backlog 추가 172에서 이미
  "정책 확인이 아니라 파싱 개선 대상"으로 판단해 뒀다 — `ContactModel`은
  주소/상세주소를 분리 저장하는 설계이므로(`ocr_scanner_service.dart`의
  `address`/`addressDetail` 필드 분리, 535~751행 로직) 상세주소가 도로명
  주소에 섞여 들어가는 건 그 분리 로직이 케이스를 못 잡은 것이다. E-02/E-08과
  같은 그룹에서 실제 명함 샘플로 같이 검증한다.
- **처리 방안(공통)**: E-03은 바로 구현 가능. E-02/E-08/O-01은 **테스트에
  쓸 실제 명함 사진(또는 최소한 OCR 원문 텍스트)이 있어야 정확히 고칠 수
  있다** — 없으면 추측성 수정이 되어 기존에 이미 맞던 다른 명함 케이스를
  깨뜨릴 위험이 크다(이 파일은 그런 회귀가 반복된 이력이 주석에
  여러 번 나온다). QA/테스터에게 실패한 명함 3종의 스캔 원본 이미지(또는
  raw OCR 텍스트, `_showRawTextCard`로 화면에서 이미 확인 가능)를 요청하는
  선행 작업을 권장.
- **화면 흐름**: 화면 흐름 변화 없음 — 카메라 스캔 → 인식 결과 편집 화면
  이라는 기존 흐름은 그대로다. **결과 값(자동 채워지는 텍스트)만
  정확해진다.**

  더더욱 그렇다).
- **방식 미확정 — 사용자가 "계획에 넣어만 두라"고 보류.** 아래 두 축으로
  선택지를 정리한다(구현안을 하나로 못박지 않음).
  - **축 1 — 추천을 어떻게 보여줄지**: (a) 태그 입력란 아래 추천 칩, 눌러야
    들어감 (b) 태그 칸에 자동으로 채워 넣고 지우게 함 (c) 타이핑 중 기존에
    쓰던 태그로 자동완성 (d) (a)+(c) 둘 다.
  - **축 2 — 후보를 어디서 뽑을지**: (A) 기기 내 규칙 기반(부서 접미사 +
    회사명 키워드 사전) (B) AI 서버 프록시에 회사·부서를 보내 생성 (C) 규칙
    기반 + 사용자가 이미 쓰던 태그 재활용.
  - **코디네이터가 사용자에게 이미 밝힌 권장안**: 표시는 (a) 추천 칩, 후보는
    (A) 규칙 기반. 근거 — ① 태그가 AI 브리핑 프롬프트로 들어가므로 틀린
    태그를 자동 입력하면 브리핑 품질이 조용히 나빠진다(E-11이 바로 그
    사고다) ② 가짜 데이터 금지 원칙상 "제안"과 "자동 입력"은 다르다 ③ (B)는
    명함 개인정보(회사·부서)를 새 목적(태그 생성)으로 서버에 보내는 것이라
    `docs/legal/privacy-policy.html` 개정이 함께 필요하고 AI 크레딧도
    차감된다. 이 문서에서도 같은 근거를 유지하되, 다른 축을 고를 수 있도록
    선택지는 살려 둔다.
- **근거가 없으면 추천을 띄우지 않는다**(빈 상태 유지) — 억지로 후보를
  만들어내지 않는다. 이것도 가짜 데이터 금지 원칙의 연장이다.
- **선행 의존성 2가지**:
  1. **E-08(이름·직함·회사명이 서로 다른 칸에 들어감, 그룹 A)** — 회사명
     칸이 틀린 상태면 추천 태그도 같이 틀린다.
  2. **F-12(부서 필드 신설)** — 지금은 부서 텍스트를 추출은 해도(아래 그룹
     M 참고) 저장하지 않고 버린다. 태그 추천에 부서를 근거로 쓰려면 최소한
     "이번 스캔에서 추출된 부서 문자열"까지는 파서가 살려 둬야 한다 —
     **다만 F-12가 하는 "영구 저장 필드로 만들기"까지는 필요 없고, 파서
     결과에서 버려지지 않는 정도로 충분하다.** 즉 F-11은 F-12의 **완전한
     완료**가 아니라 F-12 작업 중 만들어지는 "부서 문자열 추출 결과"만
     있으면 착수 가능 — 구현 순서를 짤 때 이 점을 활용해 F-12 작업의
     일부(추출)가 끝나는 시점에 F-11도 병행 가능한지 개발 단계에서 판단.
- **규칙 사전을 만든다면**: 카테고리 체계(직능/산업/회사 규모 등)와 초기
  사전 내용도 사용자 결정이 필요하다 — 이번 조사에서는 정하지 않았다.
  기존 `_departmentSuffixes`(`ocr_scanner_service.dart:326~340`, "사업본부/
  기획실/관리부/..." 등 12종)를 **재활용할 수 있다** — 지금은 회사명 leftover
  후보 중 부서처럼 보이는 줄을 후순위로 미루는 용도로만 쓰이고 값 자체는
  버려진다(아래 그룹 M에서 상세). 이 접미사 사전이 태그 후보(예: "기획" →
  "기획/전략" 태그)의 출발점이 될 수 있다.
- **화면 흐름 (축 1을 (a) 추천 칩으로 가정한 예시 — 확정 아님)**:
  ```
  ① 명함 스캔 → 인식 결과 편집 화면, 태그 칸은 비어 있음(E-11 수정 후 기준)
  ② [신규] 부서·회사명에서 추천할 태그가 있으면 태그 칸 아래에 칩 형태로
     노출(예: "#기획전략" "#제조업"). 근거 없으면 아무것도 안 뜸(빈 상태)
  ③ 칩 탭 → 태그 칸에 추가(자동으로 들어가지 않음, 눌러야 반영)
  ④ 사용자가 직접 입력도 계속 가능(기존과 동일)
  ```

### 그룹 M — 부서 필드 신설 (F-12) ✅ 사용자 확정 · ⚠️ 이번 계획 유일의 전체 테스트 대상

- **현재 상태(코드 확인)**: `_looksLikeDeptOrTagline()`(`ocr_scanner_service.dart`
  421~429행)은 "경영기획실" 같은 줄을 부서/슬로건으로 이미 판별하고 있다
  — 하지만 이 판별은 **회사명 leftover 후보에서 그 줄을 후순위로 미루는
  용도로만** 쓰이고(`_pickCompanyFromLeftover`, 455~466행), `ContactModel`에
  부서를 담을 필드 자체가 없어 **값은 결국 버려진다.**
- **⚠️ 새로 확인한 부수 효과 — 그룹 A(E-08)와의 연결고리**: 부서로 보이는
  줄이 회사명으로도 안 뽑히면, 지금 코드 흐름상 **남은 leftover 맨 앞
  줄이 title(직함) 자리로 들어간다**(880~928행 로직 — `title = titleLine ??
  (leftover.isNotEmpty ? leftover.removeAt(0) : '')`). 즉 **부서 텍스트가
  갈 곳이 없어서 지금은 직함 칸으로 잘못 들어가는 경로가 실제로 있다** —
  이는 E-08("직함/회사명이 서로 다른 칸에 들어감")의 원인 중 하나일 가능성이
  높다(실제 명함 샘플로 확정된 것은 아니고 코드 흐름 추론). **부서 필드가
  생기면 이 오분류의 일부가 자연히 줄어들 수 있다** — 그룹 A 재작업 시
  F-12 이후에 한 번 더 확인할 가치가 있다.
- **범위**: `ContactModel`에 부서 필드 추가 + OCR 추출(파서가 버리지 않고
  담아내도록) + 등록/편집 폼 입력란 + 명함 상세 화면 표시.
- **⚠️ 모델 변경 — 이 계획에서 유일하게 "전체 테스트(실기기)"가 필요한
  항목이다.** 저장·복원·마이그레이션·기기간 동기화에 직접 닿기 때문에
  CLAUDE.md 4장 기준 부분 테스트로는 부족하다. (아래 "3. 검증 방식"과 앞서
  보고한 "전체 테스트 필요 항목 없음" 서술을 이 항목 때문에 정정했다 —
  자세한 내용은 해당 절 참고.)
- **확인한 것 3가지(코드 근거)**:
  1. **구버전 앱이 만든 기존 명함(부서 필드 없음)을 읽어도 안전하다.**
     `contact_model.dart`의 `fromJson`(163~201행)은 이미 모든 선택적 필드를
     `json['필드명'] as 타입?` 널 세이프 캐스팅 + 기본값 패턴으로 처리한다
     (`officePhone`/`address`/`addressDetail`/`postalCode`/`memo` 등 전부
     동일 패턴). 부서 필드를 `department: json['department'] as String?`로
     같은 패턴으로 추가하면, 이 필드가 아예 없는 구버전 문서에서도
     `null`로 안전하게 읽힌다 — 예외 없음.
  2. **서버 백업 경로 포함 여부**: `toJson()`/`toBackupJson()`은 공통
     `_toJson({required bool includeGeo})`(130~161행)을 함께 쓴다. 좌표
     (`lat`/`lng`)와 `cardImagePath`만 `includeGeo` 조건으로 서버 백업에서
     제외되고(주소에서 파생되는 값이거나 기기 로컬 전용 파일이기 때문),
     `company`/`title`처럼 사용자가 직접 입력·확인한 텍스트 필드는 조건 없이
     양쪽에 다 들어간다. **부서도 같은 성격(파생값도 기기 종속값도 아닌
     직접 입력·확인 텍스트)이므로 조건 없이 포함하는 것을 권장** — 다른
     기기에서 로그인해도 부서 값이 그대로 복원돼야 함.
  3. **기기간 동기화(`mergeSync`) 안전성**: `contacts_repository.dart`의
     `mergeSync`(165~212행)는 **필드 단위가 아니라 `ContactModel` 객체
     단위로** `updatedAt`이 더 최신인 쪽을 통째로 채택한다(LWW). 즉 새
     필드를 추가해도 병합 로직 자체를 손댈 필요가 없다 — `toJson`/`fromJson`
     라운드트립에만 새 필드를 넣으면 `mergeSync`는 자동으로 그 필드까지
     함께 실어 나른다. **위험 없음, 별도 마이그레이션 로직 불필요.**
- **F-11과의 순서**: F-12(부서 저장)가 F-11(부서 기반 추천)보다 먼저일
  필요는 **없다** — 지금도 파서가 부서 텍스트를 판별은 하고 있어서(저장만
  안 할 뿐), F-11은 그 판별 결과를 "저장 없이 추천에만" 쓰면 F-12를 기다리지
  않고도 착수할 수 있다. 다만 **F-12가 먼저 배포되면 부서 값이 명함 데이터에
  영구히 남으므로, 추천 칩을 "이미 저장된 부서" 기반으로도 만들 수 있어
  추천 정확도가 올라간다.** 정리: 착수 자체는 F-12 없이도 가능, 완성도는
  F-12 이후가 더 높다 — 위 "그룹 L"에 이미 반영.
- **화면 흐름 (기존 등록/편집 폼 + 상세 화면 확장, 새 화면 없음)**:
  ```
  ① 명함 스캔 → 인식 결과 편집 화면에 [신규] "부서" 입력란 추가(직함 칸
     근처, 예: 직함 칸 아래)
  ② OCR이 부서로 보이는 줄을 인식하면 자동으로 채움(현재는 버려지던 값)
  ③ 사용자가 직접 수정 가능(다른 필드와 동일)
  ④ 저장 → 명함 지갑 상세 화면에도 부서 표시(직함/회사와 같은 자리, 있을
     때만 — 없으면 빈 상태 그대로, 가짜 값 채우지 않음)
  ⑤ 'AI에 보낼 정보 확인' 시트의 "기본 정보" 카드에도 부서가 있으면 포함
  ```

F-12를 2차 맨 앞(9번)에 둔 이유: 사용자가 이미 방식을 확정한 항목이라
설계 대기 없이 바로 착수할 수 있고, 1차가 배포·검증되는 동안 병행해도
서로 파일이 겹치지 않는다(`contact_model.dart`/`contacts_repository.dart`
중심 — 1차의 어떤 항목과도 파일이 겹치지 않음). F-11은 E-08 수정과 F-12
착수를 모두 전제하므로 2차 안에서도 실질적으로 가장 늦게 시작된다.

## 4. 사용자 결정이 필요한 항목

1. **F-02 — 명함 등록 필수 항목 완화 범위.** 지금 이름·회사명·주소·전화·
   이메일이 전부 필수다. 테스터 요청은 "주소만" 완화지만, 다른 항목도
   재검토할지 사용자가 정해야 한다.
   - (A) 주소만 선택 항목으로 전환, 나머지는 유지. **권장안.** 앱의 핵심
     가치(재연락 상기)에 전화/이메일이 직결되고, 요청 범위도 주소로 명확함.
   - (B) 전화·이메일도 함께 선택 항목으로 전환(다양한 명함 형식 수용 폭
     확대, 대신 '주변'뿐 아니라 다른 기능도 빈 값 처리 범위가 넓어짐).
2. **F-05 — 이미지 자르기 도입 여부와 방식.**
   - (A) 이번 스코프에 포함, 신규 패키지(예: `image_cropper`) 추가.
   - (B) 이번엔 보류(자동 크롭 정확도를 먼저 높이는 쪽에 투자).
   - 패키지를 쓴다면 자유 크롭 vs 고정 비율(명함 규격 90:50) 크롭 중 선택도
     필요.
3. **F-04 — 지도 카드/아이콘 제스처 통일 방향.**
   - (A) 카드에도 롱프레스(감지 토글) 추가.
   - (B) 카드는 탭 전용 유지, 안내 문구로 명확화. **권장안**(본문 참고).
4. **F-03 — 임시 기준 위치의 적용 범위.**
   - (A) 지도 화면 안에서만 유효(탭으로 돌아가면 실제 GPS로 복귀). **권장안**
     — 범위가 작아 빠르게 낼 수 있고, 사용자가 "지금 내가 보는 게 실제
     위치가 아니다"를 착각할 여지가 지도 화면 밖으로 새지 않음.
   - (B) '주변' 탭 목록 전체에도 반영(더 큰 설계 변경 — 위치 상태 모델
     자체를 "실제 GPS"와 "탐색 기준"으로 분리해야 함).
5. **E-06 착수 시점.** 다른 세션이 `location_service.dart`를 방금
   수정·병합했다(E-10, PR #132). 이 계획 조사 시점에는 이미 병합 완료로
   보이지만, **실제 착수 전에 그 세션이 완전히 마무리됐는지 사용자가
   최종 확인해 줄 것.** 같은 파일을 동시에 고치면 충돌 위험이 있다.
6. **E-11 — 이미 저장된 명함의 `AI, IT` 오염 태그 처리.** 자동 일괄 삭제는
   사용자가 실제로 입력한 `AI`/`IT` 태그까지 지울 위험이 있어 이번 조사에서
   정하지 않았다.
   - (A) 손대지 않음 — 새로 등록하는 명함부터만 정상화. 가장 안전하지만
     이미 오염된 기존 명함은 그대로 남는다.
   - (B) 안내만 — 명함 지갑이나 공지사항에 "태그에 `AI, IT`가 잘못 들어간
     경우가 있을 수 있으니 확인해 달라"는 안내만 띄우고 정리는 사용자에게
     맡긴다.
   - (C) 조건부 자동 정리. **권장안** — 태그가 **정확히 `['AI', 'IT']`
     두 개뿐이고 순서·철자까지 기본값과 동일한 경우만** 자동으로 비운다.
     회계사가 우연히 정확히 이 두 태그만 직접 입력했을 확률은 매우 낮아
     대상이 비교적 명확하다. 다만 "완전히 안전"하지는 않으므로(이론상
     오탐 가능) **정리 전에 해당 건수를 먼저 집계해 사용자에게 보여주고
     승인받은 뒤 실행하는 2단계 절차**를 함께 제안한다 — 특히 다른 계정
     데이터에도 영향을 줄 수 있어 조사 스크립트는 읽기 전용으로 먼저
     돌리고, 실제 정리는 별도 승인 후 진행.
7. **F-11 — 태그 추천 표시 방식(축 1).** 코디네이터가 사용자에게 이미
   (a) 추천 칩 방식을 권장했고 사용자는 "계획에 넣어 두라"며 보류한 상태다.
   - (a) 추천 칩(눌러야 반영). **권장안**(코디네이터가 이미 전달한 근거
     그대로 — 자동 입력은 가짜 데이터 위험, E-11이 실제 사례).
   - (b) 태그 칸 자동 채움 + 지우게 함.
   - (c) 타이핑 자동완성만.
   - (d) (a)+(c) 병행.
   - 후보 소스(축 2)는 권장안(A, 규칙 기반) 채택 여부도 함께 확인 필요 —
     (B) AI 서버 프록시 방식을 고르면 `docs/legal/privacy-policy.html`
     개정과 AI 크레딧 차감이 함께 발생한다.

## 5. 개인정보·"가짜 데이터 금지" 원칙 점검

- 이번 25건 중 개인정보 저장 위치를 새로 늘리는 항목은 F-11이 (B) 서버
  기반 후보 축을 고를 경우뿐이다(회사·부서를 AI 서버 프록시로 전송) — 그
  외에는 없다. F-06(AI 다양성)이 "이전 생성 문장을 서버로 다시 보낸다"는
  점만 데이터 흐름이 늘어나는 지점인데, **대화 포인트 자체가 이미 서버가
  생성해 클라이언트로 보낸 것**이라 왕복만 하는 셈이라 새로운 개인정보
  항목은 아니다. 다만 개인정보처리방침의 "위탁 처리 항목" 서술과 실제
  요청 페이로드가 달라지지 않는지 배포 전 가볍게 대조할 것(CLAUDE.md 원칙).
- **E-11이 이번 조사에서 확인된 "가짜 데이터 금지" 원칙 위반의 가장 명확한
  사례다** — backlog 추가 49(스톡사진을 프로필 사진처럼 순환 표시하던
  사건)와 정확히 같은 부류: 화면(태그 칸)을 채우려고 명함 내용과 무관한
  값(`AI, IT`)을 기본으로 심어 뒀고, 그 값이 사용자가 지우지 않으면 그대로
  저장되고 **AI 프롬프트에까지 사실처럼 전달**된다. 이번 계획에서 우선순위를
  1차 최상단으로 매긴 이유이기도 하다.
- 같은 파일의 메모 자동 채움 문구(`'AI OCR 스캔으로 자동 추출된 명함 텍스트
  정보입니다.'`)는 위 그룹 K에서 판단한 대로 **원칙 위반은 아니다**(사실을
  진술할 뿐 인물에 대해 없는 사실을 지어내지 않음) — 다만 AI 프롬프트에
  의미 없는 문장이 끼어드는 것은 별개 품질 문제라 함께 손보는 것을 권장했다.
- F-11(태그 추천) 자체가 "근거 없으면 아무것도 추천하지 않는다"는 설계로
  이미 이 원칙을 지키도록 계획했다 — 부서/회사명에서 뽑을 근거가 없는데
  억지로 태그를 만들어내지 않는다.
- F-02(주소 없는 명함 허용)는 "빈 상태를 그대로 보여준다" 원칙과 정확히
  같은 방향이라 위반 소지가 없다 — 주소가 없을 때 가짜 주소를 채우지
  않고 빈 값 그대로 저장·표시하는 설계로만 구현하면 된다(위 화면 흐름에
  이미 반영).
- E-02/E-08(이름·회사 오분류) 수정 시 실제 명함 샘플이 필요하다고 위에서
  적었는데, **그 샘플은 테스트/개발 목적으로만 로컬에서 다뤄야 하고
  저장소나 커밋에 포함하지 않는다** — 이 앱이 다루는 제3자 개인정보
  원칙(CLAUDE.md 4장)이 그대로 적용된다.
