# 1. 🚨 가장 큰 것 — 명함 하나를 고칠 때마다 **전부 다시 암호화한다**

## 무슨 일이 일어나나

`ContactsRepository._saveToDisk()`는 이렇게 동작한다.

```
명함 1장 수정
   → 전체 명함을 JSON으로 만들고            (전부)
   → AES-256-GCM으로 통째로 암호화하고       (전부)
   → base64로 바꿔                         (전부)
   → shared_preferences 키 하나에 덮어쓴다    (전부)
```

**이 경로가 저장소 안에서 11곳에서 불린다**(실측). 추가·수정·삭제·태그
변경·좌표 백필·경로 재연결 — 전부 같은 값을 치른다.

## 얼마나 걸리나 — **실측**

맥에서 실제 암호화·복호화를 돌려 쟀다(명함 필드 구성은 실제 `toJson()`과 같게
만들고, 한글 값을 채웠다).

| 명함 수 | 평문 | 저장된 문자열 | **암호화** | **복호화** |
|---|---|---|---|---|
| 100장 | 84KB | 113KB | **9.4ms** | 6.7ms |
| 300장 | 254KB | 338KB | **15.9ms** | 12.3ms |
| 500장 | 423KB | 564KB | **22.3ms** | 19.9ms |
| 1,000장 | 847KB | 1.1MB | **43.6ms** | 39.2ms |

⚠️ **한 프레임 예산은 60fps 기준 16.7ms다.** 500장이면 저장 한 번에 그 예산을
넘긴다. **그리고 이건 맥에서 잰 값이다** — 휴대폰은 더 느리다.

📌 **얼마나 더 느린지는 재지 않았다.** 기기에서 재야 안다. 다만 배수를
모르더라도 **방향은 정해져 있다** — 맥에서 이미 프레임을 넘긴다.

## 왜 화면이 멈추나

```dart
await _saveToDisk();   // 메인 아이솔레이트에서 기다린다
```

`cryptography` 패키지는 **순수 Dart 구현**이다(네이티브 바인딩 패키지가
`pubspec.yaml`에 없다 — 실측). 즉 이 계산이 **UI와 같은 아이솔레이트에서**
돈다.

⭐ **이 저장소는 이미 답을 알고 있다.** 이미지 쪽은 무거운 작업을 진작에
분리해 뒀다(실측):

```
image_rotation_bake.dart   compute() 로 회전·인코딩   (폴드 실측 2~3초 지연이 근거)
card_rect_worker.dart      상주 isolate              (compute 는 매번 새로 띄워서)
gallery_auto_detect.dart   compute()
```

**암호화만 그 대열에 안 들어갔다.**

## 고치는 방향 셋 (가벼운 것부터)

| | 무엇 | 얻는 것 | 드는 값 |
|---|---|---|---|
| **ⓐ** | 암호화를 `compute()`로 뺀다 | 화면이 안 멈춘다 | 작다 — 이미 쓰는 패턴 |
| **ⓑ** | 저장을 **모아서** 한다(디바운스) | 연속 수정에서 횟수가 준다 | 중간 — 유실 창이 생긴다 |
| **ⓒ** | 명함별로 나눠 저장한다 | 고친 것만 다시 쓴다 | **크다 — 저장 형식이 바뀐다** |

⚠️ **ⓒ는 마이그레이션이다.** 이 저장소에서 저장 형식을 바꾸는 변경은
**전체 테스트(실기기)** 대상이다(CLAUDE.md 4절). 지금 단계에서 권하지 않는다.

📌 **ⓐ만으로도 화면 멈춤은 사라진다.** 총 계산량은 그대로지만 **UI를 막지
않는다.** 먼저 ⓐ, 필요하면 ⓑ.

# 2. 🚨 서버 — 사람이 늘면 먼저 막히는 자리 셋

## ① `MAX_INSTANCES = 3`

```ts
const MAX_INSTANCES = 3;   // functions/src/index.ts:606
```

**이 값은 근거가 명확하고 의도적이다.** 주석이 이렇게 적어 두었다 —
*"배포된 설정을 조회해 보니 지정이 없는데도 이미 3이 잡혀 있었다. 어디서 온
건지 모르는 숫자에 의존하지 않으려고 고정한다. 올릴 이유가 생기면 그때 근거와
함께 올린다."*

⭐ **판단이 옳았다.** 다만 **지금이 그 "올릴 이유가 생긴 때"인지**를 출시 전에
정해야 한다.

```
주석의 계산   인스턴스당 동시 80 × 3개 = 동시 240건
```

### ✅ [측정 완료, 2026-08-26] 쟀다 — **결론은 "3으로 충분"이다** (추가 483)

`gcloud`가 `connection-sense` 프로젝트에 인증돼 있어 **배포된 설정과 실제
실행 시간을 직접 꺼냈다.**

**① 배포된 설정** — 주석의 전제가 실물과 맞는지부터 확인했다.

```
containerConcurrency  80        ← 주석의 "동시 80"이 맞다
maxScale               3        ← 주석의 "3개"가 맞다
메모리              256Mi
timeout               60초
```

**② `generateBriefing` 실행 시간** (최근 30일 · 호출 161건)

| | 시간 |
|---|---|
| 중앙 | **2.37초** |
| 평균 | 3.05초 |
| p90 | 6.21초 |
| p95 | 8.85초 |
| 최대 | 10.13초 |

**③ 이 값으로 본 처리량** (동시 240 ÷ 한 건이 무는 시간)

```
중앙 2.37초 기준  →  분당 6,085건
p95  8.85초 기준  →  분당 1,627건
```

📌 **테스터 규모는 물론 초기 이용자 규모에서도 3이 부족할 이유가 안 보인다.**
주석의 *"올릴 이유가 생기면 그때 근거와 함께 올린다"*는 판단이 옳았고,
**아직 그때가 아니다.**

### 🚨 429가 7건 있었다 — 정체를 가르지 않았으면 정반대 결론이 났다

```
응답코드 분포   200: 124건 · 400: 30건 · 429: 7건
```

429는 *"요청이 너무 많다"*는 뜻이라 **인프라가 막은 것처럼 보인다.** 실제로는
**앱 자신이 낸 것**이었다 — `index.ts:562`의 *"오늘 사용 가능한 AI 브리핑
횟수를 모두 사용했어요"*가 `resource-exhausted`로 나가고, 그것이 HTTP 429가
된다. **테스터가 하루 한도를 쓴 것이다.**

⚠️ **인프라가 막은 적은 한 번도 없다.** 이걸 안 갈랐으면 *"이미 상한에 걸리고
있다 → 올리자"*로 갔을 것이다. **같은 숫자가 정반대 결론을 만들 뻔했다.**

### ⚠️ 대신 다른 것이 보인다 — 메모리 256Mi에 동시 80

요청당 3.2MB다. **인스턴스가 늘기 전에 한 인스턴스가 먼저 터지는 모양**일 수
있다 — 즉 **실제 상한을 정하는 것이 인스턴스 수가 아니라 메모리**일 수 있다.

📌 **최근 7일 에러 0건**이라 지금 문제는 아니다. 그리고 **재 보지 않았다 —
추측으로 남긴다.**

📌 **넘치면 사용자에게는 *"잠시 후 다시 시도"*로 끝난다**(주석 확인). 즉
**돈이 새는 것보다 낫다는 판단이고, 출시 전에 다시 볼 값**이라는 뜻이다.

## ② `.limit()`이 **데이터 계층에 한 건도 없다** (실측)

```
lib/data/ 안 .limit( 사용 횟수 = 0
```

대부분은 **본인 것만 읽어서** 실무상 문제가 없다. **하나가 다르다.**

```ts
watchAllInquiriesForAdmin()      // inquiry_repository.dart:77
  → collection('inquiries').orderBy('createdAt', desc).snapshots()
```

**관리자 화면이 지금까지의 문의 전부를 실시간 구독한다.** 이용자 1만 명이
되면 관리자가 그 화면을 열 때마다 전체를 내려받는다 — **읽기 요금이 사용자
수가 아니라 누적 문의 수에 비례한다.**

같은 성격이 하나 더 있다.

```ts
tombstoneCleanup.ts:78   const snap = await collection.get();   // 전체
```

📌 **고치는 값은 작다** — `.limit(50)` + 더 보기. 지금 테스터 수에서는 안
드러나므로 **드러난 뒤에 고치면 이미 요금이 나간 뒤다.**

## ③ 공지 목록도 무제한이다

`watchPublishedNotices()` — 공지가 쌓이는 속도가 느려 당장은 괜찮지만 **상한이
없다는 성질은 같다.**

## ⭐ 가장 큰 절감 — **AAB로 올리면 3분의 1이 된다**

지금 APK 하나에 **두 ABI가 모두 들어 있다**. 스토어에 **AAB로** 올리면
Play가 **기기에 맞는 하나만** 내려보낸다.

### ⚠️ [정정, 2026-08-26] 처음 적은 "약 60MB"는 틀렸다 — 재 보니 **31.8MiB**다 (추가 483)

**AAB를 실제로 빌드해서 열어 봤다**(실측).

```
지금 테스터가 받는 fat APK      97.3 MiB
AAB → arm64 기기가 받는 양      31.8 MiB     ← 3분의 1
AAB → 32비트 기기               29.9 MiB
```

📌 **AAB 파일 자체는 85.8MiB지만 그게 내려받는 크기가 아니다.**

```
BUNDLE-METADATA(디버그 심볼)   36.0 MiB   ← Play 가 기기로 안 보낸다
arm64-v8a 네이티브             19.8 MiB
armeabi-v7a 네이티브           17.9 MiB
ABI 무관 공통(dex·에셋·리소스)  12.0 MiB
```

🚨 **처음에 이 36MiB를 공통분에 넣어 세다가 67.7MiB라는 틀린 값을 냈다.**
항목을 하나씩 열어 보고 잡았다.

> **파일 크기와 내려받는 크기는 다르다.** 이 구분이 없으면 같은 파일이
> *"별로 안 줄어드네"*(85.8 vs 97.3)와 *"3분의 1이 되네"*(31.8 vs 97.3)라는
> **정반대 결론**을 만든다.

⚠️ **어제 적은 *"약 60MB"*는 절감량이 아니라 최종 크기에 가까운 값이었고,
그마저도 컸다.** 계산으로 적어 둔 값이 실측과 두 배 차이 났다.

📌 **스토어는 선택이 아니다** — Play는 신규 앱을 **AAB로만** 받는다.
`build_app.sh`가 이미 `appbundle`을 지원한다(실측).

### ✅ [사용자 결정, 2026-08-26] **테스터 배포는 나누지 않는다**

테스터 배포(Firebase App Distribution)는 지금 **fat APK 97.3MiB**를 준다.
`--split-per-abi`로 나누면 절반 아래로 줄지만, **나누지 않기로 했다**
(*"분할하지 않아도 되"*).

📌 **두 가지를 갈라야 한다.**

| | 정할 수 있나 | 지금 |
|---|---|---|
| **스토어 제출을 AAB로** | ❌ **Play 요구사항** — 신규 앱은 AAB만 받는다 | 그대로 진행 |
| **테스터 APK를 ABI별로 분할** | ✅ 우리 선택 | **안 한다**(사용자 결정) |

⚠️ **그러니 이용자가 받는 31.8MiB는 그대로 얻는다.** 포기한 것은 **테스터가
받는 양**뿐이다 — 테스터는 계속 97.3MiB를 받는다.

📌 나누면 빌드 산출물이 ABI마다 하나씩 생겨 **"어느 파일을 올릴지"가 하나 더
늘어난다.** 테스터 수가 적은 지금 그 관리 비용이 절감보다 크다는 판단이다.

## 그다음 — 32비트를 계속 지원할 것인가

`armeabi-v7a` 37.0MB는 **32비트 기기용**이다. 빼면 fat APK가 60MB로 준다.

### ⚠️ [정정, 2026-08-26] **AAB로 가면 이 질문의 성격이 바뀐다** (추가 483)

AAB는 **기기마다 자기 ABI만 내려보낸다.** 즉 32비트를 빼도 **arm64 이용자가
받는 양은 그대로 31.8MiB다** — 줄어드는 것은 **AAB 파일 크기**(우리 쪽)이지
**이용자가 받는 양**이 아니다.

```
지금 AAB          arm64 기기 31.8MiB · 32비트 기기 29.9MiB
32비트 제거 후     arm64 기기 31.8MiB · 32비트 기기 앱을 못 깜
```

📌 **그러니 32비트 제거는 이제 용량 문제가 아니다.** 빌드·업로드가 조금
가벼워질 뿐이고, **잃는 것은 그대로다.**

⚠️ **이건 기능 결정이지 최적화가 아니다.** 대상 이용자(보험설계사)의 기기
분포를 모르므로 권고하지 않는다 — **재고 정할 일이고, AAB로 옮기고 나면
서두를 이유가 더 줄어든다.**

## 폰트 7.5MB — **줄일 수 있으나 확인이 필요하다**

```
Pretendard-Regular/Medium/SemiBold/Bold/ExtraBold   각 약 1.5MB × 5 = 7.5MB   실측
```

⚠️ **다섯 굵기가 전부 테마에서 쓰인다**(`app_theme.dart` 실측 — w400·w500·
w700·w800). **그냥 빼면 화면이 바뀐다.**

- **가변 폰트(Pretendard Variable)로 바꾸면** 한 파일로 여러 굵기를 낸다.
  ⚠️ **Flutter에서 굵기 지정이 그대로 먹는지 확인하지 않았다.** 되면 큰
  절감이고, 안 되면 화면이 틀어진다 — **재 보기 전에는 권고하지 않는다.**
- 서브셋(한자 제거)은 **명함에 한자가 들어올 수 있어** 위험하다.

## ✅ 확인해 봤으나 결함이 아니었던 것

`assets/icons3d/`(2.4MB)가 코드에서 안 쓰여 죽은 자산처럼 보였다. **번들에는

번들에서 뺐다. 파일은 도구 스크립트가 참조해서 보존"*이라고 적어 두었다.
**저장소에만 있고 앱에는 없다.**

📌 **적어 두는 이유**: 다음 사람이 같은 것을 보고 결함으로 올리지 않도록.

# 4. 구조 — 고쳐 두면 편해지는 것

## ① 화면 파일 넷이 지나치게 크다 (실측)

```
4,374줄  add_card_modal_view.dart      ← 명함 추가/수정 화면 하나
3,482줄  ocr_scanner_service.dart
2,441줄  camera_scan_modal_view.dart
1,961줄  radar_view.dart
```

⚠️ **크다는 것 자체가 결함은 아니다.** 다만 오늘 2c와 제가 **같은 파일
(`settings_view.dart` 1,846줄)을 동시에 건드려** 리베이스로 풀어야 했다.
**세션이 셋인 동안에는 큰 파일이 곧 충돌 지점이다.**

📌 **지금 쪼개라는 뜻은 아니다.** 쪼개는 것도 위험을 만든다. **다만 다음에
그 파일을 크게 손볼 일이 생기면 그때가 기회다.**

## ② 계층이 한 곳에서 거꾸로 간다 (실측)

```dart
lib/core/services/phone_call_service.dart:6
  import '../../presentation/common/glass_card.dart';
```

`core`가 `presentation`을 안다. **다른 168개 파일은 이 방향을 지킨다** —
`lib/presentation/`에서 Firestore·Auth를 직접 부르는 곳도 **0곳**이다(실측).
**하나만 튄다.**

## ③ 목록을 읽을 때마다 다시 계산한다

`filteredContacts`는 **getter**라 읽을 때마다 거르고 정렬한다. 그런데
`radar_view.dart` 한 번의 `build()`에서 **세 번 읽는다**(72·76·354행 실측).
`nearby_map_view.dart`는 두 번(179·182행).

거리 정렬은 비교할 때마다 하버사인을 두 번 부른다 — **명함당 한 번 재고
정렬하면 될 것을** 그렇게 한다.

### ⚠️ 그런데 재 보니 생각보다 작았다 — **실측**

| 명함 수 | 하버사인 호출 | 한 번 읽기 | 레이더 한 프레임(3회) |
|---|---|---|---|
| 100장 | 2,052 → 100 (**20배**) | 50µs → 13µs | 0.15ms → 0.04ms |
| 500장 | 11,044 → 500 (**22배**) | 218µs → 48µs | 0.65ms → 0.15ms |
| 1,000장 | 25,322 → 1,000 (**25배**) | 485µs → 106µs | **1.46ms** → 0.32ms |

📌 **호출은 25배지만 시간은 1,000장에서도 1.5ms다** — 프레임 예산 16.7ms 안에
있다(맥 기준).

⭐ **그래서 이건 급한 병목이 아니라 정리거리다.** 재기 전에는 1번 항목과 같은
급으로 보였다. **재고 나서 순위가 내려갔다.**

| 로그인 전 저장은 **평문**이다 | `contacts_repository.dart:_saveToDisk` | 아래 참고 |

## 로그인 전 평문 저장 — **지금은 안전하지만 이유를 알고 두어야 한다**

`uid == null`이면 암호화 키를 만들 수 없어 **평문으로 저장한다.** 이는
CLAUDE.md 4절(*"암호화되지 않는 저장소에 개인정보 원문을 넣지 않는다"*)과
정면으로 부딪히는 것처럼 보인다.

📌 **실제로는 릴리스에서 이 경로에 명함이 쌓이지 않는다** — *"로그인
건너뛰기"*는 debug 빌드에만 있다. 남는 경로는 **암호화 도입 이전의 레거시
데이터를 읽어 즉시 재암호화하는 일회성 마이그레이션**이다.

⚠️ **그래서 지금 고칠 것은 아니지만, debug 빌드로 테스트할 때는 실제 명함을
넣지 않는 편이 낫다.**
