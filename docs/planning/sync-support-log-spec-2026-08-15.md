# 동기화 지원 로그 — 스펙 초안

**작성**: 2026-08-15 (PM 세션)
**상태**: **초안 — 리갈팀 검토 대기.** 구현 착수 전이다.
**결정 경위**: 사용자가 *"충전·사용·기기이관 등 고객 불만이나 편의 지원을
위해 로그 없으면 찾을 수 없다"*고 지적, 확인해 보니 **기기이관만 아무
기록이 없어** 만들기로 확정(2026-08-15).

---

## 1. 왜 만드나

고객이 **"기기를 바꿨는데 자료가 안 넘어왔어요"**라고 하면, 지금은 **답할
근거가 없다.**

서버에 남는 것은 명함 데이터 자체(`users/{uid}/contacts/`)와 삭제 기록
(`deletedContacts/`)뿐이고, **"언제 어느 기기가 무엇을 올렸고 무엇을
내려받았는지"는 어디에도 없다.** 그래서 지원할 수 있는 방법이 **재현밖에
없다** — 고객 기기를 받아 보거나, 같은 상황을 만들어 보는 것.

이 프로젝트는 **"코드는 맞는데 실물이 틀린" 결함이 반복해서 나온 저장소**다
(CLAUDE.md 4절). 동기화는 그중에서도 가장 재현이 어려운 영역이다 — 두 기기,
시간차, 네트워크 실패가 겹친다. **사후에 무슨 일이 있었는지 볼 수 없으면
원인을 못 찾는다.**

### 지금 있는 지원 로그 (대조)

| 고객 문의 | 로그 | 탈퇴 시 |
|---|---|---|
| "AI가 안 돼요" | `aiAuditLogs` | 삭제 |
| "충전이 안 들어왔어요"(관리자 지급분) | `creditGrantAudits` | 남음 |
| "결제가 반영 안 돼요" | `purchases` — **규칙만 있고 구현 없음** | — |
| "명함이 잘못 읽혀요" | `ocrStats` | 남음 |
| 관리자 조치 이력 | `adminAuditLogs` | 남음 |
| **"기기 이관이 안 됐어요"** | **없음** | — |

## 2. 지금 동기화가 어떻게 도는가 (사실)

`lib/data/services/data_backup_service.dart`:

| 메서드 | 하는 일 |
|---|---|
| `backupContact(uid, contact)` | 명함 1건 서버에 올림 |
| `rebackupAllContacts(uid, list)` | 전량 재업로드 |
| `deleteContactBackup(uid, id)` | 서버 사본 삭제 |
| `writeTombstone(uid, id)` | 삭제 기록(묘비) 남김 — 다기기 동기화 A안(P1-39) |
| `fetchTombstones(uid)` | 묘비 조회 |
| `restoreContacts(uid)` | **서버에서 내려받음 — 기기 이관의 핵심 경로** |
| `restoreProfile(uid)` | 내 명함 내려받음 |
| `deleteAllUserData(uid)` | 탈퇴 시 전량 삭제 |

호출하는 쪽은 `contacts_repository.dart`(112·134·225·390행),
`my_profile_repository.dart`(54·68행).

**묘비 방식의 특성**: 서버 문서만 지우면 다른 기기의 로컬 사본이 다시
올라온다. 그래서 "지웠는데 되살아났다"는 문의가 구조적으로 나올 수 있고,
**그게 정상 동작인지 결함인지 로그 없이는 구분할 수 없다.**

## 3. 무엇을 남기나

`users/{uid}/syncEvents/{eventId}` (또는 최상위 `syncEvents` — §6 미결)

| 필드 | 값 | 왜 |
|---|---|---|
| `at` | 서버 시각 | 클라이언트 시계는 못 믿는다(묘비가 이미 클라 시계라 대조가 필요) |
| `deviceHash` | 기기 지문 **HMAC-SHA256** | "어느 기기"를 원본 식별자 없이 |
| `kind` | `upload` / `restore` / `tombstone` / `rebackupAll` | 무슨 동작 |
| `count` | 건수 (정수) | 몇 건이 오갔나 |
| `ok` | 성공 여부 | |
| `errorCode` | 실패 시 분류 코드 | 원문 메시지 아님 |
| `appVersion` | 앱 버전·커밋 해시 | 낡은 빌드를 결함으로 오인한 전례가 있다 |

### 기기 해시는 새로 만들지 않는다

지갑 브랜치(`feat/ai-credit-wallet`)에 **이미 있다** —
`functions/src/deviceLedger.ts`의 `deviceHash()`가 raw device id(iOS
`identifierForVendor`, Android 기기 식별자)를 **서버 전용 salt와 HMAC-SHA256**
해시한다. 설계 근거도 문서화돼 있다(`monetization-referral-engineering-spec
-2026-08-14.md` §4-2 *"탈퇴해도 사라지지 않는 것은 개인정보가 아니라 기기
지문 해시 하나뿐"*).

**같은 함수를 쓴다.** 해시 체계가 둘이 되면 나중에 대조가 안 된다.

⚠️ **의존**: `main`에는 **기기 식별자를 읽는 코드가 아예 없다**(`device_info`
계열 패키지 없음). 지갑 브랜치가 클라이언트 쪽을 함께 들고 있으므로,
**이 기능은 지갑 브랜치 병합 이후**이거나, 기기 식별자 취득만 따로 떼어
와야 한다. 병합 시점은 사용자 결정 사항이다(지갑은 main 병합 보류 중).

## 4. 무엇을 절대 안 남기나

**제3자(명함 주인) 개인정보는 한 글자도 안 남긴다.** CLAUDE.md 개인정보
원칙이자, 이 앱이 이용자 본인이 아닌 사람의 정보를 다루기 때문이다.

- 이름·전화번호·이메일·주소·회사 — **일절 없음**
- 명함 ID(`contactId`)도 **남기지 않는다** — 어느 명함이 문제였는지는
  건수와 시각으로 좁히고, 그래도 모자라면 고객 동의를 받아 별도로 본다
- 로그인 이메일 — **남기지 않는다.** `uid`만으로 충분하다
  (`aiAuditLogs`는 이메일을 남기지만 그건 감사 목적이고, 이건 지원 목적이라
  최소 수집 원칙이 더 좁게 적용된다)
- 오류 **원문 메시지** — 분류 코드만. 원문에 데이터가 섞여 들어온다

## 5. 보유 기간·탈퇴 시 처리 (제안)

| | 제안 | 근거 |
|---|---|---|
| 보유 기간 | **90일** 후 자동 삭제 | 지원 목적이면 최근 것만 있으면 된다. 문의는 대개 발생 직후 온다 |
| 탈퇴 시 | **즉시 전량 삭제** | `aiAuditLogs`와 같은 취급. 탈퇴자는 지원 대상이 아니다 |

⚠️ 자동 삭제는 **구현이 필요하다**(Firestore TTL 정책 또는 예약 함수).
"90일 보관"이라고 방침에 적고 실제로는 안 지우면 오늘 겪은 것과 같은
문서-구현 불일치가 된다.

---

## 6. 미결 — 리갈팀 검토 대기

1. **기기 해시 + uid 결합이 개인정보 처리인가.** 해시 자체는 복원 불가지만
   `uid` 아래 두면 특정 이용자에 귀속된다
2. **방침 고지가 필요한가.** 필요하면 어느 항목에 — "지원 목적 이용 로그"에
   포함되는가, 아니면 새 항목인가
3. **보유 기간 90일이 적절한가**
4. **저장 위치** — `users/{uid}/syncEvents/`(탈퇴 시 통째로 지워져 편함)와
   최상위 `syncEvents`(관리자 조회가 쉬움) 중 어느 쪽인가

**검토가 끝난 뒤 구현에 들어간다.** 오늘 명함 사진 건에서 **구현이 앞서가고
근거가 뒤따라온** 문제를 겪었다(동의 주체를 잘못 잡아 설계를 다시 함).

---

## 7. 이번 범위가 아닌 것

- **충전·결제 지원 로그** — `creditGrantAudits`가 이미 있고, 실제 결제
  (`purchases`)는 구현 자체가 없다. 결제 도입 시 별건
- **AI 이용 통계(마케팅용)** — 다른 스펙. 해시 uid 월별 집계, **출시 후**
  필요(2026-08-15 마케팅팀 요건). 이 로그와 목적이 다르므로 겸용하지 않는다
- **관리자 콘솔 조회 화면** — 로그를 남기는 것이 먼저다. 조회는 CLI·콘솔로
  시작하고, 문의가 실제로 쌓이면 화면을 만든다

---

## 8. 검증

이 기능은 **저장·복원·마이그레이션**에 해당하므로 **전체 테스트(실기기)**
칸이다(CLAUDE.md 4절). 다만 착수 전 검증 종류는 **사용자가 고른다.**

**"로그가 남았다"까지만 보면 안 된다** — 오늘 계정 삭제 결함이 정확히 그
방식으로 새어 나갔다(`deleteAllCardImages`를 부르는 코드는 있었지만 호출
시점이 계정 삭제 뒤라 규칙에 막혀 **조용히 실패**했다). 실기기 두 대로
**A에서 등록 → B에서 복원 → 서버에서 `syncEvents` 실물 조회**까지 간다.
