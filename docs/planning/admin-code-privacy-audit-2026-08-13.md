## 2. 가장 먼저 수정할 운영 결함

### P0-1. 관리자 법적 문서 편집이 실제 앱 문서에 반영되지 않음

**근거**

- 관리자 화면은 `legalDocs/{slug}`를 읽고 쓴다 (`docs/admin/admin.js:1077-1143`).
- 화면은 “앱 재배포 없이 바로 반영”되고 삭제하면 “앱/웹에서 바로 미등록”된다고 안내한다 (`admin.js:1082`, `1140`).
- 실제 Flutter 앱은 Firestore `legalDocs`를 전혀 읽지 않고 `https://connection-sense.web.app/{slug}`의 정적 Hosting HTML을 연다 (`lib/presentation/common/legal_document_view.dart:30-32`).
- 관리자 README도 `legalDocs`를 “앱 안에서 보이는 문서”라고 잘못 설명한다 (`docs/admin/README.md:70-80`).

**영향**

관리자는 개인정보처리방침을 바꿨다고 믿지만 사용자와 스토어 심사는 과거 HTML을 계속 본다. 반대로 Firestore 문서를 삭제해도 앱 문서는 사라지지 않는다. 변경·시행일·동의 범위가 실제 처리와 달라지는 법적·운영 사고가 가능하다.

**수정 원칙**

1. 실제 게시 경로가 완성될 때까지 관리자 법적 문서 편집을 비활성화하고 “현재 앱에 반영되지 않음”을 명시한다.
2. 법적 문서의 원본을 한 곳으로 정한다. 권장안은 저장소 문서에 대한 검토·승인·배포 파이프라인이며, 대안으로 서버가 안전하게 정제한 버전 문서를 앱과 웹이 함께 소비할 수 있다.
3. 초안/검토/승인/게시 상태, 시행일, 이전 버전, rollback, 게시자, 해시를 남긴다.
4. 관리자 저장 후 앱 URL과 웹 URL의 내용 해시·버전이 같은지 자동 검증한다.

### P0-2. 관리자 해제 절차가 일부 권한을 남김

- `firestore.rules:20-30`과 `functions/src/index.ts:423-438`에 관리자 이메일이 중복돼 있다.
- `docs/admin/README.md:25-27`과 `admin.js:3-7`은 Rules만 고치라고 안내한다.
- `getUserUsage`와 `grantBonusCredits`는 Functions의 별도 목록을 사용하고 Admin SDK로 Rules를 우회한다.

Rules에서만 제거된 전 관리자는 콘솔 목록은 못 보더라도 직접 Callable을 호출해 사용량을 조회하거나 크레딧을 지급할 수 있다. 커스텀 클레임 또는 서버 역할 문서 하나를 권한 원본으로 삼고, 해제 시 역할 제거·Auth 비활성화·refresh token 폐기·모든 권한 sink 거부 검증을 한 절차로 묶어야 한다.

## 3. 개인정보 저장·조회·내보내기

### 3-1. 문의 원문이 평문 운영 데이터로 저장됨

`inquiries`에는 UID, 이메일, 제목, 자유서술 문의 원문, 상태, 시각과 답변이 평문 필드로 저장된다. 전송 구간과 Firebase 저장 인프라 보호는 있으나 명함·프로필처럼 애플리케이션 AES-GCM 암호화는 적용되지 않는다. 관리자 지원을 위해 검색 가능한 평문 저장을 채택할 수는 있지만, 그 경우 다음을 명시하고 통제해야 한다.

- 개인정보처리방침의 수집 항목, 목적, 관리자 열람 범위, 보유 기간, 탈퇴/문의 종료 후 처리
- 문의 작성 화면의 민감정보 입력 자제 안내
- 최소 권한, 페이지 단위 조회, 접근 감사, 보유기간 TTL 또는 삭제 작업
- 탈퇴 후 삭제 또는 법적 보존 시 직접 식별자 분리·가명화

현재 방침의 수집 표와 보유 표에는 1:1 문의 이메일·제목·본문·답변이 없고, 탈퇴 트리거도 이를 삭제하지 않는다.

### 3-2. 관리자 로그인 때 개인정보를 필요 이상으로 선조회함

- 인증 직후 현재 선택된 탭과 무관하게 공지, 전체 문의, 법적 문서, 결제 설정, 테스터, AI 로그, OCR 통계, 업데이트 설정을 순차 로드한다 (`admin.js:106-156`).
- 전체 문의와 답변은 `limit`/cursor 없이 읽으며 목록에 필요 없는 `message` 원문도 브라우저 메모리로 내려온다 (`admin.js:996`, `1022`).
- 월별 정산, 공지, OCR 통계도 페이지 제한이 없다.

탭 최초 진입 시 lazy load하고 `limit + startAfter` 페이지네이션을 사용해야 한다. 문의 목록 요약과 원문을 분리하고, 정산·OCR은 서버 집계 결과만 내려보내는 방식이 적절하다.

### 3-3. 정산 CSV는 개인정보 평문 파일을 만듦

CSV에는 이메일, UID, 거래 ID가 들어간다 (`admin.js:385-396`). 다운로드 전 포함 항목·목적·보관/폐기 안내와 확인을 제공하고, 파일명·내용에 최소 정보만 포함해야 한다. 스프레드시트 수식으로 해석되는 `=`, `+`, `-`, `@` 선행 값도 안전하게 중화해야 한다. 현재 구매 writer가 없어 공격자 제어 CSV 수식 경로는 확정하지 않았지만, IAP 구현 전에 차단해야 한다.

### 3-4. 로그 판정

- 관리자 JS에서 이름·전화·주소 원문을 `console`에 기록하는 코드는 발견하지 못했다.
- AI 감사 로그는 UID·로그인 이메일·시각·성공·오류 유형·토큰량을 Firestore에 평문 기록하며 방침 2.0에 고지돼 있다. 명함 원문/프롬프트/응답 저장은 확인되지 않았다.
- 무료 크레딧 지급 Cloud Log는 대상 UID·증감·잔액을 남기지만 실행 관리자와 사유가 없다 (`functions/src/index.ts:892`). 비식별 운영 로그와 보호된 불변 감사 원장을 분리해야 한다.

## 4. 권한·무결성·운영 안전성

### P1-1. 일반 사용자가 관리자 답변을 위조할 수 있음

`firestore.rules:103-116`은 문의 생성 시 `userId`, 답변 생성 시 부모 소유권만 확인한다. 사용자는 변조 클라이언트로 `userEmail`을 다른 값으로 쓰거나 초기 `status='answered'`, 답변 `from='admin'`을 저장할 수 있다. 관리자 화면과 앱은 이 값을 그대로 관리자 답변으로 표시한다.

정확한 키·타입·길이, token email, `status='pending'`, `createdAt == request.time`, 사용자 `from='user'`, 관리자 `from='admin'`을 Rules 또는 서버 함수에서 강제해야 한다.

### P1-2. 무제한 문의가 관리자 콘솔 비용·가용성을 공격할 수 있음

한 인증 사용자가 문의와 답변을 무제한 생성할 수 있고 관리자 로그인은 전체 문의를 읽는다. App Check 서버 제출, UID/IP별 속도 제한, 본문 길이 제한, 페이지네이션, 보관/아카이브 정책을 추가해야 한다.

### P1-3. OCR 통계를 사용자가 임의 조작하거나 개인정보를 끼워 넣을 수 있음

`ocrStats/{uid}`는 소유자 전체 쓰기만 확인하고 키·타입·범위·단조성을 검사하지 않는다 (`firestore.rules:84-93`). 사용자는 음수·과대 카운터·임의 map·원문 개인정보 필드를 저장할 수 있고 관리자는 이를 전체 집계한다. “형태 통계만 있다”는 정책 가정이 Rules에서 보장되지 않는다.

정확한 키와 bounded nonnegative integer를 서버에서 강제하고, 가능하면 App Check 이벤트를 받아 서버가 증분·집계해야 한다.

### P1-4. 무료 크레딧 지급에 상한·멱등성·완전한 감사가 없음

0이 아닌 유한 숫자는 모두 허용되며 결과 잔액 상한이 없다. 버튼도 요청 중 비활성화되지 않고 operation ID가 없어 재시도/중복 클릭이 다시 반영된다. 작은 지급 상한, 결과 잔액 상한, `Number.isSafeInteger`, 요청 ID, 사유, actor, before/after, 고액 이중 승인을 적용해야 한다.

### P1-5. 강제 업데이트 설정이 임의 URL을 허용함

관리자는 임의 scheme/host의 URL과 임의 최소 빌드를 저장할 수 있고 앱은 그대로 외부 실행한다. 탈취된 관리자 세션이 모든 사용자를 피싱/가짜 앱 URL로 보내거나 앱을 soft-brick할 수 있다. 공식 스토어 HTTPS host/path allowlist, 실제 출시 빌드 대조, 최근 MFA, 단계 배포, rollback을 서버에서 강제해야 한다.

### P1-6. billing 저장형 XSS 경로

관리자가 Rules를 직접 호출해 `config/billing`의 `credits`에 문자열을 저장하면, 다음 관리자 로그인 때 `innerHTML`의 `value` 속성에 이스케이프 없이 들어간다 (`admin.js:221`, `283`). 일반 사용자는 쓸 수 없지만 탈취·악성 관리자 계정이 다른 관리자 세션에서 same-origin 코드를 실행할 수 있다. Rules 스키마와 DOM property 할당, CSP를 함께 적용해야 한다.

### P1-7. 중요 관리자 변경에 감사·버전·복구가 없음

billing, 테스터 App Check 우회목록, 강제 업데이트, 공지, 문의 상태, 법적 문서를 클라이언트가 직접 바꾼다. 누가·왜·무엇을·어떤 값에서 어떤 값으로 바꿨는지 남지 않는다. 민감 변경을 Callable로 통합하고 같은 트랜잭션에 client-immutable audit event를 기록해야 한다.

### P2. 브라우저·세션 보완

- 관리자 Hosting에 CSP, `frame-ancestors`, `X-Frame-Options`, `nosniff`, Referrer/Permissions Policy가 없다.
- Firebase Auth persistence를 session/memory로 제한하지 않고 idle timeout·최근 재인증·MFA 요구가 없다.
- 로그아웃은 dashboard를 숨길 뿐 문의·이메일·UID·정산 배열과 DOM을 지우지 않는다.
- 재로그인마다 `initTabs()`가 같은 정적 버튼에 이벤트를 다시 붙인다.
- 일부 저장/삭제는 예외 처리·중복 클릭 잠금·일관된 오류 상태가 없다.

| 정적 CDN | 관리자 접속 IP·요청 메타데이터 가능 | 사용자 PII 본문 전송은 확인되지 않음 | SDK/폰트 자체 호스팅 또는 CSP·Referrer Policy 검토 |

## 6. 테스트가 실제 결함을 잡도록 바꾸는 기준

현재 `test/firestore_rules/verify_rules.py`는 `users/{uid}`와 contacts 중심이며 관리자·문의·OCR·config·notices·purchases·auditLogs를 다루지 않는다. CI는 Flutter analyze/test만 실행한다.

필수 회귀 테스트:

1. 관리자 해제: 한 번의 offboarding 후 Firestore와 모든 Callable이 즉시 거부한다.
2. 문의 위조: 일반 사용자의 `from='admin'`, 초기 answered, 타 이메일, 추가 필드, 과대 본문을 Rules가 거부한다.
3. 문의 고갈: 대량 데이터에서도 첫 로그인 읽기 수와 DOM 행 수가 페이지 상한을 넘지 않는다.
4. 탈퇴: inquiries/replies/ocrStats/aiAuditLogs를 포함한 UID·이메일 연결 자료가 0건이다.
5. 크레딧: 상한 초과·unsafe integer를 거부하고 같은 operation ID는 한 번만 반영한다.
6. 업데이트: `http`, custom scheme, 비공식 host, 잘못된 빌드 관계를 거부한다.
7. 저장형 XSS: billing 속성 탈출 payload가 저장 거부되고 브라우저에서 실행되지 않는다.
8. Hosting: 비로그인/일반 사용자의 내부 리포트 직접 URL이 401/403이고 배포물에 원본이 없다.
9. 법적 문서: 관리자 게시 후 앱 URL·웹 URL·원본 버전/해시가 동일하다.
10. 세션: 로그아웃 뒤 DOM·JS 상태에 민감 문자열이 없고 재시작 시 관리자 세션이 자동 복원되지 않는다.
11. 빈 상태: Firestore가 비어 있을 때 가짜 공지·문의·매출·OCR 수치가 나타나지 않고 정확한 빈 상태와 CTA만 보인다.
12. 오류 상태: 각 탭 하나가 실패해도 다른 탭을 사용할 수 있고 재시도 동작이 중복 변경을 만들지 않는다.

테스트는 먼저 수정 전 결함을 재현해 실패하는지 확인하고, 수정 후 통과하도록 작성해야 한다. mock 호출 여부만 확인하지 말고 Rules/Functions emulator와 실제 DOM 상태·Firestore 결과·HTTP 상태를 검증한다.

## 7. 확인된 긍정적 통제

- Firestore 관리자 컬렉션과 두 관리자 Callable은 현재 검증 이메일 allowlist를 서버 측에서 확인한다.
- 사용자 문의 제목·이메일·본문·답변, 공지 제목, 감사 로그 문자열은 주요 표시 경로에서 `escapeHtml` 또는 `textContent/value`를 사용한다.
- `aiAuditLogs`는 최근 100건, 이메일 구매 조회는 50건으로 제한한다.
- Storage는 소유자 경로만 허용하며 관리자 전체 읽기 우회가 없다.
- 관리자 JS에 Gemini/Apple 서버 비밀은 없고 Firebase web apiKey는 공개 클라이언트 설정이다.
- 빈 문의·공지·결제·OCR·감사 로그에 가짜 운영 데이터를 넣는 경로는 찾지 못했다.

## 8. 완료 판정 증거

원 개발 AI는 “수정 완료”라고만 답하지 말고 다음을 남겨야 한다.

- 각 P0/P1 및 `ADMIN-VULN-*`별 수정 파일과 설계 결정
- 수정 전 실패·수정 후 통과한 테스트 이름과 핵심 출력
- 관리자 해제 후 Firestore/Callable 모두 403 또는 permission-denied 증거
- 비인증 내부 보고서 직접 URL 거부 증거
- 탈퇴 후 모든 문의·답변·통계·로그 0건 증거
- 법적 문서 앱/웹 버전·해시 일치 증거
- 크레딧 중복·상한·행위자 감사 증거
- 로그아웃 후 민감 DOM/세션 0건 증거
- 개인정보처리방침 변경 항목과 시행일
- 남은 위험과 테스트하지 못한 항목
