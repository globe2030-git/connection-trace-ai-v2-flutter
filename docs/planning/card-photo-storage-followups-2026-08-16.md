# 명함 사진 서버 저장 — 원가 분석에서 파생된 후속 3건

작성 2026-08-16 · 손익/원가 세션 · 워크트리 `…-flutter-feature`

스토리지 원가를 계산하면서(손익분석 16번, backlog 추가 240) **코드를 읽다
드러난** 항목들이다. 셋 다 비용 계산의 부산물이지 원가 절감안이 아니다 —
①은 파기 의무, ②는 설계 판단, ③은 실물 검증이다.

**이 문서는 판단과 근거만 담는다. `.dart` 파일은 건드리지 않았다** — 해당
파일들은 캐시 정리 세션 → PM(축소) 순서로 배정돼 있다.

---

## ② 축소를 어디에 넣을 것인가 ⚠️ PM의 축소 작업 **직전에** 읽을 것

가장 급하다. **넣는 자리를 틀리면 인식률이 떨어지는데, 그 사실이 한참 뒤에
드러난다.**

### 결론

**`ContactImageService.saveEncryptedCardImage()`의 암호화 직전.** 로컬
저장본과 서버 사본이 함께 축소된다.

### 왜 크롭 단계(`_cropToGuideFrame`)에 넣으면 안 되는가

**그 결과물이 곧 OCR 입력이기 때문이다.**

```
_capture()  →  _cropToGuideFrame()  →  _pendingShot
                                          ↓
_confirmPendingShot()  →  _bakeRotation()  →  scanBusinessCard(target)   ← 인식
                                          ↓
                       Navigator.pop(scanResult.imagePath)
                                          ↓
        add_card_modal_view  →  saveEncryptedCardImage(sourcePath:)      ← 저장
```

인식은 **저장보다 한참 앞**에서 끝난다. 크롭 단계에서 줄이면 **인식이 축소본을
보게 된다.** 갤러리 선택이 `imageQuality: 100`인 이유도 같다(*"OCR 인식률은
원본 해상도/압축 손실에 크게 좌우된다"* — `ocr_scanner_service.dart` 주석).
**그 값은 그대로 둬야 한다.**

저장 시점에 넣으면 인식은 원본 해상도로 하고 보관본만 줄이므로 **인식률에
영향이 전혀 없다.** "축소해도 인식은 그대로"라는 손익 문서의 전제가 성립하는
것은 이 자리에 넣을 때뿐이다.

### 왜 "서버용만 축소"는 안 되는가

그럴듯해 보인다 — 로컬은 원본 화질, 서버만 절약. **세 가지 이유로 접는다.**

1. **평문이 한 번 더 생긴다.** 지금 구조는 *"로컬 암호문을 그대로 올린다"*이다
   (`upload(encryptedFilePath: outPath)`). 서버용만 줄이려면 축소본을 따로
   만들어 **다시 암호화**해야 하고, 그 과정에 평문 바이트가 한 번 더 존재한다.
   이 구조를 고른 이유 자체가 *"업로드 경로에 평문 이미지가 존재하는 순간이
   없다"*였다(추가 220).
2. **어차피 오래 못 간다.** 기기를 바꾸면 `downloadMissingCardImages`가 서버
   사본을 내려받으므로 **새 기기의 로컬도 축소본**이 된다. "로컬만 고화질"은
   다음 기기 변경까지만 유지되는 일시적 상태다.
3. **같은 명함이 기기마다 다른 화질로 보인다.** 사용자에게는 설명할 수 없는
   현상이다.

### 구현 시 함께 봐야 할 것

- **복호화 캐시를 축소본으로 채울 것.** 지금은
  `_decryptedCache[outPath] = Uint8List.fromList(bytes)`로 **읽어들인 원본**을
  캐시한다. 축소 후 바이트로 바꾸지 않으면 **파일에는 축소본이, 화면에는
  원본이** 남아 그 세션 동안 둘이 어긋난다.
- `image: ^4.3.0`이 이미 의존성에 있다(크롭이 쓰는 것과 같은 패키지).
- **기존 로컬 `.enc`는 원본 크기로 남는다.** 소급 업로드가 없어(방침 v2.2의
  7일 고지 근거) 서버로 가지 않으므로 문제되지 않는다. 굳이 재인코딩하지 말 것
  — 그건 방침이 근거로 삼은 "소급 없음"을 흔든다.
- **설정값**: 긴 변 1,600px · JPEG 품질 80(2026-08-16 사용자 확정).
- 축소 실패 시 원본으로 진행 — 크롭·회전 실패 시 원본을 쓰는 기존 판단과 같게.

### 검증

`flutter test`로 잡히는 것은 "축소 함수가 크기를 줄이는가"까지다. **인식률이
그대로인지는 실기기로만 확인된다** — 같은 명함을 축소 전/후로 스캔해 필드
채움이 같은지 본다. 회전(F-03)이 *"미리보기만 돌고 원본으로 인식하면 어긋난다"*로
다친 것과 같은 자리다.

## ① 개별 명함 삭제 시 서버 사본이 남는다

### 무엇이 문제인가

**탈퇴는 막혀 있다.** `onUserDeletedCleanup`이 서버에서 `users/{uid}/cards/`
접두사를 통째로 지운다(`cardPhotoCleanup.ts`, Admin SDK라 보안 규칙을 타지
않는다. 배포 완료 — 추가 239).

**막히지 않은 것은 명함 한 장을 지울 때다.**

```dart
void deleteContact(String id) {          // ← void. await 하지 않는다
  _contactImageService.deleteCardImage(cardImagePath, uid: _uid, contactId: id);
  _contacts.removeWhere((c) => c.id == id);   // ← 참조를 즉시 버린다
  ...
}
```

그리고 서버 삭제는 실패해도 조용하다:

```dart
Future<void> delete(...) async {
  try { await _ref(uid, contactId).delete(); }
  on FirebaseException catch (e) { ... debugPrint ... }   // 재시도 없음
}
```

**오프라인이거나 그 순간 앱이 죽으면 서버 사본이 남는다.** 로컬 명함은 이미
지워져 `contactId` 참조가 사라졌으므로 **나중에 다시 지울 방법이 없다.**

> 아이러니한 것은 이 코드가 **이미 같은 함정을 알고 있다는 점**이다.
> `deleteContact`에는 *"경로가 끊긴 명함이라도 서버엔 사본이 있을 수 있다. 여기서
> 안 지우면 참조가 사라져 나중에 지울 수도 없는 고아 파일이 된다"*는 주석과
> 대비가 있다. 그런데 그 대비는 **로컬 경로 유실**만 막고 **네트워크 실패**는
> 막지 않는다.

### 왜 비용이 아니라 의무 문제로 다뤄야 하나

고아 1장은 **연 ₩0.64**다. 비용으로만 보면 무시해도 되는 값이라 "나중에"로
밀리기 쉽다. **그렇게 판단하면 안 된다.**

방침 v2.2는 *"이용자가 해당 명함을 삭제한 때 즉시 파기"*라고 적었다. 지우기로
고지한 것이 남아 있는 것은 **금액과 무관하게 방침 위반**이고, 남는 것은 이용자
본인이 아니라 **명함 주인(제3자)의 개인정보**다.

### 선택지

| | 안 | 덮는 범위 | 부담 |
|---|---|---|---|
| **A** | **실패한 삭제를 로컬 큐에 적어 두고 다음 실행 때 재시도** | 오프라인·앱 종료 (실제 원인) | 작다 |
| B | 서버에서 Firestore 명함 목록 ↔ Storage 파일 목록 대조 후 고아 삭제 | 전부 | Functions 신규 + 주기 실행 |
| C | 그대로 두고 탈퇴 시 일괄 삭제에 맡긴다 | 탈퇴하는 사용자만 | 없음 |

**권고는 A → (나중에) B.**

A로 시작하는 이유는 **원인이 네트워크 실패 하나로 좁혀지기 때문**이다. 큐에
넣는 값은 `contactId`뿐이라 개인정보가 아니다(무작위 ID). B는 확실하지만 주기
실행 비용과 "언제 도는가"라는 창이 생기고, 그 창 동안은 여전히 방침 위반
상태다. C는 탈퇴하지 않는 사용자의 파일이 **영원히** 남으므로 답이 아니다.

⚠️ A를 넣어도 **앱을 다시 켜지 않으면 재시도가 없다.** 그래서 B가 최종 안전망으로
남는다 — A를 "끝"으로 기록하지 말 것.

`contact_image_service.dart` · `card_photo_backup_service.dart`를 만지므로
**캐시 정리 → 축소 다음 순서**여야 한다. PM 배정 필요.

## ③ 탈퇴 시 Storage 정리는 아직 한 번도 실행된 적이 없다

### 무엇이 문제인가

`deleteUserCardPhotos`는 **코드도 있고 테스트도 있고 배포도 됐다.** 그런데
**Storage 버킷이 콘솔에서 활성화조차 되지 않았다.** 즉 **실제 버킷을 상대로
돌아 본 적이 한 번도 없다.**

이 저장소가 반복해 다친 유형이 정확히 이것이다 — 서버 평문 3건, iOS 로그인
정보 잔존, 죽어 있던 재시도 로직. **전부 코드는 맞았고 실물이 틀렸다**
(CLAUDE.md 4절).

자동 테스트는 가짜 버킷(`fakeBucket`)을 상대로 *"접두사가 맞는가"*, *"force를
켰는가"*를 확인한다. **접두사가 맞는지**는 검증되지만 **그 접두사에 파일이 실제로
있는지**는 검증되지 않는다. 테스트 주석 자체가 *"이게 어긋나면 삭제가 조용히
아무것도 안 지운다 — 실패도 안 나서 아무도 모른다"*고 적고 있다.

### 플래그를 켠 뒤 반드시 할 것

`kCardPhotoBackupEnabled = true` 이후, **탈퇴 항목은 전체 테스트 대상**이다
(CLAUDE.md 4절: 저장·복원·마이그레이션·탈퇴는 전체 테스트).

1. 실기기에서 사진 있는 명함 **2장 이상** 등록 → 업로드 성공 확인
2. **서버 실물 조회** — `users/{uid}/cards/` 아래 `.enc` 파일이 실제로 있는지
   (Firebase CLI / 콘솔). 앱 화면만 보고 판단하지 말 것
3. 계정 삭제
4. **서버 실물 재조회** — 같은 경로가 **비어 있는지**. 여기까지 봐야 ③이 닫힌다
5. 명함 한 장만 삭제하는 경우도 같은 방식으로 별도 확인(①의 검증과 겹친다)

⚠️ **2·4번을 건너뛰면 ③은 닫히지 않는다.** 앱에서 명함이 사라진 것은 로컬이
지워졌다는 뜻일 뿐이다.

### 함께 확인할 것

- **버킷 리전이 `asia-northeast3`인지** — 방침 v2.2에 "서울 리전"으로 게시했다.
  생성 후에는 바꿀 수 없다.
- **예산 알림** — Blaze는 하드 상한이 없다. 알림은 차단이 아니므로, 알림을
  걸어 두는 것이 지금 할 수 있는 유일한 방어다.

## ④ 긴 변 1,600px을 아슬하게 스치면 축소가 **통째로 건너뛰어진다**

축소 구현(main `f2c681d`)이 들어간 뒤, 실제 함수를 표본에 돌려 재다가 나왔다.

### 무엇

`needsDownscale(w, h)`는 `w > 1600 || h > 1600` — **초과일 때만 참**이다.
긴 변이 정확히 1,600이거나 그 아래면 `downscaleForArchive`가 **원본을 그대로
돌려준다.** 그런데 여기서 "원본"은 `_cropToGuideFrame`이
`encodeJpg(quality: 100)`으로 구운 **무압축에 가까운 크롭**이다.

```
긴 변 1600 → 축소 건너뜀
긴 변 1601 → 축소 함
```

### ⚠️ 이건 버그 리포트가 아니다 — 설계는 맞다

작은 사진을 다시 구우면 화질만 깎이고 크기는 오히려 늘 수 있다. 주석에 그렇게
적혀 있고 옳은 판단이며, `out.length < original.length` 가드도 있다.
**고치자는 얘기가 아니다.**

### 문제는 임계값이 **실제 출력 크기와 겹칠 수 있는 자리**에 있다는 것

크롭 결과의 픽셀 수는 **명함이 아니라 가이드 프레임 × 화면 대비 센서 배율**로
정해진다(손익 16-2에서 장당 용량이 좁게 모인 것과 같은 이유). 즉 **기기
화면비·카메라 화소에 따라 달라진다.**

### ✅ 2026-08-16 실기기 측정 — **지금은 걸리지 않는다. 다만 여유가 13%뿐이다**

⚠️ **그 전에 — 내가 낸 계산이 한 번 틀렸고 실물이 그것을 잡았다.** 경위를
남긴다. 결론만 고치면 다음 사람이 같은 자리에서 같은 실수를 한다.

#### 틀린 계산

기기에서 카메라 원본(`CAP*.jpg` JPEG 헤더, **4080×3060**)과 화면 크기(내부
1968×2184 · 커버 1080×2520)를 재고 크롭 식을 적용해 **"커버 화면이면 크롭이
1,353px이라 축소를 건너뛴다"**고 적었다.

**틀렸다.** `_cropToGuideFrame`은 디코딩 직후 **`img.bakeOrientation()`**을
부른다. EXIF 회전이 반영되면 센서 이미지가 **세로(3060×4080)**가 되는데, 그
한 줄을 빠뜨리고 가로(4080×3060)로 계산했다. 짧은 변과 긴 변이 뒤바뀌니
결과가 통째로 달라진다.

#### 실측이 잡았다

사용자가 **기기를 접은 채 명함 한 장을 직접 등록**했다.

| | |
|---|---|
| 새 `.enc` | **131,425바이트 = 128KB** |
| `축소 건너뜀` 로그 | **없음** |

**→ 커버 화면에서도 축소가 적용된다.** 예측(건너뜀·656KB)과 정반대였다.

#### 정정된 계산 — 실측과 맞는다

| 화면 | 크롭 | 긴 변 | 임계(1,600) 대비 | 결과 |
|---|---|---|---|---|
| 내부(펼침) | 1793×2934 | 2,934px | 1.83배 | ✅ 축소 적용 |
| **커버(접힘)** | 1103×1805 | **1,805px** | **1.13배** | ✅ 축소 적용 |

크롭 긴 변 = `min(화면폭×0.86, 화면높이×0.72) × 1.2 × (보이는 센서 긴변 / 화면 높이)`
— **단, `bakeOrientation` 뒤의 방향으로 계산할 것.**

### 그래서 ④는 어떻게 되나 — **살아 있되 등급이 내려간다**

**지금 이 기기에서는 두 화면 모두 안전하다.** 다만 **커버 화면의 여유가 13%뿐**
이다. 화면이 더 좁거나 카메라 화소가 낮은 기기에서는 **넘어간다.**

건너뛰었을 때의 손해도 실측했다(표본 103장 재인코딩).

| 조건 | 평균 | P90 |
|---|---|---|
| 축소 적용 (1,600px·q80) | **236KB** | 339KB |
| 임계 바로 아래에서 건너뜀 (1,599px·q100) | **892KB** | 1,229KB |

**3.8배**다. 한도 200장 기준 인당 월 ₩1.93 → **₩5.7**.

⚠️ 처음 이 항목에 *"1MB 이상, 3배 이상"*이라고 썼는데 정확히는 **892KB(3.8배)**
다. 크롭이 작아지면 파일도 함께 작아져 무한정 커지지 않는다 — 과장하지 않도록
고쳐 둔다.

📌 **참고**: 이번 커버 화면 등록은 128KB로 표본 평균(236KB)보다 작았다. 배경이
적고 단순한 명함이었을 것이다 — 16-2의 *"배경이 명함보다 비싸다"*와 같은 방향.

### ⚠️ 가장 나쁜 점 — 아무도 모른다

**실패가 아니라 정상 경로다.** 예외도 로그도 없고 화면 표시도 없다. 원가
이상으로 드러날 때쯤이면 그 기기 사용자들의 사진이 이미 원본으로 쌓여 있고,
**소급 축소가 불가능하다** — 서버에는 암호문뿐이라 각 이용자의 기기에서만
복호화할 수 있다(②에서 "서버용만 축소"를 접은 것과 같은 이유).

### 권고 — 고치지 말고 **보이게** 한다

임계값을 낮추거나 조건을 바꾸는 것은 **권하지 않는다.** 원래 의도가 맞고, 값을
건드리면 화질 하한이 함께 흔들린다.

**대신 관측을 붙인다.** 이미 있는 `CardPhotoBackupState`에 두 가지만 더:

- **축소를 적용했는가** (불리언)
- **결과 크기 구간** (예: `<300KB` / `300KB~1MB` / `>1MB`)

개인정보가 아니고(불리언 + 구간), **한도 관측(권고안 조건 가)과 같은 자리·같은
성격**이라 함께 넣으면 추가 비용이 거의 없다.

⚠️ **서버로 보낼지는 방침을 먼저 봐야 한다** — 권고안 5절과 같은 단서다.

### 검증 절차 (다른 기기에서 다시 볼 때)

1. 축소 반영 빌드 설치(2026-08-16 이후 `main`)
2. **그 기기에서 명함을 새로 등록** — 기존 `.enc`는 축소 전 파일이라 무의미
3. `adb run-as <pkg> ls -l app_flutter/contact_card_*.enc`
4. **판정** — 250KB 안팎이면 축소가 걸린 것, **900KB 안팎이면 건너뛴 것**
5. 로그에 `명함 사진 축소 건너뜀(긴 변 1600 이하)`이 찍히는지 함께 확인

⚠️ **폴더블은 접은 상태와 편 상태를 따로 봐야 한다.** 화면 크기가 크롭 크기를
정하므로 같은 기기에서도 결과가 다를 수 있다(이번에 커버 1.13배 · 내부 1.83배로
갈렸다).

📌 화면 자동 조작(`adb input tap`)으로는 등록을 완주하지 못했다 — 필수 입력이
넷(이름·회사명·휴대폰·이메일)이라 좌표 기반 입력이 중간에 어긋난다. **사람이
직접 한 장 등록하는 편이 빠르고 확실하다.**

### 그래서 권고가 바뀌는가 — **유지하되 우선순위는 내린다**

관측(축소 여부·크기 구간)을 붙이자는 권고는 **그대로**다. 다만 성격이 바뀌었다.

- ~~"지금 이 기기의 절반이 위험하다"~~ → **"지금은 안전하다. 여유가 13%뿐이라
  기기가 바뀌면 모른다"**
- 따라서 **켜기 전에 반드시 넣어야 하는 것은 아니다.** 한도 관측을 만들 때
  같은 자리에 얹으면 된다(비용이 거의 없으므로 굳이 미룰 이유도 없다).

크기 구간 경계는 실측에 맞춰 `<300KB` / `300KB~1MB` / `>1MB`가 적절하다 —
축소 적용(236KB)과 건너뜀(892KB)이 서로 다른 칸에 떨어진다.

### 곁가지 — 측정하다 알게 된 것 하나

같은 1,600px 출력에서 **배경이 명함보다 비싸다.**

| | 평균 |
|---|---|
| 여백 많은 표본 원본 | 264KB |
| 배경을 걷어내 명함이 꽉 찬 것 | **236KB** (0.89배) |

배경(가죽·책상 질감)은 고주파 노이즈라 JPEG에서 비싸고, 명함은 평평한 바탕에
글자라 잘 압축된다. **앱의 타이트한 크롭이 인식률뿐 아니라 원가에도 유리하다** —
크롭 여백을 넓히자는 논의가 나오면 원가 쪽 근거로 쓸 수 있다(다만 인식률이
우선이다. 여백 1.2는 글자 잘림 때문에 실측으로 정해진 값이다).

## 정리 — 순서

기존 순서(비용 스펙)에 ①을 끼운 모습이다.

| | 무엇 | 담당 |
|---|---|---|
| 1 | 캐시 평문 정리 | 별도 세션(진행 중) |
| 2 | **보관본 축소** — ②의 자리에 넣을 것 | PM |
| **2.5** | **개별 삭제 재시도 큐 (①-A)** | **미배정** |
| 3 | Storage 활성화(서울) + 규칙 배포 | 사용자 |
| 4 | 플래그 켜기 (8/23 이후, 8월 말 목표) | PM |
| 5 | **실기기 확인 — ③의 절차대로 서버 실물까지 + ④의 크기 확인** | 미배정 |

②는 2번 **안에서** 지켜야 할 사항이라 별도 줄이 아니다(✅ main `f2c681d`에
그대로 반영됐다). **④는 3·4번과 무관하게 지금 확인할 수 있다** — 축소는 저장
시점에 걸리므로 플래그·버킷과 상관없이 **빌드만 나오면 로컬 `.enc`로 잰다.**
④의 관측(축소 여부·크기 구간)은 한도 관측과 같은 자리라 **한도 구현에 함께
얹는 것이 싸다.**

①은 2.5로 넣었다 — 같은 파일을 만지므로 축소 뒤가 자연스럽다.

⚠️ **3번(Storage 활성화·서울)은 2026-08-16 사용자가 완료했다고 알려 왔다.**
버킷 리전이 `asia-northeast3`인지, 규칙 배포(`firebase deploy --only storage`)가
끝났는지는 **PM 확인 대기 중**이다. 리전은 생성 후 바꿀 수 없고 방침 v2.2에
"서울 리전"으로 게시돼 있어, **실물 확인 없이 다음 단계로 넘어가면 안 된다.**
