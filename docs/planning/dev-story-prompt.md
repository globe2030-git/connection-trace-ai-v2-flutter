# "앱 개발 후기" 생성용 프롬프트 — 동영상 + 만화 (앱 등록 완료 후 사용)

이 문서는 코드가 아니다 — **나중에(앱이 스토어에 최종 등록된 뒤) 새 대화창에
그대로 복사해 붙여넣을 프롬프트**를 저장해 둔 것이다. 산출물은 두 가지:
1. **AI 동영상 제작용 대본** ("커넥션센스 앱 개발 후기") — 아래 [프롬프트 A]
2. **개발 좌충우돌 만화 시나리오** (컷 단위 콘티) — 아래 [프롬프트 B]

지금(개발·등록 진행 중)은 실행하지 않는다 — 이야기가 아직 완결되지 않았기
때문. **대신 여정을 실시간으로 담는 1차 소스는
[`dev-diary.md`](./dev-diary.md)에 계속 쌓고 있다**(앱 등록까지 매 세션 갱신).
앱 등록이 끝나면 아래 프롬프트들을 실행한다.

> **소스 우선순위**: ① [`dev-diary.md`](./dev-diary.md)(이야기로 다듬어 둔
> 국면·에피소드 — 만화/영상에 가장 바로 쓰기 좋음) → ② [`backlog.md`](./backlog.md)
> (정확한 사실·수치·원인) → ③ [`HANDOFF.md`](./HANDOFF.md)(국면 요약) →
> ④ git log(왜 그렇게 했는지).

## [프롬프트 A] 동영상 대본 (복사해서 사용)

```
커넥션센스(Connection Sense) 앱의 "개발 후기" 원고를 써줘. 이 원고는 AI
동영상 제작 도구에 넣을 대본/스토리 소스로 쓸 거야 — 그러니까 기술 로그가
아니라, 사람이 듣고 흥미를 느낄 수 있는 이야기 형태로 정리해줘.

## 참고 자료 (전부 읽고 종합해)
- docs/planning/dev-diary.md — **1차 소스.** 프로젝트 시작부터 앱 등록까지의
  좌충우돌을 이미 "국면/에피소드" 서사로 다듬어 둔 일지. 여기 구조를 뼈대로
  삼되, 사실 확인은 아래 backlog로 교차 검증할 것.
- docs/planning/backlog.md — 개발 전체 기간의 시간순 작업 기록(추가 1번부터
  마지막 번호까지). 결정의 배경, 발견된 버그, 원인, 해결 과정이 다 여기
  있다. (정확한 수치·원인의 근거)
- docs/planning/HANDOFF.md — 프로젝트 개요, 현재 상태, 주요 기술적 결정들의
  요약.
- git log (가능하면) — 커밋 메시지에 "왜 그렇게 했는지"가 담겨 있으니 보조
  자료로 참고.

## 원고에 반드시 담을 것
1. **프로젝트 계기와 컨셉** — 왜 이 앱을 만들게 됐는지, 핵심 아이디어가
   무엇인지(명함을 스캔해서 인맥을 등록하고, 앱을 열면 지금 내 주변에 있는
   인맥을 보여주는 앱. ※ v1은 "패시브 레이더"로, 앱을 열었을 때 보여주는
   방식이다 — 백그라운드 자동 푸시는 v1.1 이후, 결정-3/A안).
2. **전체 여정을 몇 개의 국면(chapter)으로 나눠서** — 예: 초기 프로토타입 →
   실제 기능(GPS/OCR/카메라) 연동 → 디자인 리뉴얼 → 서버/백업 구축 →
   보안·개인정보 강화 → 관리자 콘솔 → 출시 준비. 각 국면마다 무엇을
   했고 왜 그 순서였는지.
3. **가장 흥미로운 에피소드 3~5개를 뽑아서 자세히** — 단순 기능 추가가
   아니라 "문제 발견 → 원인 추적 → 해결"의 서사가 있는 것 위주로. 예를
   들어(실제 있었던 사례들, 정확한 디테일은 backlog에서 확인):
   - 코드는 완벽했는데 실물(서버, 실기기)에서만 드러난 결함들 —
     "테스트 통과 = 동작함이 아니다"라는 걸 배운 사례들(서버에 개인정보
     평문 저장, 재시도 로직이 안 불리던 문제, 주소 선택이 실기기에서만
     안 되던 문제 등).
   - 명함 OCR 파싱 버그 사냥기 — 실제 사용자(자기 자신)가 스캔한 명함마다
     이상하게 나오는 값들을 하나씩 원인 추적한 이야기(로고 그래픽을 "DA"
     라는 글자로 잘못 읽어서 회사명이 망가지던 사건, 전화번호 라벨 뒤에
     공백이 있으면 이메일을 통째로 놓치던 사건, 같은 명함을 다시 스캔해도
     OCR 인식 결과가 매번 다르게 나온다는 걸 깨달은 순간 등). "코드로
     고칠 수 있는 문제"와 "OCR 인식률이라는, 코드로는 못 고치는 한계"를
     구분하게 된 과정도 포함.
   - 개인정보를 다루는 앱이라는 무게감 — 왜 로그에 개인정보를 안 남기기로
     했는지, 왜 "완전한 종단간 암호화"라고 과장하지 않고 정직하게
     문서화했는지.
   - 출시 준비 과정의 현실적인 장벽들 — Apple Developer Program 유료 가입,
     App Store Connect 업로드 403 에러, Firebase Blaze 요금제 카드 등록
     같은, 코드와 무관한 행정적 장벽들.
4. **AI(나, Claude)와 함께 개발한 과정 자체도 이야기 소재로** — 혼자
   짜던 시절과 뭐가 달랐는지, 실기기 재현→원인 추적→수정→재검증을
   반복하는 사이클이 실제로 어떻게 진행됐는지(예: OCR 버그 하나를 고치려고
   iOS 릴리스 빌드를 대여섯 번 다시 돌린 이야기 같은 것도 솔직하게).
5. **지금 시점(정식 배포 시점)의 결과물** — 어떤 기능들이 최종적으로
   들어갔는지, 무엇을 배웠는지, 다음에 비슷한 걸 만든다면 무엇을 다르게
   할지.

## 톤
다큐멘터리 내레이션처럼 과장하지 말고, 그렇다고 무미건조한 변경 이력도
되지 말 것 — "실제로 겪은 문제를 실제로 어떻게 풀었는지"를 담백하게
풀어내는 창업/개발 브이로그 느낌으로. 과장된 성과 포장(마케팅 톤)은
피하고, 안 풀렸던 것/타협한 것도 숨기지 말고 포함해줘.

## 출력 형식
영상 대본으로 바로 옮기기 좋게, 씬(장면) 단위로 나눠줘. 각 씬마다:
- 씬 제목(짧게)
- 내레이션으로 읽을 원고(구어체, 한글)
- (있으면) 화면에 보여주면 좋을 자료 — 스크린샷, 코드, 실기기 사진 등
  무엇을 보여주면 좋을지 제안

전체 분량은 5~10분 영상 기준(원고 기준 1,500~2,500자 내외)으로 우선
만들고, 더 길게 원하면 그때 늘려줘.
```

## [프롬프트 B] 개발 좌충우돌 만화 (복사해서 사용)

```
커넥션센스(Connection Sense) 앱의 개발 여정을 "개발 좌충우돌"이라는 제목의
웹툰/만화 시나리오로 만들어줘. AI 이미지 생성 도구로 컷을 그릴 거라, 각
컷의 그림 지시(비주얼)와 말풍선/내레이션을 나눠서 줘.

## 참고 자료 (전부 읽고 종합해)
- docs/planning/dev-diary.md — **1차 소스.** 국면/에피소드가 이미 [상황]→
  [함정]→[깨달음] 구조로 정리돼 있고, 각 에피소드에 이모지 태그와 "📸"
  캡처 지점이 있다. 이 구조를 그대로 컷으로 옮기기 좋다. 문서 맨 아래
  "에필로그 — 개그·명장면 포인트"가 회차 선정의 지침이다.
- docs/planning/backlog.md — 정확한 사실·수치·원인(그림 고증용).

## 형식
- **회차(에피소드) 단위**로 나눈다. dev-diary.md의 국면/일차를 회차로 삼되,
  가장 웃기고 공감되는 것 위주로 편성(전부 넣지 말고 6~10화 선별).
- 각 회차는 **4~7컷**. 컷마다:
  1) [컷 번호]
  2) 그림 지시 — 장면·인물 표정·화면에 뜬 에러/UI 등 무엇을 그릴지 구체적으로
     (AI 이미지 프롬프트로 바로 쓸 수 있게, 한 문장 영어 프롬프트도 병기)
  3) 말풍선/내레이션 — 짧고 리듬감 있게(구어체 한글)
- 마지막 컷은 그 회의 **깨달음 한 줄**로 마무리(교훈이되 설교조는 피하기).

## 캐릭터
- 주인공: 1인 개발자(대표). 과장된 희로애락으로 공감 유도. 실명·실제 외모
  묘사는 하지 말고 "개발자 캐릭터"로 일반화.
- 조력자: AI 어시스턴트(나, Claude)를 옆에서 훈수 두는 캐릭터로 등장시켜도 좋음.
- ⚠️ 실존 인물(명함 주인 등 제3자)·실제 개인정보는 절대 등장시키지 말 것.
  가짜 인물도 실존처럼 꾸미지 말 것(프로젝트 대원칙).

## 톤
자학 개그 섞인 공감형 개발 코미디. "코드는 맞는데 실물이 틀렸다", "에러
이름은 범인이 아니었다", "앱 만들기보다 세상에 내보내기가 더 험난했다"가
관통 주제. 과장은 하되 사실을 왜곡하진 말 것.

## 살릴 명장면(예시 — dev-diary.md 에필로그에서 갱신됨)

- 서버에 발가벗고 있던 개인정보 / 앱을 지워도 남는 iOS 유령

## 출력
회차별로 위 형식대로. 먼저 3화 분량을 만들고, 좋으면 나머지를 이어서.
```

## 참고: 이 프롬프트들을 실행하기 전에

- **1차 소스는 `dev-diary.md`다.** 새 세션에서 스토어 작업을 할 때마다 그
  일지에 "N일차/국면" 에피소드를 이어 붙여, 앱 등록 시점에 이야기가 완결돼
  있게 한다(끊기면 만화·영상 품질이 떨어진다).
- `docs/planning/backlog.md`도 그 시점까지 최신 상태인지 확인할 것.
- **앱 등록(iOS·Android 양쪽)이 실제로 완료된 뒤** 실행하는 게 가장 자연스럽다
  — "등록까지 해낸 회고" 느낌을 담아야 하므로.
- 두 프롬프트(A 동영상 / B 만화)는 같은 소스를 쓰되 산출물 형식만 다르다.
  하나만 필요하면 해당 프롬프트만 실행하면 된다.
