# "앱 개발 후기" 생성용 프롬프트 (앱 정식 배포 후 사용)

이 문서는 코드가 아니다 — **나중에(앱이 완전히 개발 완료되고 정식 배포된 뒤)
새 대화창에서 그대로 복사해 붙여넣을 프롬프트**를 저장해 둔 것이다. 목적은
AI 동영상 제작용 소스 원고("커넥션센스 앱 개발 후기") 생성.

지금(개발 중)은 이 프롬프트를 실행하지 않는다 — `backlog.md`가 아직 계속
쌓이고 있어서 이야기가 완결되지 않았기 때문. 앱 배포 완료 시점에 아래
프롬프트를 그대로 실행하면 된다.

---

## 여기서부터 프롬프트 (복사해서 사용)

```
커넥션센스(Connection Sense) 앱의 "개발 후기" 원고를 써줘. 이 원고는 AI
동영상 제작 도구에 넣을 대본/스토리 소스로 쓸 거야 — 그러니까 기술 로그가
아니라, 사람이 듣고 흥미를 느낄 수 있는 이야기 형태로 정리해줘.

## 참고 자료 (전부 읽고 종합해)
- docs/planning/backlog.md — 개발 전체 기간의 시간순 작업 기록(추가 1번부터
  마지막 번호까지). 결정의 배경, 발견된 버그, 원인, 해결 과정이 다 여기
  있다.
- docs/planning/HANDOFF.md — 프로젝트 개요, 현재 상태, 주요 기술적 결정들의
  요약.
- git log (가능하면) — 커밋 메시지에 "왜 그렇게 했는지"가 담겨 있으니 보조
  자료로 참고.

## 원고에 반드시 담을 것
1. **프로젝트 계기와 컨셉** — 왜 이 앱을 만들게 됐는지, 핵심 아이디어가
   무엇인지(명함을 스캔해서 인맥을 등록하고, 실제로 그 인맥 근처에 있을 때
   알려주는 앱).
2. **전체 여정을 몇 개의 국면(chapter)으로 나눠서** — 예: 초기 프로토타입 →
   실제 기능(GPS/OCR/카메라) 연동 → 디자인 리뉴얼 → 서버/백업 구축 →
   보안·개인정보 강화 → 관리자 콘솔 → 출시 준비. 각 국면마다 무엇을
   했고 왜 그 순서였는지.
3. **가장 흥미로운 에피소드 3~5개를 뽑아서 자세히** — 단순 기능 추가가
   아니라 "문제 발견 → 원인 추적 → 해결"의 서사가 있는 것 위주로. 예를
   들어(실제 있었던 사례들, 정확한 디테일은 backlog에서 확인):
   - 코드는 완벽했는데 실물(서버, 실기기)에서만 드러난 결함들 —
     "테스트 통과 = 동작함이 아니다"라는 걸 배운 사례들(서버에 개인정보
     평문 저장, 재시도 로직이 안 불리던 문제, 주소 선택이 실기기에서만
     안 되던 문제 등).
   - 명함 OCR 파싱 버그 사냥기 — 실제 사용자(자기 자신)가 스캔한 명함마다
     이상하게 나오는 값들을 하나씩 원인 추적한 이야기(로고 그래픽을 "DA"
     라는 글자로 잘못 읽어서 회사명이 망가지던 사건, 전화번호 라벨 뒤에
     공백이 있으면 이메일을 통째로 놓치던 사건, 같은 명함을 다시 스캔해도
     OCR 인식 결과가 매번 다르게 나온다는 걸 깨달은 순간 등). "코드로
     고칠 수 있는 문제"와 "OCR 인식률이라는, 코드로는 못 고치는 한계"를
     구분하게 된 과정도 포함.
   - 개인정보를 다루는 앱이라는 무게감 — 왜 로그에 개인정보를 안 남기기로
     했는지, 왜 "완전한 종단간 암호화"라고 과장하지 않고 정직하게
     문서화했는지.
   - 출시 준비 과정의 현실적인 장벽들 — Apple Developer Program 유료 가입,
     App Store Connect 업로드 403 에러, Firebase Blaze 요금제 카드 등록
     같은, 코드와 무관한 행정적 장벽들.
4. **AI(나, Claude)와 함께 개발한 과정 자체도 이야기 소재로** — 혼자
   짜던 시절과 뭐가 달랐는지, 실기기 재현→원인 추적→수정→재검증을
   반복하는 사이클이 실제로 어떻게 진행됐는지(예: OCR 버그 하나를 고치려고
   iOS 릴리스 빌드를 대여섯 번 다시 돌린 이야기 같은 것도 솔직하게).
5. **지금 시점(정식 배포 시점)의 결과물** — 어떤 기능들이 최종적으로
   들어갔는지, 무엇을 배웠는지, 다음에 비슷한 걸 만든다면 무엇을 다르게
   할지.

## 톤
다큐멘터리 내레이션처럼 과장하지 말고, 그렇다고 무미건조한 변경 이력도
되지 말 것 — "실제로 겪은 문제를 실제로 어떻게 풀었는지"를 담백하게
풀어내는 창업/개발 브이로그 느낌으로. 과장된 성과 포장(마케팅 톤)은
피하고, 안 풀렸던 것/타협한 것도 숨기지 말고 포함해줘.

## 출력 형식
영상 대본으로 바로 옮기기 좋게, 씬(장면) 단위로 나눠줘. 각 씬마다:
- 씬 제목(짧게)
- 내레이션으로 읽을 원고(구어체, 한글)
- (있으면) 화면에 보여주면 좋을 자료 — 스크린샷, 코드, 실기기 사진 등
  무엇을 보여주면 좋을지 제안

전체 분량은 5~10분 영상 기준(원고 기준 1,500~2,500자 내외)으로 우선
만들고, 더 길게 원하면 그때 늘려줘.
```

## 참고: 이 프롬프트를 실행하기 전에

- `docs/planning/backlog.md`가 그 시점까지 최신 상태인지 확인할 것(작업
  로그가 밀려 있으면 원고 품질이 떨어진다).
- 앱스토어/플레이스토어 출시가 실제로 완료된 뒤 실행하는 게 가장 자연스럽다
  — "출시 후 회고" 느낌을 원고에 담아야 하므로.
