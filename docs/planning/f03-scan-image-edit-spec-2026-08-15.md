# F-03 — 스캔 이미지 자르기·회전 편집 · 스펙 초안

**작성**: 2026-08-15 (PM 세션)
**상태**: **초안 — 사용자 결정 대기.** §3의 A/B/C 중 하나를 골라야 착수할 수 있다.
**근거**: 테스터 피드백 F-03. F 상태표 *"자동 크롭만. '크게 보기'는 보기 전용"*

## 1. 지금 무엇이 되고 무엇이 안 되나

### 되는 것 — 자동 크롭 (`camera_scan_modal_view.dart` `_cropToGuideFrame`)

촬영하면 **가이드 프레임 기준으로 자동으로 잘라내고, 고정 각도(반시계 90도)로
세워 준다.** 명함 규격이 제각각이라 **가이드보다 30% 여유**를 두고 자른다.

찍은 뒤 **[다시 찍기] / [확인]**을 묻는 확인 화면이 있다
(*"{앞/뒷}면 · 글자가 또렷한가요?"*).

### 안 되는 것

| | |
|---|---|
| **손으로 자르기** | 자동 크롭 결과가 어긋나도 **다시 찍는 것 말고 방법이 없다** |
| **회전** | 각도가 **−90도로 고정**이다. 명함을 반대로 넣거나 세로 명함이면 누운 채로 남는다 |
| **저장 후 편집** | 등록을 마친 뒤에는 이미지를 손댈 수 없다 |

**핵심은 "자동이 틀렸을 때 되돌릴 방법이 없다"는 것이다.** 지금 유일한 복구
수단이 **재촬영**인데, 명함 주인 앞에서 여러 번 다시 찍는 것은 실제 사용
맥락에서 부담이다.

---

## 2. 무엇을 먼저 봐야 하나 — ⚠️ 이 기능이 정말 필요한지부터

**자동 크롭이 얼마나 자주 틀리는지 우리는 모른다.** 그 숫자가 없으면
"편집기를 붙일 가치가 있는지"를 판단할 수 없다.

이 저장소에는 이미 참고할 것이 둘 있다.

- **`ocrStats`** — 인식 결과 통계가 서버에 쌓이고 있다
- **명함 검수 자료** — `~/Downloads/명함검수_이미지`, `ocr_truth.tsv` 등 실제
  촬영본 대조 자료가 있다

→ **착수 전에 "자동 크롭 실패율"을 실제 촬영본으로 재 보는 것**을 권한다.
실패가 드물면 **C안(회전만)** 으로 충분하고, 잦으면 A·B가 정당해진다.

⚠️ 이 저장소가 반복해 다친 유형이다 — **"있어야 할 것 같아서" 만든 기능이
실제로는 안 쓰이고, 대신 진짜 문제는 다른 데 있었다.**

## 3. 선택지 — 사용자 결정이 필요하다

### A안. 편집기 패키지 도입 (크게)

`image_cropper` 같은 패키지를 넣어 **자유 크롭 + 각도 조절**을 제공한다.

| | |
|---|---|
| **되는 것** | 모서리를 끌어 자르기, 임의 각도 회전, 비율 고정 |
| **비용** | ⚠️ **네이티브 의존이 늘어난다** — Android/iOS 양쪽 설정, 빌드 시간, 앱 용량 |
| **위험** | 이 앱은 **Android가 debug 키스토어로 서명**된 상태(P1-19)이고 스토어 출시 전이다. 이 시점에 네이티브 의존을 늘리면 **출시 준비에 변수가 하나 더 생긴다** |
| **개인정보** | 패키지가 이미지를 어디에 쓰는지 확인 필요. **제3자 개인정보가 담긴 사진**이다 |

### B안. 직접 구현 — 최소 크롭 (중간)

이미 쓰고 있는 **`image: ^4.3.0`** 만으로 만든다(`copyCrop`·`copyRotate`가
이미 `_cropToGuideFrame`에서 쓰이고 있다).

| | |
|---|---|
| **되는 것** | 사각 영역을 끌어 조절 + **90도 단위 회전** |
| **비용** | 새 패키지 없음. UI를 직접 만들어야 함(드래그 핸들·미리보기) |
| **한계** | 임의 각도 회전·기울기 보정은 없다 |

### C안. 회전만 (작게) ← **먼저 이걸 권한다**

확인 화면에 **[↻ 90도 회전]** 버튼 하나만 추가한다.

| | |
|---|---|
| **되는 것** | 누운 채로 나온 사진을 세운다 |
| **비용** | **가장 작다.** `img.copyRotate` 한 줄 + 버튼 하나 |
| **근거** | 지금 회전이 **−90도 고정**이라, 명함을 반대 방향으로 넣으면 **반드시 뒤집힌다.** 이건 확실히 존재하는 문제다 |

**권고**: **C안을 먼저 넣고 실사용을 본다.** 그래도 "잘라내기가 필요하다"는
피드백이 남으면 B안, 그것도 모자라면 A안. **가장 확실한 문제부터 가장 싸게
고친다.**

## 4. C안 상세 (권고안)

### 화면

촬영 확인 화면(`_pendingShot != null` 영역)의 [다시 찍기] / [확인] 옆에
**[↻ 회전]** 을 둔다.

```
        [ 사진 미리보기 ]

   "앞면 · 글자가 또렷한가요?"

  [다시 찍기]  [↻ 회전]  [확인]
```

### 동작

- 누를 때마다 **시계 방향 90도**. 네 번 누르면 제자리
- **미리보기가 즉시 바뀐다** — 누르고 나서 결과를 모르면 의미가 없다
- **[확인]을 누른 시점의 각도로 저장**된다. 회전만 하고 [다시 찍기]를 누르면
  그 각도는 버려진다

### 구현 메모

- `img.copyRotate(decoded, angle: 90)` — 이미 `_cropToGuideFrame`에서 쓰는
  방식 그대로다
- **회전할 때마다 파일을 새로 쓰지 말 것.** 각도만 상태로 들고 있다가
  **[확인] 시점에 한 번** 굽는다. 네 번 눌러 제자리로 오면 **아예 다시
  굽지 않는다**(불필요한 재인코딩은 화질을 깎는다)
- 임시 파일은 `Directory.systemTemp`에 쌓인다. **회전 중간 결과를 파일로
  남기지 않는 이유이기도 하다**

### ⚠️ OCR과의 관계

**회전한 이미지로 인식이 돌아야 한다.** 지금 흐름은 [확인] → OCR인데,
회전을 적용하지 않고 원본으로 인식하면 **화면과 결과가 어긋난다.** 이
프로젝트에서 반복된 "코드는 맞는데 실물이 틀린" 유형이 정확히 이 지점에서
난다.

## 6. 검증

**착수 전에 검증 종류를 사용자에게 물어 고르게 한다**(CLAUDE.md 4절).

| 무엇 | 어디까지 |
|---|---|
| 회전 각도 계산 | **자동 테스트** — 네 번 눌러 제자리, 재인코딩 안 함 |
| 화면·버튼 | **부분 테스트** — 실기기 촬영 → 회전 → 확인 |
| **회전본으로 OCR이 도는지** | **부분 테스트 필수** — 회전하고 [확인] → 인식 결과가 회전된 이미지 기준인지 |

**C안은 저장 구조를 바꾸지 않으므로 전체 테스트 대상이 아니다.** A·B안으로
가면 달라질 수 있다(임시 파일·용량·네이티브 의존).
