> ⚠️ **이 문서는 처음엔 "웹 교정 도구" 하나만 다루려 했으나, 작성 도중
> 사용자가 범위를 넓혔다.** 사용자 발언 그대로 옮긴다.

> *"계정에 대한 기획을 변경할 예정이고, 홈페이지도 필요하니까. 웹에서도

> 같으니까."*

> 설계가 아니라 **"무엇이 무엇을 기다리는가"**다 — 넷을 한 덩어리로 밀면
> 안 풀리는 것에 발목 잡혀 풀리는 것까지 같이 멈춘다.
>
> ⚠️ **일정을 적지 않는다.** 순서와 의존관계만 적는다(store-release-date
> 원칙과 같은 이유 — 근거 없는 시한이 우선순위를 오염시킨다).

## 0. 넷을 갈라 본다

| | 무엇인가 | 지금 착수 가능한가 |
|---|---|---|
| **A. 홈페이지** | 회사·서비스 소개(마케팅 웹사이트) | ✅ **독립 — 아무것도 안 기다린다** |
| **B. 웹 명함 교정 도구** | 이미 등록된 내 명함을 웹에서 열어 인식 오류를 고침(원 배정) | ⚠️ 화면 설계는 가능, **구현은 대기**(아래 1절) |
| **C. 웹 명함 업로드·인식** | 웹에서 명함 사진 여러 장을 올려 새로 등록 | ⛔ **대기**(서버 인식 자체가 보류 상태) |
| **D. 계정 기획 변경** | 계정을 무엇으로 식별할지(전화번호 등) 재검토 | 🔒 **사용자 결정 진행 중** — 이 문서가 정하지 않는다 |

**D는 기능이 아니라 전제조건이다.** B·C 둘 다 "내 명함을 웹에서 보려면
로그인해서 내 것임을 증명"해야 하므로, **D가 안 끝나면 B·C의 로그인 연동은
못 붙인다.** 이 사실이 원래 PM 메모(*"웹 로그인 설계 ← 계정 기획"*)보다 한
단계 더 넓다 — 로그인은 B·C 각각의 부속 기능이 아니라 **둘 다의 공통
관문**이다. 검증해서 정정한 부분이라 여기 적어 둔다.

## 2. 무엇을 먼저 하면 나머지가 쉬워지는가

- **B의 화면 설계(4절)를 지금 확정해 두면 C에 그대로 재사용된다.** C는
  "여러 장 업로드 → 서버가 인식 → 결과를 확인/수정"인데, 마지막 단계가
  B의 교정 화면과 완전히 같다. **B를 먼저 설계하는 것이 C를 두 번 만들지
  않는 길이다.**
- **로그인 화면의 틀(버튼 배치·문구)은 지금 잡아도 되지만, 실제 인증 로직은
  지금 짜면 버리게 된다.** 계정 식별 체계(D)가 바뀌면 로그인 연동 코드를
  다시 써야 한다 — **화면은 먼저, 배선은 나중**이 맞는 순서다.
- **홈페이지는 지금 만들어도 나중에 버릴 게 없다.** 계정·로그인과 무관한
  정적 페이지이기 때문이다. 그래서 **넷 중 유일하게 지금 실물 착수 가치가
  있는 항목**이다(단, 3-1의 조율 먼저).

## 3. 항목별 상세

### 3-1. A. 홈페이지 — 지금 착수 가능, 단 조율 필요

⚠️ **이미 산출물이 있다.** `docs/marketing/landing-page-copy.md`에 마케팅
세션이 만든 원페이지 카피가 있다 — Hero 문구, 문제/해결 3단, 타겟 고객,
신뢰 문구, 오퍼까지 완성돼 있고 "Firebase Hosting 무료로 배포 가능(`docs/legal`와
별도 경로)"이라고 이미 적혀 있다. **이 문서가 처음부터 다시 카피를 쓰면
중복이다.**

- **범위**: 그 카피를 실제 페이지로 만드는 일. 신규 기획이 아니라 **구현
  누락을 메우는 일**에 가깝다.
- **기술**: Firebase Hosting에 타겟 하나 더(`legal`·`admin`처럼) —
  예: `site`. 정적 HTML/CSS 한 장이면 충분하다(랜딩페이지 카피 자체가
  "원페이지"로 설계돼 있다). Flutter Web을 쓸 이유가 없다 — 상태도 로그인도
  없는 정적 페이지다.
- **도메인**: 지금은 `*.web.app` 기본 도메인으로 배포 가능. **커스텀
  도메인(예: connectionsense.kr) 구매는 비용이 드는 사업 결정이라 이
  문서가 정하지 않는다** — 필요하면 사용자에게 별도로 묻는다.
- **다음 행동**: 이 문서 하나로 착수하지 말고, **마케팅 세션(또는 그
  산출물을 만든 담당)에게 먼저 확인** — 카피가 최신인지, 이미 진행 중인
  작업이 있는지. PM이 조율한다(4-2절 규칙).

### 3-2. B. 웹 명함 교정 도구 — 대기 중(법무 답 + 로그인 배선)

⏳ **착수 조건**: 오늘 배정된 법무 검토(제3자 정보 웹 표시·공용PC/캐시 위험)
답변 + 계정 기획(D) 확정에 따른 로그인 배선. **둘 중 하나라도 안 끝나면
구현하지 않는다.**

화면 설계는 4절에, 최소 범위는 5절에, 텍스트만 먼저 하는 축소판 검토는
3-3에 있다.

### 3-3. 이미지 없이 텍스트만 먼저 — 성립하는가

⚠️ **PM이 검토를 지시한 항목.** 결론부터: **성립은 하지만 효과가 약하다.**

실물을 확인했다(`lib/data/models/contact_model.dart`). 명함 필드 값(이름·
회사·전화 등)은 **이미 서버(Firestore)에 백업되고 있다**(`toBackupJson`).
사진 서버 백업(`kCardPhotoBackupEnabled`)과는 **별개의, 이미 켜져 있는
경로**다. 즉 "필드 값만 웹에서 고치기"는 **9/15을 기다리지 않고도 데이터
자체는 이미 갖춰져 있다.**

⚠️ **다만 인식 원문(OCR이 실제로 읽어낸 글자 줄)은 어디에도 저장돼 있지
않다.** `ContactModel`에는 최종 필드값만 있고, 검수 도구(`tool/ocr_review`)가
쓰는 "원문 낱말을 눌러서 채우기"의 재료가 되는 그 원문 필드가 앱에 없다.
**그러므로 텍스트만 먼저 가는 축소판에서는 타이핑을 줄이는 핵심 장치(원문
클릭)를 못 쓴다** — 그냥 큰 화면·큰 키보드로 값을 고치는 것뿐이다. 그것도
나름 의미는 있지만(폰보다는 낫다), 이 브리프가 "반드시 넣으라"고 한 장치는
못 들어간다.

**권고**: 텍스트만 버전을 별도 1차로 내지 않는다. 사진 유무로 두 벌을
만드는 비용이, "9/15까지 몇 주 더 기다리는" 손해보다 크다. 대신 **B는
사진·텍스트를 같은 화면에서 함께 설계**(4절)해 두고, 9/15 이후 사진이
켜지는 순간 그대로 완성형이 되게 한다. (원문을 서버에 남기는 것은 이
브리프의 범위 밖이다 — 앱을 고쳐야 하는 별도 항목이므로 필요하면 후속
백로그로 제안한다.)

### 3-4. C. 웹 업로드·인식 — 보류(서버 인식 자체가 보류)

`docs/planning/server-ocr-adoption-plan-2026-08-23.md`에 이미 사용자
결정이 적혀 있다: *"서버 인식은 계획만 세운다. 결정은 앱의 다른 기능
안정화 후."* 이 결정은 **이 브리프가 뒤집을 수 없다.**

⚠️ **왜 웹 업로드가 서버 인식을 반드시 요구하는지**: 앱의 명함 인식은
기기에 설치된 Google ML Kit(온디바이스)로 돈다. **웹 브라우저에는 이
엔진이 없다.** 브라우저에서 명함 사진을 인식하려면 서버가 대신 읽어줘야
하고, 그게 바로 지금 보류 중인 "서버 인식"이다. 즉 **C는 새 기능이 아니라
이미 보류된 결정 위에 얹히는 것**이다 — 별개로 논의할 수 없다.

**지금 할 수 있는 것**: C의 화면 설계(다중 업로드 → 진행 상황 → 결과
확인)는 3-2/4절에서 설계하는 B의 교정 화면을 그대로 이어 쓰는 것으로
**설계만 메모해 둔다**(2절). 구현은 서버 인식이 풀릴 때까지 없다.

### 3-5. D. 계정 기획 변경 — 이 문서가 정하지 않는다, 제약만 적는다

`docs/planning/HANDOFF.md` **P1-49**(계정 식별 방식)와
`account-identity-matrix-2026-08-21.md`에 경우의 수 분석이 이미 있다.
결론은 아직 안 났고(*"법률 질문 L1~L3 발송과 결정 D1·D2 — 전부 사용자"*),
"2-0. 사용자가 결정할 일"에는 **I안(전화번호를 계정의 주인으로)** 이라는
새 방향도 검토 재료로 올라와 있다.

**웹 설계에 이것이 주는 제약**(방식을 정하는 게 아니라, 정해지지 않은
채로 어떻게 설계해야 나중에 안 버리는지):

- 로그인 화면 자체는 **"어떤 방법으로 로그인할지 고르는 화면"**으로
  설계하면 식별 체계가 바뀌어도 화면은 안 바뀐다(2절 "화면 먼저, 배선은
  나중").
- 웹에서 "같은 계정"임을 증명하는 실제 로직(세션 발급·명함 소유 확인)은
  D가 정해지기 전에 짜면 다시 짜야 한다 — **착수하지 않는다.**
- 기술적으로는 구글 로그인(Firebase Auth JS `signInWithPopup`)이 이미
  관리자 콘솔(`docs/admin/admin.js`)에서 검증됐고, 카카오·네이버도
  커스텀 토큰을 발급하는 Cloud Functions(`functions/src/index.ts`의
  소셜 로그인 처리)가 이미 있어 **웹에서 재사용 자체는 가능**하다(웹뷰
  대신 브라우저 리다이렉트로 OAuth를 받는 흐름만 새로 필요). 애플은 앱에서도
  아직 비활성화 상태라 웹에서도 제외가 맞다. **이건 "가능하다"는 기술
  판단이지 "지금 붙인다"는 뜻이 아니다** — D가 끝나야 붙인다.

## 4. 화면 설계 (B — 웹 명함 교정 도구)

### 4-0. 사용자용 설계 기준 — 이 절이 없으면 도구가 실패한다

⚠️ **PM 지적: 참고로 준 두 원형은 전부 "아는 사람이 쓰는" 도구다.**
`tool/ocr_review/index.html`은 개발자 검수 도구, `docs/admin/admin.js`는
관리자 콘솔이다. 그대로 옮기면 실패한다. 아래 기준으로 4-1·4-2를 다시
설계했다.

| 기준 | 무엇을 뜻하나 | 이 기획서에 반영한 것 |
|---|---|---|
| **① 쉬운 말** | "정답지"·"추출값"·"TSV"·"진단" 같은 말 금지 | 화면 문구는 앱과 같은 말만 쓴다(아래 4-3) |
| **② 설명 없이 아는가** | 처음 연 사람이 5초 안에 뭘 하는 곳인지 알아야 함 | 빈 상태·목록 헤더에 "여기서 뭘 하는지" 한 줄로 적음(4-1) |
| **③ 저장 시점** | "중간 저장" 버튼을 사람이 누르게 하면 안 됨 | **자동 저장**(입력을 멈추면 곧 저장) + "저장됨" 표시(4-2) |
| **④ 되돌리기** | 잘못 고쳤을 때 되돌릴 수 있어야 함 | 필드별 "인식된 값으로 되돌리기" + 여러 장 연속 처리 중 실수 방지(4-2) |
| **⑤ 폰에서도 열림** | PC 전용으로 짜면 폰에서 깨짐 | 반응형 1열 배치로 설계(4-1·4-2 각각 명시) |
| **⑥ 같은 말** | 앱과 웹이 같은 것을 다른 말로 부르면 안 됨 | 앱 문구(명함 지갑·명함 등록·뒷면 스캔 안내 등) 그대로 사용 |
| **⑦ 기다림 표시** | 여러 장 처리는 시간이 걸림 — 안 보이면 멈춘 줄 앎 | C(업로드) 단계와 4-1 목록 로딩에 진행 표시 명시 |

📌 **참고자료 — 리멤버의 갈래**: 리멤버는 명함을 올리면 "입력 중"으로
두고, 나중에 채워지면 **입력 중 / 입력 불가** 탭으로 갈라 **실패한 것만
골라 손보게** 한다. 우리는 지금 인식이 실패해도 빈 칸으로 그냥 저장돼서
**어느 명함을 손봐야 하는지 사용자가 스스로 기억해야 한다** — 이 도구가
그 기억의 부담을 대신 져야 한다(그래서 4-1에 "확인이 필요해요" 갈래를
넣었다).

⚠️ **다만 리멤버처럼 "맡기고 잊기"는 못 따라간다.** 리멤버의 그 편함은
**사람이 대신 타이핑해 주는 인건비 구조** 위에 있다(product-principles.md
1절에도 같은 관찰이 있다). 우리는 인식(기기 또는 서버 AI)이 실패한 자리를
**사용자 본인이 메워야 하는 구조**이고, 이 도구는 그 메우는 일을 폰보다
편한 화면에서 하게 해 주는 것 — 리멤버의 "안 해도 됨"과는 다르다는 것을
화면 문구에서도 과장하지 않는다.

### 4-1. 목록 화면 — "명함 지갑" (앱과 같은 이름)

```
상단   "OO님의 명함 지갑 · 32장"                    [검색창]
갈래   [ 전체 ]  [ 확인이 필요해요 ]                 ← ③ 기준 반영, 리멤버 참고
목록   [사진 작게] 이름 · 회사        (확인 필요 배지가 있으면 여기 표시)
       ...
빈 상태  "아직 등록된 명함이 없어요.
         커넥션센스 앱에서 명함을 스캔하면 여기서도 볼 수 있어요."
         (② 기준 — 처음 연 사람이 앱과의 관계를 바로 안다)
```

- "확인이 필요해요" 판정 기준: 이름·회사·연락처(전화 또는 이메일) 중
  하나라도 비어 있는 명함. 배지 문구는 **"확인 필요"**(개발 용어 "미검출"
  금지).
- 목록을 불러오는 동안은 뼈대(skeleton) 표시로 "불러오는 중"임을 보여준다
  (⑦ 기준).
- 반응형: 폰 너비에서는 1열 목록, 사진은 작은 정사각형 썸네일 하나로 축소.

### 4-2. 교정 화면 — "명함 정보 확인" (앱의 "명함 상세/수정"과 같은 개념)

```
[사진]                     [필드들]
회전 ↺ ↻   확대            이름       [________]
                           회사       [________]  ← 이 값으로 되돌리기
                           직함       [________]
(사진 없으면:               휴대폰     [________]
 "이 명함은 사진이 아직      사무실     [________]
  연결되어 있지 않아요")    팩스       [________]
                           이메일     [________]
                           홈페이지   [________]
                           우편번호   [________]
                           주소       [________]
                           상세주소   [________]

상단 우측: "저장됨 · 오후 3:12"  ← ③ 기준, 필드에서 손을 떼면 곧 저장
하단: [ ← 이전 명함 ]  [ 다음 명함 → ]   ← 연속 처리, 검수 도구의
                                          Ctrl+Enter를 큰 버튼으로 대체
```

- **자동 저장**(③ 기준): 입력창에서 포커스가 빠지거나, 타이핑을 멈추고
  약 1초 지나면 저장. "저장" 버�위을 누르게 하지 않는다. 저장 실패 시(망
  끊김 등)에는 "저장 안 됨 — 다시 시도" 문구로 명확히 알림(조용히
  실패시키지 않는다 — 4절 개인정보 원칙과 별개로 이것 자체가 신뢰 문제).
- **되돌리기**(④ 기준): 필드마다 인식이 원래 준 값이 있으면 "인식된
  값으로 되돌리기" 작은 링크를 옆에 둔다(검수 도구의 "왼쪽 회색값 누르면
  그대로 정답" 아이디어를 사용자용 문구로 순화). 여러 장을 연달아 고치다
  실수하면 **직전 명함으로 돌아가 다시 고치면 그만**이므로 별도의 "전체
  되돌리기"는 만들지 않는다(범위 최소화, 5절).
- **원문 클릭 채우기는 없다**(3-3 참고 — 원문 자체가 서버에 없다). 대신
  입력창 자체를 크게, 키보드가 편하게(폰에서도 확대 없이 탭 가능한 크기)
  잡아 그 공백을 최대한 메운다.
- 반응형(⑤ 기준): 폰 너비에서는 사진이 위, 필드가 아래로 세로 배치.
  사진은 핀치줌으로 확대(회전 버튼은 그대로 유지).

### 4-3. 용어 대조표 — 앱과 다르게 부르지 않는다(⑥ 기준)

| 웹에서 쓸 말 | 쓰지 않을 말(개발자 용어) |
|---|---|
| 명함 지갑 | 카드 목록, 대시보드 |
| 확인 필요 | 미검출, 빈 칸, undone |
| 인식된 값으로 되돌리기 | 원본값 복원, reset |
| 저장됨 | committed, synced |
| 이 명함은 사진이 아직 연결되어 있지 않아요 | 이미지 없음, no image |

## 6. 기술 선택

### 6-1. B·C — 바닐라 HTML/JS + Firebase 웹 SDK (Flutter Web 아님)

`docs/admin/admin.js`·`firebase.json`을 확인했다. `legal`·`admin` 두
Hosting 타겟이 이미 같은 패턴(정적 파일 + Firebase 웹 SDK를 CDN에서 직접
import)으로 운영 중이고, Google 팝업 로그인·세션 지속성·Firestore 조회까지
이미 검증돼 있다. **같은 패턴으로 타겟 하나(`card-editor` 등)를 더 두는
것을 권고한다.**

| | Flutter Web | 바닐라 HTML/JS(admin과 같은 패턴) |
|---|---|---|
| 앱 코드 재사용 | 모델·검증 로직 공유 가능 | 폼 검증 정도만 새로 씀(작은 비용) |
| 초기 로딩 크기 | 크다(엔진 포함) — "폰에서도 연다"는 기준(4-0 ⑤)에 불리 | 가볍다 |
| 검증된 전례 | 이 저장소에 없음 | `admin`·`legal` 타겟에서 이미 배포·운영 중 |
| 로그인 재사용 | Firebase Auth 웹 SDK를 새로 통합해야 함 | admin.js 패턴 그대로 가져다 씀 |
| 화면 성격 | 이 도구는 폼 + 이미지 뷰어뿐, 복잡한 상태관리 없음 | 충분 |

**결론**: 화면이 단순(폼 + 이미지 뷰어)해 Flutter Web의 코드 공유
이점이 작고, 반대로 로딩 크기·모바일 접근성에서는 불리하다. **바닐라
HTML/JS로 admin 타겟과 같은 패턴을 쓰는 쪽을 권고한다.**

### 6-2. A(홈페이지) — 정적 HTML, 새 Hosting 타겟

3-1에서 이미 다뤘다. 로그인·상태가 없는 순수 정적 페이지라 기술 선택
자체가 쟁점이 아니다.

## 8. 위험 — 무엇이 어긋나면 실패하는가

| 위험 | 무엇이 어긋나는 것인가 |
|---|---|
| 계정 기획(D)이 오래 안 정해짐 | B·C 둘 다 "화면만 있고 로그인이 안 붙는" 채로 무기한 대기 — 이 브리프의 절반이 멈춘다 |
| 법무 답 ②가 "조건부"로 옴 | 예: "URL에 명함 ID를 노출하지 말 것"·"세션 자동 만료 필수" 같은 조건이 4절 설계에 반영 안 돼 있으면 재설계 |
| 사진 백업(9/15) 이후 남은 일이 늦어짐 | storage.rules·실기기 확인이 안 끝나면 B의 "사진 보며 고치기"가 시행일이 지나도 못 켜짐 |
| 서버 인식이 계속 "보류" | C는 계획 문서로만 남고, 이 브리프의 4절 설계(교정 화면)만 B에서 쓰이고 C는 실현 안 됨 — 이 자체는 실패가 아니라 원래 사용자가 정한 방향(안정화 후) |
| 4-0의 사용자용 기준을 안 지키고 구현 | "관리자 도구를 옮겨놓은 것"이 되어 실사용자가 못 쓴다 — 이번 PM 지적의 핵심. 구현 위임 시 4-0 표를 인수 기준에 그대로 못 박아야 한다 |
| 홈페이지가 마케팅 산출물과 어긋남 | 두 번 만들거나, 서로 다른 문구가 각각 배포돼 신뢰도를 깎는다(3-1) |
| 개인정보(URL·캐시) 설계 누락 | 제3자(명함 주인) 정보가 공용 PC 브라우저 캐시·히스토리에 남으면 그 자체가 CLAUDE.md 원칙 위반 — 법무 답 ②가 정확히 이 지점을 본다 |
