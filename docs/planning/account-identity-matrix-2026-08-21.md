# 계정 식별 경우의 수 매트릭스 (P1-49) — 2026-08-21

> **왜 이 문서가 있나**: 카카오 로그인을 켜면서(추가 362) "같은 사람을 어떻게
> 알아보나"가 설계 문제로 드러났다. 사용자 결정은 *"기본 방향은 A(인증된
> 이메일로 묶기)이되, 단순한 할일이 아니라 **복합적인 경우의 수를 기준으로
> 판단해야 함**"* — 이 문서가 그 경우의 수 분석이다. **분석·법률검토 전
> 구현 금지가 유지된다.**

작성: PM 세션. 근거는 전부 실물 표기 — `[코드]` 저장소 실물, `[콘솔]` 제공자
콘솔 화면, `[기록]` backlog/HANDOFF.

## 0. 전제 — 지금 실물이 어떻게 돼 있나

| 사실 | 근거 |
|---|---|
| 식별자는 **제공자 계정**이다. uid = 구글·애플은 Firebase 기본 제공자 uid, 카카오·네이버는 `kakao:{id}`·`naver:{id}` 커스텀 토큰 | `[코드]` `functions/src/socialAuth.ts` `socialUid()` |
| **이메일은 식별에 쓰이지 않는다.** 프로필 표시용으로만 저장 | `[코드]` socialAuth.ts `buildProfile()` |
| Firebase Auth는 **계정마다 이메일이 유일**하다 — 같은 이메일이 구글 계정에 있으면 카카오 계정에는 못 넣는다 | `[기록]` 추가 362 ⑥ (실제로 겪음) |
| **uid 형식은 비가역** — 바꾸면 기존 이용자의 명함이 통째로 끊긴다 | `[기록]` P1-49 |
| 같은 기기에서 계정만 바꾸는 것은 이미 된다(`auth_gate.dart` "유지/교체" 흐름). 문제는 **기기까지 바뀔 때** | `[코드]` auth_gate.dart · `[기록]` 추가 362 |
| 휴대전화번호는 **받지 않기로 확정** — 리멤버식 전화번호 식별은 불가 | `[기록]` 추가 362 |
| 탈퇴→재가입 시 무료 회차 리셋(A안 수용, 테스트 기간 한정 허용) | `[기록]` 메모리 ai-quota-reset |

### 제공자별 이메일의 품질 — 넷이 전부 다르다

| 제공자 | 이메일 성격 | 인증 여부를 아나 | 사람 묶기에 쓸 수 있나 |
|---|---|---|---|
| 구글 | 구글 계정 이메일 | 사실상 인증됨 | ✅ 가능 |
| 애플 | 애플 계정 이메일 **또는 릴레이 주소**(`***@privaterelay.appleid.com`, "이메일 가리기") | 인증됨 | ⚠️ **릴레이면 불가** — 앱마다 다른 주소가 발급돼 같은 사람이라도 못 묶는다 |
| 카카오 | 카카오계정 이메일 | ✅ `is_email_verified` 제공 | ⚠️ **인증된 경우만** 가능 |
| 네이버 | **연락처 이메일** — 계정 이메일이 아님 | ❌ 안 줌 | ❌ **불가** — 계정별로 고유하지 않음(두 네이버 계정이 같은 이메일 가능). `[콘솔]` 네이버 개발자센터 안내 실물(추가 368) |

📌 **이 표가 결론의 뼈대다.** "이메일로 묶는다"가 성립하는 제공자는 넷 중
**구글과 (인증된) 카카오뿐**이고, 애플은 절반, 네이버는 아예 아니다.

## 1. 경우의 수 매트릭스

각 케이스: **발생 조건 → 지금(제공자 식별) 어떻게 되나 → A안(이메일 묶기)을
그대로 적용하면 어떻게 되나 → 판정**.

### ① 카카오 이메일이 인증됨 / 미인증

| | 인증됨 | 미인증 |
|---|---|---|
| 지금 | 이메일 무관, `kakao:{id}`로 정상 동작 | 동일 |
| A안 적용 시 | 묶기에 쓸 수 있다 | ⚠️ **쓰면 계정 탈취** — 남의 이메일을 미인증으로 넣은 카카오 계정으로 로그인하면 **그 사람 명함(제3자 개인정보 포함)을 통째로 가져간다** |
| 판정 | 조건부 허용 | **금지.** `is_email_verified === true`가 아닌 이메일은 식별에 쓰지 않는다 |

### ② 네이버 — 인증 여부를 안 주고, 애초에 고유하지 않음

| | 내용 |
|---|---|
| 지금 | 이메일 무관, `naver:{id}`로 정상 동작 |
| A안 적용 시 | ⚠️ **오묶임** — 연락처 이메일은 계정별 고유값이 아니므로, 남과 같은 이메일을 등록한 두 네이버 이용자가 **한 사람으로 묶인다.** 인증 여부 이전의 문제 |
| 판정 | **네이버 이메일은 식별에서 영구 제외.** A안은 네이버에 적용 불가 |

### ③ 같은 이메일이 구글·애플 기존 계정과 충돌

| | 내용 |
|---|---|
| 발생 | 구글로 가입한 사람이 같은 이메일의 카카오 계정으로 로그인 |
| 지금 | 별개 계정 둘이 생기고, 카카오 계정에는 Firebase 이메일 유일 제약 때문에 **이메일이 안 실린다**(추가 362에서 실제 발생) |
| A안 적용 시 | 자동 병합하면 편하지만 — ⚠️ **자동은 위험하다.** ①의 미인증 탈취와 ②의 오묶임이 이 자리에서 터진다 |
| 판정 | 자동 병합 금지. **명시적 연결**(아래 2절 권고)로만 |

### ④ 한 사람이 제공자별로 다른 이메일

| | 내용 |
|---|---|
| 지금 | 별개 계정 — 본인이 "다른 계정"임을 인지하기 어렵다 |
| A안 적용 시 | **이메일로도 못 묶는다.** 공통 열쇠가 없다 |
| 판정 | 어떤 자동 방식으로도 해결 불가. 명시적 연결 또는 관리자 이관(B안)만 가능 |

### ⑤ 제공자 쪽에서 이메일 변경 후 재로그인

| | 내용 |
|---|---|
| 지금 | uid가 이메일과 무관하므로 **아무 영향 없음** (현 구조의 장점) |
| A안 적용 시 | ⚠️ 이메일을 열쇠로 쓰면 **같은 사람이 다른 사람이 된다.** 반대로 바뀐 이메일이 남의 옛 이메일과 같으면 남과 묶인다 |
| 판정 | 이메일은 **불변 열쇠가 아니다.** 열쇠로 쓰더라도 "가입 시점 스냅샷"이 아니라 연결 기록으로 관리해야 한다 |

### ⑥ 탈퇴 후 재가입 ⭐ 무료 회차 리셋 우회와 얽힘

| | 내용 |
|---|---|
| 지금 | 탈퇴로 계정·데이터가 지워지므로 재가입=신규. **무료 회차가 리셋**된다(테스트 기간 한정 수용, A안) |
| A안 적용 시 | 인증 이메일(해시)을 탈퇴 후에도 보존하면 재가입을 알아볼 수 있어 **오히려 우회 방지에 쓸 수 있다** |
| 판정 | 기술적으로 유일하게 A안이 **이득**인 자리. ⚠️ 단, **탈퇴 후 개인정보(이메일/해시) 보존은 법률 검토 필수** — 기기 해시 U5(법무 질문 5번)와 같은 유형의 질문이다 |

### ⑦ 미인증으로 가입 후 나중에 인증됨

| | 내용 |
|---|---|
| 지금 | 영향 없음 |
| A안 적용 시 | 인증 시점에 "이제 묶을 수 있는" 계정이 생긴다. ⚠️ 소급 자동 병합하면 그 사이 쌓인 두 계정의 명함을 어느 쪽으로 합칠지 충돌 |
| 판정 | 소급 자동 병합 금지. 인증 후에도 **명시적 연결**로만 |

### ⑧ 애플 "이메일 가리기"(릴레이 주소) — 신규 케이스

| | 내용 |
|---|---|
| 발생 | 애플 로그인에서 이용자가 이메일 가리기를 선택 — 앱은 `***@privaterelay.appleid.com`만 받는다 |
| 지금 | 영향 없음 |
| A안 적용 시 | 릴레이 주소는 **앱마다 다르게 발급**되므로 같은 사람의 다른 제공자 계정과 절대 일치하지 않는다 — 묶기 불가. 반면 탈취 위험도 없다 |
| 판정 | 애플 릴레이 이메일은 식별에서 제외(④와 같은 결말) |

## 2. 종합 판정 — "A안 그대로"는 성립하지 않는다

매트릭스를 관통하는 결론:

1. **이메일 자동 병합은 어떤 형태로도 금지.** ①미인증 탈취, ②네이버 오묶임,
   ⑤이메일 가변성, ⑦소급 충돌 — 여덟 케이스 중 넷에서 사고가 난다. 이 앱은
   계정 하나가 새면 **제3자(명함 주인)의 개인정보**가 통째로 새는 앱이다.
2. 성립 가능한 형태는 **"인증된 이메일 + 이용자 본인의 명시적 연결"**뿐이다:
   두 로그인 수단 각각으로 실제 로그인해 본인임을 증명했을 때만 계정을 잇는다
   (Firebase account linking이 정확히 이 모델이다). 이메일은 그 연결의
   *후보 안내*("같은 이메일의 구글 계정이 있어요. 연결할까요?")에만 쓴다 —
   그나마 구글·인증된 카카오에서만.
3. **네이버·애플 릴레이 이용자는 이메일로는 영영 못 묶는다.** 이 두 집단에는
   명시적 연결(양쪽 로그인) 또는 관리자 이관(B안)만 남는다. 즉 **B안은 A안의
   대안이 아니라 보완재**로 어차피 필요하다.
4. ⑥(재가입 식별)만은 별도 판단 — 이메일 해시 보존은 우회 방지에 유효하지만
   **법률 검토가 선행**돼야 한다.

📌 **현 구조(제공자 식별)는 결함이 아니라 안전한 기본값이다.** 서두를 이유가
없고, uid 비가역성 때문에 서두르면 안 된다.

## 3. 법률 검토에 물을 것 (기존 의뢰서에 추가할 질문)

`docs/legal/legal-review-request-2026-08-15.md`의 5개 질문과 같은 형식으로:

- **L1. 탈퇴 후 인증 이메일(또는 그 해시)의 보존** — 재가입 식별(무료 회차
  우회 방지) 목적. 가명처리로 충분한가, 방침 고지가 필요한가, 보존 기간은?
  (기존 질문 5번 기기 해시와 동형 — 함께 묻는 것이 효율적)
- **L2. 계정 연결(병합) 시 데이터 이전의 근거** — 이관되는 것이 이용자 본인
  정보가 아니라 **제3자(명함 주인) 개인정보**다. 본인의 연결 동의로 충분한가?
- **L3. 네이버 "연락처 이메일" 수집·표시 고지** — 계정 이메일이 아닌 값을
  프로필에 표시하는 것에 대한 방침 문구가 지금 적절한가?

## 4. 사용자가 결정할 것 (구현 착수 전)

| # | 결정 | 선택지 |
|---|---|---|
| D1 | 명시적 계정 연결 기능을 만들 것인가 | 만든다(권고: 정식 출시 전 불필요, v1.1 후보) / 안 만든다(문의 오면 B안 관리자 이관) |
| D2 | 재가입 식별용 이메일 해시 보존(⑥) | 법률 회신 후 결정 — 테스트 기간에는 현행(리셋 허용) 유지 |
| D3 | 법률 질문 L1~L3을 기존 의뢰서에 합쳐 보낼 것인가 | 의뢰서가 아직 미발송이면 합치는 것이 한 번에 끝난다(권고) |

**이 문서로 P1-49의 "매트릭스" 절반은 끝났다.** 남은 절반(법률 검토)은 D3
결정 → 발송 → 회신 순서다. 회신 전 uid·식별 체계 변경 금지는 그대로다.
