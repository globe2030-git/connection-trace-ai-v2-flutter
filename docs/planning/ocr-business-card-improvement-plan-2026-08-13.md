# 명함 OCR 입력 정확도 개선 검토 및 개발 계획

- 작성일: 2026-08-13
- 대상: `connection-trace-ai-v2-flutter`
- 범위: 명함 촬영/갤러리 선택 → OCR → 필드 분류 → 기존 입력값과 병합 → 사용자 확인
- 상태: 정적 검토 및 개선안 작성 완료, 코드 수정·테스트 실행 전

## 1. 결론

현재 인식 오류의 중심 원인은 OCR 엔진 하나가 아니라 아래 세 단계에 있다.

1. 카메라가 **흔들리지 않는 상태만** 확인하고 흐림·빛 반사·카드 크기·기울기를 검사하지 않은 채 자동 촬영한다.
2. ML Kit이 제공한 줄별 위치 정보를 같은 높이의 문자열 하나로 합쳐, 이름·회사·직함이 서로 다른 열에 있어도 한 줄처럼 파싱한다.
3. 파서가 확신이 낮은 추정값도 빈칸 대신 자동 입력하고, 앞면·뒷면 스캔 결과를 필드별 신뢰도가 아닌 전체 덮어쓰기/빈칸 채우기로 병합한다.

따라서 정규식만 계속 추가하는 방식은 한 명함을 고치면서 다른 명함을 망가뜨릴 가능성이 높다. 다음 순서로 개선해야 한다.

> 촬영 품질 차단 → OCR 위치정보 보존 → 필드별 후보·신뢰도 산출 → 필드별 병합/확인 → 실제 결함 기반 회귀 테스트

## 2. 현재 코드에서 확인된 문제

### P0 — 잘못된 값이 사용자 데이터로 확정되는 문제

#### P0-1. 낮은 확신의 이름·회사·직함도 자동 입력

- 대상: `lib/core/services/ocr_scanner_service.dart`
- 이름/회사/직함을 명확히 식별하지 못해도 남은 줄의 순서나 글자 크기로 값을 채운다.
- 그 결과 부서명 `기획팀`을 이름으로 인정하는 테스트가 현재 정상 동작으로 고정돼 있다.
- 백로그의 E-02(이름 대신 `기업`)와 E-08(이름·직함·회사 혼합)과 같은 원인이다.

개선 원칙:

- `값 1개`가 아니라 `후보 목록 + 신뢰도 + 근거`를 반환한다.
- 높은 신뢰도만 자동 입력한다.
- 중간 신뢰도는 “제안”으로 표시하고 사용자가 선택하게 한다.
- 낮은 신뢰도는 비워 둔다. 개인정보 앱에서는 틀린 자동 입력보다 확인 가능한 빈칸이 안전하다.

#### P0-2. 앞·뒷면 및 기존 값 병합이 필드 단위가 아님

- 대상: `lib/presentation/features/wallet/views/add_card_modal_view.dart`
- 현재는 기존 이름과 새 이름이 다를 때만 다른 명함으로 추정하고, 이후 전체 덮어쓰기 또는 빈칸만 채우기 중 하나를 적용한다.
- 대상: `lib/presentation/features/radar/views/my_profile_edit_modal_view.dart`
- 내 명함 편집은 OCR이 반환한 비어 있지 않은 값을 기존 값 위에 곧바로 덮어쓴다.
- 백로그 E-01, F-01의 근본 원인이다.

개선 원칙:

- 한 스캔 세션에서 앞면·뒷면 후보를 누적한다.
- 필드마다 `기존 값 / 새 후보 / 신뢰도 / 출처(앞면·뒷면)`를 비교한다.
- 사용자가 이미 확인하거나 수정한 값은 새 스캔이 자동으로 덮어쓰지 않는다.
- 값이 충돌하면 필드별 선택 화면을 표시한다.
- 명함 등록과 내 명함 편집이 동일한 병합 규칙을 사용해야 한다.

#### P0-3. 전화번호 정규화 오류

- 대상: `lib/core/services/ocr_scanner_service.dart::_normalizePhone`
- 10자리 번호를 모두 `3-3-4`로 나눈다.
- 예: `02-1234-5678`은 10자리이지만 `021-234-5678`로 바뀔 수 있다.
- `H.`/`T.` 라벨 및 `+82` 국제 표기 분류도 충분하지 않다(E-03).

개선 원칙:

- `02`로 시작하는 9자리/10자리 번호는 각각 `2-3-4`, `2-4-4`로 처리한다.
- `H`, `M`, `Mobile`, `Cell`, `C.P`는 휴대폰, `T`, `Tel`, `Office`는 사무실, `F`, `Fax`는 팩스로 분류한다.
- `+82 10...`, `+82 (0)10...`은 국내 표준형으로 변환하되 원본 후보도 보존한다.

### P1 — OCR 입력 영상의 품질 문제

#### P1-1. 자동 촬영 조건이 선명도를 검사하지 않음

- 대상: `lib/presentation/features/wallet/views/camera_scan_modal_view.dart`
- 현재 자동 촬영은 두 프레임의 평균 밝기 차이가 작으면 “안정됨”으로 판단한다.
- 초점이 흐리거나 빛 반사가 있어도 카메라만 움직이지 않으면 자동 촬영된다.
- 백로그 E-04가 그대로 남아 있다.

개선 원칙:

- 전체 화면이 아니라 가이드 안의 명함 영역만 평가한다.
- 다음 조건을 모두 만족한 뒤 자동 촬영한다.
  - 프레임 안정성
  - 선명도(라플라시안 분산 또는 에지 에너지)
  - 과다 노출/빛 반사 픽셀 비율
  - 저조도 픽셀 비율
  - 카드가 가이드 영역을 충분히 채우는지
  - 카드 네 모서리 및 원근 왜곡 허용 범위
- 실패 이유를 사용자에게 구체적으로 안내한다: `초점을 맞춰 주세요`, `빛 반사를 줄여 주세요`, `명함을 조금 가까이 놓아 주세요`.
- 한 번의 OCR을 여러 번 돌리는 대신 촬영 직전 2~3개 후보 프레임 중 가장 선명한 한 장을 선택한다.

ML Kit 공식 가이드 기준:

- 글자 하나가 대략 16×16픽셀 이상 보이도록 명함이 화면을 충분히 채워야 한다.
- 초점 불량은 정확도를 떨어뜨리므로 재촬영을 유도해야 한다.
- 고해상도 자체보다 실제 글자가 차지하는 픽셀 수와 초점이 중요하다.

#### P1-2. 고정 가이드 크롭만 있고 카드 경계/원근 보정이 없음

- 현재 가이드 영역에 30% 여유를 더해 중앙을 자르고 고정 90도 회전한다.
- 실제 카드가 비뚤어지거나 가이드와 어긋난 경우 배경 글자가 섞이거나 글자가 잘릴 수 있다.
- 갤러리 이미지는 품질 검사나 카드 경계 보정 없이 OCR로 바로 전달된다.

개선 원칙:

- 네 모서리를 검출해 카드 영역만 원근 보정한다.
- 회전 방향은 고정값보다 텍스트/문서 방향 검출 결과를 우선한다.
- Android는 ML Kit Document Scanner의 자동 캡처·경계 검출·회전·필터 기능을 기술 검증 후보로 둔다.
- iOS는 Vision/VisionKit의 문서 영역 및 텍스트 관측 정보 활용을 기술 검증 후보로 둔다.
- 플랫폼별 스캐너로 UX가 달라지는 것이 문제라면 현재 Flutter 카메라 위에 공통 품질 게이트와 OpenCV 계열 경계 검출을 구현한다.
- 과거에 정확도를 악화시킨 일괄 대비/샤픈 처리는 되살리지 않는다. 원본과 제한된 보정 후보를 실제 벤치마크로 비교한 뒤 필드 정확도가 좋아지는 경우에만 적용한다.

### P1 — 위치정보 손실로 인한 필드 혼합

- 대상: `lib/core/services/ocr_scanner_service.dart::_extractOrderedLines`
- 모든 블록의 줄을 모은 뒤 높이가 비슷한 줄을 좌→우 문자열로 결합한다.
- 이때 `boundingBox`, 블록, 열, 줄 사이 거리 정보가 파서에 전달되지 않는다.
- 좌측 회사명과 우측 이름처럼 서로 다른 열의 항목이 하나의 줄이 되어 E-08을 유발할 수 있다.

개선 모델:

```text
OcrToken/OcrLine
  text
  boundingBox
  normalizedBox
  blockIndex / lineIndex
  height
  recognitionConfidence (플랫폼이 제공하는 경우)
  scanSide / imageId
```

- 같은 높이라는 이유만으로 서로 멀리 떨어진 줄을 합치지 않는다.
- 열/블록 군집을 유지하고, `M`, `T`, `E`, `주소` 같은 라벨은 오른쪽 또는 바로 아래의 가장 가까운 후보와 연결한다.
- 이름·회사·직함은 텍스트 규칙뿐 아니라 상대 위치, 글자 크기, 주변 라벨, 다른 필드와의 충돌을 함께 점수화한다.
- 동일 토큰이 이름과 회사 등 두 필드에 동시에 배정되지 않도록 전체 후보를 한 번에 해결한다.

## 3. 권장 결과 모델

```dart
class OcrFieldCandidate {
  final String field;
  final String value;
  final double confidence; // 내부 점수, 사용자에게는 높음/확인 필요로 표시
  final List<String> evidenceCodes; // 원문 개인정보가 아닌 규칙 코드
  final Rect? sourceBox;
  final String imageId;
  final ScanSide scanSide;
}

class OcrScanResult {
  final Map<String, List<OcrFieldCandidate>> candidates;
  final OcrImageQuality quality;
  final String imagePath; // 화면 세션에서만 사용 후 삭제
}
```

자동 입력 예시 기준:

- 높음: 이메일 정규식 완전 일치, 휴대폰 형식+라벨 일치, 주소 구조 완전 일치
- 중간: 이름 후보지만 회사/부서 가능성이 남음, 전화 형식은 맞지만 라벨 충돌
- 낮음: 단순히 남은 첫 줄, 다른 열과 합쳐진 줄, 형식 검증 실패

임계값은 코드에 흩어진 숫자가 아니라 버전이 있는 설정으로 관리하고 실제 수정률로 보정한다.

## 4. 입력 화면 개선

스캔 직후 모든 값을 조용히 확정하지 말고 아래처럼 표시한다.

```text
이름      홍길동                 [확실]
회사명    주식회사 예시          [확인 필요]  (다른 후보 보기)
직함      기획팀                 [선택 안 함]  팀장 / 기획팀
휴대폰    010-1234-5678          [확실]
회사전화  기존 02-1234-5678      [유지]        새 값 선택
```

- 불확실 필드로 먼저 포커스를 이동한다.
- 후보 선택 시 해당 글자가 있던 이미지 영역을 함께 보여준다.
- 빈 값은 가짜 예시 데이터로 채우지 않고 “인식되지 않음” 상태로 둔다.
- 앞면/뒷면 재촬영 후 전체 폼이 아니라 변경된 필드만 비교한다.
- 저장 전 필수 필드 중 `확인 필요`가 남아 있으면 한 번 더 알린다.

## 5. 테스트가 실제 결함을 잡도록 바꾸는 방법

현재 `test/ocr_scanner_parse_test.dart`는 ML Kit과 카메라/이미지 품질을 제외한 합성 문자열 파서 테스트다. 규칙 단위 테스트로는 유용하지만 실제 스캔 정확도를 보장하지 못한다. 특히 `기획팀`을 이름으로 오인하는 결과를 기대값으로 두어 알려진 결함을 고정한다.

### 반드시 먼저 실패해야 하는 결함 재현 테스트

1. 흐린 프레임은 안정적이어도 자동 촬영하지 않는다(E-04).
2. 좌우 열의 같은 높이 텍스트를 한 줄로 합치지 않는다(E-08).
3. `기획팀`만 있을 때 이름으로 자동 확정하지 않는다(E-02 계열).
4. `H. 010...`은 휴대폰, `T. 02...`는 회사전화가 된다(E-03).
5. `02-1234-5678`이 그대로 보존된다.
6. `+82 10...`이 국내 휴대폰 형식으로 정규화된다.
7. 앞면의 확인된 이름을 뒷면 스캔이 덮어쓰지 않는다(E-01).
8. 기존 값과 OCR 값이 충돌하면 해당 필드만 선택하도록 표시한다(F-01).
9. 내 명함 편집에서도 낮은 신뢰도 후보가 기존 값을 덮어쓰지 않는다.
10. 빈 OCR 결과 화면에는 샘플 이름·전화번호·주소가 나타나지 않는다.

### 테스트 계층

- 단위: 전화/이메일/주소 정규화, 후보 점수, 필드 충돌 해결
- 레이아웃: bounding box가 포함된 1열·2열·세로·앞뒷면 구조 테스트
- 이미지: 개인정보가 없는 자체 제작 명함 이미지와 사용 동의·비식별 처리된 내부 기준 이미지
- UI: 필드별 병합, 불확실 상태, 빈 상태, 재촬영, 사용자 확정값 보호
- 실기기: Android/iOS 각각 초점 불량·빛 반사·기울기·작은 글자 조건

실제 고객 명함 원본은 저장소에 커밋하지 않는다. 동의된 평가 이미지는 암호화된 로컬 전용 폴더에서만 사용하고, CI에는 개인정보 없는 합성/비식별 이미지만 둔다.

### 품질 지표

- 필드별 정확 일치율
- 잘못 자동 입력된 비율(precision을 최우선)
- 필드별 누락률
- 자동 입력 후 사용자가 수정/삭제한 비율
- 신뢰도 구간별 실제 정답률
- 흐림/반사 사진의 촬영 차단률과 정상 사진 오차단률

원문·이름·전화번호·주소·명함 이미지는 분석 로그에 남기지 않는다. 집계에는 필드 코드, 신뢰도 구간, 수정/삭제 여부, 품질 점수, 앱/파서 버전만 사용한다.

## 6. 외부 AI 보정 사용 여부

1차 개선은 온디바이스 촬영 품질과 구조 파서로 진행한다. 서버 AI는 필수가 아니다.

서버 AI를 보조 파서로 도입하려면 다음 조건을 모두 지켜야 한다.

- 로컬 파서가 필수 필드를 찾지 못한 경우에만 사용한다.
- 사용자가 전송될 항목을 확인하고 명시적으로 동의한다.
- 가능하면 명함 이미지 대신 필요한 OCR 텍스트/위치 토큰만 최소 전송한다.
- 서버와 외부 API 로그에 원문을 남기지 않고 보존 기간을 0 또는 최소로 설정한다.
- 개인정보처리방침의 수집 항목, 처리 목적, 국외 이전/수탁자, 보존 기간과 실제 전송이 일치해야 한다.
- AI 응답도 후보일 뿐 자동 확정하지 않는다.

현재 개인정보 검토가 완료되기 전에는 외부 AI 보정을 정확도 개선의 기본 경로로 켜면 안 된다.

## 7. 구현 순서

### 1단계 — P0 안전장치(작음~중간)

- `02`/`H`/`T`/`+82` 전화 규칙 수정
- 낮은 확신의 leftover 자동 입력 중지
- `OcrFieldCandidate`와 필드별 신뢰도 도입
- 앞/뒤/기존 값의 필드별 병합 및 확인 UI
- 내 명함 편집에도 동일 정책 적용
- `_isScanningOcr`가 실제 시작 시 `true`가 되도록 중복 실행 방지 상태 수정

### 2단계 — 촬영 품질 게이트(중간)

- 가이드 영역 선명도·반사·저조도·카드 점유율 측정
- 품질별 사용자 안내 및 자동 촬영 차단
- 촬영 후보 중 가장 선명한 프레임 선택
- 갤러리 이미지에도 동일한 사전 품질 검사 적용

### 3단계 — 위치 기반 파서(중간~큼)

- bounding box를 보존하는 OCR 중간 모델
- 블록/열 군집 및 라벨 근접 매칭
- 필드 후보 충돌 해결
- 기존 규칙을 후보 생성기로 재사용하되 최종 확정과 분리

### 4단계 — 측정 및 제한 배포(중간)

- 개인정보 없는 이미지 회귀 세트
- 동의된 로컬 실명함 벤치마크 도구
- 기존 버전과 신규 버전의 필드별 정확도/수정률 비교
- Android/iOS 일부 사용자에게 제한 적용 후 확대

## 8. 완료 수용 기준

- E-01, E-02, E-03, E-04, E-08, F-01 재현 테스트가 수정 전 실패하고 수정 후 통과한다.
- 낮은 신뢰도 이름·회사·직함은 자동 확정되지 않는다.
- 사용자가 확인/수정한 필드는 추가 스캔으로 자동 덮어쓰지 않는다.
- 명함 앞·뒷면 정보가 필드별로 합쳐진다.
- 흐림·강한 반사 사진은 OCR 전에 차단되고 이유가 표시된다.
- 빈 결과 UI에 가짜 명함 데이터가 없다.
- 로그/분석/오류 보고에 명함 원문, 이름, 전화번호, 이메일, 주소, 이미지 경로가 남지 않는다.
- 실제 이미지 기준 신규 방식이 기존 대비 이름/회사/직함 수정률을 낮추고 전화/이메일/주소 정확도를 악화시키지 않는다.

## 9. 개발 시 주의사항

- 기존 정규식을 한 번에 폐기하지 말고 후보 생성 규칙으로 감싼 뒤 단계적으로 전환한다.
- 이미지 전처리는 눈으로 좋아 보이는지가 아니라 필드 정확도 지표로 선택한다.
- 테스트 기대값으로 알려진 오인식을 인정하지 않는다. 오인식은 빈칸 또는 확인 필요 상태가 되어야 한다.
- 실제 명함 데이터를 디버그 로그, 테스트 실패 메시지, 스냅샷, 원격 오류 보고에 출력하지 않는다.
- 테스트 실행 전 저장소 지침에 따라 사용자에게 전체/부분/자동 테스트 중 선택을 먼저 받는다.
