## 0. 실물 확인 — 지금 코드는 이미 무엇을 하고 있나

🚨 **PM 지시서의 "묻지 않고 업데이트했다"는 지금 코드와 다르다.** 코드를
직접 읽어 확인했다(아래 근거). 짐작이 아니라 실측이다.

`add_card_modal_view.dart` 2965~2994행에 이미 확인창이 **두 개 연달아** 있다.

```
1) _showDuplicateFoundDialog (3183~3292행)

즉 **확인창 자체는 이미 있다.** 그런데 이게 globe2030님이 원하시는 것과

| 지금 있는 것 | globe2030님이 원하시는 것 |

| ① "기존 정보 유지" = **새 명함을 버린다**(등록 안 함) | "새로 추가" = **둘 다 남긴다** — 지금 이 선택지가 없다 |
| ② "새로 입력한 정보" 요약이 **이름·직함·회사 3칸만** 보여준다(3255행) | 무엇이 다른지 — **다른 칸 전부** |
| ③ 업데이트를 고르면 `_applyUpdateToExisting`이 **12개 넘는 칸을 전부 새 값으로 덮어쓴다**(3380~3431행). 직함이 OCR 오독이어도 그대로 덮인다 | 어느 값이 맞는지 **보고 고를 기회** |

**PM 보고서의 "묻지 않았다"는 아마 다른 빌드거나, 이 확인창을 보고도 무엇이
바뀌는지 몰라 그대로 "최신 정보로 업데이트"를 눌렀을 가능성이 크다** — ③번이

📌 **버튼 이름도 바꿔야 한다.** "기존 정보 유지"는 새 명함을 버리는

이름이 같은 결정을 반대로 가리키면 다음에 또 헷갈린다.

## 1. 확인창 — 무엇을 보여줄 것인가

### 1-1. 정보 구조 (위에서 아래로)

```
┌─────────────────────────────────────────┐

### 1-2. 다른 칸만 보여준다 — 3갈래로 나눠 표시

PM 지시대로 **같은 칸은 접거나 안 보여준다.** 이미 그렇게 만들려면 "다르다"를
한 가지로 뭉치면 안 된다 — 이번 사고(직함이 오독으로 덮임)와
"사무실 전화가 사라짐"은 **위험의 성격이 다르다.** 그래서 칸마다 아래 세
갈래로 나눠 표시한다.

| 갈래 | 조건 | 시각 처리 | 근거 |
|---|---|---|---|
| **다름(충돌)** | 기존값도 새값도 있는데 서로 다르다 | 두 값을 화살표로 나란히, 진하게 | 이번 사고(직함)가 이 갈래다 — 가장 눈에 띄어야 한다 |
| **사라짐(위험)** | 기존엔 있는데 새 명함엔 없다(빈칸) | 새 값 자리에 "⚠️ 새 명함엔 없음" | 이번 사고(사무실 전화)가 이 갈래 — **합치기를 누르면 없어질 수 있는 값**이라고 경고해야 한다 |
| **추가됨(안전)** | 기존엔 없는데 새 명함엔 있다 | 특별한 경고 없이 새 값만 표시 | 정보가 느는 쪽이라 위험하지 않다 |

**같은 값은 이 목록에 아예 안 넣는다**(PM 지시 "같은 칸은 접거나 안
보여준다" — 접는 것도 스크롤을 늘리므로 **아예 생략**을 골랐다. 접었다
펼치는 조작 자체가 연속 등록 중엔 방해다).

색은 **새로 만들지 않고 기존 토큰을 그대로 쓴다** — 정확히 이 파일 안에
이미 있는 패턴이다.

```
add_card_modal_view.dart 1602~1604행 (_scanFieldStatusChip)
  filled  → bg: AppColors.accentSoft   fg: AppColors.accentText
  !filled → bg: AppColors.warningSoft  fg: AppColors.warningText
```

→ **"사라짐(위험)" 칸에 그대로 재사용**: `warningSoft` 배경 + `warningText`
글자 + `Icons.error_outline`. 이미 이 화면에서 "OCR이 못 읽은 칸"에 쓰던
바로 그 시각 언어라 사용자가 이미 본 패턴이다(스캔 직후 칩 → 저장 직전
확인창까지 같은 경고색이 이어짐 = 일관성).
"추가됨"은 경고가 아니므로 칩 없이 `textPrimary`로 평범하게 쓴다. **초록색
계열 토큰이 이 앱에 없다**(`app_colors.dart` grep 결과, `channelSms`는 SMS
채널 전용 라임그린이라 재사용하면 의미가 섞인다) — 새 토큰을 만들지 말고
"위험하지 않음 = 무색"으로 표현한다.

### 1-3. 몇 칸을 비교하나 (PM이 "12칸"이라 부른 것)

`ContactModel`에서 **명함에 실제로 적힌 정보**만 추린다(시스템/이력 필드
제외):

```
이름 · 회사 · 직함 · 부서 · 휴대폰 · 사무실 전화 · 직통 전화 · 팩스 ·
이메일 · 웹사이트 · 주소 · 상세주소 · 우편번호        (13칸)
```

제외: `id`·`avatarUrl`·`geo`·`tags`·`groupIds`·`interests`·
`talkingPoints`·`commLogs`·`memo`·`cardImagePath`·`useCardAsAvatar`·
`isPriority`·`updatedAt` — 이건 "명함에 적힌 사실"이 아니라 앱이 관리하는
값이라 **비교 대상이 아니다**(태그·메모는 사용자가 이 화면에서도 고칠 수
있는 값이라 별개로 다뤄야 하고, 지금 확인창에 넣으면 12칸이 아니라
20칸에 육박해 PM이 경고한 "한 화면에 안 들어간다"가 그대로 난다).

📌 PM이 말한 숫자(12)와 정확히 안 맞을 수 있다(위 목록은 13개) — 정확한
칸 수보다 **"명함에 적힌 것만, 앱 내부 상태는 빼고"** 라는 기준이 중요하다.

### 1-4. 다른 칸이 하나도 없을 때

완전히 같은 정보를 다시 스캔한 경우(카드를 실수로 두 번 찍음)다. 이때는

- §1-1의 "다른 정보가 N곳" 블록 자체를 없앤다
- 대신 "완전히 같은 정보예요" 한 줄
- **버튼은 그대로 둘 다 보여준다** — 판단(§2)에서 이유를 설명하지만,
  미리 말하면: 이 경우엔 두 선택의 결과가 사실상 같아서(합쳐도 잃을
  정보가 없음) 사용자가 아무거나 눌러도 안전하다. 다만 "새로 추가"를
  누르면 **똑같은 명함이 두 장**이 되므로, 이 경우엔 "합치기"가 더
  이치에 맞다는 것을 문구로 살짝 안내한다: *"차이가 없어서 합쳐도 없어지는
  정보가 없어요."*

### 1-5. 스크롤 처리

칸이 많을 때(전화번호 3종 + 이메일 + 웹사이트 + 주소 2칸이 한꺼번에
바뀌는 경우, 예: 이직) 목록이 길어질 수 있다. `AlertDialog`의 `content`를
`ConstrainedBox(maxHeight: 화면 높이의 약 45%)` + `SingleChildScrollView`로
감싼다 — 이 파일에 이미 같은 필요가 있었는지는 못 봤지만, Flutter
`AlertDialog` 표준 패턴이라 새 개념을 들이는 게 아니다. 제목·근거·버튼은
스크롤 밖에 고정해 **버튼이 안 보이는 사고**(스크롤해야 버튼이 나오는
접근성 문제)를 막는다.

## 2. 버튼 — 합치기 / 새로 추가

### 2-1. 이름

| 기존 | 새 이름 | 의미 |
|---|---|---|
| "최신 정보로 업데이트" | **합치기** | 기존 한 장에 새 정보를 반영 |
| "기존 정보 유지" | **새로 추가** | 기존은 그대로 두고 새 명함을 별도로 저장 |

"기존 정보 유지"는 삭제한다 — 그 뜻(새 명함을 버림)이 globe2030님이 원한
어떤 선택지와도 안 맞는다. "새로 추가"가 그 자리를 대신하되 **동작은
정반대**(버림 → 남김)라는 걸 분명히 짚어 둔다. 코드 쪽에서 이 두 버튼의
반환값(`true`/`false`)을 그대로 뒤집어 재사용하면 조용히 의미가 바뀐
채로 넘어갈 위험이 있다 — f4 세션에 이 문서로 전달할 때 반드시 강조.

### 2-2. 어느 쪽이 기본(강조)인가 — 강조하지 않는다

이 파일 안에 이미 정확히 같은 종류의 결정이 두 번 있다(2377~2386행,
3268~3289행) — **둘 다 `TextButton` 두 개, 같은 굵기, 색만 다르다.**
`FilledButton`/`ElevatedButton`으로 어느 한쪽을 강조하지 않는다.

**근거**: 이 화면 안에 강조 버튼을 쓰는 다른 확인창(`_askKeepScanning`,
3159~3162행 "계속 찍기")은 **거의 항상 그게 맞는 선택**이라 강조가
정당했다(연속 등록 중이면 십중팔구 계속 찍는다). 그런데 **합치기 vs
새로 추가는 그렇지 않다** — 어느 쪽이 맞는지는 **매번 다르고 globe2030님만
안다**(직함이 오독이면 합치면 안 되고, 실제로 이직해서 회사가 바뀐 거면
합치는 게 맞다). 강조를 넣으면 그 판단을 앱이 대신 미는 꼴이라 위험한
방향으로 유도할 수 있다. **색으로만 구분**한다 — 합치기는 `accentText`
(파랑, 정보를 "쓰는" 동작), 새로 추가는 `textSecondary`(중립, 조용한
동작) — 기존 3282·3273행 색 배정을 그대로 이어받는다.

### 2-3. "취소" — 세 번째 버튼을 만들지 않는다

PM이 지적한 "갇히는 문제"는 실재한다 — `_showDuplicateFoundDialog`는
`barrierDismissible: false`라 **바깥을 눌러도 안 닫힌다.** 반드시 둘 중
하나를 눌러야 한다.

**그런데 세 번째 버튼(취소)을 추가하는 대신, 이 다이얼로그를
`barrierDismissible: true`로 바꾸고 뒤로가기/바깥 탭 = "돌아가서
확인하기"로 정의하는 쪽을 권한다.**

근거:
- 이미 이 파일의 **첫 번째** 중복 확인창(2367~2388행, `_findDuplicateContact`
  쪽)이 이 패턴이다 — barrierDismissible 기본값(true)이라 바깥을 누르면
  다이얼로그만 닫히고 **폼은 그대로 남는다**(2389~2396행 주석 — "시스템
  뒤로가기로 닫으면 폼이 유지되므로 고칠 길이 남아 있다"). 같은 파일 안에
  **이미 정답이 한 번 구현돼 있다.**
- 버튼을 셋으로 늘리면 PM이 우려한 "고르기 어려움"이 그대로 재현된다.
  다이얼로그를 닫는 것(바깥 탭)과 버튼을 누르는 것을 **다른 층**으로
  두면, 화면엔 버튼 둘만 보이면서도 "잠깐, 이 명함 다시 볼래" 같은
  이탈 경로가 생긴다.
- "돌아가서 확인하기"는 **입력 폼을 유지**한다(저장 안 됨, 새 명함도
  안 만들어짐) — 되돌릴 수 없는 동작이 하나도 없으므로 안전한 기본값이다.

⚠️ 지금 코드의 **두 번째** 확인창(3183행, 실제로 저장 직전 부르는 쪽)은
반대로 `barrierDismissible: false`다. **이 둘의 방식이 이미 서로 다르다**
— 이번에 새로 만드는 확인창은 **첫 번째 방식(dismissible: true)을
따른다.** (이 불일치 자체는 f4가 참고할 사항으로 별도 전달.)

## 3. 연속 등록 중의 방해 — 어떻게 줄일 것인가

### 3-1. PM이 제시한 세 갈래와 그 평가

| 갈래 | 문제 |
|---|---|
| A. 매번 묻는다 | 안전하지만, 100장 중 실제로 다른 사람에게 다시 명함을 받는(오늘 다시 만난) 경우가 아니면 대부분 "중복 아님"이라 애초에 안 뜬다 — **묻는 빈도 자체가 이미 낮다.** 이건 사실 큰 비용이 아닐 수 있다. |
| B. 확실한 것만 자동, 애매한 것만 묻는다 | 🚨 **이대로 채택하면 위험하다.** 아래 §3-2 |
| C. "이번 등록엔 항상 이렇게" 기억 | 🚨 **이대로 채택하면 위험하다.** 아래 §3-3 |

### 3-2. B를 문자 그대로 채택하면 안 되는 이유 — 이번 사고가 그 증거다

B는 보통 "매치 신뢰도가 높으면(휴대폰 번호 일치) 자동으로 처리한다"는
뜻으로 읽힌다. **그런데 이번 사고가 정확히 그 경우였다.**

```
안성률 사례 — findDuplicate가 어떻게 판정했나
  휴대폰 010-8611-2727 이 두 장에서 완전히 같다
  → DuplicateMatchField.mobile ("확실한" 매치, nameAndCompany가 아니다)
```

**"같은 사람이라는 확신"과 "새로 스캔한 값이 맞다는 확신"은 다른
질문이다.** 휴대폰 번호가 같아서 동일인이라는 건 거의 틀림없지만, 그
동일인의 **새로 읽은 직함이 OCR 오독인지 아닌지는 매치 신뢰도와 아무
상관이 없다.** B를 "매치가 확실하면 자동 처리"로 구현하면, **이번 사고를
그대로 재현하면서 심지어 물어보지도 않게 된다** — 지금보다 나빠진다.

### 3-3. C(세션 전체 기억)도 같은 이유로 위험하다

"이번 등록엔 항상 합치기"를 고르면, **그다음 90장 중 우연히 다른 이유로
중복 판정된 건**(진짜 동명이인, 실제로 이직해서 값이 다 바뀐 사람 등)에도
**같은 답이 묻지 않고 적용된다.** 각 충돌은 "이 특정 두 값 중 무엇이
맞는가"라는 **매번 다른 질문**이라, 한 번의 답이 다음 질문의 답을
보장하지 않는다. PM이 지적한 그대로("잘못 고르면 100장이 잘못된다")다.

### 3-4. 채택안 — "확실함"을 매치 신뢰도가 아니라 **차이 유무**로 다시 정의한다

**묻지 않아도 되는 경우를 "판정이 확실한 경우"가 아니라 "판단할 게 없는
경우"로 좁힌다.**

```
다른 칸이 하나도 없다(§1-4)
  → 묻지 않는다. 저장하지 않고(중복이니) 조용히 스킵 안내만 띄우고
    바로 다음 명함 촬영으로 넘어간다.
    ("○○○ 님 명함, 이미 있는 정보와 같아서 새로 저장하지 않았어요")
  → 안전한 이유: 합치기든 새로 추가든 결과가 사실상 같다(잃을 정보 없음).
    "물어볼 필요 자체가 없는" 유일한 경우다.

다른 칸이 하나라도 있다
  → 매치 신뢰도(휴대폰/이메일/이름+회사)와 무관하게 **항상 묻는다.**
    바로 이 경우가 "정보가 덮이거나 사라질 수 있는" 경우이고,
    이번 사고가 일어난 지점이다.
```

이렇게 하면 A(매번 묻는다)와 실질적으로 거의 같아 보일 수 있는데, 차이는
**"완전 동일 재스캔"** 케이스(카드를 두 번 찍음 — 100장을 찍다 보면
드물지 않게 일어난다)에서만 방해가 사라진다는 점이다. **그 외의 모든
충돌은 여전히 묻는다** — 이게 이번 문제의 핵심(자동으로 덮으면 위험하다)에
정면으로 답하는 방식이고, 속도를 위해 안전을 깎지 않는다.

📌 **"항상 이렇게 기억"은 이번 설계에서 제외를 권한다.** 대신 방해를
줄이는 다른 방법(§4에서 이어지는 "새로 추가 후 나중에 합치기")이 있다면
그쪽이 **더 안전하게 같은 목표**(속도)를 달성한다 — 지금 당장 옳고
그름을 판단하지 않고 일단 저장해 뒀다가, 촬영이 다 끝난 뒤 한 번에
정리하는 흐름이 가능하기 때문이다(§4).

## 4. "새로 추가" 뒤에 나중에 합칠 수 있는가

### 4-1. 확인 방법 — 무엇을 실행해서 "없다"를 확인했나

```bash
grep -rln "합치기\|병합\|merge" lib/
grep -n "합치기\|병합\|merge" lib/data/models/contact_model.dart lib/data/services/data_backup_service.dart
grep -rln "merge\|합치기\|병합" lib/presentation/features/wallet/
find lib -iname "*contact_detail*"
grep -n "PopupMenuItem\|더 보기\|메뉴\|삭제" lib/presentation/features/wallet/views/contact_detail_view.dart
```

**결과**: `merge`/`병합`이 코드에 나오는 곳은 전부 **다기기 데이터
동기화**(Firestore `SetOptions(merge: true)`, LWW 최신본 판정)용이지,
**사용자가 화면에서 두 명함을 골라 하나로 합치는 기능이 아니다.**
`contact_detail_view.dart`에도 그런 메뉴가 없다(위 grep에서 "삭제"조차
안 걸림). **실측 결론: 지금 앱에는 이미 저장된 두 명함을 나중에 합치는
기능이 없다.**

### 4-2. 그래서 이 확인창 문구가 반영해야 할 것

**"새로 추가"는 사실상 되돌릴 수 없는 선택이다** — 나중에 "역시 합쳐야
했다"고 판단해도 지금은 그럴 방법이 없다(직접 한쪽을 지우고 다시
입력하는 수동 작업 말고는 없다). 이걸 숨기면 globe2030님이 "일단 새로
추가해 두고 나중에 정리하지"라는, **지금은 성립하지 않는 전제**로
선택할 위험이 있다.

**권고**: "새로 추가" 버튼 자체에 경고 문구를 달면 매번 무겁다(100장
중 대부분은 중복이 아니라 이 다이얼로그 자체가 안 뜨므로, 뜬 김에도
너무 겁주면 안 된다). 대신 **"새로 추가"를 누르기 전에 한 번 더 확인하는
장치는 넣지 않고**(버튼을 셋으로 늘리는 것과 같은 문제), 확인창
본문 어딘가에 **작은 글씨로 한 줄** 둔다.

```
"새로 추가하면 두 명함이 따로 남고, 나중에 하나로 합치는 기능은
 아직 없어요."
```

이 한 줄은 §3-4의 자동 스킵(완전 동일 케이스)과도 맞물린다 — "일단 다
새로 추가해 두고 나중에 정리"라는 전략 자체가 지금은 안 통한다는 걸
알아야, globe2030님이 그 자리에서 바로 판단하실 수 있다.

📌 **후속 제안(이번 스코프 밖)**: "나중에 합치기" 기능이 생기면 이
확인창의 무게 자체가 줄어든다 — 지금 당장 확신이 없어도 일단 아무거나
고르고 나중에 고칠 수 있기 때문이다. PM에게 별도 backlog 항목으로
전달을 제안한다(번호는 PM이 배정).

## 5. 기존 흐름과의 접점 — PR #629("계속 찍기")와 만나는 지점

### 5-1. 지금 코드에 이미 있는 문제 — 합치기 경로가 "계속 찍기"를 건너뛴다

`_applyUpdateToExisting`(3342~3441행)을 끝까지 읽으면:

```
3433  context.read<WalletViewModel>().updateContact(updated);
3434  Navigator.pop(context);              ← 모달을 바로 닫는다
3435~3440  SnackBar(...)                    ← 스낵바만 띄우고 끝
```

**`_askKeepScanning`(3100행, "계속 찍을까요?")을 부르지 않는다.** 즉
지금 코드는 **중복이 아닌 새 명함**을 저장하면 "계속 찍을까요?"를
묻지만(3099~3102행), **중복이라 합쳐서 저장한 경우엔 안 묻고 바로
지갑 화면으로 내보낸다.** 오늘 병합된 PR #629가 고친 "저장할 때마다
흐름이 끊긴다" 문제가, **하필 이번에 다루는 그 갈래(중복 처리)에서는
아직 안 고쳐진 채** 남아 있다.

🚨 **100장을 연속으로 찍는 상황에서 중복이 하나라도 섞이면, 그 순간
연속 촬영이 강제로 끊긴다.** 이번 설계가 다루는 문제(연속 등록 방해)와
정확히 같은 결의 문제라 반드시 같이 짚어야 한다.

### 5-2. 이번 설계가 요구하는 것

**합치기든 새로 추가든, 저장이 끝나면 반드시 같은 자리(`_askKeepScanning`)로
합류해야 한다.** 그래야:

- "새로 추가"는 원래 흐름(2997~3121행)을 그대로 타면 되므로 자연히
  합류한다(중복이 아닌 것처럼 이어서 저장) — 새로 만들 코드가 적다.
- "합치기"는 `_applyUpdateToExisting` 끝에서 `Navigator.pop`으로 바로
  닫는 대신, 저장 완료 후 `_askKeepScanning`을 호출하고 **그 결과에 따라
  `_ContinueScanning()` 또는 `null`을 pop**해야 한다 — 지금 새 명함
  저장 경로(3098~3104행)와 같은 모양으로 맞춘다.

이건 "무엇을 보여줄까"가 아니라 "흐름을 어떻게 잇는가"의 문제라 f4
세션에 이 문서와 함께 반드시 전달돼야 한다(PM 경유).

### 5-3. 다이얼로그가 연달아 뜨는 순서 (사용자가 보는 순서)

```
[저장] 탭
  ↓
중복 있음? ── 아니오 → (주소 확인 등 기존 절차) → 저장 → 계속 찍기? → (다음 명함 or 지갑)
  │ 예
  ↓
① 이번에 설계한 확인창 (합치기 / 새로 추가)
  │
  ├─ 새로 추가 → 기존 "중복 아닌" 저장 절차 그대로 → 저장 → 계속 찍기? → ...
  │
  └─ 합치기 → (필드별 처리, f4 확정 예정) → 저장 → 계속 찍기? → ...
```

**한 번의 저장 시도에 확인창이 최대 2개**(①과 "계속 찍기") 뜬다 —
지금 "주소 없음" 확인창과 "중복" 확인창이 같은 저장 흐름에서 이미
최대 2개까지 겹치는 것과 같은 정도라 새로운 부담은 아니다(단, 주소
없음 + 중복이 동시에 걸리면 이론상 3개가 연달아 뜬다 — 이것도 이미
있는 상황이라 이번 설계로 새로 생기는 문제는 아니다).

## 6. 미결 — f4 세션 답을 기다리는 것

1. **"합치기"가 필드 단위로 정확히 무엇을 하는가** — 항상 새 값으로
   덮는지, 빈 칸만 채우는지, 다른 값은 어떻게 하는지. 이번 문서의
   diff 표시(§1-2)는 세 갈래 중 **"다름(충돌)" 칸을 합치기가 실제로
   어떻게 처리하는지**를 문구에 반영해야 완성된다(예: "합치기를 누르면
   화살표 오른쪽 값으로 바뀌어요" 같은 한 줄이 필요할 수 있다).
2. 기록 남기기(`_showKeepHistoryDialog`, 지금 있는 3번째 확인창)를
   이번 설계에 어떻게 편입할지 — 그대로 둘지, §1의 diff 확인창 안에
   체크박스 하나로 합칠지는 f4의 합치기 구현 방식에 달려 있다.
