## ⚠️ 개정 — 2026-08-28, globe2030님 직접 지시로 모델이 바뀌었다

**이 문서의 첫 판(같은 날 오전)은 "합치기 / 새로 추가" 두 버튼을 설계했다.
그 설계는 폐기한다.** globe2030님이 직접 준 방향이 다르다.

> **"같은 이름과 휴대폰이 있는 명함이 들어오면 새로운 명함으로 등록할지
> 묻고, 새로운 명함으로 한다면 그 전에거는 과거의 명함으로 남기는 거야"**
>
> **"한사람이 두 회사를 겸직해서 명함이 둘인 경우는 어느 명함을 표시명함으로
> 할지 결정하게 하면 된다"**

**왜 첫 판이 틀렸는지**: 첫 판의 "새로 추가"는 지갑에 **두 줄**을 만드는
선택지였다. 그런데 **지갑에 두 줄이 생기는 것 자체가 이번에 고치려던
"안성률 두 장" 사고의 원인**이다. 그 선택지를 확인창에 남겨 두면 사용자가
그걸 고르는 순간 같은 문제가 다시 난다. **없애는 게 맞다.**

### 새 모델

```
명함 지갑의 한 줄 = 한 사람
  그 사람 안에 명함이 여러 벌 있을 수 있다(지금 표시 중인 것 + 과거 것들)
  그중 정확히 하나가 "표시 명함"

이직  →  새 명함이 표시가 되고, 옛 명함은 "이 사람의 명함들"에 남는다(과거)
겸직  →  둘 다 지금 유효하다. 어느 걸 표시로 할지는 globe2030님이 고른다
```

**중요한 결과 하나**: 이 모델에서는 **아무것도 안 사라진다.** 첫 판에서
"사라짐(위험)"이라 부르던 것 — 새 명함에 없는 기존 값 — 은 이제 위험이
아니다. **과거 명함으로 그대로 남기 때문**이다. 이 사실이 이번 설계
전체의 톤을 바꾼다: 경고할 것이 아니라 "안전하게 넘어간다"는 걸 보여줄
것이 됐다.

이 문서는 아래 세 갈래로 나눠 다시 그린다(코디네이터 지시 그대로).

```
① 확인창                — 문구·갈래 재정리 (§2)
② 명함 여러 벌 저장 구조  — 지갑 목록·데이터 구조 요구사항 (§3)
③ 표시 명함 고르기        — 새로 생긴 화면 (§4)
```

## 1. 실물에서 확인한 것 — 첫 판에서 이미 확인한 것, 그대로 유효

이 절은 첫 판(§0)에서 코드를 실제로 읽고 확인한 내용이고, 모델이
바뀌어도 사실 자체는 그대로다 — **뭘 없애고 뭘 남길지 판단하는 근거로
계속 쓴다.**

### 1-1. 지금 코드에 확인창이 이미 3개 있다

```
add_card_modal_view.dart
  2358~2398행  1차: 전화번호만 보고 거르는 확인창("그래도 추가"/"취소")
  2965~2994행  2차: _showDuplicateFoundDialog
               ("이미 등록된 인맥입니다" — 기존 정보 유지 / 최신 정보로 업데이트)
  2981행       3차: _showKeepHistoryDialog
               (2차에서 "업데이트"를 골랐을 때만 — 기록으로 남기기 / 삭제)
```

**PM 지시서의 "묻지 않고 업데이트했다"는 짐작이고, 실측은 다르다** — 창은
이미 있다. 실제 문제는 3255행 근처에서 **이름·직함·회사 3칸만 보여주고**,
3380~3431행에서 **12칸 넘게 통째로 새 값으로 덮어쓴다**는 것이다. 그래서
사용자가 "확인하고 눌렀는데 왜 직함이 깨졌지"가 된다.

### 1-2. 새 모델에서 없애야 하는 것

```
❌ 1차 확인창(2358~2398행, "그래도 추가"/"취소")
   → 이것부터가 "두 번째 사람"을 만드는 창이다. 새 모델엔 있을 자리가 없다.
❌ 2차 확인창의 "기존 정보 유지" 개념
   → 이번엔 "그대로 두기"로 이름이 바뀌지만 뜻은 같다(새 명함 저장 안 함).
❌ "최신 정보로 업데이트"가 하던 필드별 덮어쓰기(3380~3431행)
   → 새 모델은 필드를 안 섞는다. 새 스캔을 통째로 새 "명함 벌"로 만들고,
     헌 것은 통째로 "과거"로 물러난다. §3에서 이어서 다룬다.
❔ 3차 확인창(_showKeepHistoryDialog, "기록으로 남기기"/"삭제")
   → 이 창이 하던 일(과거 값을 남길지)이 새 모델에서는 **항상 "남긴다"로
     고정**된다(모델 자체가 "과거 명함으로 남는다"이므로). 그래서 이 창은
     **필요 없어진다** — 고를 게 없다(늘 남기니까). f4 세션에 함께 전달.
```

## 2. ① 확인창 — 재설계

### 2-1. 문구·버튼 (globe2030님 말씀 그대로)

```
┌─────────────────────────────────────────┐
│  같은 분의 새 명함인가요?                  │  ← 제목. globe2030님 문구 그대로
├─────────────────────────────────────────┤
│ 휴대폰 번호가 같은 안성률 님의 명함이       │  ← 근거: 이름 + match.reason
│ 이미 있어요                               │    (기존 DuplicateMatch.reason 재사용)
│                                           │
│ 무엇이 바뀌는지 보여주는 목록(§2-2)         │
├─────────────────────────────────────────┤
│      [ 그대로 두기 ]   [ 새 명함으로 등록 ] │
└─────────────────────────────────────────┘
```

**이름 사용 근거**: "합치기"는 필드를 섞는다는 오해를 줄 수 있어 버렸다.
"새 명함으로 등록"은 globe2030님이 실제로 원하는 동작 — **새 스캔을
그대로 하나의 완결된 명함으로 저장하고, 그걸 표시로 삼는다** — 을 정확히
가리킨다. "그대로 두기"는 지금 표시 중인 명함을 안 바꾸고 이 스캔은
버린다는 뜻이라 첫 판의 "기존 정보 유지"와 동작은 같지만, **"유지"라는
말이 "이 스캔을 무시한다"는 뜻을 잘 안 담아서** globe2030님 표현을
그대로 썼다.

**식별 근거를 "이름·회사"에서 "이름"으로 좁혔다** — 첫 판은 "안성률 ·
모노얼라이언스(주)"처럼 회사까지 앵커로 보여줬는데, **겸직이면 회사가
다른 게 정상**이라 회사를 같다는 증거처럼 보여주면 오히려 헷갈린다.
globe2030님이 명시한 매칭 축("같은 이름과 휴대폰")에 맞춰 **이름 + 휴대폰
번호**만 근거로 보여준다.

### 2-2. 무엇을 보여줄 것인가 — 3갈래는 유지하되, 말과 색을 바꾼다

**셋으로 나누는 것 자체는 코디네이터 확인대로 그대로 좋다** — "무엇이
다른지 보여준다"는 목적은 안 바뀌었다. 바뀐 건 **아무것도 사라지지
않는다는 사실을 반영하는 것**이다.

| 첫 판 | 새 판 | 조건 | 시각 처리 |
|---|---|---|---|
| 다름(충돌) | **바뀜** | 기존값도 새값도 있는데 다르다 | 화살표로 나란히, 굵게. 여전히 가장 중요 — "이게 정말 맞는 정보인가"를 판단하는 자리 |
| 사라짐(⚠️위험) | **과거 명함에 남아요** | 기존엔 있는데 새 스캔엔 없다 | ⚠️ 경고 아이콘·경고색(`warningSoft`/`warningText`) **제거**. 대신 `textMuted`로 "과거 명함에서 계속 볼 수 있어요" — 잃는 게 아니라 옮겨갈 뿐이므로 |
| 추가됨(안전) | **새 정보** | 기존엔 없는데 새 스캔엔 있다 | 그대로 `textPrimary`, 특별한 색 없음 |

**"바뀜" 갈래가 여전히 이 확인창의 핵심이다** — 안성률 사례(직함이
OCR 오독으로 깨짐)가 정확히 이 갈래였고, 아무것도 안 사라지는 모델이
돼도 **"틀린 값이 새 표시 명함이 되는 것"은 여전히 막아야 할 일**이다.
그래서 여기만 눈에 띄게 남긴다(굵게 + 화살표), 나머지 둘은 정보성으로
낮춘다.

색 토큰은 첫 판과 같은 이유로 새로 만들지 않는다 — 다만 **"과거 명함에
남아요"에는 이제 경고색을 안 쓴다**(더 이상 위험이 아니므로). 이 화면
1602~1604행의 `accentSoft`/`warningSoft` 칩은 "새 정보"에만(있음=
accentSoft 톤) 쓰거나, 아예 칩 없이 텍스트만으로 충분하다 — 파괴적
결과가 없어진 만큼 시각적 경고도 줄이는 게 **"과잉 경고로 다음 사고를
못 보게 만드는 것"**을 막는다(이번 항목이 정말 위험한 "바뀜"과, 안 위험한
"과거 보존"이 같은 색이면 사용자가 어느 게 진짜 봐야 할 것인지 다시
못 가리게 된다).

### 2-3. 비교 대상 칸·완전 동일 처리·스크롤 — 첫 판 그대로 유지

내용이 안 바뀌는 부분은 재작성하지 않고 첫 판 결론을 그대로 가져온다.

- **비교 칸(13개)**: 이름·회사·직함·부서·휴대폰·사무실 전화·직통 전화·
  팩스·이메일·웹사이트·주소·상세주소·우편번호. 명함에 실제로 적히는
  정보만 — 태그·메모·그룹·통신 이력 등 "사람 단위" 값은 제외(§3-1에서
  이 구분이 왜 구조적으로도 중요한지 다룬다).
- **완전히 같으면**: "바뀜/과거/신규" 목록 자체를 없애고 "완전히 같은
  정보예요" 한 줄. 이때는 새로 저장할 이유가 아예 없으므로 §5(연속
  등록)에서 **묻지 않고 건너뛴다**(첫 판 §3-4와 동일 결론, 이 모델에서도
  안 바뀐다 — 다른 게 없으면 새 명함을 만들 이유도 없다).
- **스크롤**: `AlertDialog` content를 화면 높이 45% 정도로 제한 +
  `SingleChildScrollView`. 버튼은 스크롤 밖 고정.

### 2-4. 버튼 강조 — 재검토했지만 결론은 같다

새 모델에서는 "새 명함으로 등록"이 데이터를 **파괴하지 않는다**(과거가
남으므로). 그래서 "혹시 이제는 강조해도 되지 않나" 다시 따져봤는데,
**여전히 강조하지 않는 쪽을 권한다.**

**근거**: 파괴 위험은 없어졌지만 **"틀린 정보가 표시 명함이 되는" 위험은
그대로**다(§2-2 "바뀜" 갈래). "새 명함으로 등록"을 강조하면, 직함이
OCR로 깨진 이번 사례에서도 사용자가 강조된 버튼을 반사적으로 누를
유인이 생긴다 — **위험이 "데이터 소실"에서 "잘못된 표시"로 바뀌었을
뿐 사라지지 않았다.** 두 버튼 모두 `TextButton`, 같은 굵기, 색만
구분(새 명함으로 등록=`accentText`, 그대로 두기=`textSecondary`) —
2377·3268행 기존 패턴과 동일하게 유지한다.

### 2-5. 취소 — 첫 판과 동일 결론

세 번째 버튼을 만들지 않는다. `barrierDismissible: true`로 두고 바깥
탭/뒤로가기 = "그대로 두기도 새 명함으로 등록도 아니고, 그냥 폼으로
돌아가서 입력을 더 고칠 기회"로 정의한다. 이 파일 2367~2396행에 이미
있는 패턴(다만 그 확인창 자체는 §1-2에서 없애기로 한 1차 창이다 —
**패턴만 가져오고 그 창은 없앤다**는 뜻).

## 3. ② 명함 여러 벌 저장 구조

### 3-1. 어느 값이 "사람" 단위이고 어느 값이 "명함 한 벌" 단위인가

**이건 화면보다 먼저 정해야 화면을 그릴 수 있다.** 지금 `ContactModel`은
사람과 명함을 구분하지 않고 한 덩어리다. 여러 벌을 갖게 하려면 최소한
개념적으로라도 이 구분이 필요하다 — **이건 데이터 구조 문제라 내가
결정할 일은 아니지만, 화면이 요구하는 최소 조건은 밝혀 둔다**(f4/개발
담당에게 전달할 것).

```
명함 한 벌 단위(스캔할 때마다 다를 수 있는 값)
  이름 · 회사 · 직함 · 부서 · 휴대폰 · 사무실 전화 · 직통 전화 · 팩스 ·
  이메일 · 웹사이트 · 주소 · 상세주소 · 우편번호 · (스캔 이미지·스캔 날짜)
  → §2-3의 "13칸"과 정확히 같다. 우연이 아니라 "명함에 적힌 것"의 정의가
    같아야 하기 때문이다.

사람 단위(명함이 여러 벌이어도 하나만 있는 값)
  아바타(프로필 사진) · 태그 · 관심사 · 그룹 소속 · 소통 이력(commLogs) ·
  AI 대화 포인트(talkingPoints) · 사용자가 쓴 메모 · 우선순위(isPriority)
  → 겸직이어도 통화 기록·태그·메모는 "그 사람"의 것이지 "그 회사 명함"의
    것이 아니다. 표시 명함을 바꿔도 이 값들은 그대로 있어야 한다.
```

**제안(구조 결정은 아니고 화면이 성립하려면 필요한 최소 조건)**: 표시
중인 명함 벌의 13칸 값을 지금처럼 `ContactModel`의 최상위 필드가 그대로
비추게 하고(그래야 지갑 목록·상세 화면 등 지금 이 필드를 직접 읽는
코드가 안 깨진다), 그 옆에 "이 사람의 명함들" 구조화된 목록을 별도로
둔다. 지금처럼 메모에 문자열 한 줄로 욱여넣는 방식(`CardHistoryNote`)은
**이 화면(③ 표시 고르기)이 요구하는 "칸별로 보여주고 다시 고를 수 있게"를
구조적으로 못 한다** — `card_history_note.dart` 17~28행 자체가 "칸을
되살릴 방법이 없다"고 명시하고 있다(문자열이라 빈 칸이 통째로 빠지고
구분자가 겹치면 어긋난다). **이번 기능은 문자열 파싱이 아니라 진짜
목록(칸이 나뉜 구조)이 필요하다** — 이 문서가 다루는 화면들의 전제 조건.

### 3-2. 지갑 목록 행 — 명함이 여러 벌인 사람 표시

`wallet_view.dart` 840~970행의 지금 행 구조(아바타 → 이름/직함/회사 →
날짜/동작 버튼)는 **그대로 둔다.** 표시 중인 명함 벌의 값을 지금과
똑같이 보여주면 되므로 대부분의 사람(명함 1벌)은 화면이 하나도 안
바뀐다.

**명함이 2벌 이상일 때만** 아주 작은 표식 하나를 더한다 — 이미 918~924행에
같은 자리에 "그룹 꼬리표(최대 2개+n뱃지)"가 조건부로 들어가는 자리가
있다. 그 옆 또는 그 아래 줄에 작은 뱃지 하나를 더한다.

```
안성률
본부장 | S
모노얼라이언스(주)                    [🗂 명함 2]   ← 명함이 2벌 이상일 때만
```

- 스타일: `borderSubtle` 테두리 + `textMuted` 글자, `borderRadius: 999`
  (알약형) — 그룹 태그와 같은 급의 존재감(둘 다 "부가 정보"이지 "긴급한
  것"이 아니므로 `warningSoft`/`accent` 같은 강한 색은 안 쓴다).
- 탭하면 상세 화면으로 이동(지금과 동일 — 행 전체가 이미 탭 대상)해서
  §3-3의 "이 사람의 명함들" 섹션으로 스크롤. 뱃지 자체를 별도 탭 대상으로
  만들지 않는다(작은 뱃지를 정확히 누르게 하는 건 손가락 크기 대비 너무
  작다 — 이 앱은 걸으면서 한 손으로 쓴다는 원칙, CLAUDE.md/역할 지침).

### 3-3. 상세 화면 — "이 사람의 명함들" 섹션 (읽기 전용 부분)

`contact_detail_view.dart` 335~359행의 `_historyRows`/`_historyTile`을
대체한다. **이름부터 바꾼다** — "이전 명함"은 겸직(둘 다 지금 유효)에는
안 맞는 말이다. 코디네이터 지시대로 **"이 사람의 명함들"**로 통일한다.

```
이 사람의 명함들 (2)                         ← "N건"이 아니라 "(N)" — "건"은
                                               사건처럼 들려 다시 표현을 낮췄다
┌───────────────────────────────────────┐
│ ✓ 표시 중                                │  ← 지금 표시되는 벌에만 이 칩
│ 모노얼라이언스(주) · mono. alliance       │
│ 2026.08.28 등록                          │
├───────────────────────────────────────┤
│ 모노얼라이언스(주) · 본부장 | S           │
│ 2026.08.20 등록                          │
│                              [이걸로 표시]│  ← 표시 중이 아닌 벌에만 이 버튼
└───────────────────────────────────────┘
```

- **정렬은 최신순**(등록일 내림차순)이 기본 — 겸직이라도 "최근에 스캔한
  것이 위"가 자연스럽다. 표시 칩은 **위치가 아니라 별도 표식**이므로
  맨 위가 아닌 벌이 표시 중이어도(사용자가 일부러 옛 벌을 표시로
  고른 경우) 헷갈리지 않는다.
- **접었다 펴는 조작(첫 판이 참고한 지금 코드의 `_historyTile` 방식,
  "접혀 있다가 누르면 펼쳐진다")은 유지한다** — 13칸을 항상 다 펼치면
  겸직인 사람은 상세 화면이 아주 길어진다. 접힌 상태에서는 회사·직함·
  등록일만, 펼치면 13칸 전부.
- **각 벌은 실제로 스캔된 이미지가 있으면 작은 썸네일**도 같이 보여줄
  것을 제안한다(구현된 명함 이미지 보기 경로 재사용, `_ZoomableCardAvatar`
  참고 165~176행) — 두 회사 명함을 문자·숫자만으로 구분하기보다 실물
  이미지가 있으면 훨씬 빠르게 알아본다. 다만 이미지가 로컬 전용이라
  다른 기기에서는 안 보일 수 있다는 것도 같이 문서화(카드 이미지 자체의
  기존 제약, 99행 주석 "로컬 전용(서버 백업 안 함)"과 동일 제약이 그대로
  적용된다).

### 3-4. 새 벌 추가 시 표시 포인터 기본값

"새 명함으로 등록"을 누르면:

- 새로 스캔한 벌이 **기본으로 표시**가 된다(이직 케이스의 기본 기대와
  맞음 — 보통 최근 정보가 맞다).
- 예외(겸직이라 옛 걸 계속 표시하고 싶은 경우)는 **저장 시점에 묻지
  않는다** — §5에서 다루듯 저장 흐름 중 판단거리를 늘리지 않기 위해서다.
  대신 저장 직후 상세 화면(③, §4)에서 언제든 바꿀 수 있다. **"저장할 때
  한 번에 다 정해야 한다"는 압박을 없애는 게 목적** — 잘못 골라도
  되돌릴 수 있다는 것 자체가 이번 사고(되돌릴 방법이 없어서 문제였던 것)와
  결이 다른 안전장치다.

## 4. ③ 표시 명함 고르기 — 새로 생긴 화면

### 4-1. 어디에 있나 — 별도 화면이 아니라 §3-3의 연장

**새 풀스크린 화면을 만들 필요는 없다고 본다.** §3-3에서 그린 "이 사람의
명함들" 섹션 안의 `[이걸로 표시]` 버튼이 곧 이 기능이다 — 이유:

- 벌의 개수가 많지 않다(겸직이라 해도 보통 2~3벌). 별도 화면으로
  분리하면 이동이 하나 늘 뿐 정보가 더 필요해지지 않는다.
- 이미 상세 화면이 그 사람의 "모든 것을 한 곳에서 보는" 자리라는 게
  이 앱의 기존 구조(연락처·그룹·이력이 전부 한 시트 안에 접혀 있음,
  100~146행)와도 맞는다.

### 4-2. 인터랙션 — 즉시 반영, 확인창 없음

`[이걸로 표시]`를 누르면:

1. 그 자리에서 바로 표시 포인터를 바꾼다(추가 확인창 없음).
2. 상세 화면 맨 위 헤더(152~205행, 이름·직함·부서·회사 줄)가 그 벌의
   값으로 즉시 다시 그려진다.
3. 아주 짧은 스낵바로 확인만: `"표시 명함을 바꿨어요"`.

**확인창을 안 두는 근거**: 이 동작은 **되돌릴 수 있다**(다른 벌을
다시 눌러 표시를 되돌리면 그만) — §2 확인창이 신중해야 했던 이유
("돌이킬 수 없다")가 여기엔 없다. 매번 확인창을 두면 겸직인 사람의
상세 화면을 열 때마다 방해가 되는데, 그럴 만한 위험이 없다.

### 4-3. 벌 하나를 지울 수 있는가 — 이번 설계 범위 밖, 다만 짚어 둔다

PM 지시에는 "지운다"는 말이 없었다. **이 문서는 지우는 기능을 설계하지
않는다.** 다만 겸직이 아니라 실수로 두 번 스캔한 경우(§2-3 "완전히
같음")는 애초에 새 벌이 안 만들어지므로 지울 필요가 없다. **실수로
다른 사람 명함을 잘못 스캔해 엉뚱한 벌이 붙은 경우**(예: OCR이 완전히
다른 회사 정보를 잘못 매칭)는 이 설계로 못 없앤다 — 필요하면 별도
backlog 항목으로 제안한다(번호는 PM 배정).

### 4-4. "이 사람의 명함들" 개수가 지갑 필터·검색에 영향을 주는가

영향받는 화면(명함 개수 표시, 내보내기(vCard), AI 프롬프트 등)이
있는지는 확인하지 않았다 — **범위 밖이라 실행하지 않았다.** 데이터
구조가 정해지면(§3-1) 이런 화면들이 "표시 벌만" 보는지 "전체 13칸 ×
벌 개수"까지 보는지 다시 확인이 필요하다는 것만 남겨 둔다.

## 5. 연속 등록 중의 방해 — 결론은 그대로, 표현만 정리

첫 판 §3의 분석(코디네이터 지시 B·C 갈래가 왜 위험한지)은 모델이
바뀌어도 그대로 유효하다 — **매치 신뢰도(휴대폰 번호 일치)가 높다고
새 값이 정확하다는 뜻은 아니다**(안성률 사례가 증거), 그리고 **세션
전체 "항상 이렇게" 기억은 매번 다른 질문에 같은 답을 강제한다.** 두
갈래 다 기각 유지.

채택안도 그대로: **"다른 칸이 하나도 없을 때만" 묻지 않고 건너뛴다,
그 외엔 항상 묻는다.** 다만 이 모델에서는 근거가 하나 더 늘었다 —
완전히 같은 스캔은 새 벌을 만들 이유 자체가 없으므로(과거로 남길
"다른 정보"가 없다), 굳이 확인창을 띄우는 게 아니라 **애초에 새 벌을
안 만드는 게 맞는 동작**이다. 조용히 건너뛰고 안내만 한 줄:

```
"○○○ 님 명함, 이미 있는 정보와 같아서 새로 저장하지 않았어요"
```

## 6. "나중에 합치기" — 새 모델에서는 이 질문 자체가 사라진다

첫 판 §4는 "새로 추가를 고른 뒤 나중에 합칠 수 있는가"를 다뤘고, 지금도
사실 확인(merge 기능 없음)은 유효하지만 **새 모델에서는 이 질문이 안
생긴다** —애초에 "따로 저장"이라는 선택지가 없어졌기 때문이다.

대신 **"표시를 잘못 골랐을 때 되돌릴 수 있는가"**가 그 자리를 대신하는
질문이고, §4-2에서 다뤘듯 **된다**(다른 벌을 다시 누르면 그만). 첫
판이 우려했던 "되돌릴 수 없는 선택"이라는 위험 자체가 새 모델에서는
구조적으로 없다 — 이게 이번 방향 전환의 실질적 이득이다.

첫 판 §5-1에서 찾은 문제는 이 모델에서도 똑같이 적용된다: **지금
`_applyUpdateToExisting`은 저장 후 `_askKeepScanning`("계속 찍을까요?")을

전달할 것.

## 8. 미결 · f4에 전달할 것

1. **데이터 구조**: §3-1의 "명함 벌 목록 + 표시 포인터" 구조를 실제로
   어떻게 저장할지(로컬 저장소 스키마, 서버 백업 포맷, 마이그레이션 —
   지금 이미 메모에 쌓인 `CardHistoryNote` 기존 사용자 데이터를 어떻게
   새 구조로 옮길지 포함)는 이 문서 범위 밖이다. **다만 그 구조가
   §3-1의 "사람 단위 vs 명함 벌 단위" 구분과 §3-3이 요구하는 "칸별로
   보여주고 다시 표시로 고를 수 있음"을 만족해야 이 화면들이 성립한다.**
2. **매칭 축**: globe2030님 문구는 "같은 이름과 휴대폰"이라 지금
   `findDuplicate`의 이메일 단독 매치·이름+회사(전화 없을 때) 매치와
   범위가 다르게 들릴 수 있다 — 매칭 규칙 자체를 바꿀지는 f4가 결정할
   영역이라 이 문서는 손대지 않았고, `match.reason` 문구를 그대로
   재사용하는 것으로 설계했다(§2-1).
3. **3차 확인창(기록으로 남기기/삭제) 제거**가 맞는지 f4 확인 필요
   (§1-2) — 새 모델에서는 "항상 남긴다"로 고정되므로 물을 게 없어
   보이지만, 만약 "과거 명함을 지우는" 별도 동작이 여전히 필요하다면
   (§4-3의 backlog 후보와 연결) 이 창의 역할이 그쪽으로 옮겨갈 수 있다.

확인창 없이 즉시 반영 + 스낵바 — 되돌릴 수 있는 동작이라 매번 물을
필요가 없다고 판단했다(§4-2).
