## 1. 지금 실물 (2026-09-05 실측)

**무엇으로 쟀나**: `firestore.rules` 의 `match` 블록을 직접 훑었다(= 실제로 존재하는 경로).

```
users/{uid}
  encryptionKeyB64          암호화 키
  profile {encrypted}       내 프로필
  groups {encrypted}        그룹
  약관·광고·사진개선 동의      법적 증빙
  aiUsage · 사진 한도
  phoneVerifiedAt · phoneHash
  ├── contacts/{id}         {encrypted, schemaVersion}   ← 명함
  ├── deletedContacts/{id}  삭제 표식(tombstone)
  └── commLogs/{id}         연락 기록

phoneAccounts/{번호해시} → {uid, verifiedAt}
```

⚠️ **`grep` 이 못 보는 것**: 코드가 만들지만 rules 에 `match` 가 없는 경로는 안 걸린다.
다만 이 프로젝트는 rules 가 촘촘해 그런 경로가 있으면 **쓰기가 막힌다** — 그래서
이 경우엔 rules 를 실물로 읽어도 된다.

## 2. 🚨 DB 설계 — 갈림길을 가른 것은 **「번호만 바뀜」**이었다

### 2-1. 버린 안 — `phoneAccounts` 를 그대로 「사람」으로 쓴다

가장 싸 보인다. 이미 있는 문서이고, 번호해시가 사람을 가리킨다.

```
phoneAccounts/{번호해시} → { uids: [...] }      ← 문서 id 가 번호해시
```

🚨 **그런데 「번호만 바뀜」에서 무너진다.**

```
번호가 바뀌면 → 번호해시가 바뀌면 → 문서 id 가 바뀐다
             → 「사람」의 정체성이 바뀐다 → 명함첩 경로가 통째로 바뀐다
```

📌 **globe2030님이 물으신 두 번째 경우가 정확히 이 안을 배제한다.** 번호로 사람을
식별하는 것과 **번호를 사람의 이름으로 쓰는 것**은 다르다.

### 2-2. ✅ 채택 — 「사람」에게 **불변 id** 를 준다

```
people/{personId}                    ← 새 컬렉션. personId 는 영원히 안 바뀐다
  uids        ["abc123", "kakao:99"]  이 사람의 계정들
  phoneHash   "…"                     지금 번호 (색인과 짝을 이룬다)
  phoneChangedAt
  createdAt

phoneAccounts/{번호해시} → { personId, verifiedAt }
                            ↑ uid 가 아니라 personId 를 담는다
                            번호 변경 = 이 문서를 옮기는 것뿐이다

users/{uid}
  personId  "p_xxx"        ← 역참조 한 줄만 더한다. 나머지는 그대로
  encryptionKeyB64         ← 그대로. 키링이 여기서 키를 모은다
```

⭐ **번호가 바뀌어도 `personId` 는 그대로다** — 명함첩이 움직이지 않는다.
⭐ **`users/{uid}` 는 거의 안 건드린다** — 한 줄만 더한다.

### 2-3. ⬜ 아직 안 정한 것 — 명함첩을 **어디에 둘 것인가**

`personId` 를 만드는 데까지는 정해졌는데, **명함이 실제로 어느 경로에 앉을지**는
갈래가 둘이다. **globe2030님 판단이 필요하다.**

#### 갈래 ㉮ — 그대로 두고 **읽을 때 합친다**

```
users/abc123/contacts     그대로
users/kakao:99/contacts   그대로
                          → 앱이 people 의 uids 를 보고 양쪽에서 읽어 합친다
                          → 쓰기는 지금 로그인한 uid 아래에
```

| | |
|---|---|
| ⭐ | **이전이 0이다.** 아무것도 안 옮긴다 |
| ⭐ | 계정 하나가 탈퇴해도 나머지는 산다 |
| ⭐ | 어제 만든 **키링과 모양이 같다** — 키링은 「여러 키로 읽는다」, 이건 「여러 경로에서 읽는다」 |
| ⚠️ | 읽기가 uid 수만큼 늘어난다(실제로는 2~3개) |
| 🚨 | **rules 가 무거워진다** — 남의 uid 밑을 읽어야 하므로 `get(people/…)` 로 같은 사람인지 매번 확인해야 한다 |

#### 갈래 ㉯ — `people/{personId}/contacts` 로 **옮긴다**

```
people/p_xxx/contacts/{id}     명함이 사람 밑에 하나로 모인다
users/{uid}                    키·동의·사용량만 남는다
```

| | |
|---|---|
| ⭐ | **rules 가 단순해진다** — 「이 사람의 구성원인가」 하나로 끝난다 |
| ⭐ | 읽기가 한 경로다 |
| ⭐ | 「명함첩의 주인은 사람」이라는 방침(결정 ①)이 **구조에 그대로 드러난다** |
| ⚠️ | 이전이 필요하다 |

#### ✅ 결정 — ㉯ (2026-09-05 globe2030님)

**기준은 비용이 아니라 안정성·확장성이었다**(globe2030님: *"비용보다 설계의
안정성과 확장성에 기준을 두면"*).

⚠️ **처음 이 문서가 든 근거는 그중 가장 약한 것이었다** — *"지금은 이전 비용이
0"*. 기준을 옮기니 **㉯가 더 뚜렷하게 맞았다.** 근거를 아래로 바꿔 적는다.

##### 🚨 ㉮의 진짜 문제는 비용이 아니라 **천장**이다

```
㉮ 에서 「명함첩을 최신순 20장씩」을 어떻게 하나
   uid 3개 → 컬렉션 3개에서 각각 읽는다 → 합쳐서 정렬한다
   🚨 Firestore 커서는 컬렉션을 가로지르지 못한다 → 페이징하려면 전부 가져와야 한다
```

**느려지는 문제가 아니라 그 방식으로는 안 되는 문제다.**

⭐ **그리고 ㉮를 끝까지 밀면 ㉯가 된다.** 컬렉션 그룹 질의로 풀려면 **모든 명함에
`personId` 를 박아야** 하는데, 그 순간 「명함은 사람의 것」을 **절반만 구현한
꼴**이 된다.

##### rules 도 확장성 문제다 — 숫자를 확인했다

**공식 문서 확인(2026-09-05)**: 보안 규칙은 **단일 문서 요청당 문서 접근
호출(`get()`·`exists()`) 10회**로 제한되고, **그 호출 하나하나가 읽기로
과금**된다.

```
㉮   남의 uid 밑을 읽으므로 매번 get() 으로 「같은 사람인가」 확인
     → 10회 제한을 소모하고, 규칙이 복잡해진다
㉯   「이 사람의 구성원인가」 하나
```

📌 **이 저장소는 rules 복잡도로 이미 대가를 치렀다** — ADMIN-VULN-001(허용목록이
두 곳), `firestore.rules:237`(감사 기록을 건너뛸 수 있음). **단순한 규칙이 안전한
규칙이다.**

##### ⚠️ 그래도 ㉮ 편을 드는 논거가 하나 있다 — 숨기지 않는다

```
㉮   「사람」 매핑이 깨져도 → 자기 계정 명함은 보인다   (부분적으로 살아남는다)
㉯   「사람」 매핑이 깨지면 → 명함첩을 통째로 못 찾는다  🚨 단일 실패점
```

**막는 방법은 이미 안다.** `users/{uid}.personId` 역참조를 두면 **자기 문서 한 번
읽기**로 사람을 찾는다. 그리고 **#820 에서 세운 원칙을 그대로 쓴다** — 못 읽었을
때 그것을 「없다」로 다루지 않고, **덮어쓰지 않고**, 화면이 말한다. 암호화 키가
이미 같은 성격의 단일 실패점이었고 그때 답을 냈다.

##### ⭐ 고른 진짜 이유

```
검색 · 정렬 · 페이징    한 컬렉션이라 그냥 된다
내보내기 · 통계         합치는 코드를 매번 다시 안 쓴다
로그인 수단 추가        명함첩이 안 움직인다
계정 하나 탈퇴          명함은 사람 밑에 남는다   ← 방침과 정확히 같다
```

> **㉯를 고르는 이유는 「지금 싸서」가 아니라 「구조가 방침과 같아서」다.**
> ㉮ 는 *"명함첩의 주인은 사람"*(결정 ①)을 **말로만 두고 구조는 계정 소유로
> 남긴다.**

⚠️ **되돌릴 수 있는 선택이다**(uid 와 달리) — 틀려도 A안처럼 치명적이지 않다.

### 2-3-2. 관리자 DB 와의 관계 — **따로 가되 한 군데서 만난다**

같은 날 관리자 인증 설계도 진행 중이라
([`관리자-인증-강화와-명함-조회-설계-2026-09-05.md`](./관리자-인증-강화와-명함-조회-설계-2026-09-05.md)),
**두 DB 설계가 겹치는지**를 먼저 가른다.

```
사람 레이어(이 문서)   people/{personId} · phoneAccounts · users/{uid}.personId
관리자(그 문서)        adminSessions/{uid} · config/admins · 조회 기록

→ 컬렉션이 하나도 안 겹친다. 따로 진행해도 된다
```

⭐ **관리자 권한은 「사람」이 아니라 「계정」에 붙는다.** 관리자도 이용자로서
`personId` 를 갖겠지만, **관리자냐 아니냐는 이메일로 판별한다**(`isAdmin()`).
🚨 **사람 단위로 하면 안 된다** — 관리자가 로그인 수단을 하나 더 붙이는 순간
**그 계정까지 관리자가 된다.** 권한은 좁은 쪽에 붙인다.

#### 🚨 그런데 딱 한 군데서 만난다 — **관리자 명함 조회**

```
관리자 설계 3단계   "명함 복호화 조회 Callable"  ← 명함을 읽는다
이 문서 ㉯          명함이 users/{uid}/contacts → people/{personId}/contacts 로 옮겨간다
```

**관리자 조회는 「명함이 어디 있는지」를 알아야 만들 수 있다.** 순서가 어긋나면
**두 번 만들게 된다.**

```
✅ 이 문서 1·2단계(경로 함수 + people 신설)  →  관리자 3단계(조회)
❌ 관리자 3단계  →  경로가 바뀜  →  조회를 다시 만든다
```

📌 **관리자 설계의 1·2단계(인증·세션·잠금)는 명함을 안 읽으므로 지금 병행해도
된다.** 막히는 것은 **3단계 하나**다.

⭐ **그리고 그 순서는 원래 지켜야 하는 것이기도 하다** — 관리자 설계가
*"3단계를 1·2단계보다 먼저 하지 않는다"* 고 이미 못 박아 두었다. **두 이유가 같은
방향을 가리킨다.**

⚠️ **조회 기록에는 `personId` 를 남긴다** — uid 를 남기면 같은 사람의 계정이
여럿일 때 **누구 자료를 봤는지가 흩어진다.** 감사 기록이 흩어지면 감사가 안 된다.

### 2-3-3. 🚨 명함 파싱 원본이 지금 버려지고 있다

globe2030님 지적(2026-09-05): *"명함 파싱 역시 DB로 관리되어야 나중에 추가
분석된 파싱 자료를 업데이트할 수 있을 텐데."*

**실측(2026-09-05)**: 맞다. **원본이 안 남는다.**

```
OcrScanResult.rawText          있다  (ocr_scanner_service.dart:152)
  ↓
_scannedRawText                있다  (add_card_modal_view.dart:1133)
  ↓ 🚨 화면에 보여 주기만 한다 (2567·2584·3935·4075행)
ContactModel                   없다  ← 필드 자체가 없다
  ↓
저장                            원본은 여기서 사라진다
```

⭐ **코드가 이미 이 문제를 알고 있었다** — `ocr_scanner_service.dart:52` 주석:

> *"파서를 고쳐도 **다시 재려면 스캔을 다시 돌려야** 하는데, 좌표가 결과에 안
> 남으면 재스캔을 해도 좌표 규칙을 검증할 수 없다."*

**일괄 스캔 TSV(추가 317)에는 남기는데 이용자 명함에는 안 남긴다.** 평가용
경로에만 있고 실제 데이터에는 없다.

#### ⭐ 핵심은 **OCR 과 파싱이 다른 단계**라는 것이다

```
① OCR    이미지 → 텍스트     ML Kit. 기기에서 돈다. 비싸다
② 파싱    텍스트 → 필드      우리 코드. 싸다. 🚨 고치는 것은 거의 항상 이쪽이다
```

```
원본 텍스트가 없으면   파서를 고쳐도 옛 명함은 그대로다
                      다시 하려면 사진을 내려받아 ①부터 다시 — 수백 MB, 기기에서
원본 텍스트가 있으면   ②만 다시 돌린다 — 사진이 필요 없다
```

📌 **사진은 서버에 있다**(방침 §533). 그래서 재OCR 이 불가능하진 않다. 다만
**ML Kit 은 기기에서 돌므로** 사진을 전부 내려받아 기기에서 다시 돌려야 한다.
**원본 텍스트를 남기면 그 전체가 필요 없어진다.**

#### 담을 것과 둘 곳

```
people/{personId}/cardSources/{cardId}     ← 명함 본문과 나란히, 따로
  encrypted        rawText · rawLines · rawLineBoxes(좌표)   🚨 개인정보 원문이다
  parserVersion    이 값으로 파싱했다
  scannedAt
  schemaVersion
```

⚠️ **명함 본문과 같은 문서에 넣지 않는다.** 평소 명함첩을 열 때마다 **안 쓰는
원본이 함께 딸려온다** — 읽기 비용과 속도를 그냥 버리는 것이다. 원본은
**파서를 고쳤을 때만** 읽는다.

⭐ **`parserVersion` 이 있어야 「무엇을 다시 돌려야 하나」를 알 수 있다.** 없으면
전부 다시 돌리거나, 아무것도 못 돌린다.

🚨 **rawText 는 명함 주인의 개인정보 원문 그대로다** — 이름·전화·주소가 통째로
들어 있다. **반드시 같은 방식으로 암호화한다**(키링이 그대로 적용된다). 그리고
**방침의 수집 항목에 이 보관을 적어야 한다** — 새로 저장하는 것이 늘기 때문이다.

⬜ **크기를 못 쟀다** — 표본(TSV)이 저장소 밖(`connection-sense-assets`)에 있어
이 세션에서 접근할 수 없다. **명함 한 장의 `rawText` 가 몇 바이트인지 재기
전에는 「가볍다」고 쓰지 않는다.** 좌표(`rawLineBoxes`)까지 담으면 텍스트보다
커질 수 있다 — 좌표를 넣을지 말지는 **재고 나서** 정한다.

### 2-3-4. 어떤 DB 를 쓸 것인가 — **Firestore 를 유지한다**

globe2030님 질문(2026-09-05): *"DB 는 어떤 것을 써야 효과적인지 추천해."*

#### 결론: 바꾸지 않는다

| 왜 | |
|---|---|
| ⭐ | **오프라인 동기화가 내장이다** — 이 앱은 명함을 지하철·행사장에서 등록한다. 직접 만들면 그것만으로 큰 기능이다 |
| ⭐ | Auth · Rules · Functions · Storage 가 **한 몸**이다. DB 만 떼어 낼 수 없다 |
| ⭐ | 기기 간 동기화가 이미 돌고 있다 |
| ⚠️ | 바꾸는 비용이 막대하고 **얻는 것이 불명확하다** |

#### ⚠️ Firestore 가 약한 자리 — 정직하게

```
① 전문 검색       🚨 아예 안 된다. 「이름에 '김'이 들어간 명함」이 안 된다
② 집계·통계       약하다
③ 배치 재처리     안 맞는다 — 재파싱이 정확히 이것이다
```

**①은 지금도 문제일 수 있다** — 명함이 늘면 검색이 필요해진다. 그런데 **지금
당장 DB 를 바꿀 이유는 아니다**: 명함첩은 **한 사람 것이라 작아서**(수백~수천 장)
기기에서 전부 읽어 검색해도 된다. 🚨 **이건 계산이다 — 실제 장수 분포를 아직
안 쟀다.**

#### 📌 필요해지면 「바꾸는」 것이 아니라 「옆에 붙이는」 것이다

```
검색이 필요해지면    Algolia · Typesense 같은 검색 색인을 옆에 붙인다
통계가 필요해지면    BigQuery 내보내기 (Firestore 가 공식 지원, Blaze 필요)
재파싱             Cloud Functions 배치 — cardSources 를 읽어 파싱만 다시
```

⭐ **셋 다 Firestore 를 그대로 두고 붙이는 것들이다.** *"DB 를 바꿔야 하나"* 로
읽히는 문제들이 대부분 **이 방식으로 풀린다.**

🚨 **다만 검색 색인은 개인정보를 외부로 내보내는 것이다** — 명함 주인은 우리
서비스에 가입한 적이 없는 제3자다. **붙이려면 방침 개정과 위탁·국외이전 고지가
먼저다.** 기술 선택이 아니라 **법무 결정**이다.

### 2-4. 🚨 함께 가는 것 — 키링이 여기서 완성된다

`people/{personId}.uids` 가 정해지면 **어제 만든 키링(#826)이 바로 동작한다.**

```
knownKeysFor(uid)
  → people 에서 이 사람의 uids 를 읽는다
  → 각 users/{uid}.encryptionKeyB64 를 모은다
  → 키 목록을 돌려준다        ← 리포지토리는 한 줄도 안 고친다
```

⭐ **이것이 「자리를 미리 냈다」의 값이 실현되는 지점이다.**

🚨 **그리고 여기가 가장 위험한 한 줄이다** — `uids` 에 남의 uid 를 넣는 순간
**그 사람의 명함이 열린다.** §4·§5의 판정이 전부 이 한 줄로 수렴한다.

## 3. 번호 변경 — 계획안 둘 (globe2030님 ②)

**지금 없다**(2026-09-05 실측 — 설정 어디에도 번호 변경이 없다). 그런데 **없으면
「번호 = 사람」이 조용히 깨진다**: 번호를 바꾼 사람의 옛 번호가 `phoneAccounts` 에
그대로 남고, 통신사가 그 번호를 재배정하면 **새 주인이 남의 명함첩에 닿는다.**

### 갑안 — 이용자가 직접 바꾼다

```
설정 → 휴대폰 번호 변경 → 새 번호 입력 → 문자 인증 → 색인 문서를 옮긴다
```

| | |
|---|---|
| ⭐ | **빠르다.** 번호 변경은 흔하다(기기 변경·번호 이동) |
| ⭐ | **문자 인증이 이미 소유를 증명한다** — 남의 번호를 자기 것으로 붙일 수 없다 |
| ⭐ | 관리자가 계정 이전 권한을 **상시로 갖지 않아도 된다** |
| 🚨 | 새 번호가 **이미 다른 사람에게 붙어 있으면** 혼자 못 푼다 |

### 을안 — 관리자에게 요청해서 관리자가 바꾼다

| | |
|---|---|
| ⭐ | 예외 상황을 사람이 판단한다 |
| 🚨 | **느리다** — 흔한 일에 사람이 붙는다 |
| 🚨 | **관리자가 「남의 명함첩 주인을 바꾸는」 권한을 상시로 갖게 된다.** 관리자 인증 설계에서 가장 무거운 권한이 된다 |
| 🚨 | **본인 확인을 무엇으로 하나** — 1:1 문의 글은 이미 로그인한 사람이 쓰는 것이라 「번호가 바뀌어 못 들어오는 사람」에게는 쓸 수 없다 |

### ⭐ 권고 — **갑안이 기본, 을안은 막힌 경우만**

```
평소            갑안. 문자 인증으로 본인이 바꾼다
막혔을 때만      을안. 「새 번호가 이미 남에게 붙어 있다」 그 한 경우
```

📌 **을안을 기본으로 두면 안 되는 이유**: ① 흔한 일에 사람이 붙고 ② **관리자
권한이 상시로 무거워지고** ③ 정작 을안이 정말 필요한 사람(번호가 바뀌어 로그인
자체를 못 하는 사람)은 **문의를 넣을 길이 없다.**

⚠️ **갑안에도 반드시 붙어야 하는 것 셋**

```
① 옛 번호 색인을 지운다      안 지우면 재활용된 번호의 새 주인이 내 계정에 닿는다
② 옛 번호로는 다시 못 들어온다  바꾼 순간부터
③ 바꾼 사실을 기록한다        phoneChangedAt — 분쟁 때 필요하다
```

⬜ **을안의 본인 확인 절차는 안 정했다** — 법무 확인이 필요할 수 있다.

## 4. 계정만 바뀜 — 안내하고 유도한다 (globe2030님 ③)

지금은 `phoneAccounts` 의 uid 가 다르면 **`taken` 으로 막기만 한다**
(`functions/src/index.ts:2867` 실측). globe2030님 지시는 **막지 말고 알려 주라**는 것이다.

### 화면에 보여 줄 것

```
이미 이 번호로 만든 계정이 있습니다

    카카오로 가입     ki****@kakao.com
    명함 53장

  ▸ 그 계정으로 로그인하기            ← 권하는 쪽
  ▸ 새 계정으로 계속하기              ← 막지 않는다
```

📌 **명함 장수를 적는 이유**(globe2030님 지시): *"데이터가 있습니다"* 로는 **무엇을
잃는지 가늠할 수 없다.** 53장이라고 적어야 사람이 판단한다. 이것은 [추가 676]이
「이전 계정 데이터」 행에서 이미 쓴 원칙과 같다.

📌 **마스킹은 `maskEmail` 을 재사용한다**(`lib/core/utils/masked_email.dart`).
그 파일이 이미 정한 원칙 둘이 여기에도 그대로 맞다 — **도메인은 남긴다**(어느
계정인지 알아볼 실마리), **별표 개수는 고정**(길이를 드러내지 않는다).

### 🚨 이 화면은 개인정보를 보여 준다 — 문을 먼저 잠근다

```
✅ 문자 인증을 통과한 뒤에만 보여 준다
   → 번호 소유를 증명한 사람에게 「자기 정보」를 보여 주는 것이 된다

❌ 번호만 입력하면 보여 준다
   → 🚨 아무 번호나 넣어 「이 번호 주인은 카카오를 쓰고 명함이 53장」을 캐낼 수 있다
```

⚠️ **그래도 구멍이 하나 남는다 — 번호 재활용.** 재배정된 번호의 새 주인이 문자
인증을 통과하면 **이전 주인의 계정 정보를 본다.** 그래서 §6의 「오래」 값이
**여기에도 걸린다**: 오래된 계정이면 **장수와 마스킹을 안 보여 주고**
*"이 번호로 만든 오래된 계정이 있습니다. 본인 것이 맞다면 문의해 주세요"* 로만
말한다.

### 새 계정으로 계속하기를 골랐다면

```
그때 「사람」을 새로 만든다 (personId 신규)
🚨 옛 계정의 uid 를 새 사람의 uids 에 넣지 않는다 — 넣으면 명함이 열린다
📌 phoneAccounts 색인은 새 사람을 가리키게 옮긴다
⚠️ 옛 계정은 지우지 않는다 — 그 사람이 옛 로그인 수단으로 다시 들어갈 수 있어야 한다
```

⚠️ **[추가 675]의 30일 삭제 예약과 부딪히는 자리다.** 그 서비스는 *"uid 가 다르면
남남"* 을 전제로 이전 계정 사진을 30일 뒤에 지운다. **잇기가 켜지면 이어 놓은
계정의 사진이 조용히 사라진다** — `runDue` 의 `currentUid` 가 그때는 **「같은
사람의 uid 집합」**이 되어야 한다. 그 서비스 주석에 이미 적혀 있다.

## 5. 둘 다 바뀜 — 새 사람 (globe2030님 ④)

```
번호도 계정도 다르다 → 🚨 우리가 같은 사람인지 알 방법이 없다 → 새 사람
```

⭐ **세 안(A·B·C)이 여기서는 똑같다.** 이것은 구현의 한계가 아니라 **사실의
한계**다 — 이을 근거가 없다.

⚠️ **화면이 이 사실을 말해 줘야 한다.** 안 그러면 이용자는 *"명함이 사라졌다"* 로
읽는다. 옛 명함첩에 닿는 길은 **옛 로그인 수단** 하나뿐이고, 그것을 알려 줘야 한다.

📌 **그러므로 「로그인 수단을 잊지 않게 하는 것」이 기능이 된다** — 설정 어딘가에
*"지금 ○○로 로그인해 계셨습니다"* 가 보여야 한다.

## 7. 단계

```
1단계  명함첩 경로를 함수 하나로 감싼다        21곳 → 한 군데. 동작 무변화
2단계  people 컬렉션 + phoneAccounts 를 personId 로
3단계  knownKeysFor 가 사람의 키들을 돌려준다   ← 키링이 여기서 완성된다
4단계  번호 변경(갑안) + 옛 색인 삭제
5단계  계정 안내 화면 (마스킹 · 장수 · 유도)
6단계  30일 삭제 예약과의 충돌 해소            runDue 의 currentUid → uid 집합
7단계  cardSources — 파싱 원본을 남긴다         §2-3-3. 🚨 지금부터 등록되는 명함만 남는다
```

🚨 **7단계는 늦출수록 손해가 쌓인다.** 원본은 **저장하는 시점에만** 남길 수 있고,
안 남긴 명함은 **영영 못 되살린다**(사진에서 재OCR 하는 무거운 길밖에 없다).
⭐ **순서상 뒤지만 「지금부터라도」의 값이 가장 큰 항목이다** — 다른 단계와 달리
**미루면 데이터가 사라진다.**

⭐ **1단계는 어느 갈래(㉮·㉯)를 골라도 안 버려진다** — §2-3 결정을 기다리지 않고
지금 시작할 수 있다.

🚨 **3단계 전에 §6의 「오래」가 정해져야 한다** — 키를 키링에 더하는 것이 곧
잇기이고, 잇지 말아야 할 계정을 이으면 **남의 명함이 열린다.**
