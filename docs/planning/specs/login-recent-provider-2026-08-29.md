## 1. 무엇을 보여주나

**제공자만.** 구글·애플·카카오·네이버 중 지난번에 로그인에 성공한 수단
하나를 로그인 화면에서 그 버튼 옆에 옅게 표시한다.

```
❌ 이메일 주소를 보여주지 않는다
❌ 가입일을 보여주지 않는다
❌ 마스킹도 하지 않는다 — 애초에 표시 대상이 아니다
✅ "구글로 계속하기" 버튼에만 작은 「최근」 표식
```

**왜 이메일을 안 보여주나**: 로그인 화면은 **인증 전** 화면이다. 추가 532의
원칙(*"어느 계정인지 말하지 않는다 — 남의 가입 여부를 알아낼 수 있다"*)이
여기서는 그대로 살아 있다. 같은 날 추가 583(이중등록 화면)이 이 원칙을
완화한 것은 **휴대폰 인증을 통과한 뒤**라 조건이 다르기 때문이다 — 584는
인증 전이므로 완화 근거가 없다. 이 구분을 지울 경우 남의 기기를 잠깐 빌린
사람이 "최근 로그인 이메일"을 보고 앞사람의 계정 존재 여부(적어도 "이
기기로 누군가 로그인한 적 있다")를 알게 되는데, **제공자만 보여주면 그
정보량이 없어진다** — 이 앱은 SNS 로그인만 있어 "구글로 로그인한 사람이
있었다"는 사실 자체는 이미 앱을 쓰는 누구에게나 참이라 새로운 정보가
아니다.

## 2. 왜 필요한가

SNS 넷(구글·애플·카카오·네이버)에 이메일까지 다섯 개 로그인 수단이 있으면,
**같은 사람이 다음에 다른 것을 누른다.** 이 앱 눈에는 로그인 수단이 다르면
남남이 되므로(uid가 제공자마다 다름, 추가 557), 그 실수가 곧 "새 계정이
하나 더 생기는" 사고로 이어진다. 2026-08-28 하루에 이 뿌리에서 결함이 세
건 났다(추가 555·556·567 — 계정 전환 「유지」를 잘못 고르거나 다른 수단으로
다시 들어와 명함이 새는 사고).

**「최근」 한 줄은 누르기 전에 그 실수를 막는다** — 화면을 보고 "아, 저번에
이걸로 했지"를 떠올리게 하는 것이 목적이다. 강제하지 않는다(다른 버튼을
못 누르게 막지 않는다) — 겸직·개인 계정 분리 등 의도적으로 다른 수단을
쓰는 경우도 있다.

## 3. 시각 처리 — 옅게, 강조하지 않게

globe2030님 확정: *"옅게(강조하지 않게) 표시해야 한다. 강조하면 다른
수단을 고르기 어려워 보인다."*

```
┌─────────────────────────────────────┐
│  🔵  Google로 계속하기      [최근]    │  ← 알약형 배지, textMuted 톤
└─────────────────────────────────────┘
   카카오로 계속하기
┌─────────────────────────────────────┐
│  N  네이버로 계속하기                 │
└─────────────────────────────────────┘
```

- 배지 스타일: `duplicate-confirm-dialog-2026-08-28.md` §3-2가 쓴 것과
  같은 급의 "부가 정보" 처리를 따른다 — `borderSubtle` 테두리 +
  `textMuted` 글자, `borderRadius: 999`(알약형). 강한 색(`accent`,
  `warningSoft`)을 쓰지 않는다.
- 위치: 버튼 안쪽 오른쪽 끝(카카오·네이버는 공식 버튼 이미지를 통째로
  쓰므로 이미지 위에 겹치지 않도록 **버튼 바깥, 오른쪽 위에 살짝 겹치는
  형태**로 둔다 — 공식 버튼 규정이 "버튼 위에 다른 요소를 얹지 말 것"을
  요구할 수 있어, 카카오·네이버는 버튼 자체가 아니라 그 버튼을 감싸는
  `Stack`의 여백에 배지를 그린다).
- 애니메이션 없음, 탭 대상 아님(배지 자체를 누를 수 있게 만들지 않는다 —
  버튼 전체가 이미 탭 대상이다).
- 다국어 문구가 아직 없다(i18n은 프로젝트 마지막 단계 — CLAUDE.md).
  지금은 한국어 고정 문자열 `"최근"`.

## 4. 데이터 — 언제 쓰고, 언제 지우고, 어디에 두나

### 4-1. 저장 위치 — 새 값, 기존 세션 키와 분리

지금 `AuthRepository`의 `_sessionKey`(`auth_session_v1`, `flutter_secure_storage`)는
**로그아웃하면 통째로 지워진다**(`signOut()`이 `_secureStorage.delete`를
호출 — 실측 확인). 로그아웃 뒤에도 "최근 로그인 수단"을 보여주려면 **이
값과 분리된 새 저장소**가 필요하다.

```
새 키: last_login_provider_v1
저장소: shared_preferences (일반 키 — 값이 provider.name 하나뿐이라
        개인정보가 아니다. flutter_secure_storage를 쓸 이유가 없다)
값: SnsAuthProvider.name (예: "google") 문자열 하나
```

### 4-2. 쓰는 시점

각 로그인 수단이 **성공**했을 때(기존 `_persist()`가 세션을 저장하는 것과
같은 지점들 — `signInWithGoogle`, `signInWithApple`,
`signInWithSocial`(카카오·네이버) 성공 직후). 게스트 로그인(`signInAsGuest`,
QA 전용·release 빌드엔 없음)은 대상에서 제외한다 — 실제 SNS 수단이 아니라
"최근"으로 보여줄 의미가 없다.

### 4-3. 지우는 시점

```
✅ 로그아웃(signOut)       — 지우지 않는다. 이 값이 살아남아야 다음 로그인
                            화면에서 「최근」을 보여줄 수 있다(존재 이유).
🚨 계정 삭제(deleteAccount) — 지운다. 그 계정 자체가 없어졌으므로 "최근"으로
                            안내하면 이용자를 없어진 계정으로 유도하는
                            꼴이 된다.
```

### 4-4. 읽는 시점

앱 시작 시 `AuthRepository._load()`와 별개로(그 함수는 활성 세션만 읽는다)
`LoginView`가 열릴 때 한 번 읽는다. `AuthRepository`에
`SnsAuthProvider? get lastProvider`를 추가하고, 생성자에서 세션과 함께
비동기로 로드해 두면 `LoginView`가 별도 `FutureBuilder` 없이 바로 쓸 수
있다(패턴은 기존 `_load()`와 동일하게 `notifyListeners()`로 갱신).

## 6. 검증 — 이번 항목은 부분 테스트로 충분하다

CLAUDE.md 3절 표 기준: 로직 분기(로그인 성공 시 기록)와 화면(배지 표시)이
섞여 있지만, **저장·복원·마이그레이션·탈퇴 자체를 바꾸는 변경이 아니다**
(기존 로그인/로그아웃/탈퇴 흐름 위에 얹는 부가 표시일 뿐, 실패해도 로그인
자체는 그대로 동작한다) — 그래서 전체 테스트(실기기) 대상은 아니라고
판단한다. **자동 테스트**(위 4가지 케이스) + **부분 테스트**(로그인
화면에서 배지가 실제로 옅게 보이는지, 다른 버튼이 안 가려지는지)로
충분하다.

⚠️ **실기기 부분 테스트는 이번 작업에서 못 했다** — 폴드·아이폰 둘 다
다른 세션(4a·b4)이 점유 중이라 PM(사용자)에게 기기 배정을 먼저 물어야
한다. 지금까지 확인한 것은 **자동 테스트뿐**이다(계산이 아니라 자동
테스트로 확인했다는 뜻이며, 실기기 실측은 별도로 필요).
