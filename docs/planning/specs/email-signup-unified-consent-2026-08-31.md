## 1. 확정된 흐름

```
로그인 화면
  [카카오] [네이버] [구글] [Apple]
  ───── 또는 ─────
  [이메일로 시작하기]              ← 신설
        │ 어느 버튼을 눌러도 (탭한 provider를 기억해 둔다)
        ▼
  ⑨ 시작하기 전에 (SignupConsentView) — provider를 알고 그린다
        │ 「동의하고 시작하기」
        ▼
  동의를 **메모리에** 쥔다(_LoginViewState 레벨, 아직 아무 데도 안 씀)
        │
        ├─ 소셜  → OAuth 수행
        │           ├─ 성공 → uid 확보 → 쥐고 있던 동의를 이제 적용
        │           └─ 취소/실패 → 로그인 화면으로 돌아옴, **동의는 그대로 쥔 채**
        │                          (다른 버튼을 눌러도 ⑨를 다시 안 띄운다)
        └─ 이메일 → ⑧ 이메일·비밀번호 (EmailSignupView)
                      ├─ 성공(로그인 또는 신규가입) → uid 확보 → 동의 적용
                      └─ 실패(비밀번호 오류·이미 가입된 다른 수단 등)
                                     → ⑧에 남아 재시도, **동의는 그대로 쥔 채**
        ▼ (성공 공통)
  번호 확인(PhoneVerifyView) — 기존 그대로, 코드 변경 없음
```

⚠️ **소셜 버튼 하나당 provider를 하나 기억한다.** 예: 카카오를 눌러 ⑨를
통과한 뒤 카카오 OAuth가 실패해서 로그인 화면으로 돌아왔는데, 이번엔
구글을 누르면? → **같은 동의를 그대로 쓴다.** 동의 화면(⑨)은 이메일 채널
노출 여부(`adEmailChannelAvailable`)가 provider마다 다르므로(네이버만
이메일 항목이 빠짐), **이론적으로는 다시 그려야 정확하다.** 하지만
globe2030님이 승인한 "을"안의 취지(*"화면이 살아 있는 동안 들고 있는다"*)가
재입력 마찰을 줄이는 것이므로, 아래처럼 좁혀서 처리한다.

```
쥐고 있던 동의가 있는데 다른 provider를 누른 경우
  → 이메일 채널을 원래 안 보여줬던 경우(예: 네이버로 시작 → 취소 →
    카카오로 재시도)라면 문제 없음(더 보여줄 채널이 생기는 방향)
  → 반대로 이메일 채널을 보여줬는데(예: 구글) 다음에 네이버를 누르면
    "이메일 항목에 체크했던 값"이 네이버에는 쓸 수 없는 채널이 된다
  → 적용 시점(§4)에서 provider별로 다시 걸러낸다 — adEmailChannelAvailable이
    false면 email 값을 무조건 false로 내려서 저장한다. 화면을 다시
    그리지 않고 **적용 단계에서 한 번 더 필터링**하는 것으로 충분하다
    (globe2030님 재확인 불필요 — 기술적으로 닫히는 문제)
```

## 2. 갑을병 판단 — 동의를 어디서 저장하나 (3차 왕복 답변 반영)

**채택: 을) 화면이 살아 있는 동안(= `_LoginViewState`가 살아 있는 동안)
메모리로 들고 있는다. 저장은 계정이 실제로 만들어진 시점에.**

```
❌ 갑(버리고 다시 받는다)   재시도가 흔한 경로(OAuth 취소·비밀번호 오타)인데
                          매번 다시 동의 화면을 보여주면 마찰이 크다
❌ 병(서버에 먼저 저장)     uid가 없어 누구의 동의인지 적을 수 없다. 계정이
                          안 만들어지면 주인 없는 동의 기록이 남는다
✅ 을(화면 생존 동안 보유)  이 저장소에 이미 같은 패턴이 있다
                          (`briefing_overlay_view.dart`의 `_consentedSelection`)
```

🚨 **동의 시각은 체크한 시각이 아니라 계정이 실제로 만들어진 시각으로
적는다.** 다행히 **추가로 손댈 것이 없다** — `AdConsentService.save()`가
이미 호출 시점에 `FieldValue.serverTimestamp()`를 쓴다(클라이언트 시각을
안 보낸다). 그러므로 **"저장 호출을 uid가 생긴 뒤에만 하는 것"** 하나만
지키면 시각은 자동으로 맞다. 화면(⑨)에서 체크한 시각을 어딘가에 따로
적어 두지 않는다 — 적으면 그 값을 실수로 쓸 위험만 생긴다.

## 3. 병합 판단 — 기존 광고 동의 화면·만 14세 체크를 지금 옮기나

**채택: 얕은 병합(shallow merge).** 화면은 하나로 합치되, **저장·게이팅
로직은 기존 서비스별 규칙을 그대로 유지**한다.

### 왜 완전 병합이 안 되는가

⑨는 **uid를 모르는 시점(OAuth/이메일 생성 전)에 뜬다.** 그런데
`AdConsentService.shouldAsk(uid)`(이미 답한 계정에게는 다시 안 묻는다)는
**uid가 있어야 판단할 수 있다.** 완전 병합(⑨가 저장까지 직접 한다)을 하면
아래 사고가 난다.

```
기존에 이미 「거부」로 답한 계정이, 새 기기에서 로그인 화면을 다시 보게
되면(세션이 없어져서) → ⑨를 또 보고 → 기본값(꺼짐)으로 다시 저장
→ 서버 기록은 원래 "거부"라 값 자체는 안 바뀌지만, **화면이 매번
다시 물어보는 것 자체가 "2년마다 재확인"과 다른, 원치 않는 재확인
루프**가 된다. 더 나쁜 경우: 이미 "동의"였던 계정이 재로그인 때
아무 것도 안 고르고 넘어가면 **자기도 모르게 광고 동의가 조용히
꺼진 것처럼 저장될 위험**이 생긴다
```

### 그래서 이렇게 가른다

| 항목 | ⑨에서 하는 일 | 실제 저장 시점 |
|---|---|---|
| 만 14세·이용약관·개인정보처리방침(필수 3종) | 체크해야 「동의하고 시작하기」가 눌린다 | **서버에 저장하지 않는다** — 아래 §3-1 근거 |
| 광고성 정보 수신(선택 1종) | 이메일/앱 알림 토글을 **provider에 맞게** 보여준다 | uid가 생긴 뒤 **`AdConsentService`가 판단**(§4) — 이미 답한 계정이면 화면에서 고른 값을 버리고 기존 값을 지킨다 |

### §3-1. 왜 필수 3종은 새로 저장하지 않는가

광고 동의만 정보통신망법 §50이 **2년마다 재확인**을 요구한다(추가 457).
만 14세 확인·약관 고지는 그런 주기 요건이 없는 **1회성 게이트**다. 지금도
(변경 전) 서버에 저장하지 않고 로그인 화면마다 다시 체크받는 방식이라 —
⑨로 옮겨도 **그 성격이 바뀌지 않는다.** 새 필드를 만들면 `firestore.rules`
(`clientWritableUserFields`)·개인정보처리방침을 함께 고쳐야 하는데, 지금
얻는 것(감사 추적)에 비해 범위가 커진다. **필요해지면 별도 backlog 항목으로
다시 연다** — 이번 스펙 범위 밖으로 명시적으로 뺀다.

### §3-2. 기존 스탠드얼론 광고 동의 화면(`ad_consent_view.dart`)은?

**지우지 않는다.** `auth_gate.dart`의 `_maybeAskAdConsent`(로그인 뒤,
번호 확인 뒤에 도는 안전망)를 **그대로 둔다.** 이유:

```
이미 로그인 상태로 남아 있는 이용자(세션이 사실상 무기한, 추가 456)는
앞으로도 LoginView를 다시 볼 일이 없다 → ⑨를 절대 못 본다
→ 이 사람들에게 광고 동의를 물을 수 있는 유일한 경로가
  `_maybeAskAdConsent`(로그인 상태에서 uid 기준으로 shouldAsk 판정)다
→ 지우면 "이미 로그인된 채 아직 답 안 한 사람"에게 영원히 못 묻는다
```

즉 **⑨는 "새로 로그인 화면을 보는 사람"(신규 가입 + 로그아웃 후 재로그인)
전용 입구**이고, `_maybeAskAdConsent`는 **"이미 로그인돼 있는데 아직 안
답한 사람"을 위한 기존 안전망**이다. 둘 다 결국 `AdConsentService.save()`
하나로 수렴하고, 그 함수의 `shouldAsk`/`firstAnswer` 판정이 겹쳐 물어도
안전하게 걸러 준다(§4) — **두 벌이 서로를 깨지 않는다.**

## 4. 광고 동의 적용 로직 — `AdConsentService`에 메서드 하나 추가

```dart
/// ⑨에서 미리 골라 둔 값을, 계정이 실제로 만들어진 뒤 적용한다.
///
/// 이미 답한 계정이면 **화면에서 고른 값을 버리고 아무것도 하지 않는다** —
/// 재로그인한 기존 이용자가 무심코 다시 지나간 ⑨가 예전 답을 덮으면 안
/// 되기 때문이다(자세한 이유: email-signup-unified-consent-2026-08-31.md §3).
///
/// [emailChannelAvailable]은 호출 시점의 provider 기준으로 넘긴다 —
/// [adEmailChannelAvailable]과 같은 판정을 두 번 하지 않기 위해서다.
Future<void> applyFreshSignupChoice({
  required String uid,
  required bool email,
  required bool push,
  required bool emailChannelAvailable,
}) async {
  final state = await fetch(uid);
  if (state == null || state.answered) return; // 모르거나 이미 답했다 — 손대지 않는다
  await save(
    uid: uid,
    email: email && emailChannelAvailable,
    push: push,
    firstAnswer: true,
  );
}
```

- `state == null`(읽기 실패)일 때도 저장하지 않는다 — 기존 `shouldAsk`와
  같은 보수적 판단(모르면 안 건드린다).
- `LoginView`는 이 메서드를 **`unawaited()`로, `mounted` 가드 없이** 부른다.
  로그인 성공 직후 `AuthGate`가 위젯 트리를 통째로 갈아 끼우므로(§6),
  `mounted`를 확인하면 이 호출이 취소될 수 있다 — `_storeAppleRefreshTokenOnServer`
  (auth_repository.dart:437)가 이미 같은 이유로 같은 패턴을 쓰고 있다.

🚨 **일괄 체크("필수 항목에 모두 동의")는 선택 항목(광고)을 켜지 않는다.**

따로 눌러야 켜진다(추가 457, 방통위·KISA 안내서).

⚠️ **광고 선택 UI는 새로 그리지 말고 `ad_consent_view.dart`의
`_ChannelRow`/`_Box`/`_OptionalBadge`류 위젯을 공유 위젯으로 뽑아 재사용할
것.** 두 화면이 따로 그리면 어긋나고, 어긋나면 한쪽이 법 요건을 잃는다는
것이 이 저장소가 이미 여러 번 확인한 실패 패턴이다(추가 631의 "병안을 버린
이유"와 같은 논리). 구체적으로: `ad_consent_view.dart`에서
`_OptionalBadge`·`_ConsentCard`·`_ChannelRow`·`_RowDivider`·`_Box`를
`lib/presentation/features/auth/widgets/consent_widgets.dart`로 빼서 두
화면이 같이 쓴다(리팩터링, 동작 변경 없음).

### 5-2. `EmailSignupView`(⑧, 신설) — `lib/presentation/features/auth/views/email_signup_view.dart`

이메일 + 비밀번호 + 비밀번호 확인 세 칸. **로그인/가입을 가르는 화면을
따로 만들지 않는다** — "계속하기"를 누르면:

```
1. signInWithEmailAndPassword 시도
   성공 → 기존 계정으로 로그인 완료
   'user-not-found' → 2로
   'wrong-password'/'invalid-credential' → "비밀번호가 올바르지 않습니다.
        다시 시도하거나 [비밀번호 재설정](⑩)" 표시, 재시도
   그 외 오류 → 일반 오류 문구
2. createUserWithEmailAndPassword 시도(신규 가입)
   성공 → 신규 계정 생성 완료, sendEmailVerification() 비동기 발송(실패 무시)
   'email-already-in-use' → "이 이메일은 다른 방법으로 이미 가입돼
        있어요. 다른 로그인 수단을 사용해 주세요." (어떤 수단인지는 밝히지
        않는다 — 계정 식별 매트릭스가 "이메일 자동 병합 전 형태 금지"를
        요구하므로 여기서 연결을 유도하지 않는다)
```

### 5-3. `PasswordResetView`(⑩, 신설) — `lib/presentation/features/auth/views/password_reset_view.dart`

이메일 입력 → "재설정 메일 보내기". `AuthRepository.sendPasswordReset(email)`

🚨 **가입한 이메일인지 알려주지 않는다.** `sendPasswordResetEmail`이
