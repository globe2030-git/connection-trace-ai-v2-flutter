## 0. 용어 고정과 전제 — 이미 정해진 것 / 아직 안 정해진 것

### 0-1. 이미 정해진 것 (다시 묻지 않는다)

```
휴대폰 인증(채택)     이 번호로 오는 인증번호를 받는가만 확인. 이름·생년월일·CI/DI 없음
```

⚠️ **본 문서 전체에서 "본인확인"이라는 말을 쓰지 않는다.** 법률 조사

만들고 ②사고 시 §30③(방침·계약이 다르면 정보주체에 유리하게)이 회사 방어를
깎는다. **화면·방침·이 문서 어디서나 "휴대전화번호 확인"/"전화번호 인증"만
쓴다.**

가입 폼에서 받을 항목(HANDOFF "가입 방식 확정" 절, 2026-08-25 사용자):


만 14세는 **자기 선언 그대로 간다** — 휴대폰 인증에서 생년월일이 나오지

### 0-2. 아직 안 정해진 것 — 이 문서가 답을 대신 정하지 않는다

법률 조사(`account-identity-legal-research-2026-08-25.md` 883~937행)가
남긴 **D1~D5**, 매트릭스 문서(`account-identity-matrix-2026-08-21.md`
153~159행)가 남긴 **M-D1~M-D3**. ⚠️ **이름이 겹친다** — 법률 조사의 D1(계정
구조)과 매트릭스의 D1(명시적 연결 기능)은 **다른 질문**이다. 이 문서에서는
`L-D1`·`M-D1`처럼 접두사를 붙여 구분한다. 표로 모으면:

| 번호 | 무엇을 | 출처 | 이 문서의 취급 |
|---|---|---|---|

| L-D2 | 생년월일 보관 범위(전체/생년만/판정후 폐기) | 법률조사 934행 | 6절 방침 목록에만 반영, 이 문서는 선택 안 함 |
| L-D3 | 성별 개인 레코드 vs 익명 집계 | 법률조사 935행 | 09-15 범위 밖(계정 개편 때) — 이 문서는 안 다룸 |
| L-D4 | 만 14세 체크박스 제거 여부 | 법률조사 936행 | 0-1의 자기신고 유지 전제와 함께 사용자 결정 대기 |
| L-D5 | 알림톡 발송사(알리고/티킹, 하나인지 둘인지) | 법률조사 937행 | **5절에서 "알림톡 대기 항목"으로 분리** — 이 결정 자체는 알림톡 심사와 무관하게 지금 가능 |
| M-D1 | 명시적 계정 연결 기능을 만들 것인가 | 매트릭스 157행 | **4절 화면 흐름에서 v1.1 후보로 유지**(매트릭스 권고 그대로) |
| M-D2 | 재가입 식별용 이메일 해시 보존 | 매트릭스 158행 | 이 작업과 별개 트랙(이메일, 전화번호 아님) — 안 다룸 |

**L-D1이 이 설계의 뼈대를 정하므로, 이 문서는 L-D1에 대한 구체적 권고안(2절)을
먼저 세우고 그 위에 나머지를 쌓았다.** 사용자가 다른 안을 고르면 3~7절 중
uid 관련 부분만 다시 짜면 되고, 화면 흐름·방침 목록·순서는 대체로 그대로

## 1. 지금 구조에서 무엇이 바뀌나 — 실물 확인

### 1-1. 지금 "사람"이라는 개념이 없다 — uid가 곧 사람이다

코드를 직접 열어 확인했다.

```
functions/src/socialAuth.ts:42  socialUid()
  카카오 → "kakao:{회원번호}"
  네이버 → "naver:{회원번호}"
  구글·애플 → Firebase 기본 제공자 uid(접두사 없음)

firestore.rules:542            match /users/{uid}
firestore.rules:545,548        allow read: isOwner(uid) · allow delete: isOwner(uid)
firestore.rules:561-567        allow create/update: 필드 화이트리스트(clientWritableUserFields, 502행)
firestore.rules:569-581        하위 컬렉션: contacts/{contactId}(+commLogs), deletedContacts/{contactId}
                                — 전부 users/{uid} 아래에 종속

users/{uid} 문서 필드(코드로 확인한 것)
  encryptionKeyB64   명함 로컬 암호화 키 — 기기를 바꿔도 이 문서에서 복원(추가 72)
  profile            표시용 프로필(이름·이메일 등)
  aiUsage            AI 사용량/무료체험 잔액 — Admin SDK 전용, 클라이언트 쓰기 불가
  cohortWeek         가입 주차 계측 — 위와 동일
  groups·accountSwitches·adConsent* 등  기능이 늘 때마다 이 한 문서에 계속 붙어 왔다
```

즉 지금 구조에서 **uid는 "로그인 수단 하나"가 아니라 "사람 그 자체"다.**
암호화 키·AI 사용량·동의 기록·명함 전부가 이 uid 하나에 물려 있다. 같은
사람이 구글로도 로그인하고 카카오로도 로그인하면(추가 362에서 실제
발생) **완전히 별개인 두 "사람"**이 생긴다 — uid가 다르므로 명함도,
AI 잔여 횟수도, 동의 기록도 전부 별도다.

### 1-2. 로그인 흐름도 uid 하나만 상정하고 짜여 있다

```
lib/presentation/common/auth_gate.dart
  _lastHandledUid(메모리) + kLastSignedInUidPrefsKey(로컬 저장)
  로그인한 uid가 "마지막 uid"와 다르고 로컬에 데이터가 있으면
  "유지/교체" 다이얼로그(281행) — 계정을 자동으로 합치지 않는다(매트릭스
  2절 원칙과 일치)
  AccountBootstrapService.call() (95행) — 로그인마다 부트스트랩 호출,
  서버가 uid 기준으로 멱등 처리(freeGrantedAt)
```

`bootstrapAccount`(functions/src/index.ts:948)도 `request.auth.uid` 하나만
보고 그 uid 문서에 무료체험을 지급한다. **"이 uid와 저 uid가 같은 사람"이라는
개념 자체가 코드 어디에도 없다.**

### 1-3. I안이 바꾸려는 것 — "사람"을 uid보다 위에 하나 더 둔다

전화번호가 "사람"이 되면, 지금처럼 uid=사람이 아니라 **전화번호=사람,
uid=그 사람이 쓰는 로그인 수단(복수 가능)**이 된다. 이건 근본적으로 새
계층이고, **이 계층을 uid 자체를 바꿔서 만들 것인가, uid는 그대로 두고
위에 매핑을 얹을 것인가**가 바로 L-D1이 갈라 놓은 지점이다. 다음 절에서
두 방식을 실측 기반으로 비교한다.

## 2. 설계안 두 가지 — L-D1에 대한 권고

### 2-1. B안: uid 자체를 전화번호로 바꾼다 (완전 리멤버식에 가까움)

`phone:{e164}`를 새 uid로 삼고, 기존 `kakao:{id}`/`naver:{id}`/구글·애플
uid 문서(`users/{oldUid}`)와 그 하위 `contacts`·`deletedContacts`
서브컬렉션 전체를 새 uid 아래로 옮긴다.

**왜 비싸고 위험한가 — 1절에서 확인한 실물 그대로**: `encryptionKeyB64`가
uid에 물려 있어 문서를 옮기면 키도 함께 옮겨야 하고(다행히 키 자체는
그대로 복사하면 됨 — 재암호화는 불필요), `aiUsage`·`cohortWeek`는
Admin SDK 전용이라 클라이언트가 옮길 수 없고, `contacts` 서브컬렉션은
명함 수만큼 문서가 있어(테스터 5명 + 본인, 지금 서버 명함 103건·사진
102건, `tomorrow-2026-08-27.md`) **일괄 복사가 필요**하다. uid가 비가역이라는
경고(P1-49)가 가리키는 것이 바로 이 작업이다.

### 2-2. A안(권고): uid는 그대로 두고, 전화번호는 별도 매핑 계층으로 둔다

새 컬렉션 하나만 추가한다.

```
phoneAccounts/{phoneHash}
  uid          이 번호를 처음 인증한 계정의 uid (kakao:.../naver:.../구글·애플 uid 그대로)
  verifiedAt   인증 시각
  updatedAt    (재바인딩 시 갱신)
```

`phoneHash`는 평문 전화번호를 문서 ID로 쓰지 않는다 — 기존 `deviceLedger`
컬렉션이 이미 같은 패턴을 쓰고 있다(`firestore.rules:259-260`
`match /deviceLedger/{deviceHash}` `allow read, write: if false`,
`functions/src/index.ts:1006` `deviceHash(rawDeviceId, deviceHashSalt.value())`
— Secret Manager의 salt로 HMAC). **전화번호도 같은 방식으로 새 secret
(`phoneHashSalt`)를 하나 더 두고 해시한다.** 컬렉션 규칙도 deviceLedger와
동일하게 `allow read, write: if false`로 닫아, 오직 Cloud Functions(Admin
SDK, Rules 우회)만 쓰게 한다 — 클라이언트가 "나는 이 번호를 인증했다"고
직접 우겨 쓸 수 없게 하려는 것이다(`aiUsage`를 `clientWritableUserFields()`에서
뺀 것과 같은 이유, `firestore.rules:502-527`).

실제 전화번호(E.164)와 인증 시각은 **users/{uid} 문서에 새 필드로
저장**한다 — `phone`·`phoneVerifiedAt`. 이 필드도 `clientWritableUserFields()`에
**넣지 않는다**(`aiUsage`·`cohortWeek`와 같은 취급) — 인증은 반드시 서버의
OTP 확인을 거쳐야 하므로 클라이언트가 직접 쓸 수 있으면 검증을 우회하는
구멍이 된다.

**uid·contacts·encryptionKeyB64·aiUsage — 지금 있는 것은 단 하나도 옮기지
않는다.** 문서 구조·소유 관계가 안 바뀐다는 뜻이다. "사람=전화번호"라는
개념은 `phoneAccounts` 컬렉션 하나가 담당하고, 그 위에서 uid는 지금처럼
"이 사람이 지금 로그인한 방법"으로 계속 쓰인다.

### 2-3. 비교와 권고

| | B안(uid 치환) | A안(매핑 계층) |
|---|---|---|
| 기존 계정 마이그레이션 | **필요**(문서·서브컬렉션 일괄 복사) | **불필요**(3절 참고) |
| uid 비가역 위험 | **정면으로 부딪힘** | 회피(uid는 안 바뀜) |
| 이중등록 차단 | 됨(번호=uid이므로 구조적으로 하나) | 됨(phoneAccounts 유일성 검사로 됨, 방식만 다름) |
| 여러 소셜로 만든 기존 중복 계정 정리 | 이전 과정에서 자동으로 발견됨 | 매트릭스 원칙대로 **명시적 연결**(M-D1)이 별도로 필요 — 자동 병합 아님 |
| 번호 재사용(90일) 사고 시 피해 범위 | uid 자체가 새 사람 것이 됨 — 전체 데이터 노출 | 재바인딩 시 세션 무효화·2차 확인으로 방어 가능(법률조사 351~356행 권고와 정확히 대응) |
| 개발 규모·일정(09-15) | 큼 — 데이터 이관 로직·검증·롤백 설계 필요 | 작음 — 새 컬렉션 하나 + Cloud Function 하나 |
| 법률조사 자체의 위험 서열(368~372행) | "가장 큼"(완전 리멤버식) | "가장 작음"(SNS 유지+번호 보조)에 근접 |

📌 **권고: A안.** 이유는 셋이다. ① 법률 조사가 스스로 낸 위험 서열에서
가장 안전한 쪽과 구조가 같다(SNS 로그인은 유지, 전화번호는 "같은 사람
찾기"에만 쓴다). ② 실측 결과 uid에 걸려 있는 것(암호화 키·AI 사용량·명함
서브컬렉션)이 많아 B안의 이관 범위가 넓다 — 09-15까지 시간이 촉박한
지금 새로 만드는 위험을 하나 더 얹는 셈이다. ③ **A안도 I안이 원래
얻고자 한 것(이중등록 원천 차단)을 그대로 달성한다** — `phoneAccounts`의
문서 ID 유일성이 "이 번호로는 계정을 하나만 만들 수 있다"를 그대로
강제하기 때문이다. B안이 주는 추가 이득은 "uid 자체가 사람과 같아지는
개념적 단순함"뿐인데, 그 대가(마이그레이션·비가역 위험)가 이 시점에는
안 맞다.

⚠️ **이건 PM의 권고이지 결정이 아니다.** L-D1은 여전히 사용자 결정이다.
이 문서는 A안을 축으로 3~7절을 상세 설계했고, B안을 고를 경우의 절차도
3-2절에 남겨 두었다 — 어느 쪽을 고르든 이 문서에서 바로 넘길 수 있게.

## 3. 기존 계정 마이그레이션 — 테스터 5명 + 본인

### 3-1. A안(권고)을 고른 경우 — "마이그레이션"이 사실상 없다

핵심: **A안은 데이터를 옮기지 않는다.** 각 테스터가 새 빌드에서 로그인한
뒤 "휴대전화번호 확인" 단계를 **한 번** 통과하면 끝난다. 그 사람의 기존
uid·명함·AI 잔여 횟수·암호화 키는 손도 대지 않는다.

**절차(서버, 한 Cloud Function 호출 안에서 트랜잭션으로)**:

```
1. 클라이언트가 전화번호 입력 → 서버가 OTP 생성(6자리, TTL 3~5분,
   시도 횟수 제한) → 알림톡 발송 → phoneOtpChallenges/{sessionId}에
   해시된 코드 저장(평문 코드는 저장하지 않음)
2. 클라이언트가 코드 입력 → 서버 Cloud Function(phoneVerifyConfirm)이
   Firestore 트랜잭션 안에서:
   a. challenge 유효성(만료·시도횟수) 확인
   b. phoneHash = HMAC(e164, phoneHashSalt) 계산
   c. phoneAccounts/{phoneHash} 조회
      - 없음 → 생성 { uid: 현재 로그인 uid, verifiedAt: now }
               + users/{uid}.phone, phoneVerifiedAt 기록(Admin SDK)
      - uid == 현재 uid → 이미 인증된 상태, 그대로 성공 반환(멱등)
      - uid != 현재 uid → 실패 반환("이미 다른 계정에 연결된
        번호입니다") — 자동 병합하지 않는다(매트릭스 2절 원칙)
3. challenge 문서 삭제(또는 used 표시)
```

**"중단 지점 복구"에 대한 답**: 이 절차의 유일한 상태 변경(2번)이 **Firestore
트랜잭션 하나**로 묶여 있어 부분 실패가 구조적으로 없다 — 트랜잭션은
커밋되거나 안 되거나 둘 중 하나다. 함수 호출이 타임아웃·네트워크 오류로
끊겨도:

```
트랜잭션이 이미 커밋됐다   phoneAccounts 문서가 존재 → 클라이언트가 재시도해도
                        2번 "uid == 현재 uid" 분기로 떨어져 그대로 성공 처리(멱등)
트랜잭션이 커밋 전에 끊겼다  phoneAccounts 문서가 없음 → 클라이언트가 다시
                        인증번호를 요청해 처음부터 다시 하면 됨(부작용 없음)
```

즉 **"중단된 채로 애매하게 남는 상태" 자체가 설계상 존재하지 않는다.**
이것이 A안이 B안보다 마이그레이션 위험이 작다고 말하는 근거의 실체다.

**충돌 케이스(테스터가 이미 두 소셜 계정을 갖고 있던 경우)**: 추가
362에서 실제로 카카오·구글 양쪽에 계정이 생긴 사례가 있었다. 이 사람이
먼저 로그인한 계정에서 전화번호를 인증하면 `phoneAccounts`가 그 uid를
가리키게 된다. 나중에 다른 계정으로 로그인해 같은 번호를 인증하려 하면
2단계에서 "이미 다른 계정" 실패를 받는다 — 이 경우 **M-D1(명시적 계정
연결)이 있어야 정식으로 합칠 수 있다.** M-D1을 아직 안 만들었다면
안내 문구로 "먼저 인증했던 방법으로 로그인해 주세요. 이전 방법을 모르면
문의해 주세요"까지만 하고 v1.1로 넘긴다(매트릭스 157행 권고와 동일).

### 3-2. B안(비권고)을 고른 경우 — 참고용 절차

L-D1이 나중에 B안으로 결정되면 쓸 수 있도록, 되돌릴 수 없는 실수를
막는 절차를 남겨 둔다.

```
상태 필드   users/{oldUid}.migrationStatus ∈
            {none, copying, verifying, ready, done, failed}
            (기본값 none — 필드가 없으면 마이그레이션 미대상)

1단계 준비  oldUid 문서에 migrationStatus='copying', migrationTargetUid=newUid 기록
            (newUid = "phone:{e164}", 실제 Auth 레코드는 커스텀 토큰 최초
            로그인 시 자동 생성 — kakao/naver와 동일 방식이라 사전 생성 불필요)

2단계 복사  users/{oldUid} 최상위 필드(encryptionKeyB64·profile·aiUsage·
            cohortWeek·groups 등)를 users/{newUid}에 복사, 각 필드에
            migratedFrom=oldUid 마커
            contacts 서브컬렉션은 500건 단위 배치로 복사, 문서마다
            migratedFrom 마커 — 재시도 시 이미 있는 문서(같은 contactId +
            같은 updatedAt)는 건너뛴다(멱등)
            deletedContacts(tombstone)도 동일하게 복사

3단계 검증  oldUid·newUid의 contacts 문서 수 대조(+ contactId 집합 비교).
            불일치 → migrationStatus='failed'로 멈추고 **oldUid를 그대로
            살려 둔다**(사용자는 계속 예전 uid로 정상 이용 — 실패가
            사용자에게 보이지 않는다). 사람이 원인을 보고 재시도.
            일치 → migrationStatus='ready'

4단계 전환  ready 상태에서만 실행. oldUid 문서에 redirectUid=newUid 기록.
            앱은 로그인 직후(기존 소셜 로그인 그대로) uid를 얻으면, 그
            uid 문서에 redirectUid가 있는지 먼저 확인 → 있으면 서버에
            "이 소셜 계정은 {newUid}로 이전됐다"를 알리는 별도 호출로
            newUid용 커스텀 토큰을 다시 받아 그것으로 재로그인한다
            (Firebase의 기존 계정 연결과 유사하지만 uid 자체를 바꾸는
            것이라 자체 구현이 필요 — Firebase 표준 기능이 아니다)
            성공 시에만 migrationStatus='done'

5단계 보존  oldUid 문서·서브컬렉션은 done 이후에도 **즉시 삭제하지 않고
            30일 보존**(계정 전환 삭제 유예와 같은 패턴,
            `account-switch-card-deletion-2026-08-27.md`) 후 삭제 —
            전환 도중 미처 못 옮긴 것이 있어도 되돌릴 창을 남긴다
```

**중단 지점 복구**: 각 단계가 상태 필드에 그대로 기록되므로, 어느
단계에서 끊겨도 **다음 시도는 그 상태부터 이어간다**(0단계로 되돌아가지
않는다). 다만 이 절차 자체가 A안보다 훨씬 길고, 검증·재시도 로직을
새로 짜야 하며, 3단계 실패가 실제로 몇 % 나올지는 잰 적이 없다(계산이지
실측이 아니다) — **B안을 고르면 이 절차의 구현·검증에 09-15까지 남은
시간의 상당 부분이 들어간다.**

### 3-3. 어느 안이든 공통으로 필요한 것

- 마이그레이션(또는 매핑 생성) 전에 **테스터 5명 + 본인에게 무엇이
  일어나는지 미리 안내**한다 — 앱 잠금·계정 전환 다이얼로그와 같은
  수준의 명시적 동의 없이 조용히 시키면 "왜 갑자기 전화번호를 묻냐"는
  질문을 받는다.
- 실제 실행은 **전체 테스트(실기기)** 대상이다 — CLAUDE.md 4절의
  "저장·복원·마이그레이션·탈퇴" 조건에 정확히 해당한다. A안이라도
  `phoneAccounts` 생성이 실패해 그 사람 uid가 이상해지는지, 기존
  "유지/교체" 다이얼로그와 안 부딪히는지는 실기기로 확인해야 한다.

### 4-3. 매트릭스 8케이스가 I안에서 어떻게 풀리는지

| 케이스 | A안(매핑) 적용 시 |
|---|---|
| ① 카카오 이메일 인증/미인증 | **무관해짐** — 식별 기준이 이메일이 아니라 전화번호로 바뀌므로 이메일 인증 여부 자체가 판정에서 빠진다 |
| ② 네이버 이메일 비고유 | **무관해짐** — 같은 이유. 네이버 이메일 문제 자체가 I안에서는 발생하지 않는다(단, 4-2절 표시용 이메일 저장 자체는 그대로) |
| ③ 같은 이메일이 구글·애플과 충돌 | 여전히 발생 가능하지만 **판정 기준이 아니다** — 이메일이 같아도 전화번호가 다르면 별개 계정, 전화번호가 같으면 3절 "이미 다른 계정" 분기 |
| ④ 제공자별로 다른 이메일 | **I안의 존재 이유 그 자체** — 전화번호가 같으면 3절에서 걸린다(이메일로는 못 묶던 것을 전화번호로 묶음) |
| ⑤ 제공자 쪽 이메일 변경 | 무관해짐 |
| ⑥ 탈퇴 후 재가입 | ⚠️ **phoneAccounts 문서를 탈퇴 시 지우면 재가입 식별 효과가 사라진다.** 지우지 않으면 매트릭스 M-D2(이메일 해시 보존)와 같은 유형의 법률 질문이 전화번호에도 그대로 생긴다 — **탈퇴 시 phoneAccounts를 지울지 보존할지는 이 문서가 정하지 않은 새 질문**(6절에 등록) |
| ⑦ 미인증 후 인증됨 | 무관해짐(전화번호는 처음부터 인증 절차를 거치므로 "미인증 상태의 식별자"가 없다) |
| ⑧ 애플 릴레이 이메일 | 무관해짐 |

📌 **A안의 실질적 효과는 "8케이스 중 이메일 문제였던 다섯(①②③⑤⑧)을
통째로 무의미하게 만들고, 진짜 풀어야 했던 하나(④)를 해결하며, 하나(⑥)는
새 버전의 같은 질문으로 옮기고, 하나(⑦)는 애초에 안 생기게 만드는 것"이다.**

## 5. 알림톡 의존 — 기다리지 않아도 되는 것과 기다려야 하는 것

심사(10 영업일, 마감 ~09-01)와 발송사 계약이 끝나기 전에는 **실제
알림톡 발송**이 안 된다. 그런데 이 기능의 상당 부분은 발송과 무관하다.

### 5-1. 지금 바로 할 수 있는 것 (알림톡 무관)

```
1. L-D1~L-D5 사용자 결정 확보(0-2절)                    ← 이 문서가 만든 선택지로 바로 질문 가능
2. L-D5(발송사 확정) — 알리고/티킹 중 하나로 확정        ← 심사 신청 자체에 필요해 오히려 선행돼야 함
3. phoneAccounts 컬렉션 + firestore.rules 설계·리뷰      ← deviceLedger 패턴 재사용, 새 기능 없음
4. phoneHashSalt 시크릿 발급(Secret Manager)             ← deviceHashSalt와 동일 절차
5. OTP 생성·검증 순수 함수 + 단위 테스트                  ← socialAuth.ts처럼 "HTTP 호출 없는 순수 함수" 원칙 그대로
6. phoneVerifyConfirm Cloud Function의 트랜잭션 로직      ← 발송 부분만 스텁(테스트 더블)으로 두고 나머지 구현·테스트
7. 가입 폼 UI(이름·생년월일·전화번호 입력 칸, 유효성 검사) ← 값 입력만, "발송" 버튼은 비활성 상태로 먼저 만들 수 있음
8. lastLoginAt 서버 기록 추가                            ← 법률조사 351행 1순위 권고, 전화번호와 무관하게 지금 없음(0건)
9. 전화번호 재바인딩 시 revokeRefreshTokens 서버 호출      ← revokeMySessions(index.ts:2401)가 이미 있음 — 자기 호출용이던
                                                          것을 재바인딩 시점에 서버가 직접 부르도록 확장하면 됨(신규 아님)
10. 방침 v2.5·약관 §5·§6 문안 초안(게시는 아님)           ← 6절 목록. 문안을 미리 잡아 두고 공고일만 배포일에 맞춰 계산
11. 법무에 새 질문 등록(6절 "L6" 후보 — 6-2 참고)         ← 발송과 무관, 오히려 지금 물어야 배포 전에 회신이 옴
```

**11건이 알림톡 심사·계약을 기다리지 않고 지금 진행 가능하다.**

### 5-2. 알림톡 심사·계약이 끝나야 되는 것

```
1. 실제 OTP 발송 연동(알리고/티킹 API 키·템플릿 승인)
2. 발송 포함 종단 실기기 테스트(가입 폼 → 문자 수신 → 입력 → 성공)
3. phoneAccounts 매핑 실사용(테스터 대상 3절 절차 실행)
4. 방침 게시(전화번호 "수집 개시" 자체가 이 시점 이후여야 함, 6절)
5. 배포
```

### 5-3. 순서상 주의할 것

L-D5(발송사 확정)는 **알림톡을 기다리는 항목이 아니라 알림톡 심사
신청의 선행 조건**이다 — "알리고인지 티킹인지도 안 정한 채 심사부터
넣을 수는 없다"(0-3절의 발견). 즉 이 결정은 다른 결정들과 달리
**월요일 심사 신청 전에 끝나야 하는, 가장 급한 것**이다.

## 6. 되돌릴 수 없는 것 — 전부 세어 본다

```
1. uid 형식(B안을 고를 경우)              변경 후 기존 이용자 데이터가 통째로 끊김(이미 알려진 것)
2. phoneHash 알고리즘·salt               한번 정해 실제 데이터가 쌓이면 알고리즘을 바꿀 경우
                                        전원의 해시가 새로 계산돼야 하고 기존 매핑과 안 맞음
```

사용자 최종 결정이다.

**③ 이 작업의 가장 큰 위험**: **L-D1을 "완전 리멤버식"(B안)으로 확정하고
9월 15일을 목표로 uid 물리 이관까지 욱여넣는 것.** 실측 결과 uid에는
암호화 키·AI 사용량·명함 서브컬렉션이 전부 물려 있어(1절) B안의 이관

같은 목적(이중등록 차단)을 새 컬렉션 하나로 달성하면서 uid 비가역
위험을 아예 피해 간다 — **"전화번호를 계정의 주인으로"라는 목표와
"uid 자체를 전화번호로 바꾼다"는 방법은 분리할 수 있고, 분리하는 편이
이번 일정에는 훨씬 안전하다**는 것이 이 설계의 핵심 주장이다. L-D1이
B안으로 확정되면 이 문서의 5·7절 순서표를 다시 짜야 한다(마이그레이션
구현·검증에 상당한 시간이 새로 들어간다).
