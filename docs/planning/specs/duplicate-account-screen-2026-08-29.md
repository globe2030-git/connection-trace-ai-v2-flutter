# 이중등록 화면 — 설계 옮김 (2026-08-29)

- 상태: **결정은 났으나(추가 583, globe2030님 확정) 화면설계 문서 형태로는
  안 옮겨져 있던 것을 옮긴 것 — 구현 전.**
- ⚠️ **이 문서는 구현하지 않는다.** 이 화면은 **휴대폰 인증이 끝난 직후**
  뜨는 화면이라(§1), 휴대폰 인증 자체를 만들고 있는 `b4`(ct-phone-otp,
  `feat/phone-otp`, backlog 571·573)의 작업과 떼어 놓을 수 없다. 인증 완료
  콜백에 이 화면을 끼우는 지점, 기존 계정 조회 방법(전화번호로 uid 찾기),
  uid 통일 방식(추가 557 결정 ③에서 아직 미정인 A/B안)이 전부 그 작업
  내부에 있다. **이 문서는 b4가 그 지점에 끼울 화면의 완성된 설계**이고,
  `lib/`는 한 줄도 고치지 않았다.

## 1. 언제 뜨나 — 인증 뒤, 조건부

```
[로그인 화면] → SNS/이메일 로그인 → [휴대폰 인증: 번호 입력 → 인증번호 확인]
                                              ↓ 성공
                            그 번호로 이미 가입된 계정이 있는가?
                                 있다 → 🚨 이 화면 (이중등록 화면)
                                 없다 → 광고 동의 → 앱 진입 (기존 흐름 그대로)
```

**추가 583과 584는 같은 목적의 다른 화면이다** — 583은 인증 **뒤**에
"이게 내 계정인가"를 돕고, 584(`login-recent-provider-2026-08-29.md`)는
누르기 **전**에 돕는다.

## 2. 왜 이 자리에서는 추가 532 원칙을 완화하는가

추가 532: *"어느 계정인지 말하지 않는다 — 번호만 넣어 보고 남의 가입
여부를 알아낼 수 있다."*

**이 원칙은 인증 전에 성립하지, 인증 후에는 성립하지 않는다.** 이
화면은 **인증번호를 맞힌 뒤**에만 뜬다 — 즉 그 번호로 오는 문자를 실제로
받을 수 있는 사람만 도달한다. 남의 번호를 넣어 봐도 인증번호를 못 받으므로
이 화면 자체에 도달하지 못한다. **열거 위험은 인증 단계가 이미 막고
있다.** 그래서 532를 지우지 않고 **적용 범위를 "인증 전"으로 좁힌다** —
584(로그인 화면, 인증 전)는 여전히 532를 그대로 지킨다.

## 3. 화면 — 채택한 넷 (리멤버 실물 관찰 기준)

근거: `docs/planning/remember-signup-flow-2026-08-26.md` §4.

```
┌─────────────────────────────────────────┐
│         이미 계정이 있습니다               │
│                                           │
│  +82 10-****-**** 번호로 가입한 계정이     │
│  있어요. 아래 계정으로 로그인해 주세요      │
│                                           │
│  ┌───────────────────────────────────┐  │
│  │ ✉  gl*******@ic****.com           │  │
│  │    2026-04-29 가입                 │  │
│  └───────────────────────────────────┘  │
│                                           │
│  [ 새 계정 만들기 ]                        │
│                                           │
│  로그인할 수 없나요? 문의하기               │
└─────────────────────────────────────────┘
```

| 요소 | 왜 |
|---|---|
| ① **이메일 마스킹** (`gl*******@ic****.com`) | 번호를 넣어 본 사람에게 남의 이메일을 통째로 보여주지 않는다. §2에서 완화한 것은 "가입 여부"뿐이지 "이메일 원문"이 아니다 |
| ② **가입일** | *"이게 내 계정인가"*를 판단할 단서 — 이메일만으로는 기억 못 하는 경우가 많다(리멤버 실물 관찰에서 우리가 처음 알게 된 것) |
| ③ **「새 계정 만들기」를 막지 않는다** | 강제 병합이 아니라 선택지를 준다 — 예: 가족이 예전에 이 번호로 가입했다가 번호를 물려받은 경우(§4) |
| ④ **「로그인할 수 없나요? 문의하기」** | 🚨 막다른 길을 만들지 않는다 — 번호는 있는데 그 계정의 로그인 수단을 모르면 이용자가 갇힌다 |

### 3-1. "아래 계정으로 로그인해 주세요"가 뜻하는 것

이 화면은 **자동으로 그 계정에 로그인시키지 않는다.** 카드를 누르면
"어느 SNS/이메일로 그 계정에 가입했었는지"를 보여주거나, 그 계정에 연결된
로그인 수단으로 다시 시도하도록 안내한다(예: "이 계정은 카카오로
가입했어요. 카카오로 로그인해 주세요"). **구체적인 재로그인 유도 문구는
b4가 uid 통일 방식(추가 557 A/B안)을 정한 뒤에 확정한다** — 지금은 카드
자체의 정보 구성(마스킹 이메일 + 가입일)만 이 문서가 확정한다.

### 3-2. 「새 계정 만들기」를 누르면

지금 로그인한 SNS/이메일 수단으로 **새 계정**을 만들고 이어서 정상
흐름(광고 동의 → 앱)으로 진행한다. 이 경우 **휴대폰 번호는 두 계정에서
공유되는 상태**가 된다 — "휴대폰 = 사람"(추가 557 결정 ①) 원칙의 예외를
사용자가 명시적으로 선택한 경우다. ⬜ **이 상태를 이후 어떻게 다루는지는
미정**(예: 두 계정이 나중에 서로의 존재를 인지해야 하는지) — b4 판단
영역.

## 4. 남는 위험 — 번호 재활용, 완화만 하고 없애지는 못한다

통신사가 해지된 번호를 90일 뒤 다른 사람에게 재배정한다(추가 462). 새
주인이 인증에 성공하면 **전 주인의 마스킹 이메일과 가입일을 보게 된다.**

**완화**: 리멤버와 같은 방식 — **자동 로그인은 시키지 않는다**(§3-1).
로그인은 여전히 그 계정의 자격증명(비밀번호, 또는 그 계정에 연결된
SNS)을 요구하므로, 새 주인이 전 주인의 자격증명을 모르면 그 계정에 들어갈
수 없다 — 마스킹된 이메일과 가입일 두 조각만으로는 로그인이 안 된다.

**추가로 걸리는 것**: 추가 557 결정 ③(오래 안 쓴 계정은 휴대폰만으로
자동으로 안 잇는다)이 여기에 겹친다. ⬜ **"오래"가 몇 개월인지 미정**
— 통신사 번호 회수 기간(90일)보다 짧게는 못 잡는다는 제약만 정해져
있다.

## 5. b4에게 남기는 것 — 이 문서가 안 정한 것

```
- 이 화면을 인증 완료 콜백의 어느 지점에 끼울지(코드 위치)
- "그 번호로 이미 가입된 계정이 있는가"를 어떻게 조회할지
  (Firestore에 전화번호 → uid 인덱스가 필요 — 없다면 새로 만들어야 함)
- 카드를 눌렀을 때의 정확한 재로그인 유도 흐름(§3-1)
- 「문의하기」가 여는 대상(기존 1:1 문의 화면 재사용? 새 채널?)
- 번호 재활용 대응의 구체적 정책("오래"의 값, §4)
- uid 통일 방식(A: custom token 통일 / B: 전화번호 계정에 link) —
  추가 557에서 아직 미정이라고 명시된 채로 남아 있다
```

## 6. 확인하지 못한 것

- 이 화면이 이메일 가입 경로(`email-password-signup-2026-08-29.md`)와
  SNS 가입 경로 양쪽에서 완전히 같은 모양으로 뜨는지 — 설계상 같아야
  한다고 판단했으나 b4의 실제 구현에서 인증 완료 콜백이 경로별로 갈라져
  있다면 확인이 필요하다.
- 이 문서 작성 시점(2026-08-29) 기준 `feat/phone-otp` 브랜치에 이 화면이
  이미 부분적으로 만들어져 있는지 여부 — origin/main에는 없음을
  확인했으나(이중등록 관련 코드 0건, grep 기준) `feat/phone-otp` 브랜치
  자체는 이 문서 작성 과정에서 코드 레벨로 열어보지 않았다.
