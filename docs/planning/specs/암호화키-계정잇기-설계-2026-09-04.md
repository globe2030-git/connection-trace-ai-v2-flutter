# 암호화 키 — 계정을 이을 때 명함을 잃지 않는 설계

|  |  |
|---|---|
| **문서** | 한 사람의 계정이 둘 이상이 될 때 **명함을 어떻게 계속 읽을 것인가** |
| **왜 먼저** | 🚨 uid 세 안(A·B·C) 중 **무엇을 골라도 여기서 만난다** — 안을 고른다고 사라지지 않는다 |
| **왜 무거운가** | **실패하면 명함을 영영 못 읽는다.** CLAUDE.md 4절의 「저장·복원·마이그레이션 = 전체 테스트 등급」 |
| **관련** | [`계정식별-uid-세-안-비교-2026-09-04.md`](./계정식별-uid-세-안-비교-2026-09-04.md) §5 |
| **작성** | 2026-09-04 |
| **상태** | ⬜ **설계만. 코드는 한 줄도 안 고쳤다** |

---

## 1. 지금 실물 (2026-09-04 실측)

**무엇으로 쟀나**: `encryption_key_service.dart` · `data_crypto_service.dart` ·
`contact_image_service.dart` 를 직접 열었다.

```
키           uid 당 하나. AES-256-GCM
보관 두 곳    ① 기기 보안저장소  enc_key_v1_{uid}   (Keychain / Keystore)
             ② Firestore       users/{uid}.encryptionKeyB64
조회 순서     메모리 캐시 → 로컬 → 서버 → 없으면 새로 발급
사진          🔵 **같은 키를 쓴다** — ContactImageService 가 같은 서비스를 재사용
암호문 형식    nonce(12B) + ciphertext + MAC(16B)   ← **버전도 키 식별자도 없다**
```

⭐ **서버에도 있다는 것이 이 설계의 전제다** — 기기를 잃어도 키를 되찾을 수 있고,
**옮길 수도 있다.**

⚠️ **정직하게**: 키가 암호문과 같은 Firestore 프로젝트에 있으므로 **제로-지식이
아니다.** 이 문서는 그 한계를 바꾸지 않는다(그건 P2-1의 몫이다).

---

## 2. 문제 — 두 계정을 이으면 키가 둘이 된다

```
계정 A 의 명함  →  키 A 로 암호화돼 있다
계정 B 의 명함  →  키 B 로 암호화돼 있다
                   ↓ 한 사람으로 잇는다
              명함들이 서로 다른 키로 암호화된 채 한 명함첩에 모인다
```

🚨 **어느 명함이 어느 키로 잠겼는지 적힌 곳이 없다** — 암호문에 키 식별자가 없다(§1).

---

## 3. 두 갈래

### ❌ 갈래 1 — 재암호화 (한쪽을 전부 다시 암호화한다)

```
계정 B 의 명함을 전부 복호화 → 키 A 로 다시 암호화 → 저장
```

| | |
|---|---|
| ⭐ | 끝나면 키가 하나로 깔끔해진다 |
| 🚨 | **중간에 끊기면 반쯤 암호화된 상태가 된다** — 앱 종료·배터리·네트워크 |
| 🚨 | 실패한 명함은 **어느 키로도 안 열릴 수 있다** |
| 🚨 | 사진까지 하면 수백 MB — 시간도 길고 끊길 확률도 커진다 |
| ⚠️ | **되돌릴 수 없다.** 원본을 덮어쓰기 때문이다 |

### ✅ 갈래 2 — 키링 (키를 여럿 들고 다닌다) ← **채택**

```
「사람」이 키를 여러 개 갖는다.  복호화할 때 가진 키를 차례로 시도한다.
```

⭐ **AES-GCM 이 이것을 가능하게 한다** — MAC 이 붙어 있어 **틀린 키로 복호화하면
반드시 실패**한다. 코드도 이미 그 실패를 예외로 던진다(`DataDecryptException`,
`data_crypto_service.dart:7`). **즉 「어느 키인지」를 적어 두지 않아도 골라낼 수 있다.**

| | |
|---|---|
| ⭐ | **암호문 형식을 안 바꾼다** — 기존 데이터가 그대로 열린다 |
| ⭐ | **재암호화가 없다 → 손실 위험이 0 이다** |
| ⭐ | 잇는 즉시 읽힌다. 기다릴 것이 없다 |
| ⚠️ | 키가 쌓인다 (로그인 수단 수만큼 — 실제로는 2~3개) |
| ⚠️ | 첫 시도가 틀리면 한 번 더 시도한다 (비용은 §6) |

---

## 4. 왜 갈래 2인가 — 이 저장소의 원칙 그대로다

> **동기화는 아무도 안 보는 자리다 — 거기서 자동으로 합치면 잃어도 모른다.**
> (`identical_contacts.dart` 머리말)

재암호화는 **원본을 덮어쓰는 작업**이고, 아무도 안 보는 자리에서 돈다.
**키링은 아무것도 덮어쓰지 않는다** — 읽는 방법만 늘린다.

📌 **되돌릴 수 있는 쪽을 고른다.** 이 문서가 정한 것은 그것 하나다.

---

## 5. 설계

### 5-1. 키링 — 「사람」이 가진 키 목록

```
지금    users/{uid}.encryptionKeyB64          키 하나
더함    「사람」이 아는 키들의 목록             uid 별 키를 모은 것
```

⚠️ **어디에 두는지는 uid 세 안 중 무엇을 고르느냐에 달렸다** — C안이면 「사람」
문서에, A안이면 통일된 uid 문서에. **이 문서는 「무엇을 담는가」만 정하고 「어디에」는
안 정한다.**

담는 것:

```
keyB64      키 원문(base64)          지금과 같다
uid         이 키가 원래 어느 계정 것인지   🚨 감사·파기에 필요하다
addedAt     언제 키링에 들어왔나
```

### 5-2. 복호화 — 순서대로 시도한다

```
① 이 명함을 마지막에 연 키가 기억돼 있으면 그것부터   (로컬 캐시)
② 없으면 현재 계정의 키
③ 그래도 실패하면 키링의 나머지를 차례로
④ 전부 실패하면 «못 읽는 명함»으로 표시하고 화면에 그대로 말한다
```

🚨 **④가 이 설계에서 제일 중요하다.** 그리고 **지금은 그렇게 안 되어 있다** —
2026-09-04 실측:

```dart
// contacts_repository.dart:740
// 복호화 실패(위변조/키 불일치 등)를 포함해 어떤 이유로든 로드에
// 실패하면 크래시하지 않고 빈 목록으로 시작한다.
debugPrint('Error loading saved contacts: $e');
```

⚠️ **`debugPrint` 는 릴리스 빌드에서 아무 데도 안 나온다.** 즉 **화면은 그냥
비어 있고, 아무 말도 하지 않는다.**

📌 **크래시하지 않는 것 자체는 옳은 판단이다** — 다만 거기서 멈췄다.
`data_crypto_service.dart:9` 가 이미 경고하고 있다: *"조용히 빈 데이터로
넘어가면 사용자가 「명함이 다 사라졌다」고 오해할 수 있다."* **예외는
만들어 뒀는데 화면이 그 사실을 말하지 않는다.**

⭐ **그래서 §8 의 1단계는 키링과 무관하게 지금도 값이 있다.**

### 5-3. 성공한 키를 기억한다

```
명함 id → 이 명함을 연 키의 uid      기기 로컬에만 (서버에 안 보낸다)
```

⭐ 두 번째부터는 첫 시도에 열린다. ⚠️ **캐시가 없어도 동작은 같다** — 느릴 뿐이다.
캐시가 정답의 자리에 있으면 안 된다.

### 5-4. 재암호화는 **선택이지 전제가 아니다**

키링이 있으면 재암호화를 **안 해도 된다.** 그래도 하고 싶다면(키를 줄이려고)
이렇게 한다:

```
① 새 키로 암호화한 사본을 **먼저 쓴다**
② 성공을 확인한 뒤에 옛 것을 지운다
③ 옛 키는 마지막 명함이 옮겨질 때까지 키링에 남긴다
```

⚠️ **순서가 뒤집히면 갈래 1의 위험이 그대로 돌아온다.**

---

## 6. 비용 — 아직 안 쟀다

```
⬜ 명함 한 장 복호화에 걸리는 시간        키가 틀렸을 때의 실패 비용도 함께
⬜ 사진 한 장 복호화에 걸리는 시간         사진이 훨씬 크다
⬜ 계정당 명함·사진 장수의 분포           Firestore 실물 조회 필요
```

📌 **최악은 「명함 수 × 키 수」이지만 실제로는 다르다** — 대부분 첫 키에서 열리고,
틀린 키의 실패는 MAC 검사라 복호화 전체보다 싸다. ⚠️ **다만 이것은 계산이다.
실측이 아니다** — 재기 전에는 「빠르다」고 쓰지 않는다.

---

## 7. 파기 — 잊으면 안 되는 자리

🚨 **키링은 「지우는 것」을 어렵게 만든다.**

```
탈퇴          그 사람의 키를 전부 지운다 — 하나라도 남으면 명함이 열린다
계정 전환      다른 세션이 만든 30일 뒤 삭제(leftover_account_purge_service)와
              같은 자리다. ⚠️ 그 서비스가 지우는 enc_key_v1_<uid> 가 바로 이 키다
번호 재활용    결정 ③ — 오래 안 쓴 계정은 자동으로 잇지 않는다
              🚨 **잇지 않으면 키도 주지 않는다.** 키링에 넣는 것 자체가 「잇기」다
```

⚠️ **방침 문서와 맞춰야 한다** — `privacy-policy.html` 의 파기 서술에 키가
어떻게 다뤄지는지 적혀 있어야 한다. 방침과 구현이 어긋나는 것 자체가 법적
리스크다(CLAUDE.md 4절).

---

## 8. 단계

```
0단계  §6 을 잰다                    「빠르다」를 말하기 전에
1단계  못 읽는 명함을 화면이 말하게    ⭐ 키링 없이도 지금 값이 있다
       지금은 조용히 빈 목록이 될 수 있다 (§5-2 ④)
2단계  키링 자료구조 + 복호화 시도 순서   uid 안 결정과 무관하게 만들 수 있다
3단계  잇기와 연결                     uid 안이 정해진 뒤
4단계  (선택) 재암호화로 키 줄이기      §5-4 순서를 지켜서
```

⭐ **1·2단계는 uid 세 안 결정을 기다리지 않아도 된다.** 어느 안을 골라도 필요하다.

---

## 9. 안 정한 것 · 확인 못 한 것

```
⬜ 키링을 어디에 둘지            uid 세 안 결정에 달렸다 (§5-1)
⬜ 키 개수 상한                  로그인 수단이 늘면 키도 는다. 상한이 필요한가
⬜ §6 의 세 가지 비용            전부 미측정
⬜ 방침 문구                     파기 서술에 키를 어떻게 적을지 (법무 검토가 필요할 수 있다)
⬜ 「못 읽는 명함」 화면           문구·행동(다시 시도? 문의?)이 안 정해졌다
```

⚠️ **위를 안 재고 「안전하다」고 말하지 않는다.** 이 문서가 정한 것은
**「재암호화가 아니라 키링으로 간다」** 하나이고, 나머지는 열려 있다.
