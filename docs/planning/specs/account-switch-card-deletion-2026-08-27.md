### 1-1. 왜 서버 데이터는 대상이 아닌가

Firestore·Cloud Storage에 있는 A의 명함은 **A 계정 자신의 살아있는
데이터**다. B가 이 기기에서 로그인했다고 해서 A의 계정 데이터를 지우는 것은
"기기 정리"가 아니라 **A 몰래 A의 계정을 건드리는 일**이 된다 — A가 다른
기기에서 여전히 이 앱을 정상적으로 쓰고 있을 수도 있다. 법무 회신도 정확히
이 둘을 구분했다(질문 9 표, "무엇이 움직이나" 행: *"이 기기에 남아 있던
것만. A의 서버 백업은 건드리지 않습니다"*). 오늘 결정은 이 구분을 그대로
유지하고, 그 위에서 **로컬 잔존물의 보전 여부만** 뒤집는 것이다.

### 1-2. 스코프 밖에서 발견한 위험 — 내 프로필 사진은 이 방식에 넣으면 안 된다

`contact_image_service.dart:54-62`를 보면 **내 프로필 사진은 계정과 무관한
고정 파일명**(`_my_profile_card`)을 쓴다:

```dart
/// **내 명함 사진**이 쓰는 예약 id(2026-08-26).
/// 내 명함은 ContactModel이 아니지만 사진은 남의 명함과 같은 경로로
/// 보관한다 — ...
static const String myProfileCardId = '_my_profile_card';
```

즉 A의 프로필 사진과 B의 프로필 사진이 **같은 파일**을 공유한다. B가 새
프로필 사진을 설정하면 그 순간 A의 파일을 덮어써 버리므로, "30일 뒤 삭제"
스케줄에 이 id를 넣으면 **B가 그 사이에 저장한 자기 프로필 사진을 30일
뒤에 지워버리는 사고**가 난다. **그래서 이번 삭제 대상에서 `_my_profile_card`는
명시적으로 제외한다.** (프로필 사진을 계정별로 분리하는 것은 별개의 개선
과제로 남긴다 — 오늘 결정의 범위가 아니다.)

**지울 대상의 정확한 정의**: "교체" 선택 시점에 로컬에 있던 **일반 명함
목록의 contactId 집합**(내 프로필 제외)에 대응하는 `contact_card_<id>.enc`
파일들 + A의 로컬 암호화 키(`enc_key_v1_<A_uid>`).

## 2. 30일 유예를 어디에 기록하나

### 대안과 대가

| | 기기(SharedPreferences) | 서버(Firestore) |
|---|---|---|
| 앱 삭제·재설치 시 | 기록도 사라지지만, **지울 대상 파일도 같이 사라진다** — 문제없음 | 기록은 남는데 지울 대상 파일이 이미 없음 — 무의미 |
| 다른 기기에서 확인 가능한가 | 아니오 | 이론상 가능하나, 지울 대상 자체가 **이 기기에만 있는 파일**이라 다른 기기가 알아도 할 수 있는 게 없음 |
| A 계정 문서에 쓰려면 | 해당 없음 | A는 로그아웃 상태 — B로 인증된 세션이 `users/A` 문서에 쓰려 하면 **본인 uid만 쓸 수 있는 보안 규칙과 충돌** 가능성. 굳이 뚫을 이유가 없음 |
| 구현 난이도 | 낮음(기존 `shared_preferences` 패턴 그대로) | 높음(권한 모델을 새로 고민해야 함) |

### 권고: **기기(SharedPreferences)**

지우려는 대상 자체가 "이 기기에만 있는 파일"이므로, 그 예정 시각도 이
기기에만 있는 것이 자연스럽다. 앱을 삭제하면 기록과 대상이 함께 사라져
정합성이 깨질 일도 없다. 서버에 두는 안은 이 스코프에서는 얻는 것 없이
복잡도만 늘린다(계정 A/B 어느 쪽 문서에 둬도 이상하다 — A는 로그아웃
상태고, B의 문서에 A의 잔존물 정보를 적는 것도 목적이 어긋난다).

### 저장 형식(제안)

새 `shared_preferences` 키(예: `pending_leftover_card_photo_purge_v1`)에
**uid를 키로 하는 맵**을 JSON으로 저장한다.

```json
{
  "<A_uid>": {
    "contactIds": ["<uuid1>", "<uuid2>", "..."],
    "scheduledAt": "2026-09-26T00:00:00.000Z"
  }
}
```

- `contactIds`는 "교체" 선택 시점(`clearLocal()` 호출 **직전**)의
  `contactsRepo.contacts.map((c) => c.id)`를 그대로 캡처한다 — UUID뿐이라
  개인정보가 아니다.
- 맵이라 **같은 uid로 여러 번 스케줄이 잡히면 최신 것으로 덮어쓴다**(A→B→A→C처럼
  여러 번 전환해도 항목이 무한히 쌓이지 않는다).
- **키가 아니라 값이 개인정보가 아님을 확인할 것**: uid 자체는 계정
  식별자라 `recordAccountSwitch`(아래 3-1)와 같은 급의 취급이면 된다(명함
  내용 없음).

## 3. 누가 실제로 지우나

### 결론: **앱(클라이언트)만 할 수 있다. Cloud Functions는 이 스코프에 아예 손이 닿지 않는다.**

이번에 지우는 대상(명함 사진 `.enc` 파일, `flutter_secure_storage`의
로컬 키)은 **이 특정 기기의 로컬 저장소에만 존재한다.** Cloud Functions는
Firestore·Cloud Storage 같은 서버 자원만 건드릴 수 있고, 기기 로컬 파일
시스템에는 애초에 접근 경로가 없다. 그러므로 "Functions로 할지 앱으로
할지"는 선택지가 아니다 — **이 기능은 배포(`firebase deploy`)가 전혀
필요 없다.** CLAUDE.md 6절의 과금·배포 관문과 무관하게, 일반 앱 릴리스로
출시할 수 있다.

### 실행 시점(제안)

`AuthGate`가 매 로그인/앱 실행 시점마다 이미 계정 동기화 로직을
돌린다(`auth_gate.dart:_handleAccountSync`). 그 흐름 끝에 "만료된 예약이
있는지" 점검하는 단계를 하나 추가한다:

1. 앱 실행 시 `pending_leftover_card_photo_purge_v1`을 읽는다.
2. 각 항목에 대해:
   - **그 uid가 지금 로그인하려는 uid와 같으면 → 예약을 취소**(4절 "복구"
     참고). 사용자가 원래 계정으로 돌아온 것이므로 지울 이유가 없어졌다.
   - **`scheduledAt`이 지났으면** → 해당 `contactIds`의
     `contact_card_<id>.enc` 파일 삭제 + 그 uid의 로컬 키(`enc_key_v1_<uid>`)
     삭제 + 예약 항목 제거.
   - 아직 안 지났으면 그대로 둔다.
3. **현재 로그인 중인 uid는 절대 건드리지 않는다**(안전장치 — 설계·구현
   모두에서 이중으로 확인할 것. 실수로 현재 계정의 사진을 지우는 사고가
   나면 이 기능 전체의 신뢰가 깨진다).

### 정밀도에 대한 정직한 한계

앱을 30일 넘게 안 켜면 그만큼 삭제도 늦어진다(정확히 30일이 아니라 "30일이
지난 뒤 다음 실행 시점"). 이건 §21①의 "지체 없이"에 대한 미세한 여유이지만,
애초에 "30일"이라는 유예 자체가 법정 기한이 아니라 이번 결정으로 **새로
설정하는 내부 정책 기준**이므로, 그 정책을 "다음 실행 시점"으로 정의하면
된다(방침에 그렇게 명시하면 문제없다 — 6절 참고). 백그라운드에서 앱이 꺼진
상태로 정확히 지우는 것(예: WorkManager 등)은 새 의존성이 필요해 이번
범위에서는 권장하지 않는다.

### 4-1. 진짜 보장은 서버 백업이다 (30일 유예와 무관하게 항상 동작)

A의 텍스트(Firestore)와 대부분의 사진(Cloud Storage, 백업 켠 이후 등록분과
소급 업로드분)은 **오늘 결정과 무관하게 전혀 지워지지 않는다**(1절).
따라서 A로 재로그인하면 몇 년이 지난 뒤라도 `forceRestoreFromServer`가
텍스트와 사진을 정상 복원한다. **"30일 뒤에 로컬 잔존물을 지운다"는 이
서버 백업의 존재를 전제로 안전한 것이지, 30일이 복구 가능 기간의
한계가 아니다.**

### 4-2. 30일 안에는 보너스로 "즉시" 복구된다 (네트워크 없이)

`contacts_repository.dart:229-233` 주석이 이미 이 메커니즘을 설명한다 —
서버에서 내려받은 명함은 사진 경로가 없는데, 로컬에 같은 `contactId`의
`.enc` 파일이 남아 있으면 `relinkMissingCardImagePaths()`가 파일명 규칙으로
**즉시 재연결**한다. 즉 30일 이내에 A로 돌아오면:
- 로컬 잔존 파일이 아직 있으므로 사진을 다시 내려받을 필요가 없다(빠르고,
  혹시 그 사진이 서버에 아직 안 올라간 상태였어도 — quota 초과·업로드
  실패 등 — 로컬 사본으로 복구된다).
- 30일이 지나 이미 지워졌다면 `downloadMissingCardImages`가 Cloud Storage에서
  다시 받아온다 — 다만 **서버에도 없던 사진**(업로드가 끝내 실패했거나
  한도 초과로 애초에 안 올라간 사진)은 이 시점에는 정말로 사라진다. 이건
  "30일 유예"의 실패가 아니라 애초에 업로드가 안 됐던 별개의 결함이다
  — 아래 4-3 참고.

### 4-3. 예약 취소(자동 "실행 취소")

A로 재로그인하는 순간(3절 2번 규칙) 대기 중이던 A의 삭제 예약은 **자동으로
취소**된다. 사용자가 별도로 "취소" 버튼을 누를 필요가 없다 — **로그인 자체가
취소 행위**다. 이것이 "실수 대비"의 실질이다: 잘못 눌러서 교체했어도, 다시
로그인만 하면(그리고 그 다이얼로그에서 다시 "교체"를 고르기만 하면 —
자기 자신에게 돌아오는 것이므로 안전) 아무 일도 없었던 것처럼 된다.

### 4-4. 잔여 위험(정직하게 남기는 것)

**서버에도 로컬에도 없던 사진**(백업 켜기 전 등록 + 아직 소급 업로드 전에
전환, 오프라인 등록 후 미동기화, 사진 한도 초과)은 30일 뒤 로컬 잔존
파일마저 지워지면 **영구 손실**된다. 이건 이번 기능이 만드는 위험이
아니라 **원래 있던 업로드 실패/한도초과 문제**가 이 시점에 드러나는
것이다. 완화책으로 5절 안내 문구에 "아직 서버에 저장되지 않은 사진이
있다"는 경고를 조건부로 추가하는 것을 권고한다(아래).

**권고(선택 사항, 개발자 판단에 맡김)**: "교체" 선택 직후, `CardPhotoBackupStateService().clear()`를

## 5. 안내 문구 — `auth_gate.dart:_showAccountSwitchNotice`

### 🚨 2026-09-04 정정 — 아래 초안은 「유지」를 남기는 전제였고, 그 전제가 뒤집혔다

**이 절은 원래 「유지하고 계속 쓰기」/「현재 계정 데이터로 교체」 두 버튼을
그대로 두고 30일 안내만 덧붙이는 안이었다.** 같은 날 나온 법무 검토
(`docs/legal-drafts/reviews/account-switch-30day-deletion-2026-08-27.md` ③-(가))는
정반대로 *"현행 `auth_gate.dart`의 「유지/교체」를 **대체**"*라고 썼다.
**두 문서가 서로 달랐고, 8일 동안 아무도 그 차이를 못 봤다** — 구현이 안 되고
있었으므로 부딪힐 일이 없었기 때문이다.

**globe2030님이 2026-09-04에 「유지」를 없애는 쪽으로 확정했다**:

> *"A 계정으로 로그인해서 명함을 등록하고, 로그아웃 후에 다른 B 계정으로
> 로그인을 하게 될 때. 유지하고 계속 쓰기가 의미가 있냐는 거였어. 그래서
> 로그인한 계정으로 데이터를 보이는 게 맞지 않냐였어."*

📌 **요지는 「계정마다 데이터가 유일해야 한다」**이다. 그래서 이 화면은
**선택이 아니라 안내**가 됐다 — 교체는 확정이고, 화면은 무엇이 일어나는지와
되돌리는 길을 말한다.

⚠️ **잃는 것도 적어 둔다.** 「유지」는 *"같은 사람이 로그인 수단을 바꿨을 때
명함을 새 계정으로 옮기는 유일한 통로"*이기도 했다(backlog 4887행,
*"고객이 구글에서 카카오로 로그인 변경을 해달라고 하면?"*). **그 통로는 이
결정으로 닫힌다.** 대신 이전 계정의 서버 백업은 그대로 살아 있어 그 계정으로
로그인하면 복원된다.

### 실제 문구 (구현된 것)

```
제목: 지금 로그인한 계정의 명함을 보여드립니다

이 기기에는 이전에 쓰시던 계정의 명함·프로필이 남아 있었습니다.
계정마다 데이터를 따로 두므로, 이 기기의 화면은 지금 로그인하신
계정의 데이터로 바뀝니다.

이전 계정의 명함은 그 계정의 서버 백업에 그대로 있습니다.
그 계정으로 다시 로그인하시면 복원됩니다.

이 기기에 남아 있는 이전 계정의 명함 사진은 30일 뒤 이 기기에서
삭제됩니다. 그 전에 이전 계정으로 다시 로그인하시면 삭제되지 않습니다.

[알겠습니다]   [지금 바로 삭제]
```

「지금 바로 삭제」에는 **한 번 더 확인**을 뒀다(되돌릴 수 없다). 법무 검토
③ 요소 6(*"지금 바로 지우는 길"*)이며, §36(삭제 요구)의 실질적 통로가 없으면
*"왜 30일이나 붙잡느냐"*에 답할 수단이 없다.

⬜ **아직 안 만든 것 — 설정 화면의 「이전 계정 데이터」 행**(법무 검토 ③-(나)).
*"다이얼로그는 한 번 지나가면 다시 볼 수 없다"*가 그 근거다. 이번 범위에서
빠졌음을 여기 남긴다.

### 옛 초안 (참고용 — 채택되지 않음)

기존 문구에 이어 붙이는 형태로 설계했던 안이다. **기존
문장은 그대로 두고**, "교체"에 대한 문단 뒤에 30일 안내를 추가한다.

```
제목: 다른 계정으로 로그인했습니다

이 기기에는 이전에 쓰던 계정의 명함·프로필 데이터가 남아 있습니다.

유지하면 이 기기의 명함이 지금 로그인한 계정의 데이터가 되고,
이후 저장·수정할 때 지금 계정의 서버 백업에 함께 저장됩니다.
이전 계정과 지금 계정이 같은 분이 아니라면 교체를 선택해 주세요.

교체해도 이전 계정에 백업된 명함은 지워지지 않으며,
그 계정으로 다시 로그인하면 복원됩니다.

다만 이 기기에 남아 있는 이전 계정의 명함 사진은
30일 뒤 이 기기에서 삭제됩니다. 그 전에 이전 계정으로
다시 로그인하시면 계속 이용하실 수 있습니다.

[유지하고 계속 쓰기]   [현재 계정 데이터로 교체]
```

**문구를 고른 이유**:
- "이 기기에서 삭제됩니다"라고 못 박아, "계정 자체가 삭제된다"는 오해를
  막는다(실제로 서버는 안 지운다).
- "명함 사진"으로 한정했다(1절에서 정한 스코프와 일치) — 텍스트는 이미
  "유지/교체" 설명에서 다뤄졌고, "사진"만 새로 등장하는 개념이라 별도로
  짚었다.
- "그 전에 다시 로그인하시면 계속 이용하실 수 있습니다"로 **되돌리기 방법을
  같은 문단에 붙였다** — 사용자가 "30일 뒤 삭제"만 보고 겁먹지 않게.
- 4-4의 조건부 경고(업로드 안 된 사진이 있을 때)를 넣기로 하면, 이 문단
  바로 뒤에 "그중 N장은 아직 서버에 저장되지 않아 삭제 후 복구되지 않을 수
  있습니다"를 추가한다.

## 7. 검증 등급과 확인 항목

CLAUDE.md 4절 표에 따르면 **저장·복원·마이그레이션·탈퇴에 관련된 변경은
전체 테스트(실기기) 대상**이다. 계정 전환은 이 넷 모두에 걸쳐 있어(로컬
삭제+복원+계정 간 이동) 전체 테스트가 필요하다는 데 의문의 여지가 없다.
아래는 **배포 직전 전체 테스트에서 이 기능에 한해** 확인해야 할 항목이다
(다른 항목과 함께 돌리는 전체 테스트 체크리스트의 일부로 편입).

```
[ ] 1. 계정A로 로그인 → 사진 포함 명함 N장 등록 → Cloud Storage에
      실제로 업로드됐는지 확인(관리자 콘솔 또는 Firebase CLI로 실측,
      "계산"이 아니라 "실측"으로 남길 것)

[ ] 2. 로그아웃 → 계정B로 로그인 → "다른 계정으로 로그인했습니다"
      다이얼로그에서 5절의 새 문구(30일 언급)가 실제로 보이는지 확인

[ ] 3. "현재 계정 데이터로 교체" 선택 → 기기 파일 탐색(adb run-as 등)으로
      `contact_card_<A의 각 id>.enc` 파일이 **즉시 지워지지 않고**
      그대로 남아 있는지 확인(즉시 삭제가 아님을 실측)

[ ] 4. 🚨 가장 중요: B 계정으로 새 명함을 등록(사진 포함) →
      A의 잔존 파일 삭제 절차가 돌 때 **B가 방금 등록한 사진 파일이
      하나도 함께 지워지지 않는지** 확인 — contactId 스코프가 정확한지의
      핵심 검증. 잘못되면 현재 계정 사진이 날아가는 사고가 된다

[ ] 5. (30일 경과를 앞당길 수 있는 디버그 경로가 있다면) 예약 만료 후
      앱 재실행 → A의 `.enc` 파일들과 로컬 키(`enc_key_v1_<A_uid>`)가
      실제로 삭제됐는지 확인. 키 확인은 `getOrCreateUserKey(A)`를
      다시 부르면 서버본(`users/A.encryptionKeyB64`)으로 정상 대체
      되는지로 간접 확인 가능

[ ] 6. 30일 이내에 계정A로 재로그인 → 다이얼로그에서 "교체" 선택 →
      텍스트·사진이 정상 복원되는지, 그리고 이후 예약이 취소되어
      로그아웃해도 A의 파일이 재삭제 대상에 남지 않는지 확인

[ ] 7. 여러 번 전환(A→B→C) 시나리오 — 각 계정의 예약이 독립적으로
      잡히고, 잘못된 uid가 취소/삭제되지 않는지 확인

[ ] 8. 내 프로필 사진(`_my_profile_card`)은 이번 기능 대상에서 제외됐다
      — 기존 동작(전환 후 새로 설정하면 즉시 덮어써짐)이 그대로인지
      회귀 확인만 하고, 새로 30일 삭제 대상에 들어가지 않았는지 확인

[ ] 9. 전 과정에서 A 계정의 **서버 데이터**(Firestore 문서, Cloud
      Storage 사진)가 전혀 지워지지 않았는지 Firebase 콘솔/CLI로 실측
      — "기기 로컬 한정" 스코프가 지켜졌는지의 핵심 검증
```
