# 한 사람의 명함들을 칸으로 나눠 보관한다 — 설계

> **2026-08-28 개정** — 처음엔 「이력(history)」으로 잡았다. globe2030님 둘째
> 말씀이 그것을 바꿨다.
>
> *"한사람이 두 회사를 **겸직**해서 명함이 둘인 경우는 어느 명함을 **표시명함**
> 으로 할지 결정하게 하면 된다"*
>
> 🚨 **겸직은 「과거」가 아니다. 둘 다 지금 유효하다.**
>
> ```
> ❌ cardHistory  "지나간 것들"        겸직을 못 담는다
> ✅ cards        "이 사람의 명함들"    그중 하나가 표시(primary)
> ```
>
> ⭐ **자료 구조는 같은데 이름이 뜻을 정한다.** 「이력」으로 만들면 나중에
> 겸직을 넣을 때 구조를 다시 짜야 한다. **지금 바꾸면 공짜다.**
>
> 📌 그러면 이직과 겸직이 **같은 기능 하나**로 덮인다.
> ```
> 이직   새것이 표시가 되고 옛것도 목록에 남는다
> 겸직   둘 다 유효하고 표시만 고른다
> ```
> ⚠️ 파일 이름은 그대로 둔다 — 여러 곳이 이 경로를 참조한다.

작성 2026-08-28 · **코드 변경 없음. 설계만.**

> globe2030님: *"이름도 같고 휴대폰이 같은데 **회사를 이직**하면 이전 명함을
> **히스토리로 기억**되야 된다는 거."* → *"**칸으로 나눠 보이게 해줘**"*

---

## 0. 먼저 — 이 기능은 이미 있다. 그런데 세 군데가 새고 있다

`grep -rn "CardHistoryNote" lib` · `grep -n "이전 정보" add_card_modal_view.dart`
로 실물을 열어 확인한 것이다.

```
있는 것   _showKeepHistoryDialog  「기록으로 남기기」/「삭제」   add_card_modal_view:3349
          기록 만들기              :3396~3413
          읽기                     card_history_note.dart
          화면                     contact_detail_view:344  「이전 명함 N건」
```

**만들 것은 「이력 기능」이 아니라 「이력이 새지 않는 구조」다.**

### 🚨 새는 곳 ①  — 「그래도 추가」로 가면 이력 경로에 아예 안 간다

```
add_card_modal_view:2368   첫 창  [취소] [그래도 추가]
                                          └→ 새 명함이 된다. 이력 창까지 안 간다
add_card_modal_view:3308   둘째 창 [기존 정보 유지] [최신 정보로 업데이트]
                                                    └→ 여기서만 이력이 남는다
```

📌 **오늘 「안성률」이 두 장이 된 경로가 이것이다.** 구조를 아무리 잘 만들어도
**이 길이 열려 있으면 이력이 안 쌓인다.** UI/UX 설계(PR #639)의 「첫 창 제거」와
**한 묶음**이다.

### 🚨 새는 곳 ②  — **메모를 고치면 이력이 지워진다**

```
add_card_modal_view:493    _memoController = TextEditingController(text: c?.memo ?? '')
add_card_modal_view:3119   memo: _memoController.text.trim()
card_history_note.dart:55  static String userMemo(...)   ← 🚨 부르는 곳이 0건
```

확인한 명령: `grep -rn "userMemo" lib` → **정의 한 줄만 나온다.**

**편집 화면이 메모 칸에 이력 줄까지 통째로 띄우고, 저장할 때 그 텍스트를 그대로
덮어쓴다.** 이용자가 메모를 정리하면서 이력 줄을 지우면 **이력이 사라진다.**
`userMemo`는 그것을 막으려고 만들어졌는데 **아무도 안 쓴다.**

⚠️ CLAUDE.md 4절 표의 *"서비스는 정상, 부르는 쪽이 없음"* 과 같은 자리다.

### 🚨 새는 곳 ③  — 기록할 때 **빈 칸이 통째로 빠진다**

```dart
// add_card_modal_view:3396~3412
final oldFields = [
  if (existing.company.trim().isNotEmpty) existing.company,
  if (existing.title.trim().isNotEmpty) existing.title,
  ...
].join(' / ');
```

**값이 없는 칸은 아예 안 들어간다.** 그래서 조각 개수가 명함마다 다르고,
*"세 번째 조각이 부서인지 휴대폰인지"* 를 알 방법이 없다.
주소에 `/` 가 들어가면 더 어긋난다.

📌 `card_history_note.dart` 주석이 이미 이렇게 적어 뒀다 —
*"칸이 제대로 나뉜 이력이 필요하면 **저장 구조를 바꾸는 것**이 답이지 이
문자열을 파싱하는 것이 아니다."* **이번 일이 그 「저장 구조를 바꾸는 것」이다.**

---

## 1. 무엇을 저장하나 (PM 물음 ①)

**명함 한 벌 + 언제 들어왔나.** 「지나간 것」이 아니라 **이 사람의 명함 한 장**이다. 값이 없던 칸은 **`null` 로 명시해 남긴다** —
"없었다"와 "모른다"가 갈려야 한다.

```
date          바뀐 날 (YYYY-MM-DD)
company       회사명
title         직함
department    부서
phone         휴대폰
officePhone   사무실 전화
directPhone   직통
fax           팩스
email         이메일
website       웹사이트
address       주소
addressDetail 상세주소
postalCode    우편번호
```

⚠️ **이름은 안 넣는다.** 이력이 붙는 조건이 *"이름·휴대폰이 같은 사람"* 이라
이름은 안 바뀐다. 넣으면 모든 이력에 같은 값이 반복된다.

⚠️ **사진·태그·관심사·좌표·메모·소통이력은 안 넣는다.** 명함에 인쇄된 것이
아니라 **이용자가 쌓은 것**이라 이직해도 이어지는 값이다(지금도 그렇게 돈다).

---

## 2. 어디에 저장하나 (PM 물음 ②) — **`ContactModel` 에 `cards` + `primaryCardIndex`**

⚠️ 이름을 `cardHistory` 로 하지 않는다 — 위 개정 참고. **표시할 것을 가리키는 값이 함께 필요하다.**

```
❌ memo 안에 JSON     새는 곳 ②가 그대로 남는다. 이용자가 지울 수 있는 곳에
                      지우면 안 되는 것을 두는 셈이다
✅ 새 필드 cards        이용자가 손댈 수 없는 자리
   + primaryCardIndex   어느 것을 표시할지 (기본: 가장 최근 것)
```

📌 **`memo` 안은 안 된다는 근거가 이미 실물에 있다** — 위 「새는 곳 ②」.
**같은 실수를 구조로 반복하게 된다.**

### 서버 백업

`toBackupJson` 에 **포함한다**(`contact_model.dart:212` 의 `memo` 와 같은 자리).

- 지금도 이력이 `memo` 안에 있어 **이미 서버에 올라가고 있다.** 새 필드로
  옮기는 것은 **새 수집이 아니라 자리 옮김**이다.
- 기기를 바꾸면 이력이 사라지는 것이 맞지 않다 — 좌표(파생값)와 성격이 다르다.

⚠️ **방침 문서는 안 고쳐도 된다고 본다**(보내는 항목이 늘지 않으므로). 다만
**법무 세션 확인을 받는 편이 안전하다** — 판단은 사용자.

### 마이그레이션

`fromJson` 에서 필드가 없으면 **빈 목록**. 옛 데이터가 그대로 열린다.

## 3. 이미 쌓인 이력 (PM 물음 ③) — **옛 것은 옛 모양 그대로 둔다**

⭐ PM 안대로 간다. **추측해서 칸에 배치하지 않는다.**

```
옛 이력 (memo 안 문자열)   그대로 둔다. CardHistoryNote 로 계속 읽는다
새 이력 (cardHistory)      칸으로 보여 준다
상세 화면                  둘을 함께, 날짜순으로 섞어 보여 준다
```

📌 **옮기지 않는 이유**: 조각이 어느 칸인지 모른다. 넣으면
*"틀린 이력이 그럴듯하게"* 남는다 — CLAUDE.md 4절 *"가짜 데이터를 만들지
않는다"* 에 걸린다.

⚠️ **옛 이력은 시간이 지나면 자연히 줄어든다.** 새로 쌓이지 않으므로.

---

## 4. 몇 벌까지 쌓나 (PM 물음 ④) — **상한 없음. 대신 재고 정한다**

한 벌이 대략 **200~400바이트**(칸 13개, 대부분 짧음). 이직이 잦아도 **한 사람에
5벌을 넘기 어렵다** → **2KB 안쪽**.

⚠️ **이건 계산이다. 실측이 아니다.** 명함 103장 기준으로 재면 확정된다 —
**구현 전에 잴 필요는 없고, 붙인 뒤 진단 화면에서 세면 된다.**

📌 **상한을 지금 두지 않는 이유**: 상한이 있으면 **오래된 이력이 조용히
사라진다.** 이력의 값어치는 오래된 것에 있다. **커지면 그때 재고 정한다.**

## 5. 삭제 (PM 물음 ⑤)

```
명함을 지우면          이력도 함께 지워진다 (같은 문서 안이므로 자동)
이력만 지우기          🚨 필요하다 — 지금도 「삭제」 갈래가 있다(:3349)
                       그 선택을 그대로 잇는다: 「기록으로 남기기」/「삭제」
이력 한 벌만 지우기     이번 범위 밖. 필요하면 나중에
```

⚠️ **제3자 개인정보라 지울 수 있어야 한다.** 명함 삭제로 함께 지워지므로
개인정보 보호법상 파기 요구는 충족된다.

## 6. 화면 — UI/UX 세션 몫

로직이 주는 것만 적는다.

```
List<CardHistoryEntry>   날짜 내림차순
각 항목                  칸 이름 + 값 (값이 null 인 칸은 화면이 뺀다)
🚨 「무엇이 바뀌었나」     이전 벌과 지금 값을 비교해 다른 칸만 강조할 수 있다
                        ← PM이 「합치기」에 요구한 그것과 같은 재료다
```

⭐ **이 구조가 있으면 「합치기」 확인창의 「무엇이 바뀌는지 보여 주기」도 같은
재료로 만들 수 있다.** 두 일이 한 구조를 쓴다.

## 7. 검증 — **전체 테스트가 붙는다**

`ContactModel` 에 필드가 느는 **저장 구조 변경**이다(CLAUDE.md 4절 표).

```
저장·복원·마이그레이션·재설치 왕복
서버 백업·복원에 이력이 실리는지
옛 데이터(필드 없음)를 열었을 때 안 깨지는지
```

⚠️ **배포 직전에 몰아서 한다.** 지금은 부분 테스트 + 자동 테스트로 쌓아 둔다.
