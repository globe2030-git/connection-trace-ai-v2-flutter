## 1. 🚨 전제 정정 — 관리자는 이미 볼 수 있다

처음 요청은 *"암호화된 자료를 관리자가 볼 수 없으니 평문으로 저장하자"* 였다.
**앞부분이 사실과 다르다.**

```
암호문   users/{uid}/cards/{id}.encrypted
키       users/{uid}.encryptionKeyB64        ← 같은 프로젝트 · 같은 문서 트리
```

코드 주석이 그 한계를 **일부러 적어 뒀다**(`encryption_key_service.dart:19`,
`data_backup_service.dart:22`):

> *"Firestore 프로젝트 관리자 권한을 가진 사람은 이론적으로 키와 암호문 둘 다에
> 접근할 수 있다 — 완전한 제로-지식 암호화는 아니다."*

그리고 **붙는 도구도 이미 있다** — `tool/_firebase_admin.py` 가 Admin SDK 로
접속하고 `tool/verify_server_privacy.py` 가 실제로 서버 명함을 읽는다.

> **못 보는 것이 아니라, 「읽어서 보여 주는 화면」을 안 만든 것이다.**

### 그래서 평문 저장을 안 한다 — 얻는 것 하나, 잃는 것 셋

**얻는 것**: Firebase 콘솔에서 **눈으로 바로** 읽는 편의 하나.

```
① 이 저장소가 이미 「결함」으로 판정한 상태로 돌아간다
   verify_server_privacy.py 머리말: "명함 5건 중 3건이 이름·전화번호·이메일·
   주소까지 평문으로 읽히는 상태였다(추가 77)"
   🚨 릴리스 체크리스트의 「평문 문서가 없는가」 검사가 항상 실패하게 된다

② 개인정보처리방침 세 줄이 거짓이 된다 (2026-09-05 실측, 행 번호 확인)
   1035행  "기기에 저장할 때와 서버에 저장할 때 모두 AES-256-GCM 방식으로 암호화합니다"
    533행  "회사 서버(Cloud Firestore·Cloud Storage, 서울 리전)에도 암호화하여 저장"
   1041행  "저장 시 암호화하고 본인 계정으로 인증된 이용자만 접근할 수 있도록 통제"

③ 유출 시 피해가 달라진다
   이 앱이 담는 것은 이용자 본인이 아니라 **명함 주인**의 개인정보다
   가입한 적도 동의한 적도 없는 제3자다
```

📌 **①②는 명함 데이터를 버려도 안 사라진다** — 2026-09-05에 받은
*"테스트 데이터라 지워도 된다"* 조건이 안 덮는 부분이다.

⭐ **그리고 조회 화면이 평문 저장보다 오히려 낫다** — **누가 언제 누구 자료를
봤는지 기록이 남는다.** 콘솔에서 평문을 눈으로 훑는 것은 **우리 쪽에 아무
기록도 안 남는다.**

## 2. 지금 관리자 인증의 구멍 다섯 (2026-09-05 실측)

관리자 콘솔은 **이미 운영 중**이다(`https://connection-sense-admin.web.app`).
지금 잠금장치는 이것뿐이다.

```
Google 계정 로그인  +  이메일 화이트리스트 2개  +  email_verified
```

| | 구멍 | 근거 |
|---|---|---|
| 1 | **2단계 인증이 없다** — 구글 계정 하나가 뚫리면 전부 열린다 | 사용자 지적 |
| 2 | **세션이 안 끊긴다** — refresh token 이 계속 갱신된다. 브라우저를 닫아도 유지 | 유휴 만료 코드 없음 |
| 3 | **허용목록이 두 곳**(`firestore.rules` + `adminEmails.ts`)이고 손으로 맞춘다 | ADMIN-VULN-001 · README *"단일 원본 전환은 후속 과제"* |
| 4 | **개인 메일이 아직 관리자**(`globe@creamhouse.net`) | README *"정리하고 싶으면 빼도 된다"* |
| 5 | 🚨 **감사 기록을 건너뛸 수 있다** | `firestore.rules:237` 주석이 직접 인정 |
| 6 | 🚨 **Functions 테스트를 CI 가 안 돌린다** | 워크플로에 `npm test` 가 없다 (17개 파일이 수동 전용) |

5번 원문 그대로:

> *"악성/탈취 관리자가 **대상 문서만 쓰고 감사 기록 호출을 의도적으로 생략**하면
> 아무것도 안 남는다."*

⭐ **감사 기록이 옵션이면 감사가 아니다.** 여기에 「명함 조회」가 더해지면
**누가 남의 명함을 봤는지도 안 남는다.**

📌 **6번은 이번에 새로 찾았다.** 관리자 인증 로직이 들어갈 자리가 바로
**테스트가 안 도는 자리**다. 1단계에서 함께 닫는다.

## 3. 설계 — 네 가지 결정

### 3-1. 세션 상태를 **Firestore 문서**에 둔다 (커스텀 클레임 아님)

```
❌ 커스텀 클레임   유휴 20분은 「활동할 때마다 연장」인데 ID 토큰은 최대 1시간
                  캐시된다 → 활동마다 강제 갱신이 필요해 무겁다
                  🚨 그리고 **즉시 차단이 안 된다** — 계정 탈취를 알아도
                     토큰이 살아 있는 동안은 유효하다
✅ adminSessions/{uid}   그 자리에서 끊긴다
```

담는 것:

```
otpVerifiedAt   휴대폰 인증을 통과한 시각
lastActiveAt    마지막 활동 시각
phoneHash       어느 번호로 인증했나 (감사용, 원문은 저장하지 않는다)
```

### 3-2. 🚨 하트비트도 **Callable** 로 한다 — 로직을 한 곳에 둔다

처음에는 클라이언트가 `lastActiveAt` 을 직접 쓰게 하려 했다. **그러면 rules 가
「지금 세션이 살아 있나」를 스스로 판정해야 하고, 만료 계산이 rules 와 TypeScript
두 곳에 생긴다.** 구멍 3(허용목록이 두 곳)과 **정확히 같은 구조**다.

```
adminSessions/{uid}   allow read, write: if false     ← 전면 차단. Admin SDK 만
```

⭐ **그래서 만료 계산이 TypeScript 한 곳에만 있다.** 클라이언트가 못 쓰므로
**죽은 세션을 하트비트로 되살리는 경로**도 원천적으로 없다.

⚠️ **대가**: 활동 중 하트비트마다 함수 호출이 하나 는다. 관리자가 두엇이므로
비용은 무시할 수준이다(계산이다 — 실측이 아니다).

### 3-3. 만료는 둘이다 — 유휴 20분 **그리고** 절대 상한 12시간

```
유휴 만료    20분 무활동            (2026-09-05 사용자 확정)
절대 상한    12시간                 활동이 계속돼도 다시 인증한다
```

🚨 **절대 상한이 없으면 탭 하나를 열어 둔 채 영원히 산다.** 유휴만으로는
「자리를 비운 브라우저」는 막아도 「계속 열어 둔 브라우저」는 못 막는다.

📌 **유휴 만료가 막는 것과 못 막는 것을 정확히 적어 둔다.**

```
막는 것    자리를 비운 브라우저 · 잠그지 않은 화면 · 공용 PC
못 막는 것 🚨 세션을 쥔 공격자 — 공격자도 하트비트를 보낸다
```

⚠️ **어떤 구현도 후자를 못 막는다.** 후자를 잡는 것은 **§3-4 의 기록**이다.

### 3-4. ⭐ 조회는 **Callable 로만** — rules 에 관리자 예외를 만들지 않는다

이것이 이 설계의 핵심이다.

```
❌ rules 에 "관리자면 남의 cards 도 읽기 허용" 을 넣는다
   → 관리자가 콘솔에서 그냥 읽을 수 있고, 그러면 기록을 우회한다
   → 구멍 5 를 그대로 복제한다

✅ cards 는 계속 본인만 읽는다. 관리자는 Callable 로만 읽는다
   → 그 Callable 이 **같은 트랜잭션에서** 조회 기록을 쓴다
   → 🚨 기록 없이는 조회가 불가능해진다
```

⭐ 이것이 `firestore.rules:237` 주석이 말한 *"완전한 원자성"* 패턴이다 —
`grantBonusCredits`(`creditGrantAudits`)가 이미 쓰고 있다.

⚠️ **정직하게**: Firebase **콘솔**에서는 프로젝트 소유자가 여전히 읽을 수 있다.
이 설계가 막는 것은 **앱·관리자 콘솔 경로**다. 콘솔 접근은 Google Cloud IAM 의
몫이고 이 문서의 범위가 아니다 — **막았다고 쓰지 않는다.**

### 3-5. 3단계 설계 — 복호화 조회 Callable (2026-09-05, 개발A)

⚠️ **이 절은 설계만이다. `functions/src` 는 한 줄도 안 건드렸다.** 법무 답이
나오기 전에는 짓지 않는다(아래 「먼저 답이 있어야 하는 것」).

#### 서버가 키를 얻는 길 — **새로 저장할 것이 없다**

```
users/{uid}.personId  →  people/{personId}.uids  →  각 users/{uid}.encryptionKeyB64
```

Firestore 읽기 **세 번**이면 키 목록이 모인다. `data-schema.md:206` 이
*"키링이 여기서 키를 모은다"* 라고 이미 명시하고 있다.

🚨 **키링을 서버에 따로 저장하지 않는다.** 저장하면 진실의 원천이 둘이 되어
잇기·끊기에서 어긋나고, **키를 한 군데 더 쌓는 것 자체가 위험을 늘린다.**
키는 계정마다 그대로 두고 **모으는 일만** 한다.

#### 🚨 「어느 키로 잠갔는지」 표시는 **없다** — 저장 코드로 확인했다

```
data_crypto_service.dart:40   encryptJson 반환값
  "nonce + ciphertext + MAC 을 이어붙여 base64 문자열 하나로 인코딩한 것
   — 별도 필드 구조 없이 문자열 하나로 저장/전송하기 위함"
```

⚠️ **후보 이름(`keyVersion`·`keyId`·`encVersion`·`keyUid`)을 grep 해서 안 나온
것이 근거가 아니다** — `grep` 은 이름을 알아야 찾으므로 「없다」를 말할 수 없다
(규약 4장). **저장하는 쪽을 열어서 확인했다.**

**그래서 키를 차례로 시도하고 `DataDecryptionException`(MAC 불일치)을 잡는
수밖에 없다** — `data_crypto_service.dart:172` 의 `decryptJsonWithAny` 와 같은
모양이다. ⭐ **성공한 키가 곧 「그 명함이 어느 계정 것이었나」다** — 조회 기록에
남길 값이 있다.

#### ⚠️ 키 순회는 **여기서 정하는 것이 아니다** — 이미 정해져 있다

🚨 **이 절을 처음 쓸 때 「키를 차례로 시도한다」를 새로 정하는 것처럼 적었는데,
`암호화키-계정잇기-설계-2026-09-04.md` 가 이미 정해 두었다.** 원본을 안 열고
썼다 — [추가 669] 의 *「① 원본으로 돌아간다」* 에 걸린 자리라 경위를 남긴다.

```
§5-2  복호화는 순서대로 시도한다
      ① 마지막에 연 키가 기억돼 있으면 그것부터  ② 현재 계정의 키
      ③ 키링의 나머지를 차례로  ④ 전부 실패하면 «못 읽는 명함» 으로 화면에 말한다
§5-3  성공한 키를 기억한다 — 🚨 **기기 로컬에만. 서버에 안 보낸다**
§5-4  재암호화는 선택이지 전제가 아니다
§6    비용은 **아직 안 쟀다** — *"최악은 명함 수 × 키 수이지만 이것은 계산이다"*
```

**그러므로 3단계가 하는 일은 「정하는 것」이 아니라 「서버에 적용하는 것」이다.**

```
① 키 순회      §5-2 를 서버에서 그대로 한다
               ⚠️ 다만 §5-2 의 ①(로컬 캐시)은 서버에 없다 — ②③만 남는다
               오늘 knownKeysFor(uid) 는 키 하나짜리 목록이라 동작이 같다
               (encryption_key_service.dart:160)
② 경로 헬퍼     앱의 lib/core/utils/account_paths.dart 와 같은 모양으로 서버에도
               ⭐ 이쪽은 3단계에서 새로 정하는 것이 맞다
```

#### 🚨 §5-3 과 조회 기록이 정면으로 부딪힌다 — **여기서 못 정한다**

```
§5-3      성공한 키를 기억한다 → **기기 로컬에만. 서버에 안 보낸다**
조회 기록  「어느 uid 키로 열렸는지」를 남긴다 → **서버에 쓴다**
```

**둘 다 이유가 있다.**

```
§5-3 쪽   명함 ↔ 계정 대응이 서버에 쌓이면
          「그 사람이 어느 계정을 거쳐 왔는지」가 서버에 남는다
3단계 쪽   조회 기록의 값은 「무엇을 봤는가」에 있고,
          어느 계정 것이었나가 그 일부다
```

✅ **법무 답이 왔다 (2026-09-05) — 「병」이다.**

```
갑  조회 기록에 키 uid 를 안 남긴다        ❌ **법이 요구하는 것을 스스로 지우는 것**
을  남기되 §5-3 의 판단을 다시 본다        ❌ **필요 없다** — 아래
병  personId 만 남기고 uid 는 안 남긴다    ✅ **채택**
```

🚨 **「을이 필요 없다」가 이 답의 핵심이고, 내가 못 본 자리다.** 나는 둘이
부딪힌다고 읽었는데 **애초에 안 부딪혔다.**

```
§5-3 이 막는 것      「명함 → 그것을 연 키의 uid」 **전수 대응표**
접속기록이 남기는 것   **열람한 그 건** 하나
```

⭐ **다른 자료다.** 전자는 그 사람의 계정 이력을 통째로 재구성할 수 있게 하고,
후자는 *"관리자가 이 명함을 언제 봤다"* 만 남긴다. **§5-3 을 다시 볼 이유가 없다.**

📌 **왜 못 봤나 — 「같은 필드가 들어간다」는 것만 보고 「같은 자료」로 읽었다.**
`uid` 라는 글자가 양쪽에 나오니 충돌로 보였는데, **무엇이 얼마나 쌓이는지**가
다르다. ⚠️ **다음 사람도 똑같이 헷갈릴 자리라 경위를 남긴다.**

⭐ **그리고 갑·을·병을 세운 방식 자체가 틀렸었다.** 셋을 전부 **「무엇을 안
남길까」** 로만 세웠는데, 물어야 할 것은 **「어느 쪽이 무겁고 둘을 어떻게
조화시키나」** 였다. **선택지를 한 방향으로만 세우면 답이 그 안에 없을 수 있다** —
실제로 갑은 **법이 요구하는 것을 지우는 선택**이었다.

#### ✅ 조회 기록에 남기는 것 (법무 확정)

```
personId          ⚠️ uid 가 아니다
명함 id
사유
IP
expireAt
보관 기간          **2년**
```

📌 **방침 문안은 v2.8 로 미룬다**(법무 판단) — *"3·4단계가 아직 없는데 적으면
과장이다."* 🚨 **그러므로 이 절이 확정됐다고 방침을 먼저 고치지 말 것.**

⚠️ **「§5-3 과 부딪히니 안 남긴다」가 답이 아닐 수 있다.** **조회 기록 자체는
개인정보 안전성 확보조치(접근기록 보관) 쪽에서 오히려 요구되는 것**으로 보인다.
그러면 갑은 법이 요구하는 것을 스스로 지우는 셈이 된다. **어느 쪽이 무겁고 둘을
어떻게 조화시키는지**가 질문이다.

✅ **2026-09-05 — 법무 검토에 올렸다(④). 비어 있는 것이 아니라 답을 기다리는
것이다.** 함께 올린 것 셋은 아래 「법무에 함께 올릴 것」이고, **보관 기간(⬜)도
같은 질문에 묶여 있다.** 🚨 **답이 오기 전에 갑·을·병 중 하나를 골라 짓지
않는다** — 지으면 ⬜ 를 짐작으로 메우는 것이 된다.

#### ⚠️ 비용은 관리자 경로에서 달라진다

§6 이 *"대부분 첫 키에서 열리고, 틀린 키의 실패는 MAC 검사라 싸다"* 라고
적었는데 **그 전제는 앱**이다 — 로컬 캐시(§5-2 ①)가 첫 시도를 맞히기 때문이다.

🚨 **서버에는 그 캐시가 없다.** 관리자가 한 사람의 명함을 통째로 열면
**명함마다 키를 처음부터 시도**한다. ⬜ **그래서 §6 의 ⬜ 셋(명함 한 장
복호화 시간 · 사진 한 장 · 계정당 장수 분포)은 3단계에도 그대로 열려 있다.**
⚠️ **재기 전에는 「빠르다」고 쓰지 않는다** — §6 이 스스로 *"이것은 계산이다.
실측이 아니다"* 라고 적어 두었다.

🚨 **②가 없으면 C안 뒤에 아무것도 못 찾는다** — 키만 바뀌는 것이 아니라
**읽는 자리 자체가 옮겨간다**(`data-schema.md:197`).

```
계정에 남는 것   users/{uid}                    ← personId · encryptionKeyB64
사람으로 가는 것  users/{uid}/contacts           ⚠️ people/{personId}/contacts 로
                users/{uid}/cardSources        ⚠️ 함께
                users/{uid}/deletedContacts    ⚠️ 함께
```

📌 **명함을 읽는 3단계는 「사람으로 가는 쪽」이다.**

#### 🚨 서버와 앱이 비대칭이다 — §7 에 한 줄 보탠다

⚠️ **새 발견이 아니다.** `암호화키-계정잇기-설계-2026-09-04.md` §7(파기)이
*"계정 전환 — 그 서비스가 지우는 `enc_key_v1_<uid>` 가 바로 이 키다"* 라고
이미 짚었다. **다만 「서버 사본은 남는다」가 거기 안 적혀 있다** — 그 한 줄을
보탠다.

```
leftover_account_purge_service.dart:245   지우는 것: deleteLocalKey(uid) 하나뿐
같은 파일 :26-30   "이전 계정의 서버 백업(Firestore 텍스트 · Cloud Storage 사진)은
                   이 서비스가 절대 건드리지 않는다. 몇 년 뒤에 그 계정으로
                   로그인해도 복원된다"
```

```
앱     로컬 키가 30일 뒤 지워진다   →  그 기기에서는 못 연다
서버   encryptionKeyB64 가 남는다   →  🚨 관리자는 열 수 있다
```

⚠️ **관리자는 「이용자 본인이 그 기기에서 못 여는 명함」을 열 수 있다.**
🚨 **버그가 아니다** — *"몇 년 뒤에도 복원된다"* 가 이 앱의 약속이고, 서버 키가
남는 것이 그 약속의 실현 수단이다. **고칠 일이 아니라 적어 둘 일이다.**

⭐ **그리고 이 비대칭이 3단계를 [추가 675·677] 에서 구해 준다.**
`encryption_key_service.dart:145-155` 이 *"키를 더하는 날 지우는 쪽도 함께 봐야
한다 — 잇기로 키링에 올린 키를 저쪽은 「이전 계정 것」으로 보고 30일 뒤에
지운다"* 고 경고하는데, **그것은 로컬 키 이야기라 서버는 안 걸린다.**

🚨 **그래서 더 위험하다 — 서버에서 테스트하면 통과하는데 앱에서만 깨진다.**
그 자리는 C안 1단계(앱)의 몫이다. **여기 적어 두는 것은 「3단계가 안 걸린다」를
안 걸린다는 이유로 잊지 않기 위해서다.**

## 4. 관리자 휴대폰 번호를 어디에 두나

⭐ **새로 만들 것이 없다** — 알리고 + `phoneOtpConfirm` 이 이미 서 있고,
`phoneOtp.ts` 의 `verifyOtp` · `phoneHash` · `generateOtpCode` · `decideSend` 가
**전부 순수 함수**라 그대로 재사용한다.

번호는 `config/admins` 문서에 **해시로만** 둔다.

```
config/admins   { "<이메일>": "<번호해시>", ... }
                allow read, write: if false      ← 클라이언트는 읽지도 못한다
                Callable 이 Admin SDK 로만 읽는다
```

📌 **이 문서가 나중에 구멍 3(허용목록 두 곳)의 단일 원본이 된다.** 이번에는
**2차 인증 번호 조회용으로만** 쓰고, 이메일 판별까지 옮기는 것은 4단계다 —
원본을 셋으로 늘리지 않기 위해 **미래의 단일 원본 자리에 먼저 앉힌다.**

🚨 **관리자가 이 문서를 못 고치게 한다.** 고칠 수 있으면 관리자 하나가
**다른 관리자의 2차 인증 번호를 자기 것으로 바꿀 수 있다.**

**「대가」라는 이름으로 네 곳(커밋 메시지 · PR 본문 · backlog 679 · 이 문서)에
적었다.**

⭐ **틀린 방향도 기록해 둔다 — 「과소」가 아니라 「과대」였다.** 없는 비용을
경고하는 것은 안전해 보이지만, **다음 사람이 그 경고 때문에 필요한 검사를 안
붙인다.** 실제로 이 세션은 다른 세션에까지 *"CI 시간이 늘 것"* 이라고 알렸다.

📌 **왜 8초인가**(이건 실측 뒤에 붙인 설명이다): 의존성이 넷뿐이고
(`firebase-admin` · `firebase-functions` · `google-auth-library` · `typescript`)
전부 순수 JS 라 네이티브 빌드가 없다. `setup-node` 의 npm 캐시도 걸린다.

⚠️ **그래도 남는 것 하나**: 문서만 바뀐 PR 은 `paths-ignore` 로 여전히
건너뛴다 — 그 조건은 안 건드렸다.

🚨 **3단계를 1·2단계보다 먼저 하지 않는다.** 관리자 하나가 뚫린 상태에서
*"명함을 평문으로 보여 주는 화면"* 을 여는 것이 되고, 그 명함은 **동의한 적 없는
제3자의 것**이다.
