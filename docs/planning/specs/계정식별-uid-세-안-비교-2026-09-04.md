|  |  |

| **왜 지금** | 🚨 **uid 는 되돌릴 수 없고, 스토어 등록 전이 마지막 창이다**([추가 564]) |
| **전제 방침** | [`account-device-policy-2026-08-28.md`](./account-device-policy-2026-08-28.md) 결정 ① — 명함첩의 주인은 **사람**이고, 사람을 식별하는 것은 **휴대폰 번호** |

## 0. 출처 정정 — A·B안은 [추가 557]이 아니라 **[추가 564]**에 있다


⚠️ **한 번 잘못 붙은 출처는 그다음부터 아무도 안 의심한다**(CLAUDE.md 4절).

## 1. 지금 실물 — uid 가 어떻게 만들어지나 (2026-09-04 실측)

**무엇으로 쟀나**: `functions/src/socialAuth.ts` · `index.ts` 코드를 직접 열었고,
Firebase Phone Auth 사용 여부는 `lib/`·`functions/src/` 전체 `grep`.

| 로그인 수단 | uid 를 누가 정하나 | 형식 | 근거 |
|---|---|---|---|
| 구글 · 애플 | **Firebase** | Firebase 가 만든 임의 문자열 | `signInWithCredential` |
| 카카오 | **우리** | `kakao:{회원번호}` | `socialAuth.ts:45` |
| 네이버 | **우리** | `naver:{회원번호}` | `socialAuth.ts:45` |
| 이메일 | **Firebase** | Firebase 가 만든 임의 문자열 | email/password |

```
Firebase Phone Auth   ❌ 안 쓴다
                      PhoneAuthProvider · verifyPhoneNumber · signInWithPhone → 전부 0건
                      문자는 알리고로 직접 보내고 phoneOtpConfirm 이 우리 서버에서 검증한다
```

⚠️ **`grep` 이 못 보는 것**: 다른 이름으로 감싼 호출은 안 걸린다. 다만 Firebase
전화 인증은 SDK 심볼이 고정돼 있어 **이 경우엔 0건을 「안 쓴다」로 읽어도 된다** —
쓰고 있다면 저 셋 중 하나가 반드시 나온다.

### 이미 있는 「사람 → 계정」 매핑

```
phoneAccounts/{번호해시} → {uid, verifiedAt}      index.ts:2838
```

📌 **이것이 사실상 「사람」의 씨앗이다.** 지금은 uid 를 **하나만** 담고, 다른
uid 가 오면 `taken` 으로 막는다(`index.ts:2872`). 세 안의 차이는 결국
**이 문서를 어떻게 넓히느냐**로 귀결된다.

## 2. 세 안

### A안 — 전부 custom token 으로 통일한다

구글·애플도 `signInWithCredential` 대신 우리 서버가 발급한 custom token 으로
로그인시킨다. **uid 를 전부 우리가 정한다**(예: 번호 해시 기반).

```
지금   구글 → Firebase 가 uid 결정
바꿈   구글 → 우리가 ID 토큰을 검증하고 → 우리가 정한 uid 로 custom token 발급
```

**⭐ 얻는 것** — 한 사람 = 한 uid 가 **구조적으로** 성립한다. 로그인 수단이
몇 개든 uid 가 안 바뀌므로 「잇기」라는 개념 자체가 필요 없어진다.

**🚨 잃는 것 셋**

```
① 토큰 검증을 우리가 떠안는다
   지금은 Firebase 가 공개키 회전 · aud · nonce · 만료를 다 본다
   직접 하면 한 군데만 틀려도 남의 계정으로 로그인된다
   ⚠️ 이 앱은 제3자(명함 주인) 개인정보를 담는다 — 무게가 다르다

② 기존 이용자 uid 가 전부 바뀐다
   명함이 users/{uid} 아래 있어 전원 마이그레이션이 필요하고 되돌릴 수 없다

③ 애플 요구사항이 따로 붙는다
   계정 삭제 시 토큰 폐기(P1-37 과 같은 자리)
```

⚠️ **①③은 실측이 아니라 「일반 지식 + 문서 서술」이다.** 착수 전에 Firebase·
Apple 공식 문서 원문으로 확인해야 한다([추가 564] 가 이미 *"확인 못 한 것"* 을
가르라고 적어 둔 결이다).

---

### B안 — 전화번호 계정에 link 한다

Firebase 의 전화번호 계정을 기준으로 삼고, 다른 제공자를 그 계정에 `link` 한다.

**⭐ 얻는 것** — Firebase 표준 경로. **토큰 검증을 Firebase 가 계속 해 준다**
(A안의 허점 ①이 없다).

**🚨 그런데 지금 구조에서는 성립하지 않는다**

```
① 「전화번호 계정」이 존재하지 않는다
   Firebase Phone Auth 를 안 쓰기 때문이다(§1 실측)
   → 도입하려면 알리고를 버려야 한다
   → 🚨 알림톡 템플릿 승인(2026-09-04 승인 완료)과 그 심사가 통째로 무용지물
   → 문자 요금이 Firebase 로 넘어간다

② Firebase 는 이미 존재하는 두 uid 를 합쳐 주지 않는다
   link 는 "지금 로그인한 계정에 수단을 추가"이지
   "각자 데이터를 가진 두 계정의 병합"이 아니다
   → 결국 한쪽 데이터를 옮기고 그 계정을 지워야 한다
```

⚠️ **②도 공식 문서로 재확인이 필요하다.** 다만 ①만으로도 B안은 **알리고를
버리는 대가**를 치른다 — 알림톡이 승인된 지금 시점에 값이 맞지 않는다.

---

### C안 — uid 는 건드리지 않고 「사람」을 한 겹 올린다 (2026-09-04 신규 제안)

```
uid            지금 그대로 둔다 (provider 별)
「사람」        phoneAccounts 를 넓혀 여러 uid 를 담게 한다
명함첩 소유    uid 직접 참조에서 「사람」 참조로 옮긴다
```

**⭐ 얻는 것**

```
uid 를 안 바꾼다           → A안의 허점 ②③이 사라진다
Firebase 가 계속 검증한다   → A안의 허점 ①이 사라진다
알리고를 그대로 쓴다        → B안의 허점 ①이 사라진다
```

**⚠️ 대가 — 데이터 이전**

명함첩 소유를 `uid` 에서 「사람」으로 옮겨야 한다. **작지 않다.**

📌 **다만 결정적인 차이가 있다** — 옮기는 것이 **우리 Firestore 데이터**이지
**Auth 계정이 아니다.** 틀리면 **다시 옮길 수 있다.** uid 는 그렇지 않다.

⚠️ **C안이 A·B보다 낫다고 단정하지 않는다.** 이 문서를 쓰는 시점에 셋 중 유일하게
**실제로 만들어 본 적이 없는 안**이고, 데이터 이전 규모를 아직 안 쟀다(§5).

## 3. 비교표

| 기준 | A안 (custom token 통일) | B안 (전화번호 계정 link) | C안 (사람 레이어) |
|---|---|---|---|
| **되돌릴 수 있나** | ❌ uid 가 바뀐다 | ❌ 계정을 지워야 한다 | 🟡 데이터 이전이라 다시 옮길 수 있다 |

| **알림톡 승인 활용** | ✅ | ❌ 무용지물 | ✅ |
| **기존 이용자 영향** | 🚨 전원 uid 변경 | 🚨 계정 병합 필요 | 🟡 데이터 경로만 변경 |

| **스토어 출시 전 필수인가** | ✅ (uid 라서) | ✅ (uid 라서) | 🟡 **골격만 잡아 두면 뒤로 미룰 수 있다** |

## 4. 네 경우가 각 안에서 어떻게 되나

globe2030님이 물으신 네 경우다.

| | 무엇이 바뀌나 | A안 | B안 | C안 |
|---|---|---|---|---|
| ① | **기기만** (번호·계정 그대로) | 셋 다 같다 — 서버 동기화로 내려온다. 🚨 **다만 세 안 모두 「기기 간 중복 합치기」가 따로 필요하다**(§6-③) |  |  |
| ② | **번호만** (계정 그대로) | uid 불변 → 번호 갱신만 | 전화번호 계정 재인증 | 「사람」의 번호 갱신 |
| ③ | **계정만** (번호 그대로) | ⭐ 애초에 안 생긴다 (uid 가 번호 기반) | link 로 붙인다 | 「사람」에 uid 를 더한다 |
| ④ | **둘 다** | 새 사람 | 새 사람 | 새 사람 |

📌 **④는 세 안이 같다** — 번호도 계정도 다르면 **우리가 같은 사람인지 알 방법이
없다.** 그래서 새 명함첩이 생기고, 옛 명함첩에 닿는 길은 **옛 로그인 수단**뿐이다.
⚠️ **이 사실을 화면이 말해 줘야 한다** — 안 그러면 이용자는 명함이 사라졌다고 읽는다.

⚠️ **②는 세 안 모두 「번호 변경 기능」이 있어야 성립한다.** 지금 설정 어디에도
없다(2026-09-04 실측). **없으면 번호를 바꾼 사람의 `phoneAccounts` 에 옛 번호가
그대로 남고, 그 번호가 재배정되면 「휴대폰 = 사람」이 조용히 깨진다.**

## 5. 🚨 재는 도중에 드러난 것 — **세 안이 모두 여기서 부딪힌다**

`users/{uid}` 아래에 무엇이 있는지 세다가 나왔다. **비교표보다 이게 더 중요할 수
있다.**

**실측 (2026-09-04, `grep` 으로 셌다)**

```
users/{uid} 하위 컬렉션     cards · deletedContacts   (둘)
users 를 참조하는 파일       9개
경로를 직접 조립하는 자리    30곳
```

⚠️ **그런데 30곳이 전부 옮길 대상은 아니다.** 성격이 갈린다.

| `users/{uid}` 아래에 있는 것 | 사람에 붙어야 하나 | |
|---|---|---|
| `cards` · `deletedContacts` | ✅ **사람** | 명함첩 자체 |
| **`encryptionKeyB64`** | 🚨 **사람** | **아래 참조** |
| 약관·광고·사진개선 동의 3종 | ❓ **판단 필요** | 법적 증빙이다. 「누가 동의했나」가 계정인지 사람인지 |
| `aiUsage` · 사진 한도 | ❓ **판단 필요** | 사람 단위여야 공정하지만, 지금은 계정 단위 |
| `phoneVerifiedAt` · `phoneHash` | ✅ 사람 | 애초에 사람의 속성 |

### 🚨 암호화 키가 세 안 모두의 급소다

```
명함은 users/{uid}.encryptionKeyB64 의 키로 암호화돼 있다
→ 계정이 바뀌면 키도 따라가야 명함을 읽을 수 있다
→ 두 계정이 각자 키를 갖고 있으면, 잇을 때 한쪽을 복호화해 다른 키로 다시 암호화해야 한다
```

**A안**: uid 가 바뀌므로 키 위치가 바뀐다 — 마이그레이션에 **복호화·재암호화가 포함**된다.
**B안**: 계정을 합칠 때 같은 문제.
**C안**: 「사람」으로 옮길 때 같은 문제.

⚠️ **즉 이것은 안을 고른다고 사라지지 않는다.** 어느 안이든 **키를 어떻게 다룰지**를
따로 설계해야 한다. 📌 **그리고 이 작업은 실패하면 명함을 영영 못 읽는다** —
CLAUDE.md 4절의 *"저장·복원·마이그레이션은 전체 테스트 등급"* 이 정확히 이 자리다.

⭐ **이 발견은 「하나를 고치니 다음 것이 보였다」의 사례다** — 이전 규모를 세려다
비용의 본체가 파일 수가 아니라 **암호화 키**라는 것이 드러났다.

## 6. 결정과 **무관하게** 지금 해 둘 것 셋

⭐ **어느 안을 고르든 버려지지 않고, 동작을 하나도 안 바꾼다.**
🚨 **미루면 그 사이 가입자의 명함이 uid 에 직접 묶여 쌓인다.**

### ① `phoneAccounts` 를 넓힐 수 있게 읽는 쪽을 열어 둔다

```
지금    phoneAccounts/{번호해시} → {uid, verifiedAt}
바꿈    읽는 코드를 "uid 하나일 수도, 여럿일 수도" 로 만들어 둔다
        ⚠️ 쓰는 쪽은 그대로 — 지금도 하나만 넣는다
```

### ② 명함첩 경로를 함수 하나로 감싼다

```
지금    users/{uid}/... 를 코드 곳곳에서 직접 조립
바꿈    "이 사람의 명함첩 경로"를 돌려주는 함수를 거치게 한다
        지금은 그 함수가 uid 를 그대로 돌려준다 — 동작 무변화
```

📌 **나중에 「사람」으로 옮길 때 고칠 곳이 한 군데가 된다.**

### ③ 기기 간 중복 합치기 — 이건 지금도 매일 일어나는 결함이다

```
contacts_repository.dart:219  mergeSync 는 여전히 id 로만 맞춘다 (2026-09-04 실측)
→ 두 기기에서 같은 사람을 각각 등록하면 둘 다 살아남는다
```

방침 문서가 *"사고가 아니라 정상 경로다 — 폰과 태블릿을 같이 쓰면 그냥 일어난다"*
고 적어 둔 자리이고, **아직 안 고쳐졌다.** ⭐ **고칠 재료는 이미 있다** —
「이름 + 휴대폰」 매칭 규칙이 명함 등록 쪽에는 붙어 있다. **`mergeSync` 에도
붙이면 된다.**

## 7. 권고 — 다만 결정은 globe2030님 것이다

```
1. §5-2 를 잰다                    특히 계정 수와 키 재암호화 비용
2. §6 의 셋을 지금 넣는다           결정과 무관하고 되돌릴 것이 없다
3. 🚨 암호화 키 설계를 먼저 한다     §5 — 어느 안을 골라도 필요하다
4. 잰 숫자를 놓고 셋 중 하나를 고른다
```

⭐ **3을 1·2와 같은 자리에 둔 이유**: 키는 **안을 고른 뒤에 따라오는 것이 아니라
안과 무관하게 필요한 것**이다. 먼저 풀어 두면 세 안의 비용이 오히려 또렷해진다.

⚠️ **B안은 알림톡 승인을 버리는 대가가 명확하므로, 특별한 이유가 없으면
A와 C의 대결이 될 것으로 본다.** 그리고 **A는 보안 표면을, C는 데이터 이전을**
값으로 치른다 — 어느 쪽이 이 팀에 싼지는 §5를 재야 안다.

📌 **가장 나쁜 선택은 「고르지 않고 그냥 두는 것」이다.** 그 사이에도 가입은
계속되고, uid 에 직접 묶인 데이터가 쌓인다. **스토어 등록 전이 마지막 창이다.**
