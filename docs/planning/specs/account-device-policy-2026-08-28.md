# 계정·기기 방침 — 명함첩의 주인은 누구인가 (2026-08-28 globe2030님 확정)

> 📌 **이 문서는 「무엇을 만들지」가 아니라 「무엇이 참인지」를 정한다.**
> 화면·구현은 여기서 갈라져 나온다.

---

## 왜 지금 정했나 — 실제로 터졌다

2026-08-28에 같은 뿌리에서 결함이 **셋** 나왔다.

| 무엇 | 어떻게 보였나 | 뿌리 |
|---|---|---|
| 아이폰 명함 229장 | 같은 사람이 두 줄 | 계정을 갈아타며 「유지」 |
| 「백업 130장」인데 서버 0장(추가 555) | 화면이 거짓말 | 「유지」로 넘어온 명함의 장부를 물려받음 |
| 아이폰 썸네일 안 보임(추가 554) | 사진이 없는 줄 알았음 | 재설치로 경로가 낡음 |

**앱이 스스로 남긴 기록**(`users/{uid}.accountSwitches`)에 **아이폰 `keep` 2건·폴드 `keep` 1건**이 찍혀 있었다. 추측이 아니라 **기기가 적어 둔 것**이다.

> 🚨 **셋 다 「계정과 기기와 명함첩의 관계」가 정해져 있지 않아서 났다.**

---

## 결정 ① — 명함첩의 주인은 **사람**이다

**계정은 열쇠, 기기는 창이다. 명함첩은 사람의 것이다.**

그리고 **사람을 식별하는 것은 휴대폰 번호**다(2026-08-25 확정한 「I안」).

### 왜 로그인 수단으로는 안 되나

SNS 로그인 4종을 넣기로 했다. 그러면 **같은 사람이 카카오로 가입했다가 다음에 구글을 누르는 일이 반드시 생긴다.** 앱 눈에는 남남이다.

그때 명함첩이 텅 비어 보이고, 그래서 **「기존 자료를 그대로 쓸까요?」**를 묻게 된다.
**그 질문이 2026-08-28 사고 셋의 방아쇠였다.**

> ⭐ **휴대폰 인증이 하는 일은 그 질문을 없애는 것이다.**
> 앱이 같은 사람인 줄 알면 물어볼 이유가 없다.

### ⚠️ 「본인확인」이 아니다 — 문서에 그렇게 쓰지 않는다

문자 인증은 **"지금 그 번호를 받을 수 있다"**만 증명한다. 실명확인(본인확인기관)이 아니다.
**방침·안내에 「본인확인」이라고 쓰면 과장이다**(CLAUDE.md 4절 — 과장하지 않는다).

**얻는 것은 셋이고, 그것으로 충분하다.**

```
① 로그인 수단이 달라도 같은 명함첩       ← 2026-08-28 사고의 뿌리
② 무료 20회 재가입 우회 차단             ← 과금 방어
③ 기기를 바꿨을 때 되찾는 열쇠
```

### 발송 수단

**카카오 알림톡(알리고)** — 알림톡 발신프로필·템플릿 심사가 이미 진행 중이라 인프라가 겹친다.

⚠️ **아래는 아직 확인하지 않았다. 확인하고 이 줄을 고칠 것**(memory: 콘솔·API 절차는 확인 먼저):
- 카카오 알림톡 심사 기준이 **인증번호 발송 템플릿**을 허용하는지
- 카카오톡 미가입자 **대체발송(SMS/LMS)** 구성
- 알리고가 인증번호 전용 API를 주는지, 일반 발송인지

---

## 결정 ② — 「그대로 쓸까요?」를 **없앤다**

**답이 정해져 있는 것을 사용자에게 묻지 않는다.**

| | **같은 휴대폰** | **다른 휴대폰** |
|---|---|---|
| **같은 기기** | 같은 명함첩 — 로그인 수단이 달라도 **자동으로 이어진다** | 🚨 **새 명함첩. 기기에 남은 자료를 안 가져간다** |
| **다른 기기** | 같은 명함첩 — 서버에서 복원 **(정상 기능)** | 남남 |

📌 **「유지」라는 선택지 자체가 사라진다.** 추가 555가 고친 것은 *"「유지」로 넘어온 명함을 「백업됨」이라 말하던 것"*인데, **이 결정이 서면 「유지」로 넘어오는 명함이 애초에 없다.**

⚠️ **그렇다고 추가 555의 수정이 헛것은 아니다** — 이미 그렇게 넘어온 명함이 실제로 기기에 있다. **과거분을 정직하게 말하는 것은 계속 필요하다.**

---

## 결정 ③ — 휴대폰 번호 재활용에 대비한다

통신사는 해지된 번호를 회수해 **다른 사람에게 다시 준다.**
그 사람이 옛 주인의 명함첩을 열면 **제3자 개인정보 유출**이다. 이 앱은 명함 주인(제3자)의 정보를 담으므로 무게가 다르다.

```
오래 안 쓴 계정은 휴대폰만으로 자동으로 잇지 않는다
기존 로그인 수단이 남아 있으면 그걸로 한 번 더 확인한다
```

⚠️ **「오래」가 몇 개월인지는 아직 안 정했다.** 통신사 번호 회수 기간을 확인하고 그보다 짧게 잡는다.

---

## 🚨 방침과 별개로 반드시 고쳐야 하는 것

**같은 계정·다른 기기에서도 명함이 두 배가 된다.**

`mergeSync`는 **id로만 맞춘다.** 두 기기에서 같은 사람을 각각 등록하면 id가 달라 **둘 다 살아남는다.**
삭제 전파(묘비, `tombstones`)는 제대로 들어가 있는데 **중복 합치기가 없다.**

📌 **이건 사고가 아니라 정상 경로다.** 폰과 태블릿을 같이 쓰면 그냥 일어난다.
globe2030님이 정한 매칭 규칙(**이름 + 휴대폰**)을 여기에도 붙여야 한다.

## 지금 코드가 어떻게 돼 있나 (2026-08-28 실측)

```
구글·애플     signInWithCredential      → uid를 Firebase가 정한다
카카오·네이버  signInWithCustomToken     → uid를 우리가 정한다
Firebase 전화번호 인증                   → 미구현 (grep 결과 없음)
```

⚠️ **제공자마다 uid를 정하는 주체가 다르다.** 「휴대폰 = 사람」을 세우려면 이 갈라짐을 먼저 다뤄야 한다. 두 갈래가 있고 **아직 안 정했다**:

```
A  전부 custom token 으로 통일        우리가 uid를 통제한다 · 구글·애플 경로를 고쳐야 한다
B  전화번호 계정에 나머지를 link      Firebase 표준 · 카카오·네이버가 기본 제공자가 아니라 까다롭다
```

🚨 **uid는 한 번 정하면 되돌릴 수 없다. 스토어 등록 전이 마지막 창이다.**

# 가입 순서 — 휴대폰 인증을 어디에 끼우나 (2026-08-28 globe2030님 확정)

## 지금 코드가 하는 것 (2026-08-28 실측)

```
로그인 화면
  ☑ 만 14세 이상입니다          필수 — 체크해야 로그인 버튼이 눌린다
  약관·방침은 고지 문구           별도 체크를 안 받는다
  ↓
SNS 로그인 (구글·애플·카카오·네이버)
  ↓
광고 수신 동의 화면              선택 — 필수와 한 화면에 안 섞는다
  ↓
앱 진입
  ↓ 그 기능을 쓸 때
위치 동의 · AI 전송 동의          각각 따로
```

📌 **약관·방침에 체크를 안 받는 근거**가 `login_view.dart:218`에 적혀 있다 —
계약 이행에 필요한 최소분만 처리해 **별도 동의가 필요 없다**(개인정보 보호법
§15①4). 그래서 **고지**만 한다.

📌 **광고 동의를 떼어 낸 근거**는 추가 457이다 — 필수와 섞으면 이용자가
*"다 체크해야 하는구나"*로 읽어 **선택 동의의 의미가 사라진다.**

⚠️ **이 둘은 이미 법률 조사를 거친 판단이다. 휴대폰 인증을 넣으면서 흔들지 않는다.**

## ✅ 확정한 자리 — SNS 로그인 **뒤**, 광고 동의 **앞**

```
로그인 화면 (만 14세 ☑)
  ↓
SNS 로그인
  ↓
🆕 휴대폰 인증 (알림톡)         ← 여기
  ↓
광고 수신 동의
  ↓
앱 진입
```

**왜 이 자리인가**

```
① 명함첩을 열기 전에 「누구인지」가 정해져야 한다
   늦으면 엉뚱한 명함첩을 보여 준 뒤 바꿔야 한다 — 2026-08-28 사고가 그것이다
② 광고 동의보다 앞이어야 한다
   알림톡이 광고 매체로 들어오면 번호가 있어야 물을 수 있다
③ 이미 가입한 사람이면 광고 동의를 다시 안 묻는다
   ⚠️ 다시 물으면 정보통신망법상 처리결과 통지 의무가 또 생긴다
```

## ✅ 건너뛰기는 **없다** (globe2030님 확정)

```
❌ 건너뛰기 없음   방침이 성립한다. 대신 가입 문턱이 생긴다        ← 채택
⚠️ 건너뛰기 허용   문턱은 낮지만 「휴대폰 = 사람」이 무너진다
                 건너뛴 사람은 2026-08-28 사고를 그대로 다시 겪는다
```

📌 **건너뛰기를 하나라도 허용하면 「휴대폰이 사람이다」가 방침이 아니라 권고가
된다.** 그러면 예외를 다루는 코드가 필요하고, 그 예외가 바로 오늘 터진 자리다.

## 이미 가입한 사람일 때

```
번호가 새 번호     → 새 명함첩. 그대로 진행
번호가 이미 있다   → 「기존 명함첩을 이어받습니다」
                   새 로그인 수단을 그 사람에게 연결한다
                   광고 동의·만 14세는 다시 안 묻는다 (이미 답했다)
```

⚠️ 단, **오래 안 쓴 계정은 자동으로 잇지 않는다**(위 결정 ③ — 번호 재활용).

## 🚨 함께 해야 하는 것 둘 — 안 하면 방침과 구현이 어긋난다

```
① 개인정보처리방침에 「휴대전화번호」를 수집 항목으로 넣는다
② 알리고를 처리위탁 수탁자로 공개한다   문자를 남이 대신 보내는 것이다
```

⚠️ **방침과 구현이 어긋나는 것 자체가 법적 리스크다**(CLAUDE.md 4절 — BYOK
서술 불일치로 이미 한 번 겪었다). **법무 검토를 붙인다.**

## ✅ 인증번호 유효시간 = **3분** (2026-08-28 globe2030님 확정)

알림톡 템플릿 초안이 이미 *"3분 안에 앱 화면에 입력해 주세요"*였다.
**초안 그대로라 템플릿 문안을 고칠 필요가 없다.**

🚨 **앱이 이 3분을 지켜야 한다.** 문구와 구현이 어긋나면 **템플릿을 다시
심사받아야 하고 영업일 2일이 든다.** 서버에서 만료를 판정한다(기기 시계를
믿지 않는다).

### ✅ 나머지 넷도 확정했다 (2026-08-28 globe2030님)

```
재발송 간격      3분    (= 유효시간과 같다)
하루 발송 상한   5번    같은 번호 기준
틀린 횟수 상한   5번    넘으면 그 인증번호를 버린다
만료 뒤 화면     "시간이 지났어요, 다시 받기"
```

📌 **이 넷은 템플릿 문안에 안 들어가므로 바꿔도 재심사가 없다** — 쓰면서
조정할 수 있는 값들이다.

### ⭐ 재발송 간격을 유효시간과 같게 둔 것 — 빈틈이 없다

**코드가 죽는 순간 재발송이 열린다.** 두 개의 코드가 동시에 살아 있는 구간이
생기지 않아서, *"어느 코드가 맞는 건가"*를 다룰 필요가 없다.

⚠️ **대가는 「못 받은 사람이 3분을 기다린다」는 것이다.** 문자가 안 오면
이용자는 화면을 보며 3분을 센다 — 가입 단계에서는 긴 시간이다. 흔한 다른
설계는 **30초~1분 뒤 재발송을 열고, 재발송하는 순간 이전 코드를 죽이는** 것이다.

📌 **재심사가 없는 값이니 실기기에서 직접 기다려 보고 정해도 된다.**
지금은 3분으로 만든다.

### ⚠️ 두 상한이 이어지는 자리 — 구현할 때 볼 것

**틀린 횟수 5번을 넘기면 그 코드를 버리는데, 다시 받으려면 발송 상한(하루 5번)을
쓴다.** 그래서 **최악의 경우 하루 안에 막힌다.**

```
그때 이용자에게 무엇을 보여 주나
→ 🚨 여기서 고객센터 전화번호가 필요해진다
   (알림톡 신청 월요일 항목 2번과 같은 번호다)
```

**상한에 걸린 사람을 그냥 두면 그날 가입을 못 한다.** 안내 문구에 연락처를 넣는다.

### 만료·상한 판정은 서버가 한다

기기 시계·기기 저장 횟수를 믿지 않는다. 앱을 지웠다 깔아도 상한이 유지돼야 한다.
