# 「병합」과 「전환」 — 같은 번호에 계정이 둘일 때 (2026-09-05)

> 🚨 **이 문서는 결정이 아니다.** globe2030님이 *"병합과 전환을 정리해서 다시
> 보자"* 고 하셔서 **판단에 필요한 것만** 갖춘 것이다. **어느 쪽이 낫다고
> 고르지 않는다.**
>
> ⚠️ **설계 문서를 안 고쳤다.** 결정 전에 설계를 고치면 되돌릴 것이 늘어난다.

---

## 0. 🚨 먼저 — 우리는 지금 **셋 중 어느 쪽도 아니다**

「전환이 현상 유지에 가깝다」로 읽기 쉬운데, 재보니 아니다.

| | 번호 하나에 | 둘째 계정이 인증하면 | 근거 |
|---|---|---|---|
| **지금 (실물)** | 계정 **하나** · 영구 | 🚨 **인증 자체가 막힌다**(`taken`) | `index.ts:2872` |
| **전환 (리멤버)** | 계정 여럿 · **활성 하나** | 첫째가 **잠긴다** | 공식 자료 |
| **병합 (C안)** | **사람** 하나 · uid 여럿 | 둘 다 **살아서 묶인다** | `data-schema.md` §7 |

```
지금   phoneAccounts/{번호해시} = { uid, verifiedAt }
       uid 를 하나만 담고, 다른 uid 가 오면 taken 으로 막는다
```

🚨 **[추가 642] 가 이 구조에서 났다** — 탈퇴해도 문서가 남아 **이미 지워진
uid** 가 주인으로 남았고, 같은 번호로 다시 가입하면 **본인 번호인데 영원히
막혔다**(`index.ts:1854-1856` 주석이 그대로 적고 있다).

📌 **그러므로 「전환」도 현상 유지가 아니다.** 지금은 **선착순 영구 점유**이고
전환은 **후착순 + 잠금**이다. **셋 다 바꾸는 것이다.**

---

## 1. ① 무엇을 다르게 하는가

### 데이터 구조

| | 병합 | 전환 |
|---|---|---|
| 새 컬렉션 | `people/{personId}` **신설** | **없다** |
| 명함이 사는 곳 | `people/{personId}/contacts` 로 **이동** | `users/{uid}/contacts` **그대로** |
| 함께 옮겨가는 것 | `cardSources` · `deletedContacts` · `commLogs` | — |
| `phoneAccounts` | `{ personId }` 로 바뀜 | `{ uid, ... }` + **활성/잠금 상태** |
| `users/{uid}` | `personId` 역참조 한 줄 추가 | 그대로 |
| 마이그레이션 | 🚨 **기존 명함을 통째로 옮긴다** | **없다** |

### 화면

```
병합   명함첩이 하나다. 어느 계정으로 들어와도 같은 목록이 보인다
전환   명함첩이 계정마다 있다. 전환하면 다른 목록이 보인다
       🚨 **두 계정 명함을 한 화면에서 못 본다**
```

### 키

| | 병합 | 전환 |
|---|---|---|
| 필요한 키 | 여러 uid 의 키를 **모아야 한다**(키링) | 활성 계정 키 **하나** |
| 복호화 | `§5-2` 순서대로 시도 · `§5-3` 성공 키 캐시 | 지금과 같다 |
| 비용 | ⬜ **아직 안 쟀다**(`암호화키…설계` §6) | 지금과 같다 |
| 파기 | 🚨 `§7` — 하나라도 남으면 명함이 열린다 | 지금과 같다 |

⭐ **병합을 고른 기술적 근거 둘이 전환에서는 성립하지 않는다.**
`data-schema.md:222-227` 이 적어 둔 것이다:

```
🚨 Firestore 커서는 컬렉션을 가로지르지 못한다
   → uid 마다 흩어 두면 「최신순 20장씩」이 안 된다 (느린 게 아니라 안 된다)
🚨 rules 의 문서 접근 호출은 단일 요청당 10회 제한 + 호출마다 과금
```

🚨 **이 둘은 「병합이 나은 이유」가 아니라 「병합을 고르면 따라오는 제약」이다.**
그 구분이 중요하다 — 병합을 고르면 **저 둘을 감당해야** 하고, 전환을 고르면
**저 둘이 사라진다.** 어느 쪽으로도 「그래서 병합이 낫다」가 안 나온다.

📌 둘 다 **「여러 uid 를 한 화면에서 본다」는 전제 위에** 있기 때문이다. 전환은
한 번에 한 계정이므로 **문제 자체가 안 생긴다.**

### 🚨 그런데 전환에도 같은 질문이 돌아온다

**계정을 전환하면 옛 계정 명함을 어떻게 보여 줄 것인가.**

```
갈래 ㉮  안 보여 준다     간단하다. 위 제약 둘이 정말로 사라진다
                        ⚠️ 대신 §2 「전환이 잃는 것」 ①②가 그대로 남는다

갈래 ㉯  보여 준다        🚨 **같은 문제가 그대로 돌아온다** —
                        커서가 컬렉션을 가로지르지 못하는 것도, rules 조회
                        10회 제한도 똑같이 걸린다. 즉 **이름만 전환이고
                        구조는 병합이 필요해진다**
```

⭐ **그러므로 「전환」을 고를 때 ㉮인지 ㉯인지를 함께 정해야 한다.** ㉯를
고르면 전환의 이점(키 하나 · 마이그레이션 없음)이 대부분 사라진다.

## 2. ② 각각 무엇을 잃는가

### 🚨 전환이 잃는 것

```
① 두 계정 명함을 한 화면에서 못 본다               ← 가장 큰 것
② 이미 두 계정에 나뉜 사람은 영영 못 합친다
   (합치려면 별도의 이관 기능이 필요하고, 그것은 결국 병합이다)
③ 「이 번호의 명함첩」이라는 약속을 못 한다
   — 번호는 하나인데 명함첩이 둘이다
④ 잠긴 계정으로 돌아가려면 매번 휴대폰 인증을 다시 한다
```

⚠️ **②가 조용한 손실이다.** ①은 쓰면서 바로 느끼지만, ②는 **나중에야
드러나고 그때는 이미 늦다.** 데이터가 갈린 채로 시간이 지날수록 합치기 어렵다.

### 🚨 병합이 잃는(치르는) 것

```
① 키링 전체가 따라온다      순회 · 캐시 · 🚨 파기가 어려워진다(§7)
② 마이그레이션이 되돌리기 어렵다   암호화된 데이터를 옮기는 일이다
③ 관리자 조회 범위가 넓어진다      법무 ①②③ — 조회 한 번 = 그 사람의 모든 계정
④ 30일 삭제와 부딪힌다             [추가 675·677·681] — 고칠 곳이 셋이다
⑤ 새 컬렉션 하나와 규칙이 는다
```

⚠️ **③은 이미 법무에 올라가 있고 답이 왔다** — 조회 기록은 `personId` 만 남기고
2년 보관. **범위가 넓어지는 것 자체는 남는다.**

```
grep -rn "personId" lib functions/src   (주석 제외)   →   0건
```

⭐ **`personId` 는 살아 있는 코드에 한 줄도 없다.** `#837` 도 *"이 변경만으로는
테스트가 늘지도 줄지도 않아야 맞다"* 고 스스로 적었고 실제로 그랬다.

| 언제 바꾸나 | 코드 | 데이터 | 문서 |
|---|---|---|---|
| **지금** | **0** | **0** | 넷을 고친다(아래) |
| 명함을 `people` 밑으로 옮긴 뒤 | 경로 전부 | 🚨 **암호화된 명함을 되돌려 옮긴다** | 같음 |
| 키링을 실제로 채운 뒤 | 키 경로 · 파기 경로 | 🚨 위 + 키 정리 | 같음 |

⚠️ **문서 비용은 이미 발생했다.** 어느 쪽으로 가든 이 넷은 손봐야 한다 —
`data-schema.md` §7 · `사람-레이어-C안-설계` · `암호화키-계정잇기-설계` ·
`관리자…설계` §3-5. **전환을 고르면 「다시 쓰기」이고 병합이면 「그대로」다.**

창이 얼마나 열려 있는지는 **다음에 무엇을 짓느냐**에 달렸다.

## 5. ⑤ ⬜ 아직 모르는 것 — 짐작으로 안 적는다

```
⬜ 한 사람이 두 계정에 명함을 나눠 가진 경우가 실제로 얼마나 되나
   🚨 이것이 ②「전환이 잃는 것」의 무게를 정한다. **안 쟀다.**
   재는 법: 서버에서 같은 phoneHash 를 거쳐 간 uid 가 둘 이상인 사례를 센다
   ⚠️ 지금 phoneAccounts 는 uid 하나만 담으므로 **이 자료가 없을 수 있다**

⬜ 리멤버가 「잠긴 계정」의 데이터를 어떻게 하나 — 보존인가 삭제인가
   확인된 것은 "A 가 잠긴다 · 다시 쓰려면 휴대폰 인증"까지다

⬜ 우리 이용자가 실제로 계정을 여럿 쓰나 · 왜 쓰나
   (수단을 바꾼 것인가, 일·개인을 나눈 것인가 — 답이 다르면 필요한 것도 다르다)

⬜ 전환에서 「명함 이관」을 나중에 붙일 수 있나
   붙인다면 그것이 결국 병합이므로, **미루는 것인지 안 하는 것인지**가 갈린다

⬜ 전환을 고른다면 ㉮(안 보여 준다)인가 ㉯(보여 준다)인가
   🚨 ㉯면 제약 둘이 그대로 돌아와 **이름만 전환**이 된다
```

⚠️ **첫 줄이 이 문서에서 가장 중요한 ⬜ 다.** 전환의 가장 큰 손실이
*"두 계정 명함을 한 화면에서 못 본다"* 인데, **그런 사람이 없으면 손실도 없다.**
🚨 **그런데 지금 구조상 그 자료가 서버에 없을 수 있다** — `phoneAccounts` 가
uid 를 하나만 담기 때문이다. **없으면 「모른다」로 두고 정해야 한다.**
