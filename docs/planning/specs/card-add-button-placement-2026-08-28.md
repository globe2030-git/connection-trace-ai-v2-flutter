# 명함 등록 버튼 위치 + 연속 등록 흐름 — 설계 (2026-08-28)

---

> 🚨 **[정정 2026-08-28 · 추가 543] 이 문서의 「190장」은 틀렸다.**
>
> **폴드 실물은 명함 103장**이다. **190은 「스캔 파싱 횟수」(누적)** 이지 명함 수가
> 아니었다 — 진단 화면의 「전체 · 스캔 파싱 횟수 190회」를 명함 수로 읽었다.
>
> 📌 **표 이름은 정확했고 읽는 쪽이 다른 뜻으로 읽었다** — 어제 87%(「좌표가
> **없는** 주소의 형태」를 실패율로 읽음), 오늘 아침 188건(「**채워진** 비율」을
> OCR 성능으로 읽음)과 **같은 병이고 하루에 세 번째**다.
>
> ⚠️ 아이폰 「126장」은 globe2030님 본인 말씀이라 그대로 두되, **진단 화면의
> 「188회」와 섞지 말 것** — 그쪽도 스캔 횟수다.
>
> ⭐ **다만 이 문서의 결론은 안 바뀐다.** 근거가 *"300번 넘게 눌렀다"* 에서
> *"126장을 등록하며 그만큼 눌렀다"* 로 줄 뿐이고, **「저장하면 흐름이 끊긴다」**
> 는 장수와 무관하게 성립한다.



> **상태: 설계만 완료, 구현 전.** `lib/`를 한 줄도 고치지 않았다. 이 문서는
> `flutter-developer`에게 위임할 브리프로 쓸 수 있게 작성했다.
> 작성: `flutter-ui-designer` 서브에이전트 (PM 위임, globe2030님 원 요청).

## 0. 원 요청과, PM이 다시 잡은 진짜 문제

**globe2030님 원문(1차)**:
> "한장 한장 할때도 연속으로 할때도 명함추가 버튼이 위에 있어서 불편해.
> 명함 지갑이던 주변이던 하단의 설정 옆에 명함추가 버튼이 있으면 좋을것
> 같아."

**globe2030님 원문(2차, PM 보강)**:
> "일괄스캔도 있으면 좋긴해" / "그럴 경우 저장 이후에 계속 다시 눌러야 해"

**근거의 무게**: globe2030님이 이 버튼을 오늘 하루 아이폰 126장·폴드
190장 등록에 눌렀다. 취향이 아니라 300번 넘게 누른 사람의 실측 불편이다.

**2차 발언이 1차 발언의 원인을 가리킨다.** 버튼이 "위에 있어서" 불편한
것이 아니라, **저장할 때마다 화면이 통째로 닫히고 지갑으로 돌아가서, 다음
명함을 등록하려면 다시 그 버튼을 찾아 눌러야 하는 것**이 불편의 실체다.
버튼을 아래로 옮겨도 이 왕복은 그대로 남는다 — 손이 이동하는 거리만 짧아
질 뿐, **누르는 횟수(126번)는 줄지 않는다.**

그래서 이 설계는 세 갈래를 모두 다룬다.

1. 저장 → 다음 장 사이를 잇는 흐름 (본체, 새 기능)
2. 명함 등록 버튼을 하단으로 (globe2030님 원 요청, 배치 변경)
3. "명함 일괄 스캔"을 일반 이용자에게 열 수 있는가 (기존 기능 검토)

세 갈래는 **배타적이지 않다.** ①을 하더라도 ②를 함께 하는 것이 자연스럽고,
③은 별도 판단이 필요하다.

## 1. 실물 확인 — 지금 무엇이 있고 무엇이 없는가

### 1-1. 지금의 등록 흐름 (실측)

```
wallet_view.dart:392       "명함 등록" 원형 아이콘(40×40) — 머리글 오른쪽 위
radar_view.dart:609        같은 자리·같은 모양의 "명함 등록" 원형 아이콘 — 주변 화면
                           (wallet_view.dart:361~365 주석: "자리·모양을
                            완전히 통일했다" — 2026-08-12 사용자 결정)
add_card_modal_view.dart:3033   ContactModel 생성 → addContact/updateContact
add_card_modal_view.dart:3036   Navigator.pop(context)   ← 등록 모달이 완전히 닫힌다
add_card_modal_view.dart:3038   SnackBar "🎉 …명함이 등록되었습니다!"
```

**저장은 예외 없이 모달을 닫는다.** "저장하고 계속" 같은 분기가 코드에
없다 — `_saveContact`(가칭, 3033행 부근) 안에 `Navigator.pop`이 조건 없이
한 번 있을 뿐이다.

### 1-2. "앞/뒷면"과 "여러 장"은 다른 개념이다 (확인 필요했던 지점)

`add_card_modal_view.dart:917~962`에 `_performGalleryScan`이 있고
`GalleryOcrBatch`(`file_picker_modal_view.dart:30`)라는 "여러 장" 개념이
이미 존재한다. 이름만 보면 "여러 장 등록"처럼 보이지만, 실제로는:

```dart
// add_card_modal_view.dart:926
// "명함 한 장은 앞면과 뒷면까지가 최대 행동" (2026-08-14 사용자 결정)
if (_scanCount != 0) { ... 단일 선택 경로로 되돌린다 ... }
```

**한 장의 카드의 앞·뒷면 2장을 한 번에 고르는 기능**이지, **서로 다른
명함 여러 장을 연달아 등록하는 기능이 아니다.** globe2030님이 겪은
"연속으로 할 때"는 이 경로가 애초에 다루지 않는 시나리오다.

### 1-3. "명함 일괄 스캔(관리자)" 실물 — `ocr_batch_scan_view.dart` 전체를 읽었다

`settings_view.dart:509,547` — `auth.isAdmin && _adminUnlocked`(버전 7번
탭)일 때만 설정 화면에 나타난다. 화면을 열어 기능을 끝까지 확인했다:

| 있는 것 | 없는 것 |
|---|---|
| 갤러리에서 여러 장 선택 → 순서대로 OCR (`_pickAndScan`) | **`ContactsRepository`/`WalletViewModel`으로의 저장 경로 자체가 없다** — `addContact` 호출이 파일 전체에 0건 |
| 결과를 표(카드 리스트)로 보여줌 | 필드 수정(전부 읽기 전용 `Text`, `_field()`) |
| TSV로 클립보드 복사·파일 저장·공유(AirDrop 등) | 중복 명함 판정(`findDuplicate`) 연동 |
| 카메라가 아니라 **갤러리/adb로 넣은 폴더**에서만 읽음 | 태그·그룹 지정, 대표 이미지 지정 |
| "빌드 해시" · "원문(raw)" · "좌표" 열 — OCR 규칙 회귀 진단용 | 카메라 촬영 자체(이 화면엔 카메라 진입점이 없다) |

**결론(③에 대한 답)**: 이 화면은 **명함 등록 화면이 아니라 OCR 인식 품질
회귀 테스트 도구다.** "저장" 버튼이 하나도 없고(둘러본 액션 4개는 전부
표를 파일/클립보드/공유로 **내보내는** 것뿐), 목적 자체가 "규칙을 고칠
때마다 여러 장을 한 번에 돌려 표로 비교"(문서 주석, 14~19행)다. 개인정보
칸(이름·전화·이메일·주소)이 통째로 화면에 펼쳐지는 것도 검수자(관리자)를
전제한 설계다.

📌 **"있다"는 사실과 "낼 수 있다"는 판단은 다르다.** 이 화면을 일반
이용자에게 그대로 내놓으면: 스캔은 되는데 **저장 버튼이 없어 아무것도
지갑에 안 들어간다.** 즉 지금 모양 그대로는 낼 수 없다 — 저장·중복 판정·
필드 수정·그룹 지정을 새로 얹어야 하는데, 그러면 사실상 ①(새 연속 등록
흐름)과 같은 크기의 작업이 된다. **"이미 있어서 열기만 하면 된다"는
전제는 실물 확인 결과 성립하지 않는다.**

## 2. ① 저장 → 다음 장 사이를 어떻게 잇나 — 본체

세 갈래를 검토했다.

### ⓐ 저장 후 카메라로 즉시 복귀 ("저장하고 계속 찍기")

저장 시점(`Navigator.pop` 자리)에서 모달을 닫는 대신:
1. 짧은 확인 배지("✅ 홍길동 님 저장됨")를 모달 안에 인라인으로 띄운다
   (이미 있는 `_showInlineNotice` 패턴 재사용 — 새 컴포넌트 불필요).
2. 폼 컨트롤러 전체를 초기화하고(새 명함 등록 상태로 리셋),
3. 즉시 카메라 화면(`CameraScanModalView`)을 다시 연다 — 사용자가 다음
   명함을 화면에 대고 있는 채로 이어 찍을 수 있게.
4. 모달 자체를 닫는 것(=지갑으로 복귀)은 **사용자가 "그만 찍기"를 눌렀을
   때만** 일어난다.

**대가**:
- 실수로 계속 찍히는 경우를 반드시 막아야 한다 — 오촬영·중복 등록 위험.
  → 매 장마다 "다른 명함을 스캔하셨나요?"류의 확인이 이미 있으므로
    (`_showDifferentCardScannedDialog`), **저장 직후에도 "계속 촬영 /
    그만하고 지갑으로" 두 버튼짜리 확인 한 번**을 반드시 끼운다. 자동으로
    카메라가 열리게 두지 않는다(자동 연속 촬영이 오조작을 만든 전례가
    이 저장소에 이미 있다 — CLAUDE.md 4절, 2026-08-26 동의 화면 오탭).
- 폼 리셋이 완전해야 한다 — 이전 명함의 태그·그룹·메모가 한 글자라도
  새 명함에 새어 들어가면 "잘못된 사람 정보가 저장된다"는 이 프로젝트의
  가장 무거운 결함 유형(제3자 개인정보 오기재)이 된다. **리셋 대상
  컨트롤러 전체를 명시적으로 나열하는 체크리스트**가 구현 브리프에
  반드시 있어야 한다.

**장점**: 흐름이 안 끊긴다. 126번 누른 것 중 "지갑으로 돌아갔다가 다시
버튼을 찾아 누르는" 왕복이 사라진다 — **개수는 그대로지만 각 회차가
짧아진다.**

### ⓑ 여러 장 먼저 찍고, 나중에 한꺼번에 확인·저장 (일괄 접수)

먼저 카메라로 N장을 쭉 찍기만 하고(OCR은 그때 하거나 나중에), 다 찍은
뒤 표/카드 목록에서 각 장을 확인하고 한꺼번에(또는 골라서) 저장한다.
**"명함 일괄 스캔(관리자)" 화면과 뼈대가 같다** — 위 1-3에서 확인했듯
그 화면에 저장·수정·중복판정을 얹으면 이 갈래가 된다.

**대가**:
- 작업량이 가장 크다 — 저장 경로 신설, 각 장 필드 수정 UI(지금은 읽기
  전용), 중복 판정 연동, 개인정보 노출 화면을 일반 이용자 눈높이로
  다시 설계(지금 문구 "명함 주인의 개인정보가 그대로 표시되니 화면
  공유에 주의" 같은 관리자 대상 경고를 일반 이용자용으로 바꿔야 함).
- **되짚어보기가 늦다** — "찍을 땐 안 보이던 인식 오류"를 N장 다 찍고
  나서야 한꺼번에 보게 되면, 그사이 명함 실물(종이)을 이미 치웠을 수
  있다. OCR이 실물 없이는 고칠 수 없는 오류를 낸 경우 재촬영 동선이
  길어진다.
- **장점**: 촬영 자체는 가장 빠르다 — "확인" 단계가 촬영과 분리돼 있어
  촬영 리듬이 안 끊긴다. 명함을 쌓아두고 한 번에 처리하는 사용 패턴
  (예: 명함첩을 통째로 정리)에는 이쪽이 더 맞을 수 있다.

### ⓒ 버튼만 하단으로 옮긴다 (배치만)

가장 작은 변경. 다만 PM 지적대로 **126번은 그대로 남는다** — 매 장마다
"저장 → 지갑 목록 렌더링 → 버튼을 다시 찾아 누름"의 왕복이 사라지지
않는다. 손 이동 거리(한 손 조작 관점)만 줄어든다.

### 권장

**ⓐ를 본체로, ⓒ(버튼 위치, 아래 3장)를 함께 한다.** 근거:

- ⓑ는 되짚어보기가 늦다는 구조적 단점이 있고, 작업량도 가장 크다 —
  "관리자 도구를 열어서 쓴다"가 아니라 "일반 이용자용을 새로 만든다"에
  가깝다. **당장 답이 아니라 별도 검토 대상으로 남겨 둔다.**
- ⓐ는 지금 있는 컴포넌트(카메라 화면, 다른-명함-스캔 확인 다이얼로그,
  인라인 배지)를 그대로 재사용할 수 있어 새로 만들 것이 적다.
- ⓒ는 어느 쪽을 택하든 함께 하는 것이 자연스럽다 — ⓐ를 하더라도 "그만
  찍기"를 누른 뒤 지갑으로 돌아왔을 때, **다음 세션에 다시 등록을
  시작하는 진입점**은 여전히 필요하고 그 자리는 globe2030님이 요청한
  위치가 맞다(아래 3절).

⚠️ 이것은 권장이지 확정이 아니다 — **globe2030님이 결정할 것**(4절).

## 3. ② 명함 등록 버튼을 하단으로 — 배치 대안 비교

globe2030님 표현 — *"명함 지갑이던 주변이던 하단의 설정 옆에"* — 은
**양쪽 화면 모두**를 뜻하는 것으로 읽었다. 실제로 두 화면(`wallet_view.dart:392`,
`radar_view.dart:609`)이 2026-08-12 사용자 결정으로 자리·모양을 이미
통일해 뒀으므로, **한쪽만 옮기면 그 결정(통일)이 다시 깨진다.** 옮긴다면
**양쪽을 함께** 옮겨야 앞뒤가 맞는다.

### 걸리는 점 (미리 드린 것) — 탭과 동작은 성격이 다르다

`main_tab_screen.dart:183~211`의 `NavigationBar`는 "주변·명함·설정" 3개
목적지 — **누르면 그 화면에 머무는 곳**이다. 반면 "명함 등록"은 **눌러서
모달을 열고 끝나면 닫히는 동작**이다. 하단 내비게이션 바에 "머무는 곳"
셋과 "실행하고 닫히는 동작" 하나를 나란히 두면, **누르는 사람 입장에서
"이것도 탭인가?"라는 혼동이 생길 수 있다** — 이것은 일반적인 UX 원칙
(Material Design의 Navigation Bar 가이드도 "목적지"만 놓으라고 규정)에
근거한 우려이지, globe2030님 요청을 반박하는 근거는 아니다. 아래에서
이 걸림을 넘는 대안 셋을 비교한다.

### ⓐ 정확히 요청대로 — 4번째 탭 자리에 원형 버튼 (탭이 아니라 동작임을 모양으로 구분)

```
[ 주변 ]   [ 명함 ]   [ ➕ ]   [ 설정 ]
```

`NavigationBar` 목적지 4개 중 하나로 "명함 등록"을 넣되, **선택 상태가
없는 것으로 시각적으로 구분**한다 — 다른 셋은 누르면 그 라벨이
강조되고 화면이 바뀌지만, 이 버튼은 눌러도 밑줄/색 강조가 남지 않고
모달만 뜬다.

**대가**:
- `NavigationDestination` 4개면 폭이 좁아진다 — 특히 폴드 펼친 화면
  기준으로는 여유가 있지만, 일반 폭 화면(단말기)에서는 라벨 4개가
  붙어 답답해질 수 있다(실측 필요 — 아래 5절).
- Flutter `NavigationBar`는 본래 "목적지"용 위젯이라, 그 안에 "동작"을
  끼워 넣으려면 `onDestinationSelected`에서 인덱스를 가로채 모달만
  열고 `_currentIndex`는 바꾸지 않는 예외 처리가 필요하다 — 코드가
  살짝 부자연스러워진다(불가능하지는 않다).
- **장점**: globe2030님 요청을 가장 그대로 따른다. 하단 어디에 있는지
  예측 가능성이 가장 높다(항상 같은 자리, 항상 같은 손 위치).

### ⓑ FAB(떠 있는 원형 버튼) — 하단 바 위에 얹힌 별도 버튼

```
[ 주변 ]   [ 명함 ]        [ 설정 ]
                 (＋)  ← 하단 바 위에 살짝 겹쳐 떠 있음
```

Material 표준 패턴(`Scaffold.floatingActionButton`,
`FloatingActionButtonLocation.centerDocked` 등). "동작"이라는 성격이
모양(떠 있음, 다른 스타일)으로 이미 구분돼 위 걸림이 자연히 풀린다.

**대가**:
- **globe2030님 요청과 완전히 일치하지는 않는다** — "설정 옆"이 아니라
  "설정과 명함 사이 위에 떠 있음"이 된다. 손 도달 거리는 하단 바 안에
  두는 것과 비슷하지만, 자리 표현이 다르다.
- 주변 화면은 하단에 지도·리스트 콘텐츠가 스크롤되는 화면이라, FAB가
  콘텐츠 위를 가릴 수 있다(스크롤 시 콘텐츠와 겹침 — 실측 필요).

**장점**: Android/iOS 사용자에게 "떠 있는 버튼 = 주요 동작"이라는 관습이
이미 있어 학습 비용이 낮다. "탭인가 동작인가"의 혼동이 없다.

### ⓒ 하단 바 가운데 큰 버튼 (인스타그램/카카오톡 방식)

```
[ 주변 ]   [ 명함 ]  ( ➕ 크게, 살짝 튀어나옴 )  [ 설정 ]
```

4번째 자리를 다른 셋보다 확연히 크게·다른 색으로 만들어 하단 바 안에
있으면서도 "이건 동작"이라는 것을 모양으로 알린다. ⓐ와 ⓑ의 중간.

**대가**: 구현 난이도가 셋 중 가장 높다(커스텀 `NavigationBar` 또는
`BottomAppBar` + `Notch` 조합 필요, Flutter 기본 `NavigationBar` 위젯의
표준 API 밖). 큰 버튼이 다른 두 라벨(명함·설정)과 시각적 균형을 깨뜨릴
수 있다 — 특히 라벨 텍스트가 있는 지금 스타일과는 무게감이 안 맞는다.

**장점**: 사용자 인지도가 가장 높은 패턴(카카오톡·인스타그램 사용자층과
겹친다 — 이 앱 이용자가 영업직이라 두 앱 모두 일상적으로 쓸 가능성이
높다). 시각적으로 "가장 중요한 동작"이라는 신호가 세 방식 중 가장
강하다.

### 비교 요약

| | globe2030님 요청 일치도 | 구현 난이도 | 탭/동작 혼동 위험 | 한 손 도달성 |
|---|---|---|---|---|
| ⓐ 4번째 탭 자리 | 가장 높음 | 낮음(예외 처리 1건) | 중간(모양으로 구분 필요) | 좋음(하단 바 안) |
| ⓑ FAB | 중간 | 낮음(표준 위젯) | 낮음(관습적으로 구분됨) | 좋음(하단 근처) |
| ⓒ 가운데 큰 버튼 | 중간 | 높음 | 낮음 | 가장 좋음(엄지 중심) |

### 권장

**ⓑ(FAB, `centerDocked`)를 권장한다.** 이유:

- globe2030님이 실제로 원하신 것은 "**정확히 저 자리**"가 아니라
  "**엄지가 닿기 쉬운 하단**"이다(5절 한 손 조작 근거 참고). FAB도 하단
  중앙 부근이라 그 요구를 충족한다.
- 탭/동작 혼동이 없어 `NavigationBar`의 "선택 상태" 의미를 깨뜨리지
  않는다 — ⓐ처럼 4번째 자리를 만들고 "안 눌린 것처럼 보이게" 예외
  처리할 필요가 없다.
- 표준 Flutter 위젯(`FloatingActionButtonLocation.centerDocked` +
  `BottomAppBar`)이라 유지보수 부담이 가장 낮다.

⚠️ **강요하지 않는다.** globe2030님이 "정확히 그 자리(4번째 탭 위치)"를
원하신다면 ⓐ도 무리 없이 갈 수 있는 선택지다 — 이 판단은 순수하게
취향·일관성의 영역이라 어느 쪽으로도 근거가 갈린다.

## 4. globe2030님이 결정하실 것

1. **① 흐름 갈래**: ⓐ(저장 후 카메라 복귀) / ⓑ(먼저 다 찍고 나중에 일괄
   확인) / 둘 다 필요 없고 지금처럼 매번 지갑으로 돌아가는 것으로 충분한지.
   → 권장: ⓐ.
2. **② 버튼 위치**: ⓐ(4번째 탭 자리) / ⓑ(FAB) / ⓒ(가운데 큰 버튼) /
   지금 자리 유지. → 권장: ⓑ.
3. **③ 「명함 일괄 스캔」**: 관리자 전용으로 계속 둘지, 아니면 일반
   이용자용으로 별도 개발(저장·수정·중복판정 추가)할지 — 이 경우 사실상
   ①의 ⓑ 갈래와 같은 작업이 된다는 것을 감안해서 결정.
4. 이 셋을 확정하면 `flutter-developer`에게 구현 브리프로 이 문서를
   넘길 수 있다.

## 5. 근거 메모

- **한 손 조작(추측)**: globe2030님이 폴드에서 190장을 등록하셨다는
  사실 자체는 실측이지만, "화면 위쪽 오른편이 엄지에 안 닿아서
  불편했다"는 **인과관계는 추측이다** — globe2030님이 그렇게 명시하지
  않으셨다. 다만 일반적으로 폼팩터가 큰 기기(폴드 펼침 상태)에서 오른손
  엄지가 화면 우상단에 닿기 어려운 것은 널리 알려진 인체공학적 사실이라,
  추측이라도 근거로 쓸 만하다고 판단했다.
- **실측 vs 계산 구분**: 이 문서의 "126장·190장"은 PM이 전달한 수치이고
  이 설계 세션에서 직접 측정하지 않았다 — **전달받은 실측**으로 표기한다.
  나머지(코드 구조, 버튼 위치, `ocr_batch_scan_view.dart`의 저장 경로
  부재)는 이 세션이 직접 읽어 확인한 것이다.
- **확인 명령**: `grep -n "addContact" lib/presentation/features/settings/views/ocr_batch_scan_view.dart`
  → 결과 없음(0건) — "일괄 스캔에 저장 경로가 없다"의 근거.
