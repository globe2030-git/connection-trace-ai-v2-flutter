## 1. 결정 — 회원가입 수단은 다섯

```
카카오 · 네이버 · 구글 · 이메일    ← 리멤버 방식 그대로 넷
+ 애플                            ← 우리는 iOS 심사 요구사항(4.8)으로 필수
```

근거 문서: `docs/planning/remember-signup-flow-2026-08-26.md` — 리멤버
**웹** 회원가입 화면 실물 관찰(사용자가 직접 녹화, 93초). 이 문서 §0의
흐름표가 원본이다.

```
회원가입   카카오 / 네이버 / 구글 / 이메일  (넷)
   ↓
약관 모달  만14세(필수) · 이용약관(필수) · 개인정보(선택) · 광고 수신(선택)
   ↓
이메일 + 비밀번호
   ↓
본인 확인  이름 입력 → 휴대폰 번호 → 인증번호 6자리(3분 타이머·재전송)
   ↓
🚨 "이미 리멤버 계정이 있습니다"   ← 번호로 기존 계정을 찾아 보여준다
```

⚠️ **관찰이지 추천이 아니다** — 리멤버가 하는 방식이 적법·최선이라는
뜻은 아니다. 우리 판단의 법적 근거는 별도 법무 회신(추가 473)이고, 이
문서는 "업계 실물이 어디에 있는지"만 보여준다.

## 2. 우리 흐름에 끼워 넣는 자리 — 이미 확정된 순서와 충돌하지 않는다

추가 560이 이미 확정한 순서:

```
로그인 화면(만 14세 ☑) → SNS/이메일 로그인 → 휴대폰 인증(건너뛰기 없음)
  → 광고 수신 동의(선택) → 앱 진입
```

이메일 경로가 새로 끼는 자리는 **"SNS/이메일 로그인" 한 단계 안**이다 —
구글·애플·카카오·네이버와 **나란히 다섯 번째 버튼**으로 로그인 화면에
추가되고, 그 뒤(휴대폰 인증 · 광고 동의)는 SNS 넷과 완전히 같은 파이프를
탄다. **이메일이라고 별도 흐름을 새로 만들지 않는다** — 이미 확정된
순서(560)를 흔들 이유가 없다.

## 3. 이메일 경로 자체의 화면 — 리멤버 관찰 기준 골격

### 3-1. 이메일 버튼을 누르면

```
1) 이메일 입력
2) 비밀번호 입력(+ 확인)
3) 계정 생성(Firebase Auth createUserWithEmailAndPassword 등)
4) 이후는 SNS 넷과 합류 — 휴대폰 인증 → 광고 동의 → 앱
```

⚠️ **로그인(기존 이메일 계정)과 가입(신규)을 가르는 화면이 필요하다** —
SNS는 Firebase가 "있으면 로그인, 없으면 가입"을 알아서 처리하지만,
이메일+비밀번호는 **이용자가 스스로 "처음인지 아닌지"를 말해야 한다**
(또는 이메일을 먼저 입력받아 존재 여부를 조회한 뒤 갈래를 나눈다 —
b4가 결정할 UX 세부).

### 3-2. 비밀번호 정책 — 아직 정하지 않았다

⬜ **미정**: 최소 길이, 복잡도 요구사항, 재설정(비밀번호 찾기) 흐름.
리멤버 녹화에는 이 화면이 안 잡혔다(가입만 관찰, 재설정 경로는 안 봄).
b4가 정할 때 Firebase Auth 기본 최소 길이(6자)를 그대로 쓸지, 더 엄격한
규칙을 둘지 결정이 필요하다.

### 3-3. 이메일 인증 — 필요한가

⬜ **미정**. Firebase Auth의 이메일 인증 링크 발송 기능을 쓸지, 아니면
어차피 뒤따르는 **휴대폰 인증**(추가 560, 건너뛰기 없음)이 신원 확인
역할을 대신하므로 이메일 인증은 생략할지 — 이건 b4가 판단할 기술
결정이다. ⚠️ 다만 이메일 인증을 생략하면 **비밀번호 재설정 메일이 남의
받은편지함으로 갈 여지**가 있다는 것은 짚어 둔다(오타 계정으로 가입
가능해지는 경우).

## 4. 우리가 리멤버와 다르게 갈 것 — 이미 결정된 것

`remember-signup-flow-2026-08-26.md` §6 정리표를 그대로 가져온다.

| | 판단 |
|---|---|
| 광고를 *"광고성 정보"*라고 부르기 | ✅ 이미 같다. 바꿀 것 없음 |
| 휴대폰 인증(본인확인 아님) | ✅ 이미 같다. 우리 선택이 업계와 어긋나지 않음 |
| 만 14세 자기 신고 | ✅ 같다. 관행이 적법성의 근거는 아님(참고만) |
| **전체 동의 버튼**(리멤버는 있음, 우리는 없음) | ❔ **정하지 않음** — 넣으면 마찰↓ 위험↑. 넣을지는 사용자 결정 사항이지 이번 문서 범위가 아니다 |
| 매체를 나눌 것인가(이메일/앱 알림 구분) | 우리가 나눔 — 법무 회신상 안전한 쪽이라 **유지** |
| **이중등록 화면**(번호로 기존 계정 찾기) | ✅ **추가 583으로 이미 채택** — 별도 문서 `duplicate-account-screen-2026-08-29.md` 참고. 이메일 가입 경로도 휴대폰 인증을 거치므로 **이 화면을 그대로 공유한다** — 이메일 전용 이중등록 화면을 새로 만들 필요 없음 |
| 광고 동의의 위치 | 지금은 로그인 직후 별도 화면(추가 472) — 이메일 가입이 들어와도 이 배치는 안 바뀐다. 이메일도 "로그인=가입" 구조가 아니게 되지만, 광고 동의를 가입 흐름 안에 넣을지는 **이번 범위 밖**(정하지 않음) |

## 5. 이 문서가 안 다루는 것 — b4가 결정할 영역

```
- 비밀번호 정책(§3-2)
- 이메일 인증 필요 여부(§3-3)
- 로그인/가입 갈래를 어떻게 나누는 UI(§3-1)
- Firebase Auth 이메일 제공자 활성화 여부·설정(콘솔 작업, 배포 성격이라
  사용자 결정 필요할 수 있음 — b4가 확인)
- 방침 개정 필요 여부(이메일+비밀번호 자체는 이미 이메일 수집을 하고
  있어(SNS 계정도 이메일을 받음) 새로운 수집 항목은 아닐 가능성이 높지만,
  "비밀번호 보관 방식"은 방침에 명시해야 할 수 있다 — 법무 확인 필요,
  b4가 판단하거나 legal-researcher에 위임)
```

## 6. 확인하지 못한 것

- 앱(iOS·Android) 가입 흐름 실물 — 리멤버 녹화는 **웹**이었다. 앱은
  다를 수 있다.
- 카카오·네이버·구글로 가입했을 때의 흐름 — 녹화는 이메일 경로만 탔다.
- 이메일 가입이 현재 코드에 이미 부분적으로 존재하는지 — 이 문서
  작성 시점(2026-08-29)에 `login_view.dart`(origin/main)를 확인한 결과
  이메일 옵션 자체가 없다(구글·카카오·네이버·애플 넷만 존재). 즉 **0%
  구현 상태**이고, b4의 `feat/phone-otp` 브랜치에서 진행 중인 작업의
  진척도는 이 문서 작성 시점 기준으로 별도 확인이 필요하다(이 문서는
  origin/main만 봤다).
