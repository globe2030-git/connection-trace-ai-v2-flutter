## ② 내보낼 때 이름 형식 고르기 — **지금 한다**

### 왜 이것이 답인가

*"겹치는 것을 막지 못하면 구분이라도 되게"*의 답으로 `#`를 떠올렸지만,
**리멤버의 `#`는 카카오톡 차단용**이었다(분석 문서 1절). 리멤버가 구분에 실제로
쓰는 것은 **이름 형식**이다 — 주소록 이름 칸에 직책·회사명을 함께 넣는다.

```
홍길동                    ← 기본
홍길동 부장
홍길동 부장(가상상사)      ← 리멤버의 현재 설정값
홍길동(가상상사)
```

📌 이름만 보고 **동명이인이 갈리고, 내가 넣은 것인지도 안다.** 주소록 앱을
바꿔도, 클라우드로 옮겨도 따라간다 — 그룹 라벨보다 질기다.

### 기본값은 **"이름만"** 이다

⚠️ 주소록은 이용자 것이고 **이름을 건드리는 쪽이 더 큰 개입**이다. 켜고 싶은
사람이 켠다.

### 화면

```
첫 내보내기 때 한 번 묻는다 → 고른 값을 기억 → 그다음부터 안 묻는다
설정 → (연락처 내보내기)에서 언제든 바꾼다
```

🚨 **묻는 화면에는 미리보기가 있어야 한다.** *"이름 형식을 고르세요"*만으로는
무엇을 고르는지 모른다. 네 형식을 **실제 예시로** 보여 준다(가상값).

🚨 **"이미 내보낸 것은 바뀌지 않습니다"를 화면에 적는다.** 나중에 형식을 바꿔도
폰에 이미 들어간 연락처 이름은 소급해서 안 고쳐진다. 안 적으면 *"켰는데 왜
그대로냐"*가 문의로 온다.

### 구현

| 어디 | 무엇 |
|---|---|
| `vcard_util.dart` | `ContactModel` 인코더에 이름 형식 인자. `N`/`FN` 조립 규칙 |
| 저장 | `shared_preferences` — **형식 코드만** 넣는다(개인정보 아님) |
| 내보내기 시트 | 첫 1회 선택 + 미리보기 + 소급 안 됨 안내 |
| 설정 | 「연락처 내보내기」 항목에서 변경 |
| 테스트 | 네 형식이 만드는 `N`/`FN`을 각각 고정 |

### 🚨 함께 고쳐야 하는 것 — vCard 이스케이프가 지금 없다

`vcard_util.dart`는 값을 **그대로 끼워 넣는다**(2026-08-26 실측). vCard에서
`;` `,` `\` `줄바꿈`은 구조 문자라 이스케이프해야 한다.

```
회사명이 "가상상사;연구소" 이면      ORG 필드가 두 성분으로 갈라진다
이름 형식으로 "홍길동 부장(가상상사)" 를 넣으면   지금은 괜찮지만
회사명에 세미콜론이 있으면 그 순간 깨진다
```

📌 **이름 형식을 넣으면 이름 칸에 들어가는 값이 길고 복잡해진다 — 지금 안
고치면 그때 터진다.** 같은 PR에서 처리한다.

## ③ 앱 잠금 — **한다. 순서는 뒤**

### 왜 값이 큰가

이 앱에는 **제3자(명함 주인)의 개인정보**가 들어 있다. 지금은 **폰만 열면 전부
보인다.** 기기 잠금과 별개로 앱을 한 번 더 잠그는 것은 개인정보 안전조치로도
근거가 된다.

리멤버에도 있다(`암호 잠금 설정` — 꺼짐).

### 왜 지금이 아닌가

앞에 9/1 알림톡 심사·스토어 등록·과금이 있다. 그리고 이것은 **넣어도 스토어
심사 변수가 생기지 않는** 기능이라, 미뤄도 잃는 것이 없다.

### 구현 계획

```
잠그는 방법     기기 생체·자격증명(local_auth 계열) 우선. 자체 PIN 은 나중
잠그는 시점     앱을 다시 열 때 + 백그라운드에 N초 이상 있다가 돌아올 때
설정 위치       「데이터 및 개인정보」 — 명함 데이터 바로 아래가 자연스럽다
```

🚨 **생체 실패 시 잠기지 않게 반드시 기기 자격증명(PIN·패턴) 폴백을 둔다.**
얼굴·지문이 안 될 수 있고, 그때 자기 명함첩에 못 들어가면 그것이 더 큰 사고다.

⚠️ **잠금은 암호화를 대체하지 않는다.** 화면을 가릴 뿐 저장된 데이터는 그대로다.
설정 문구가 이 둘을 섞어 말하면 안 된다 — 이 저장소는 *"완전한 종단간 암호화"*
같은 과장을 금지하고 있다(CLAUDE.md 4절).

### 지금 하는 것

**법무 검토 문항에 넣어 둔다** — *"제3자 개인정보를 다루는 앱에서 앱 수준 잠금이
안전조치로 요구되는지, 권고 수준인지"*. 답이 "요구"에 가까우면 순서가 올라간다.

## ① 카카오톡 자동 친구 추가 방지 — **지금은 안 한다**

### 판단 근거는 취향이 아니라 구조다

```
리멤버   명함첩 전체가 주소록으로 자동 동기화된다
        → 카톡 친구가 무더기로 생긴다 → 그래서 이 기능이 필요했다
우리     사용자가 고른 몇 건을 일회성으로 내보낸다
        → 문제의 크기가 애초에 다르다
```

📌 **리멤버의 이 기능은 "자동 동기화"라는 자기 설계가 만든 문제를 자기가 막는
장치다.** 우리는 그 문제를 아직 만들지 않았다.

### 그리고 우리가 통제할 수 없는 기능이다

효과가 **카카오 쪽 동작에 달려 있다.** *"막아 드립니다"*라고 쓸 수 없고
*"이름 앞에 `#`을 붙여 저장합니다"*라는 **사실까지만** 말할 수 있다. 안 되는
날 그것이 우리 책임이 된다.

⚠️ 이 저장소의 원칙과도 맞물린다 — 과장하지 않는다(CLAUDE.md 4절).

### 언제 다시 보나 — **닫는 조건을 적어 둔다**

```
지속 동기화(휴대폰 연락처 자동 저장)를 도입하기로 결정하는 날
  → 그날 이 항목을 함께 검토한다. 그때는 필요해진다
```

그때 함께 볼 것: vCard `CATEGORIES`(그룹 라벨)를 기기가 실제로 받아 주는지 —
**아직 안 쟀다**(문서 근거뿐).
