## 1. 무엇을 볼 것인가 — 목적별 지표

각 지표를 **A(이미 있는 데이터로 계산 가능)** / **B(새로 계측 필요)**로
구분했다. HANDOFF "6. 화면별 통계 지표 제안"과 backlog 추가 152의 후보 중
이번 베타 목적 3가지에 실제로 대응하는 것만 추렸다 — 나머지(퍼널 전반,
리텐션 등)는 5절 GA 판단과 함께 다시 다룬다.

### ① AI 사용성

| 지표 | 구분 | 계산/수집 방법 |
|---|---|---|
| 호출 성공률, 실패 사유 분포 | A | `aiAuditLogs`의 `ok`/`errorCode` 집계 |
| 지연시간 분포(P50/P95) | A | `aiAuditLogs.latencyMs` |
| 1인당 하루 평균 호출 수, 활성 사용자 수(distinct uid) | A | `aiAuditLogs` uid별 그룹 |
| 정식앱 경로 vs 테스터 허용목록 경로 비율 | A | `appCheckVerified`/`viaAllowlist` — 지금은 거의 전부 허용목록일 것, 스토어 정식 경로가 실제로 쓰이기 시작하는지 보는 용도(6절 App Check 복원 이후 의미가 커짐) |
| 짧은 시간 내 동일 사용자 재요청(불만족 신호 근사치) | A(근사) | `aiAuditLogs`에 어떤 명함에 대한 요청인지는 없다(의도된 설계 — PII 최소수집). 대신 "같은 uid가 N분 내 연속 호출"을 재시도 신호로 근사 사용 |
| 브리핑 결과를 실제로 "썼는지"(대화 포인트→소통기록 저장, 추가 165) | **B** | 이 저장은 **기기 로컬에만** 남는다(서버에 신호 없음). 서버에서 절대 못 봄 — GA 이벤트 없이는 "본 것"과 "쓴 것"의 차이를 서버가 알 방법이 없다. 5절 GA 판단과 연동 |
| 화면 이탈/체류시간 | **B** | GA 없이는 불가능. 우선순위 낮음(아래 4절 참고) |

### ② 실제 비용(손익분기 검증) — 2절에서 절차를 별도로 구체화

| 지표 | 구분 | 계산/수집 방법 |
|---|---|---|
| 호출 1회당 실제 토큰(prompt/candidates/thoughts/total) | A | `aiAuditLogs` — 이미 충분함, **새 계측 불필요** |
| 호출 1회당 실제 원가(KRW) | A(계산) | 2절 공식 |
| 무료 20회 → 첫 충전 전환율 | **B(집계만 없음)** | 원재료(`aiAuditLogs`의 uid, `purchases`의 uid)는 있지만, 아직 IAP 미구현이라 `purchases`가 비어 있어 지금은 계산 불가 — IAP 연동(P1-2/P1-4) 이후 항목. pnl 문서 15-2절의 "4% 손익분기" 검증에 씀 |

### ③ 로직 헛점

| 지표 | 구분 | 계산/수집 방법 |
|---|---|---|
| 크래시 발생 여부·빈도 | A | Crashlytics 콘솔(릴리스 빌드만 집계됨 — 지금 배포가 정확히 release라 대상) |
| 명함 인식 필드별 실패/수정률 | A | `ocrStats` 집계(관리자 콘솔 "명함 인식" 탭에 이미 있음) |
| 1:1 문의 내용(정성) | A | `inquiries` — 버그 제보의 1차 채널 |
| 서버측 에러코드 분포(APP_CHECK 실패, 한도초과 외의 예외 등) | A | `aiAuditLogs.errorCode`, Cloud Functions 로그(`firebase functions:log`) |
| 앱 내에서 발생했지만 크래시로 안 잡히는 "조용한 실패"(예: 저장 실패, 동기화 실패) | **B** | Crashlytics는 `FlutterError.onError`/`PlatformDispatcher.onError`만 잡는다 — 앱이 스스로 catch해서 조용히 넘기는 경로는 잡히지 않는다. 지금은 3절의 피드백 경로(1:1 문의)로만 발견 가능. 새 계측(비-fatal 로그 전송)은 이번 범위 밖으로 두되, 베타 종료 보고서에 "빈도가 낮아 문제 없었다"인지 "감지가 안 됐을 뿐"인지 구분해서 적을 것 |

## 2. 비용 실측 → 충전 티어 회차 확정 절차 (가장 중요)

### 2-1. 지금 상태

⚠️ **2026-08-18 갱신**: 충전 사다리가 **30 / 100 / 200 / 450 / 1,500 / 2,600 / 5,500회**
(₩1천·3천·5천·1만·3만·5만·10만)로 7단계 전부 확정됐다(추가 303).
상위 3단계는 값만 확정이고 `active:false` 상태다. 아래 "1,000원당 10회 비례" 서술은 그 이전 상태다.

`config/billing.tiers`는 이미 **1,000원당 10회 비례**로 7단계가 채워져
배포돼 있다(`sessions/2026-08.md` "0-11": 10/30/50/100/300/500/1000회, 각각 1천/3천/5천/
1만/3만/5만/10만원). 이건 실측 전 **잠정치**이고, 이 절차의 목적은 이
숫자를 실측 기반 값으로 바꾸는 것이다 — 반드시 올리거나 내려야 한다는
뜻은 아니다. 실측 결과가 잠정치와 크게 다르지 않으면 "실측으로 확인함"만
기록하고 값은 유지해도 된다.

### 2-2. 원가 계산 공식

Gemini 과금 단가(`functions/src/index.ts` 주석, `gemini-3.6-flash`,
`THINKING_LEVEL="MINIMAL"` 고정 사용 중): 입력 $1.50/1M 토큰, 출력+사고
토큰 $7.50/1M 토큰(사고 토큰이 출력과 동일 단가로 과금되는 것이 확인된
사실 — pnl 문서 각주 참고).

```
원가(USD) = (promptTokenCount × 1.50 + (candidatesTokenCount + thoughtsTokenCount) × 7.50) / 1,000,000
원가(KRW) = 원가(USD) × 환율   # pnl 문서는 ₩1,430/$ 사용 — 실측 시점 환율로 재확인
```

`totalTokenCount`는 세 값의 합이라 이중 계산 방지용 검증에만 쓰고 원가
계산에는 위 세부 필드를 직접 쓴다(단가가 입력/출력 다르기 때문).

### 2-3. 표본 요건 — "얼마나 쌓이면 계산해도 되는가"

기존 실측(2026-08-08, backlog 추가 100)에서 이미 드러난 변동성:
- 같은 조건에서도 명함 2건 간 원가가 **39% 차이**($0.0014 vs $0.0023).
- 사고 단계(THINKING_LEVEL)만 MINIMAL→HIGH로 바꿔도 **4.5배**
  차이($0.0023 vs $0.0103).

테스터가 10명 안팎(2026-08-10 기준 등록 9~10건)이라 통계적으로 좁은
신뢰구간을 얻는 건 애초에 무리다. **목표를 "정밀한 평균"이 아니라
"설계 가정과 크게 어긋나는지 스크리닝"으로 낮춘다.** 아래 조건을
**모두** 만족하면 계산에 들어간다(먼저 도달하는 게 아니라 전부 충족):

1. 성공 호출(`ok=true`) **150건 이상**.
2. 참여 uid(distinct) **5명 이상** — 특정 한두 명의 사용 패턴에 좌우되는
   걸 막기 위함.
3. 관측 기간 **영업일 기준 7일 이상** — pnl 문서가 "월 사용량의 60%가
   한 주에 몰린다"고 가정했는데, 이게 맞는지도 이번에 같이 확인할 수 있다.

150건·5명·7일 중 어느 하나라도 못 채운 채 상황이 급하면(예: 사용자가
빨리 확정하고 싶다고 할 때), **"미달 상태에서의 잠정 재확인"**이라고
명시하고 그 시점 표본으로 계산한다 — 표본 부족을 숨기지 않는다.

### 2-4. 계산 절차

1. **표본 추출**: `aiAuditLogs`를 기간 지정해 전량 조회. 기존
   `tool/verify_server_privacy.py`/`tool/verify_device_local.py` 패턴을
   재사용해 Firebase CLI 리프레시 토큰 → 액세스 토큰 교환 → Firestore
   REST 관리자 조회 방식으로 새 스크립트(`tool/analyze_ai_cost.py` 가칭)를
   `flutter-developer`에게 위임해 만든다. **출력에 email은 넣지 않는다**
   (uid만, 집계 목적에 이메일이 필요 없음 — CLAUDE.md 개인정보 원칙).
   집계 항목: 성공 호출 수, uid distinct 수, 원가(KRW) 평균·중앙값·
   P90·최댓값, 일별 추이, `THINKING_LEVEL` 재시도(거부 후 재호출) 발생
   여부.
2. **PM(이 역할) 검토**: 평균이 기존 가정($0.0023/회, ₩3.29)과 **±30%
   이내**면 "가정 확인됨"으로 결론짓는다. 벗어나면 pnl 문서 13/15절의
   방법론(순매출 대비 원가 비중을 낮게 유지하는 목표선)에 새 원가를
   대입해 티어별 회차 재계산 후보를 만든다. 평균만이 아니라 **P90(최악에
   가까운 케이스)**도 함께 보고한다 — 평균만 보면 사고 단계가 튄 소수
   사용자의 비용이 가려진다.
3. **가능하면 실제 청구액과 대조**: Google Cloud Billing 콘솔(또는
   대시보드)에서 같은 기간 Gemini API 실 청구액을 확인해 `aiAuditLogs`
   추정치와 비교한다. `usageMetadata` 기반 추정이 실제 청구와 어긋날
   가능성(요금 정책 변경, 캐싱 등)을 배제하기 위함 — 이 프로젝트는
   "코드는 맞는데 실물이 다르다"는 결함이 반복됐으므로 같은 습관을
   비용 검증에도 적용한다. 대조가 어려우면(청구 지연 등) 생략 가능하되
   생략 사실을 보고서에 남긴다.
4. **사용자 승인**: 계산 결과 + 권고 티어 회차 표를 사용자에게 제시한다.
   **최종 가격/회차 확정은 사용자 결정**(사업 방향·손익이 걸린 판단,
   PM이 대신 정하지 않는다).
5. **반영**: 관리자 콘솔 "충전 관리" 탭에서 `config/billing.tiers` 값을
   갱신(코드 배포 불필요, 이미 있는 화면 그대로 사용).
6. **문서화**: backlog에 "추가 N"으로 실측 결과 기록,
   `docs/planning/business/pnl-analysis-freemium.html`에 실측 반영한 새 절
   추가(15절 이후 16절로) — 이 갱신은 리포트 문서 성격이라 `docs/admin/`
   제약(디자인 세션 영역)과는 별개로 PM이 직접 써도 되는 영역이나, 혹시
   그 세션이 동시에 이 파일을 만지고 있을 수 있으니 실행 시점에
   `git diff --name-only`로 충돌 여부 먼저 확인할 것.

### 2-5. 누가 판단하는가

- **원가 계산 자체**(공식 적용, 집계)는 기술적 산출이라 PM이 스크립트
  결과를 검토해 확정한다.
- **가격/회차 최종 확정**은 손익·가격 정책이 걸린 사업 판단이라
  **사용자가 최종 승인**한다. PM은 계산된 후보안(들)과 근거를 제시하는
  역할까지.

  썼는지 ② 브리핑 내용이 유용했는지(1~5) ③ 헷갈렸던 화면·문구 ④ 크래시/
  버그 경험 여부(있었다면 언제·무엇을 하다) ⑤ 충전 가격대 인식(비싸다/
  적당하다/모르겠다). 1차는 1주차 말, 2차는 종료 직전(6절과 연동).

### 지금 만들지 않을 것 (가짜 기능 금지 원칙에 따라 명시)

- **인앱 평점 요청(`in_app_review`)**: 스토어 정식 공개 전(TestFlight/
  App Distribution 단계)에는 리뷰 프롬프트가 실질적 의미가 없다. 정식
  출시 시점 항목으로 P2에 남긴다.
- **자동 피드백 위젯(예: "이 화면 어땠나요?" 인라인 평가)**: 지금
  만들면 응답이 몇 건 안 나올 표본(10명대)에 UI 복잡도만 늘린다. 사용자
  수가 늘어나 설문/1:1문의로 커버가 안 될 때 재검토.
- **에러 상황 컨텍스트 문의 딥링크**(예: AI 브리핑 실패 시 "이 오류
  신고하기" 버튼 → 문의 폼에 에러코드 사전 채움): 유용하지만 지금 급한
  일은 아니다. 소규모 개선으로 P2에 등록(9절 참고), 여유 있을 때 진행.

## 5. GA(Firebase Analytics) 도입 여부

### 판단

**권장: 지금(베타 기간) 붙이지 않는다. 정식 출시 준비 단계(스토어 공개
직전)에 붙인다.**

근거:
- **표본이 작다.** 테스터 10~13명 규모에서는 GA의 퍼널/리텐션 통계가
  통계적으로 의미 있는 신호를 못 만든다 — 이 인원이면 3절의 직접
  설문·1:1 문의가 GA보다 정보 밀도가 높다(익명 이벤트 카운트보다 "왜
  그랬는지"를 직접 물을 수 있다).
- **지금 붙이면 개발 리소스가 급한 다른 항목과 경쟁한다.** 크레딧 지갑
  전환·IAP 연동·버전 게이트 등 출시 전 필수 항목이 이미 대기 중이다.
- **정책 개정 부담이 발생한다.** GA는 기기 식별자·이벤트를 Google
  서버로 전송하므로, 붙이는 순간 개인정보처리방침 위탁 표·자동수집장치
  항목을 개정해야 한다(CLAUDE.md 원칙 — 새 외부 전송이 생기면 방침도
  함께 고침). 베타 기간에 방침을 또 바꾸는 것보다, 정식 출시용 방침
  개정 작업에 한 번에 합치는 게 효율적이다.
- **반대로, 정식 출시 전에는 반드시 필요하다.** 리텐션(D1/D7/D30),
  화면별 이탈, "본 것과 쓴 것"의 차이(1절 B항목들) 같은 서버 로그로는
  절대 못 보는 지표는 실사용자 규모가 커지면 필수가 된다. 이번 베타
  종료 보고서에 "다음 단계 = GA 도입"을 P1로 명시해 놓는다(9절).

### 인구통계(성별/연령/지역) — 직접 수집 vs GA 추론

사용자가 관심을 표한 항목이라 판단을 담아 정리한다.

| 방식 | 장점 | 단점 |
|---|---|---|
| **가입 시 직접 입력** | 정확도 높음, "어떤 목적으로 뭘 모으는지"를 동의 화면에 명시하기 쉬워 방침상 책임 소재가 분명함 | 가입 절차에 마찰 추가(현재 Google/Apple 로그인만으로 가입이 끝나는 구조를 깨야 함), 민감정보(성별)는 그 자체로 더 무거운 동의가 필요할 수 있음 |
| **GA 추론(광고 ID 기반 인구통계)** | 가입 절차에 마찰 없음 | 소규모 앱에서는 추정 정확도가 낮음(광고 신호 기반), **"누가 무엇을 근거로 추정했는지"를 회사가 설명하기 어려워 방침 서술이 모호해짐** — 이 프로젝트가 이미 "과장 금지"(예: 종단간 암호화 서술 정정) 원칙을 지켜온 것과 같은 문제가 재발할 수 있음 |

**권장**: 지금 단계에서는 **둘 다 하지 않는다.** 목적(무엇을 위해
인구통계가 필요한지 — 예: 특정 연령대 타겟 마케팅 검증)이 아직 명확히
정의되지 않았다면 수집 자체가 최소수집 원칙에 어긋난다. 목적이 생기면
그때 **직접 입력(선택 항목, 명확한 동의)** 쪽을 권장한다 — GA 추론보다
법적 책임 소재가 분명하고, 이 프로젝트의 "과장하지 않는다" 원칙과도
더 잘 맞는다. **최종 도입 여부·시점은 사용자 결정**(8절).

## 7. `latestBuild`(버전 게이트) 운영 규칙

### 지금 당장

**올리지 않는다.** 다른 세션이 아직 빌드 6으로 활성 테스트 중이라, 지금
`latestBuild`를 7로 올리면(권장 배너는 "나중에"로 넘길 수 있지만) 테스트
도중 배너가 뜨는 것 자체가 "내가 이미 업데이트를 놓쳤나" 하는 혼란과
작업 흐름 방해를 만든다. 그 세션이 끝났다는 확인(다음 HANDOFF 갱신 또는
사용자 확인)을 받은 뒤에 올린다 — 이 문서에 "대기" 상태로 남겨 다음
세션이 임의로 올리지 않게 한다.

### 앞으로의 운영 규칙 (빌드를 낼 때마다)

1. **배포 완료 ≠ 즉시 `latestBuild` 갱신.** 스토어 심사/배포 채널 전파
   지연(보통 수시간~1일)을 기다린다.
2. **플랫폼 분리 필드를 적극 활용한다**(`latestBuildIos`/
   `latestBuildAndroid`, 추가 165 후속 — `AppUpdateService`가 이미
   지원). 두 플랫폼의 심사/배포 완료 시점이 다르면 **먼저 끝난 쪽만
   먼저 올린다.** 굳이 동시에 맞출 필요 없음.
3. **올리기 전 최소 1개 계정으로 실제 업데이트 설치가 되는지 확인**한다
   (배포 채널 등록 지연으로 "업데이트 있다는데 스토어엔 아직 안 보임"
   상태를 막기 위함).
4. **`message` 필드에 이번 빌드의 핵심 변경 요약을 채운다** — 사용자가
   "왜 업데이트해야 하는지" 알아야 배너를 진지하게 받아들인다.
5. **`minSupportedBuild`(강제)는 베타·테스트 기간 내내 0으로 유지한다.**
   스토어 미공개거나 심사/전파가 불안정한 동안 강제 업데이트를 걸면
   사용자를 빈 페이지로 보내고 앱을 막는 사고가 난다(`sessions/2026-08.md` "0-14"에
   이미 같은 경고가 있음). 강제는 정식 출시 후 배포 채널이 안정된
   뒤에만 고려한다.
6. **동시에 다른 세션이 같은 테스터 그룹으로 활성 QA/테스트 중인지
   먼저 확인한다.** 확인 방법: HANDOFF.md 최상단 섹션에 "진행 중" 표시가
