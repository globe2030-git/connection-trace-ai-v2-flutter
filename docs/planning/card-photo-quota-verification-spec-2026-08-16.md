## 0. 왜 필요한가

한도는 **스토리지 원가의 유일한 천장**이다(예산 알림은 폭주를 막지 스토리지를
감시하지 않는다 — 후속 문서 ③ 정정 절). **천장에 구멍이 있으면 손익 16번의
"최악이어도 여기까지"가 성립하지 않는다.**

코드는 이미 배선돼 있다. **미구현이 아니라 미검증이다.**

```dart
// contact_image_service.dart
final quota  = await _quota.fetch(uid);               // 서버 값, 없으면 200
final synced = (await _backupState.load()).syncedCount;
if (!canUpload(synced, quota)) {
  await _backupState.record(contactId, CardPhotoBackupState.quotaExceeded);
  return;                                             // 업로드하지 않는다
}
```

| 확인한 것 | |
|---|---|
| `kFreeCardPhotoQuota = 200` | ✅ 확정값과 일치 |
| `users/{uid}.cardPhotoQuota` **서버 전용** | ✅ `clientWritableUserFields()`에 없고 rules가 `hasOnly`로 막는다 |
| 초과 시 **업로드만 중단** | ✅ 권고안 4절대로 |
| 경고 임계 `kCardPhotoQuotaWarnRatio = 0.8` | ✅ 200장이면 160장 |

## 1. ⚠️ 먼저 — 알려진 결함 하나

**재설치하면 카운터가 0으로 돌아간다.**

`syncedCount`의 출처는 `SharedPreferences`의 `card_photo_backup_state_v1`
**하나뿐**이고(저장소 전체에서 참조가 그 파일 한 곳), **서버 백업·복원 경로에
들어 있지 않다.** 앱을 지웠다 깔면 0/200에서 다시 시작해, 서버에 이미 200장이
있어도 **200장을 더 올릴 수 있다.**

**악의가 아니다.** 기기 변경·재설치는 이 기능을 만든 이유 그 자체다 — **한도가
가장 자주 깨지는 경로가 하필 이 기능의 주 사용 경로**다.

원가 자체는 작다(1인 400장 = 월 ₩3.9). **문제는 천장 구실을 못 하게 되는 것**이다.

### ⚠️ 고치는 방향 — PM의 ②안에 사실 정정이 하나 있다

PM 제안: *"복원 경로가 이미 서버 파일 목록을 훑으니 그 자리에서 세면 된다."*

**복원 경로는 서버 목록을 훑지 않는다.** `downloadMissingCardImages`는 **로컬이
아는 `contactId`를 하나씩 돌며** `download()`를 시도할 뿐이고, 그 안에 `listAll`
호출이 없다.

#### ⚠️ 내가 여기서 한 번 틀렸다 — `listAll`은 규칙상 막혀 있지 않다

이 문단의 초판에 *"애초에 `listAll`은 규칙상 거부된 전례가 있다(추가 186)"*고
적었다. **186을 잘못 인용했다.** 그 항목을 다시 읽으면 원인이 규칙이 아니다:

> 계정이 이미 사라져 `request.auth`가 null이므로 `storage.rules`의
> `isOwner(uid)`가 거짓이 되어 **Storage 삭제도 `listAll`도 거부된다.**

**탈퇴 순서 결함이었다** — 계정을 먼저 지우고 나서 파일을 지우려 해 인증이
사라진 것이다. **로그인 상태라면 규칙은 허용한다.**

현재 규칙에도 근거가 있다.

```
match /users/{uid}/{allPaths=**} {
  allow read: if isOwner(uid);      // Storage에서 read = get + list
}
```

그리고 `card_photo_backup_service.dart`의 `deleteAllForUser()`가 이미
`listAll()`을 부른다(PM 확인).

⚠️ **그래도 "쓸 수 있다"고 단정하지 않는다.** 그 함수는 플래그가 꺼져 있어
**한 번도 실행된 적이 없다.** 규칙 텍스트가 허용해 보이는 것과 실제로 통과하는
것은 다르다 — 오늘 이 문서가 반복해서 확인한 그대로다.

### 그래서 ②의 셀 방법 — **`listAll` 1순위, `restored` 크기 2순위**

| | 방법 | 장점 | 확인해야 할 것 |
|---|---|---|---|
| **1순위** | 복원 시 `users/{uid}/cards`를 **`listAll`로 세기** | **"못 읽었다"가 예외로 드러난다** — 성공하면 참값, 실패하면 실패인 게 분명하다 | **규칙 실물 통과 여부**(플래그 켠 뒤 1회) |
| 2순위 | `restored`(내려받기 성공 수)로 세기 | 새 호출이 없다 | 아래 함정 |

⚠️ **2순위를 쓸 때의 함정**(PM 지적): `download()`는 `bool`을 돌려주므로
**"서버에 없다"와 "못 읽었다"가 구분되지 않는다.** 회선이 불안하면 `restored`가
적게 잡히고 **카운터가 낮게 설정돼 오히려 더 올릴 수 있게 된다.**

→ **어느 쪽을 쓰든 원칙은 같다. 실패가 한 건이라도 있으면 카운터를 건드리지
말 것.** 못 셌으면 **이전 값을 유지**한다 — **0으로 만들지 않는다.**
`listAll`이 나은 이유는 그 판단을 **예외 하나로 명확히** 할 수 있다는 것이다.

## 2. 검증 항목

⚠️ **검증 종류는 사용자가 고른다**(CLAUDE.md 4절). 이 항목들은 **저장·복원·
재설치**에 걸리므로 규약상 **전체 테스트 등급**이다. 착수 전에 표를 제시할 것.

⚠️ **전제**: `kCardPhotoBackupEnabled = true`로 켠 뒤에만 의미가 있다. 꺼져
있으면 업로드 자체가 없어 `syncedCount`가 늘지 않는다.

### ⚠️ 시작 전에 반드시 적을 것 — **어느 빌드인가**

**2026-08-16에 이것 하나가 없어서 하루치 관찰의 출처를 잃었다.** 두 세션이 같은
기기에 각자 빌드를 얹었고, 나중에 *"그 명함이 누구 빌드에서 저장된 것인가"*를
두고 서로 반대 결론을 냈다. 결국 `logcat`의 **프로세스 ID 변화**로 겨우 갈랐다.

**검증을 시작하기 전에 아래를 적고 시작한다.**

```
커밋 해시      git log --oneline -1
플래그 값      grep kCardPhotoBackupEnabled lib/core/services/card_photo_backup_service.dart
APK 빌드 시각  ls -l build/app/outputs/flutter-apk/app-debug.apk
설치 시각      adb shell dumpsys package <pkg> | grep lastUpdateTime
앱 PID         adb shell pidof <pkg>
```

📌 **PID를 적어 두는 이유**: 관찰 중 PID가 바뀌면 **그 앞뒤는 다른 빌드**다.
2026-08-16에 이걸로 판별했다.

### ⚠️⚠️ "설치했다"가 "그 코드가 돈다"는 아니다 — 확인하고 시작한다

⚠️ **아래는 확정된 원인 규명이 아니다. 2026-08-16에 설명되지 않은 불일치가
있었고, 절차는 그것과 무관하게 필요하다.**

그날 두 세션이 같은 기기에 각자 빌드를 얹었고, **어느 빌드에서 나온 관찰인지를
끝내 확정하지 못했다.** 서로 반대를 가리키는 사실이 나란히 있다.

| 관측 | 무엇을 가리키나 |
|---|---|
| PM의 `install -r` 직후 **PID 4160 → 5489** | 설치가 프로세스를 **죽인다** |
| 다른 세션의 설치 시점에 `.enc` **16장**(= 17:55보다 앞) + **PID 불변**(17:26→18:11) | 설치가 프로세스를 **안 죽였다** |

**셋이 동시에 참일 수 없다.** 아직 안 본 것이 있다 — 두 설치가 몇 초 차이였을
수도, 같은 서명·같은 버전 코드라 설치가 조용히 넘어갔을 수도, 기준선을 잰
시점이 생각과 다를 수도 있다. **모르는 채로 둔다.**

📌 **그날 우리는 정황 하나로 결론을 세웠다가 두 번 뒤집혔다.** 세 번째를 만들지
않기 위해 **"설명되지 않은 불일치가 남아 있다"**로 적는다.

### 그래서 절차로 없앤다 — 원인을 몰라도 된다

`install -r`이 프로세스를 죽이든 안 죽이든, **PID가 바뀐 것을 눈으로 확인하고
시작하면 이 물음 자체가 생기지 않는다.**

⚠️ **`Success`는 "파일이 바뀌었다"이지 "그 코드가 돈다"가 아니다.**

**→ 설치 뒤 반드시 강제 종료하고 다시 띄운 다음, PID가 바뀐 것을 확인하고 시작한다.**

```
adb shell am force-stop <pkg>
adb shell monkey -p <pkg> -c android.intent.category.LAUNCHER 1
adb shell pidof <pkg>        # ← 설치 전과 다른 값이어야 한다
```

⚠️ **되돌릴 때도 같다.** "플래그 false 빌드를 설치했다"만으로는 부족하고,
**앱을 다시 띄워 그 코드가 실제로 도는 상태까지** 만들어야 한다.

⚠️ **끝나면 플래그를 되돌리고 "확인했다"까지 한다** — 소스 값 확인 + 게이트
테스트 통과(`card_photo_backup_gate_test.dart`는 값이 `true`면 실패한다) +
그 APK가 설치됐는지 `lastUpdateTime` 대조.

### ⚠️ 기기 기준선 — 개수로 판정하지 말 것

2026-08-16 검증용으로 등록한 명함 **3장이 기기에 남아 있다**(사용자가 "그냥 둬"로
결정). 배포 직전 검증 때 **이 셋을 기준선에 포함**해야 한다.

| 시각 | contactId | 크기 |
|---|---|---|
| 17:55 | `1786870508869` | 143KB |
| 18:07 | `1786871267773` | 109KB |
| 18:11 | `1786871462630` | 257KB |

**전체 19장**(08-14 이전 16 + 위 3). ⚠️ **개수 변화로 판정하면 어긋난다** —
세션이 여럿이면 서로의 등록을 모른 채 각자 기준선과 비교하게 된다(같은 날 두
세션이 각각 *"16 → 17"*로 보고했고 실제로는 19였다). **파일명·크기·시각까지
본다.**

### ⚠️ V-1이 답해야 할 것 — **업로드가 실제로 도는지 아무도 본 적이 없다**

⚠️ **2026-08-16의 "서버 0건"은 아직 설명되지 않았다.** 플래그를 켠 빌드를
깔았는데 **그 코드가 실제로 돌았는지 확정되지 않았다**(위 불일치). 유출이
없다는 것만 확정이다 — 서버를 직접 조회했다.

**그리고 알맹이는 그대로 남는다.** `upload()`가 성공하는 것을 **지금까지 아무도
본 적이 없다.** 플래그가 계속 꺼져 있었기 때문이다.

**V-1은 "한도에 걸리는가"만이 아니라 "애초에 올라가기는 하는가"를 함께 봐야
한다.** 순서상 후자가 먼저다 — ⚠️ **안 올라가면 한도 검증은 의미가 없다**(아무것도
안 올라가니 한도에 닿을 일도 없고, 그걸 "한도가 잘 막았다"로 오독하기 쉽다).

📌 **함께 볼 것 — `PERMISSION_DENIED`**: 같은 날 로그에 OCR 통계 Firestore 쓰기가
**14번 거부**됐다(`cloud_firestore/permission-denied`). 업로드와 직접 관계는
확인되지 않았지만, **한도 값은 Firestore에서 읽는다**(`users/{uid}.cardPhotoQuota`).
그 읽기도 거부되는 상태인지 **V-1에서 함께 확인할 것.**

### V-1. 한도에 걸리는가 (막힘)

200장을 실제로 채울 수 없으므로 **서버 값을 내려서** 본다.

1. 콘솔에서 `users/{uid}.cardPhotoQuota = 2`로 설정
2. 앱에서 사진 있는 명함 **3장** 등록
3. **판정**
   - 1·2번째: 서버 `users/{uid}/cards/`에 `.enc`가 **생긴다**
   - 3번째: **생기지 않는다**, 백업 상태가 `quota`로 기록된다

⚠️ **앱 화면만 보고 판단하지 말 것.** 서버 실물을 조회해야 한다 — 로컬에는
어차피 저장된다(그게 설계다).

### V-2. 한도를 올리면 풀리는가 (해제)

**이것이 권고안 조건 가)의 "올릴 수 있는 구조"를 함께 닫는다.**

1. V-1 상태에서 `cardPhotoQuota = 5`로 올린다
2. 앱을 다시 켠다 (캐시가 있으므로 갱신 시점 확인 필요)
3. 명함 1장 추가 등록
4. **판정** — 서버에 `.enc`가 생긴다. **앱 재배포 없이 풀려야 한다**

⚠️ 이미 `quota`로 기록된 건이 **자동으로 다시 올라가는지도** 본다. 안 올라간다면
그 사실을 기록할 것 — 사용자에게는 "한도를 늘렸는데 예전 사진은 그대로 안 올라감"
으로 보인다.

### V-3. ⚠️ 재설치 후 카운터 (1절 결함 — **이게 없으면 안 잡힌다**)

1. `cardPhotoQuota = 2`, 명함 2장 등록해 한도를 채운다
2. **앱 삭제 → 재설치 → 같은 계정 로그인**
3. 복원이 끝난 뒤 **설정 화면의 "백업 N/2장"** 확인
4. 명함 1장 추가 등록
5. **판정**
   - **기대(고친 뒤)**: `2/2`로 표시되고 새 사진은 **안 올라간다**
   - **현재(고치기 전)**: `0/2`로 표시되고 새 사진이 **올라간다** ← 결함 재현

⚠️ ②를 구현했다면 **회선을 끊은 채 복원**하는 경우도 볼 것 — 카운터가 **0으로
떨어지지 않고 이전 값을 유지**해야 한다.

⚠️ **`listAll` 방식을 골랐다면 여기서 규칙 통과 여부도 함께 닫힌다.** 복원이
로그인 상태에서 도는지, `permission-denied`가 나지 않는지 로그로 확인할 것 —
그 함수는 지금까지 **한 번도 실행된 적이 없다.**

### V-4. 한도에 걸려도 명함은 정상인가 (제품이 안 망가지는가)

권고안 4절: *"한도가 앱의 핵심 기능을 막아서는 안 된다."*

V-1의 3번째 명함에 대해:

| 확인 | 기대 |
|---|---|
| 명함이 목록에 있다 | ✅ |
| 이름·회사·전화·주소가 다 있다 | ✅ |
| **사진이 기기에서 보인다** | ✅ (로컬에는 저장된다) |
| 검색·AI 브리핑·소통기록 | ✅ 전부 동작 |
| 서버에만 사진이 없다 | ✅ 이것만 다르다 |

### V-5. 80% 사전 안내가 실제로 뜨는가

임계는 `warnThreshold(quota) = floor(quota × 0.8)`.

1. `cardPhotoQuota = 5` (경고선 4장)
2. 3장 등록 → 설정 화면: **"백업 3/5장 · 기기를 바꿔도 복원됩니다"**
3. 4장째 등록 → **"백업 4/5장 · 곧 한도에 닿습니다"**
4. 5장째 등록 → **"백업 5/5장 · 한도에 닿아 새 사진은 백업되지 않습니다.
   기기를 바꾸면 복원되지 않습니다"**

⚠️ **마지막 문장("기기를 바꾸면 복원되지 않습니다")이 반드시 있어야 한다.**
이 기능을 만든 이유가 정확히 그 상황을 없애는 것이었다.

| V-3 | **재설치 후 카운터** | **1절 결함 — 다른 항목으로는 안 잡힌다** |
| V-4 | 걸려도 명함은 정상인가 | 한도가 제품을 망가뜨리지 않는가 |
| V-5 | 80% 사전 안내 | **조건 나)** |

**V-3이 핵심이다.** 나머지는 설계대로 도는지 보는 것이고, V-3만이 **알려진
결함을 재현**한다. ②를 구현하기 전이라면 V-3은 **실패하는 것이 정상**이고,
그 실패를 확인해 두는 것 자체가 값이다 — 고친 뒤 같은 절차로 다시 보면 된다.

## 4. 이 스펙이 다루지 않는 것

- **위조 클라이언트** — 한도는 클라이언트가 세므로 조작 가능하다. App Check
  (P0-9)의 몫이다(권고안 6절). 여기서 검증하지 않는다.
- **충전 사용자 2,000장** — 값만 다르고 경로가 같다. V-1~V-5를
  `cardPhotoQuota`만 바꿔 그대로 쓴다. ⚠️ 다만 **충전 자체가 미구현**이라
  "충전한 사용자에게 2,000이 실제로 적용되는가"는 과금 구현 뒤의 일이다.
- **원가 재계산** — 한도가 제대로 걸리면 손익 16번의 천장 수치가 그대로
  성립한다. 걸리지 않으면 **천장이 없는 것이므로 16-6을 다시 써야 한다.**
