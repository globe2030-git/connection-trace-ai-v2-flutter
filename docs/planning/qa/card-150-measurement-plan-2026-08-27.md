## 0. 촬영 프로토콜 — 지키면 좋은 것 (규칙 아님)

> **촬영 조건이 다르면 플랫폼 차이가 아니라 촬영 차이를 재게 된다.**
> 정답지가 생겨서 "완전히 못 재는" 상황은 아니지만(150장 평균에 묻힌다),
> 노이즈를 줄여 두면 그만큼 결과가 또렷해진다.

⚠️ **아래는 지키면 좋은 것이지 규칙이 아니다.** 150장을 찍는 사람에게
규칙이 많으면 안 지켜지고, 안 지켜졌는데 지켜진 줄 알면 그게 더 나쁘다.
**①②만 신경 쓰고 나머지는 여유가 있을 때만 챙긴다.**

```
① (중요) 명함 한 장을 두 기기로 연속 촬영한다 — 한 장씩 번갈아, 150장을
   한 기기로 다 찍고 나서 다른 기기로 몰아서 찍지 않는다.
   → 조명·각도·손 상태가 거의 같은 시점에 찍히게 하는 것이 목적

② (중요) 먼저 찍는 기기를 교대한다 — 예: 홀수 번째 카드는 아이폰 먼저,
   짝수 번째는 안드로이드 먼저.
   → "먼저 찍는 쪽이 매번 유리/불리"한 순서 효과를 상쇄한다

③ (여유 있으면) 같은 자리·같은 조명에서 찍는다(책상 위 한 자리 고정).
```

**등록 순서를 기록해 둔다** — 채점·비교 양쪽에 매칭 키로 쓴다(1-3절).

## 1. 실험 설계에서 코드로 확인한 것들

### 1-1. 촬영 변수는 정답지가 흡수한다

정답지가 생기면 "A기기 ↔ B기기" 비교가 아니라 "A기기 ↔ 정답", "B기기 ↔
정답"으로 축이 바뀐다. 촬영 잡음은 각 기기 쪽에 랜덤하게 섞여 들어가고
150장 평균을 내면 상쇄된다 — 단, 0절의 ①②를 지키면 상쇄가 더 빨리(적은
표본으로도) 일어난다.

### 1-2. 양 플랫폼이 실제로 같은 인식기를 쓰나

```
pubspec.yaml:54          google_mlkit_text_recognition: ^0.15.0   ← iOS·Android 공용, 단일 패키지
lib/core/services/ocr_scanner_service.dart:4, :320, :414
                         TextRecognizer(script: .korean / .latin) — 플랫폼 분기 없이 같은 Dart 코드
```

**OCR 텍스트 인식 자체는 양쪽 다 구글 ML Kit이다.** 다만 이 Flutter
패키지는 내부적으로 iOS에는 `GoogleMLKit/TextRecognition` iOS SDK를,
Android에는 Android용 ML Kit 바이너리를 각각 심는다 — **같은 제품군이지만
플랫폼별로 별도로 빌드된 네이티브 코드**다.

| 층 | 무엇을 하나 | 플랫폼별로 갈리나 |
|---|---|---|
| ① OCR 텍스트 인식 | ML Kit이 사진에서 줄 단위 텍스트를 뽑는다 | ⚠️ **갈릴 수 있다** — 네이티브 바이너리가 플랫폼별. **직접 촬영을 택했으므로 카메라 화질·렌즈 차이도 이 층에 함께 섞인다**(갤러리 프로토콜이었다면 여기서 빠졌을 변수) |
| ② 필드 파싱 | 이름·회사·전화 등으로 나누는 정규식/규칙(`ocr_scanner_service.dart`) | ❌ 안 갈린다 — 순수 Dart, 플랫폼 분기 없음 |
| ③ 주소 검증(행안부 API) | HTTP로 서버(행안부)에 검색 요청 | ❌ 안 갈린다 — 순수 네트워크 호출, OS 무관 |
| ④ 주소 검증 폴백(OS 지오코더) | 행안부 실패 시에만 동작(`geocoding: ^5.0.0`) | ⚠️ **갈린다** — Android `Geocoder` vs iOS `CLGeocoder`. 기존 기준선(32.3%)이 이미 이 차이를 보여준다 |
| ⑤ AI 보정 | — | **존재하지 않는다** — 1-4 |

📌 **직접 촬영을 택했으므로 ①에서 나는 차이는 "OCR 엔진 차이"와 "카메라
화질 차이"가 섞인 값이다.** 정답지가 있으면 어느 쪽이 원인인지까지는
못 갈라도 최소한 **"둘 중 무엇이 더 정확했나"**는 결과가 나온다 —
이번 실험의 정직한 결론은 "iOS/Android 종합 인식 정확도 차이"이지
"OCR 소프트웨어 자체의 차이"가 아니라는 것을 보고서에 적을 것.

### 1-3. 결과를 어떻게 꺼내 비교하나

```
저장 위치     Firestore users/{uid}/contacts/{contactId} (계정마다 서브컬렉션)
             lib/data/services/data_backup_service.dart:40~42
필드(13개)    이름·회사·부서·직함·휴대폰(phone)·사무실(officePhone)·
             직통(directPhone)·팩스·이메일·홈페이지·주소·상세주소·우편번호
             (lib/data/models/contact_model.dart:47~72)
암호화       AES-256-GCM, 계정별 키가 users/{uid} 문서의 encryptionKeyB64에 있다
             복호화 도구는 이미 저장소에 있다 — tool/_firebase_admin.py의
             list_contacts() / encryption_key() / decrypt_payload()
```

`contactId`는 계정마다 무작위라 **등록 순번**(0절에서 기록해 둔 것) 또는
**전화번호**로 짝짓는다.

**"자동인식 결과 그대로 저장"을 권한다(강제 아님, 새 조건과 충돌 안 함)**
— 채점·비교의 정확도를 위해서는 사람이 값을 고치지 않고 저장하는 편이
좋다. 이름·회사명은 필수 입력이라(`add_card_modal_view.dart:3865~,3887~`)
OCR이 완전히 놓치면 저장이 막히는데, 그런 카드는 최소한만 입력하고
**기록에 "수기 보완"이라고 표시**한다.

📌 **개인정보**: 실제 이름·전화번호를 채운 비교표는 이 저장소(git)에
커밋하지 않는다. `../connection-sense-assets/문서/`에 별도 보관.

`generateBriefing`/`AiBriefingService`를 참조하는 코드는 briefing 화면·

### 1-5. AI 무료 회차 — 등록은 안 부르므로 안 닳는다

150장 × 2기기 = 300건을 등록해도 `aiUsage.dailyCount`/`monthlyCount`

혹시 모자라면 관리자 `grantSupportCredits`(`functions/src/index.ts:1784`)로
보너스 지급 가능.

### 1-6. 계정을 나눠야 한다

같은 계정을 두 기기에 쓰면 `mergeSync()`(id 기준 병합)와 휴대폰번호 중복
확인 대화상자가 **한쪽 기기의 스캔 결과를 덮어쓸 위험**을 만든다
(`contacts_repository.dart`, `add_card_modal_view.dart`). **아이폰은
원래 계정을 인앱 전체삭제로 비우고(3절), 폴드는 임시 계정으로 전환한다**
(1-7).

### 1-7. 폴드 — 임시 계정 전환 절차 (오늘 낮에 사용자가 혼자 함, 화면 순서 그대로)

근거: `lib/presentation/common/auth_gate.dart`의 "계정 전환 안전장치".

```
_showAccountSwitchDialog() — 마지막 로그인 uid와 다른 계정으로 로그인하면
(그리고 기기에 로컬 데이터가 있으면) 뜬다. 선택지 둘:

  "유지하고 계속 쓰기"        — 기기에 남아 있던 이전 계정 명함이
                              지금 로그인한 계정 것으로 편입된다
                              🚨 backlog #377 사고가 정확히 이것
  "현재 계정 데이터로 교체"    — clearLocal() 후 forceRestoreFromServer(새 uid).
                              "교체해도 이전 계정에 백업된 명함은 지워지지
                              않으며"(주석 원문) — 기존 계정 서버 사본은 안전
```

**화면에 뜨는 순서 그대로**:

1. 폴드 설정 → 로그아웃(기존 계정 — 서버 데이터는 안 건드림).
2. 비교용 임시 계정(1-6의 대안 B: 기존 테스터 계정 15개 중 명함 0장인
   것 재사용 — `tool/_firebase_admin.py`의 `list_users()`+`list_contacts()`로
   확인)으로 로그인.
3. **"다른 계정으로 로그인했습니다"** 대화상자가 뜬다.
   🚨🚨🚨 **여기서 반드시 "현재 계정 데이터로 교체"를 누른다.** "유지하고
   계속 쓰기"를 누르면 폴드에 남아 있던 기존 103장이 새 계정으로
   편입된다(backlog #377 실제 사고 전례).
4. 폴드 명함 지갑이 0장인지 확인 → 150장 등록.
5. 등록·측정을 마치면 로그아웃 → **원래 계정으로 재로그인**.
6. **또 같은 대화상자가 뜬다.** 🚨🚨🚨 **이번에도 반드시 "현재 계정 데이터로
   교체"를 누른다.** (반대 방향 실수 — "유지"를 누르면 방금 등록한
   비교용 150장이 원래 계정으로 편입돼 기존 103장과 섞인다.)
7. 원래 계정의 103장이 그대로인지 확인.

⚠️ **위험은 오직 하나, 대화상자 문구를 안 읽고 아무거나 누르는 것이다.**
CLAUDE.md "자동 탭 전에 화면을 먼저 확인한다"와 같은 이유로, **매번
문구를 읽고 고른다.**

나머지는 전부 계산(추정)이라고 표시한다.

#### 등록 시간 (직접 촬영, 확정된 조건)

| 시나리오 | 장당(카드 1장 = 두 기기 촬영 1쌍) | 근거 |
|---|---|---|
| 자세 잡기 + 자동촬영 대기(실측 8초) × 2기기 + OCR·확인·저장 | **40~70초/카드쌍** | 5초(자세) + 8초(실측, 자동촬영) + 2~5초(OCR·확인·저장, 수정 없이) — 이걸 두 기기 각각 |

**150카드쌍(=300회 촬영) 총합**: 150 × 40~70초 = **100~175분(약 1.7~2.9시간)**

📌 **첫 10~15쌍을 실제로 재서 페이스를 확인하고 나머지를 가늠할 것.**
0절의 ①②(번갈아 촬영, 순서 교대)는 이 시간 추정에 영향을 주지 않는다 —
같은 두 번 촬영을 순서만 바꾸는 것이라 총 시간은 그대로다.

#### 채점(정답지) 시간 — 2절에서 상세

**핵심: 1,800칸을 전부 사람이 보는 게 아니라 "불일치한 칸만" 본다.**
계산 근거와 예상 칸 수는 2절.

#### 등록과 채점을 나눠서 해도 되는가 — ✅ 된다

Firestore의 명함 데이터는 **명함을 삭제하거나 회원 탈퇴할 때만 지워진다**
(개인정보처리방침의 파기 사유 두 가지뿐, CLAUDE.md "개인정보를 다루는
앱이다" 절과 같은 원칙). 자동 만료(TTL)나 일정 기간 후 삭제 로직은
코드 어디에도 없다. **그러니 오늘은 등록까지만 하고, 채점은 다른 날
해도 데이터가 사라지지 않는다.** 단, **실물 명함(종이)은 채점이 끝날
때까지 순서대로 보관**해야 한다 — 매칭 키가 등록 순번이므로 순서가
흐트러지면 채점이 어려워진다.

## 2. 채점(정답지) 프로토콜 — 불일치한 칸만 사람이 본다

**150장 × 13칸 = 1,950칸을 전부 입력하는 것은 불가능하다. 그렇게 적으면
이 계획은 지켜지지 않는다.** 그래서 순서를 이렇게 짠다.

```
① 두 기기 결과를 칸 단위로 diff 한다             ← 기계(스크립트)가 한다
② 일치하는 칸은 「둘 다 같음」으로 두고 넘어간다   ← 사람이 볼 필요 없음
③ 불일치한 칸만 사람이 실물 명함을 보고 정답을 고른다
④ 일치한 칸 중 표본을 뽑아 「둘 다 틀린 경우」가 얼마나 되는지 잰다
```

### 2-1. ①을 돌리기 전에 — 정규화 규칙을 먼저 정한다

⚠️ **정규화 없이 문자열을 그대로 비교하면 진짜 오류가 아닌 표기 차이까지
"불일치"로 잡혀 판정할 칸이 부풀어 오른다.** 예: 전화번호를 한쪽은
`010-1234-5678`, 다른 쪽은 `010 1234 5678`로 뽑으면 값은 같은데 문자열은
다르다. 이 저장소에 이미 있는 규칙(`tool/ocr_review/README.md` "정답지
작성 규칙")을 그대로 재사용한다:

```
전화·팩스     라벨(M/T/F)·국가번호(+82) 빼고 하이픈만 (010-1234-5678)
이메일        표기 그대로(대소문자 등 그대로 비교)
주소          끝 쉼표 등 트레일링 문자 제거 후 비교
그 외         앞뒤 공백만 제거(trim) 후 비교
```

이 규칙을 diff 스크립트에 먼저 넣고 돌린다 — **이 세션은 스크립트를
직접 작성하지 않았다**(계획 문서 범위), 다음 세션(`flutter-developer` 또는
간단한 파이썬 스크립트 작업)에 넘긴다. `tool/_firebase_admin.py`의
`list_contacts`/`decrypt_payload`를 그대로 재사용하면 새로 만들 것은
"정규화 후 diff" 로직뿐이다.

### 2-2. 판정할 칸이 몇 개쯤인가 — 계산(추정), 실측 아님

**근거 수치**: 91장 정답지 기준 필드별 평균 정확도 **76.9%**(맞음 70·
틀림 14·빈값 7, backlog 추가 409). 이것을 "한 기기가 한 칸을 맞힐 확률
p=0.769"로 놓는다.

두 기기가 **서로 다른 실수를 한다고 가정**(같은 값으로 동시에 틀릴
확률을 0으로 두는 보수적 가정 — 이러면 "판정 대상"을 과대 추정하게
되므로 시간 계획엔 안전한 쪽이다)하면:

```
두 기기가 일치할 확률   = 둘 다 맞음(p²) = 0.769² ≈ 0.591
두 기기가 불일치할 확률 = 1 - 0.591 ≈ 0.409  ← 이 칸들만 사람이 본다
```

**칸 수로 환산**(가정: 카드당 13칸 중 평균 8~9칸이 채워짐 — ⚠️ 이 값은
저장소에 실측이 없어 **가정**이다. 팩스·직통·홈페이지는 실제 명함에
드물고, 이름·회사·휴대폰·주소는 거의 항상 있다는 정성적 판단으로만 잡음):

```
150장 × 8.5칸(가정) = 1,275개의 "채워진 칸" 쌍
× 41% 불일치        ≈ 약 520칸이 사람이 봐야 하는 대상
```

📌 **2-1의 정규화를 거치면 이 숫자는 줄어들 것으로 예상되지만 얼마나
줄지는 실측해야 안다.** 그래서 **①(diff 스크립트)을 먼저 돌려 실제
판정 대상 칸 수를 세는 것 자체가 이 계획의 다음 단계**다 — 아래 시간
추정은 diff를 돌리기 전 "최악을 가정한 상한"으로 읽을 것.

### 2-3. ③ 판정 시간 — 계산(추정)

520칸이 150장에 퍼져 있으므로 카드 단위로 보면(1장에 여러 칸이 몰릴 수
있어 실제로 손대는 카드 수는 520보다 적다 — 대략 100~140장으로 추정,
근거는 없음) **카드 한 장을 집어 실물과 대조하고 판정하는 데 30초~1분**
(이미 순서대로 쌓여 있어 찾는 시간은 거의 안 듦, 대조할 칸이 1~3개인
경우가 대부분).

```
100~140장 × 30~60초 ≈ 50~140분(약 1~2.3시간)
```

### 2-4. ④ "둘 다 틀림" 표본 확인 — 빠뜨리면 안 되는 이유

⚠️ **둘이 같아도 둘 다 틀릴 수 있다.** 파싱 로직(1-2절 ②)이 공유
코드라서, 특정 형태의 명함에서 **같은 방식으로 같이 틀리는 것**이
가능하다 — 오히려 이런 경우일수록 "일치=정답"이라는 착시가 강하게
생긴다. 이걸 안 재면 최종 결론에 **검증되지 않은 전제**가 들어간다.

**표본 크기**: 일치한 칸(약 1,275-520 ≈ 755칸, 카드로는 대략 100장
안팎으로 추정) 중 **20장을 무작위로 뽑아 그 카드의 채워진 칸 전부를
실물과 대조**한다. 20장 × 8.5칸 ≈ 170칸, 판정은 이미 일치를 확인한
값이 맞는지만 보면 되므로 카드당 30초 안팎 → **약 10~15분.**

### 2-5. 채점 총 시간 (계산, 큰 폭)

```
①~② diff 스크립트 실행(사람 대기시간 거의 없음)     수 분
③ 불일치 칸 판정                                    50~140분
④ 일치 칸 중 "둘 다 틀림" 표본 확인                  10~15분
─────────────────────────────────────────────
합계                                              약 1~2.5시간
```

⚠️ **이 폭은 2-2의 가정(카드당 채워진 칸 수, 오차 동시발생 없음)에
좌우된다.** diff를 실제로 돌리면 이 문서의 추정을 실측으로 바꿀 수 있다
— 그렇게 되면 이 문서의 숫자를 실측치로 갱신할 것.

```
① 150장 등록을 마친 뒤 「주변」 탭을 연다
```

## 7. 보고

### ① 판정할 칸이 몇 개쯤인가

**계산(추정), 실측 아님.** 91장 기준선(76.9%)을 두 기기에 각각 적용하면
두 기기가 일치할 확률은 약 59%, 불일치할 확률은 약 41%다. 카드당
채워진 칸이 평균 8.5개(가정)라고 보면 150장 × 8.5칸 × 41% ≈ **약
520칸**이 사람이 봐야 하는 대상이다. 여기에 표기 차이(공백·하이픈 등)를
정규화하면 실제 숫자는 이보다 줄어들 것으로 예상되며, **정확한 숫자는
diff 스크립트를 실제로 돌려야 나온다** — 이 계획의 다음 단계로 남겨
둔다.

### ② 등록/채점 각각 몇 시간인가

```
등록   100~175분(약 1.7~2.9시간) — 유일한 실측치(자동촬영 8초/장) 기반 계산
채점   약 60~150분(약 1~2.5시간) — 91장 기준선(76.9%) 기반 계산, 폭이 큼
─────────────────────────────────
같은 날 다 하면       약 2.7~5.4시간
채점을 다른 날로 미루면  등록만 오늘 1.7~2.9시간, 채점은 언제든(데이터가
                      명함 삭제·탈퇴 전까지 서버에 그대로 남는다)
```

### ③ 사용자가 12시에 바로 시작할 수 있는 상태인가

**대체로 그렇다.** 딱 하나 사전 준비가 필요하다 — **폴드에 쓸 임시
계정**을 정해야 한다(1-6절 대안 B: 기존 테스터 계정 15개 중 명함 0장인
것을 `tool/_firebase_admin.py`로 미리 확인해 두는 것을 권장, 몇 분이면
된다). 그 외에는 코드 확인이 이미 끝나 있어 12시부터 바로 1단계(폴드
계정 전환)를 시작할 수 있다.
