## 0. 이 실험의 가장 큰 함정 — 먼저 답한다

> **촬영 조건이 다르면 플랫폼 차이가 아니라 촬영 차이를 재게 된다.** 조명·
> 각도·거리·손떨림이 조금만 달라도 OCR 결과가 갈린다. 150장을 두 번 찍으면
> 300번의 서로 다른 촬영이 되고, "아이폰이 더 낫다"가 나와도 기기 때문인지
> 그때 더 잘 찍혀서인지 구분이 안 된다.

**코드로 확인한 결론: 촬영 변수를 통째로 없앨 수 있다.** 이 앱은 카메라로
바로 찍는 경로 말고 **갤러리(사진첩)에서 이미지를 불러와 인식하는 경로를
정식 기능으로 지원한다** — 측정용 임시 코드가 아니라 이용자가 쓰는 실제
버튼이다.

```
lib/presentation/features/wallet/views/add_card_modal_view.dart:917~968
  _performGalleryScan() — "갤러리에서 앞·뒷면 2장을 한 번에 골라 순서대로
  인식한다"(주석 원문, backlog P2-②). _performOcrScan()과 결과 처리 로직을
  공유한다(:968~) — 카메라로 찍든 갤러리에서 고르든 그 뒤 인식·파싱은
  **같은 코드 경로**를 탄다.

lib/core/services/ocr_scanner_service.dart:270, :287
  pickImageFromGallery() / pickImagesFromGallery() — image_picker 기반이라
  iOS·Android 둘 다 동작한다(플랫폼 분기 없음).
```

**그래서 1순위 권고안은 이것이다.**

> **같은 사진 파일 하나를 양쪽 기기에 넣고, 둘 다 "갤러리에서 선택"으로
> 등록한다. 앱 카메라로 재촬영하지 않는다.**

이렇게 하면 남는 차이는 순수하게 **OCR·파싱 소프트웨어 층**뿐이다(카메라
화질 차이까지도 사라진다 — 애초에 똑같은 바이트를 두 기기에 넣으므로). 구체
절차는 2절.

⚠️ **차선책도 적어 둔다** — 위 방식을 쓰지 않기로 하면(예: "실제 사용
경험처럼 각자 카메라로 찍어 보고 싶다"), 촬영 조건을 최대한 맞춰야 한다:
거치대(또는 같은 자리에 고정) 사용, 같은 조명, 같은 순서로 한 장씩 번갈아
찍기(피로도·조명 변화가 한쪽에 몰리지 않게), 각도·거리를 매 장 눈대중이
아니라 가이드 프레임에 맞춰 일정하게. **이 경우 결과 차이의 일부는 촬영
잡음이라는 것을 보고서에 반드시 명시**해야 한다 — 안 그러면 "아이폰이
낫다/안드로이드가 낫다"는 결론이 실제로는 "그날 손이 더 안정적이었다"일 수
있다.

## 1. 실험 설계에서 코드로 확인한 것들 (PM 질의 1~5 답)

### 1-1. 촬영 변수 제거 가능한가 — ✅ 가능 (위 0절)

### 1-2. 양 플랫폼이 실제로 같은 인식기를 쓰나

```
pubspec.yaml:54          google_mlkit_text_recognition: ^0.15.0   ← iOS·Android 공용, 단일 패키지
lib/core/services/ocr_scanner_service.dart:4, :320, :414
                         TextRecognizer(script: .korean / .latin) — 플랫폼 분기 없이 같은 Dart 코드
```

**OCR 텍스트 인식 자체는 양쪽 다 구글 ML Kit이다.** 다만 이 Flutter
패키지는 내부적으로 iOS에는 `GoogleMLKit/TextRecognition` iOS SDK를,
Android에는 Android용 ML Kit 바이너리를 각각 심는다 — **같은 제품군이지만
플랫폼별로 별도로 빌드된 네이티브 코드**다. 구글이 정확도를 맞추려고
하지만 100% 동일을 보장하지는 않는다. **그래서 이 층에서 나는 차이가 이번
실험이 잴 수 있는 진짜 신호다** — 다른 층(아래)은 애초에 코드가 같아서 큰
차이가 안 나는 게 정상이다.

**등록 파이프라인을 층으로 갈랐다** — 코드로 실제로 확인:

| 층 | 무엇을 하나 | 플랫폼별로 갈리나 |
|---|---|---|
| ① OCR 텍스트 인식 | ML Kit이 사진에서 줄 단위 텍스트를 뽑는다 | ⚠️ **갈릴 수 있다** — 네이티브 바이너리가 플랫폼별 |
| ② 필드 파싱 | 이름·회사·전화 등으로 나누는 정규식/규칙(`ocr_scanner_service.dart`) | ❌ 안 갈린다 — 순수 Dart, 플랫폼 분기 없음 |
| ③ 주소 검증(행안부 API) | HTTP로 서버(행안부)에 검색 요청 | ❌ 안 갈린다 — 순수 네트워크 호출, OS 무관 |
| ④ 주소 검증 폴백(OS 지오코더) | 행안부 실패 시에만 동작(`geocoding: ^5.0.0`) | ⚠️ **갈린다** — Android `Geocoder` vs iOS `CLGeocoder`, 서로 다른 네이티브 구현. 기존 기준선(32.3%)이 이미 이 차이를 보여준다 |
| ⑤ AI 보정 | (PM 질의에 있었던 항목) | **존재하지 않는다** — 아래 1-4 |

📌 **①·④만 플랫폼별로 갈릴 수 있는 층이다.** ②·③은 코드가 같으므로 두
플랫폼이 다르게 나오면 그 자체가 이상 신호(버그)지 "플랫폼 차이"가 아니다.
**이 사실 자체가 하나의 결과다** — 비교 결과가 크게 안 갈리더라도 "원래
소프트웨어 층 대부분이 공유돼 있어서 그렇다"고 설명할 수 있다.

### 1-3. 결과를 어떻게 꺼내 비교하나

두 기기 모두 텍스트는 서버(Firestore)에 백업되므로, **adb 없이도 서버에서
바로 비교 자료를 꺼낼 수 있다.**

```
저장 위치     Firestore users/{uid}/contacts/{contactId} (계정마다 서브컬렉션)
             lib/data/services/data_backup_service.dart:40~42
필드(13개)    이름·회사·부서·직함·휴대폰(phone)·사무실(officePhone)·
             직통(directPhone)·팩스·이메일·홈페이지·주소·상세주소·우편번호
             (lib/data/models/contact_model.dart:47~72)
암호화       AES-256-GCM, 계정별 키가 같은 users/{uid} 문서의 encryptionKeyB64에 있다
             복호화 도구는 이미 저장소에 있다 — tool/_firebase_admin.py의
             list_contacts() / encryption_key() / decrypt_payload()
```

**두 계정(아이폰 계정·폴드 계정)에서 각각 `list_contacts()`로 150건씩
꺼내 복호화하면, 13개 필드가 그대로 나온다.** `contactId`는 기기·계정마다
무작위로 생성되므로 **id로는 짝을 못 맞춘다** — 대신:

- **같은 순서로 등록한다**(1절 프로토콜) → 등록 순번으로 짝짓기
- 또는 **전화번호로 짝짓기**(같은 실물 명함이면 전화번호가 같다 — 단,
  OCR이 전화번호를 완전히 틀리게 뽑은 극소수 케이스는 순번 짝짓기가 더
  안전하다)

🚨 **"자동인식 결과"와 "최종 저장값"은 다르다.** Firestore에 남는 것은
**사용자가 저장을 누른 최종값**이라, 사람이 고친 흔적까지 섞여 있으면
순수 OCR 비교가 안 된다(둘 다 사람이 똑같이 고치면 차이가 지워진다).
**해법**: 이번 비교 실험에 한해 **자동 인식 결과를 손으로 고치지 않고
그대로 저장한다.** 이러면 Firestore 최종값 = OCR 원본값이 되어, 별도
디버그 덤프 도구(`ocr_measure_dump.dart`, `measure_sample_sink.dart`는
`kDebugMode` 게이트가 있어 release 빌드에선 아예 안 돈다 — 2절 C-3 참고)
없이도 순수 비교가 가능해진다.

⚠️ **예외**: 이름·회사명은 앱이 **필수 입력**으로 막아 둬서(`add_card_modal_view.dart:3865~`,
`:3887~`) OCR이 완전히 놓치면 저장 자체가 안 된다. 그런 카드는 최소한만
입력해 저장하고, **기록표에 "이 칸은 수기 보완함"으로 표시**해 그 칸만
비교에서 빼거나 따로 주석을 단다.

📌 **비교표에 실제 이름·전화번호 같은 제3자 개인정보 원문을 채운 결과물은
이 저장소(git)에 커밋하지 않는다.** CLAUDE.md 원칙과 같은 이유다 — 아래
4절 표는 빈 양식만 담고, 실제로 채운 표는 `../connection-sense-assets/문서/`에
저장한다.

### 1-4. AI 보정 레이어는 없다 — 명함 등록은 AI를 부르지 않는다

```
generateBriefing/AiBriefingService를 참조하는 파일: app_check_service.dart,
ai_usage_service.dart, ai_briefing_service.dart, briefing/ 화면들,
settings의 AI 관련 화면, ai_usage_chip.dart 뿐이다.
add_card_modal_view.dart / contacts_repository.dart 어디에도 없다.
```

**등록 파이프라인에 AI(Gemini) 호출이 없다.** OCR은 100% 기기 내부(ML
Kit), 주소는 행안부 API·OS 지오코더뿐이다. 그래서 PM 질의 "인식 경로에
AI 보정 층이 있는지"의 답은 **"없다, 지금 파이프라인엔 그 층 자체가
존재하지 않는다"**다.

### 1-5. AI 무료 회차가 버티나 — ✅ 버틴다 (등록은 AI를 안 씀)

1-4에서 확인했듯 **카드 등록은 AI를 한 번도 안 부른다.** 150장 × 2기기 =
300건을 등록해도 `aiUsage.dailyCount`/`monthlyCount`(하루 20 / 월 100,
`functions/src/index.ts:165,168`)는 **전혀 줄지 않는다.**

⚠️ 단, 등록과 별개로 **"등록한 김에 AI 브리핑도 눌러보자"**를 하면 그건
정상적으로 소진된다. 하루 20회를 넘기면 막히는데, 그때 푸는 방법은 이미
있다 — 관리자 콘솔의 **`grantSupportCredits`**(1:1 문의 응대용 보너스
지급, `functions/src/index.ts`)로 그 계정에 보너스 회차를 얹을 수 있다.
이번 실험엔 필요 없을 가능성이 높지만(등록만 하면 안 씀), 혹시 브리핑도
같이 시험해 보고 싶다면 미리 참고.

### 1-6. 계정을 나눠야 하나 — ✅ 나눠야 한다 (코드로 확인한 위험)

같은 계정을 두 기기에 로그인하면 **서버 데이터가 한 계정 안에서 합쳐진다.**
관련 코드:

```
lib/data/repositories/contacts_repository.dart
  mergeSync() — id 기준으로 로컬·서버를 합친다. 전화번호 기준 중복은
  안 걸러진다(그건 별도 UI 흐름).

lib/presentation/features/wallet/views/add_card_modal_view.dart
  "휴대폰 번호 기준으로 기존 인맥과 중복이면 물어본다"(HANDOFF 1절) —
  **저장 시점에 로컬에 이미 로드된 목록과 비교**한다. 두 기기가 같은
  계정으로 같은 명함을 각자 등록하면, 나중에 동기화가 한 번이라도 지나간
  뒤에는 두 번째 기기가 "이미 있는 명함"으로 보고 **덮어쓸지 물어본다** —
  둘 중 하나의 스캔 결과가 사라질 수 있다.
```

**그래서 같은 계정 공유는 이번 실험에 안 맞는다.** 대안 둘:

| 방법 | 대가 |
|---|---|
| **A. 완전히 새 계정을 하나 더 만든다**(예: 여분 Google 계정) | 깨끗하지만 계정이 하나 늘어난다(관리 부담 — 다음에 또 헷갈릴 소지) |
| **B. 기존 "테스터 계정 15개" 중 명함 0장인 것을 재사용한다**(추천) | 새 계정을 안 만들어도 됨. 어떤 계정이 비어 있는지는 `tool/_firebase_admin.py`의 `list_users()` + `list_contacts()`로 확인 가능(코드로 이미 있는 도구, 실행만 하면 됨) |

⚠️ **아이폰 쪽은 계정을 바꿀 필요가 없다** — 원래 계획대로 **지금 쓰던
계정을 인앱에서 전체 삭제**해 0장으로 만들면 된다(3절 "①" 방법, 삭제해도
좋다고 사용자가 이미 허락).

**폴드 쪽만 계정을 바꿔야 한다** — 폴드는 기존 103장을 지우면 안 되기
때문이다(1-7).

### 1-7. 폴드 상태 — 지우지 않고 이 실험이 성립하나

✅ **성립한다.** 앱을 지우거나 기존 계정 명함을 지우지 않고도, **계정만
잠깐 바꿔서** 0장 상태를 만들 수 있다는 것을 코드로 확인했다. 근거는
`lib/presentation/common/auth_gate.dart`의 "계정 전환 안전장치"다.

```
_showAccountSwitchDialog() — 마지막 로그인 uid와 다른 계정으로 로그인하면
(그리고 기기에 로컬 데이터가 있으면) 뜬다.

선택지 둘:
  "유지하고 계속 쓰기"        — 기기에 남아 있던 이전 계정 명함이
                              **지금 로그인한 계정 것으로 편입**된다
                              (🚨 backlog #377 사고가 정확히 이것 — 실제로 터진 적 있음)
  "현재 계정 데이터로 교체"    — clearLocal() 후 forceRestoreFromServer(새 uid) —
                              기기 로컬을 비우고 **새로 로그인한 계정 자신의
                              서버 데이터**로 갈아 끼운다. 주석 원문: "교체해도
                              이전 계정에 백업된 명함은 지워지지 않으며" —
                              **이전 계정(폴드의 기존 103장)의 서버 사본은
                              안전하다.**
```

**절차 (폴드에서)**:

1. 설정 → 로그아웃(지금 쓰는 원래 계정에서 로그아웃 — 서버 데이터는
   안 건드림).
2. 비교 실험용 계정(1-6의 B, 비어 있는 테스터 계정)으로 로그인.
3. "다른 계정으로 로그인했습니다" 대화상자가 뜨면 **반드시 "현재 계정
   데이터로 교체"를 고른다.** (여기서 실수로 "유지"를 고르면 폴드에 남아
   있던 기존 103장이 새 계정 쪽으로 편입될 위험이 있다 — 🚨 코드 주석이
   실제 사고 사례로 남겨 둔 자리다.)
4. 폴드가 0장인지 확인 → 150장 등록(1절 프로토콜).
5. 끝나면 로그아웃 → **원래 계정으로 재로그인**.
6. 다시 "다른 계정으로 로그인했습니다"가 뜨면 **또 "현재 계정 데이터로
   교체"를 고른다.** (이번엔 반대 방향 실수를 막는 것이다 — "유지"를
   고르면 방금 등록한 비교용 150장이 원래 계정 쪽으로 편입돼 **기존 103장과
   섞인다.**)
7. 원래 계정의 103장이 그대로 돌아왔는지 확인.

⚠️ **이 절차의 유일한 위험은 5~6단계에서 대화상자 문구를 안 읽고 아무거나
누르는 것이다.** CLAUDE.md의 "자동 탭 전에 화면을 먼저 확인한다"와 같은
원칙 — **사람이 직접 하는 절차이니 서두르지 말고 대화상자 문구를 매번
읽고 고른다.**

### 1-8. 현실성 — 300장이면 몇 시간인가

**실측값은 하나뿐이고, 나머지는 계산(추정)이다 — 명시한다.**

```
실측(backlog 추가 293 계열): 아이폰 자동촬영 — 명함 한 장을 한 자리에
놓고 카메라가 인식해 자동 셔터가 눌리기까지 8초. "확인했다"가 아니라
"이 표본에서 8초"라고 그 문서 자신이 못박아 뒀다(각도·거리를 바꾼
표본 없음).

정답지 만들기(그라운드트루스 채점) 1~2분/장 — 이건 등록 시간이 아니라
"채점 시간"이다(backlog 추가 445 계열). 등록과 헷갈리면 안 된다.
```

등록 전체 흐름(촬영/불러오기 → OCR → 확인 → 저장)의 실측치는 이 저장소에
없다. **아래는 계산(추정)이다**:

| 시나리오 | 장당 추정 시간 | 근거 |
|---|---|---|
| **갤러리 프로토콜(0절 권장안) + 수정 없이 그대로 저장** | **10~20초** | 카메라 촬영·자동감지 대기(8초)가 아예 없다 — 이미 찍힌 사진을 고르기만 함. OCR 처리 1~3초 + 화면 확인·저장 몇 초 |
| **앱 카메라로 직접 촬영 + 수정 없이 저장** | **20~35초** | 자세 잡기 ~5초 + 자동촬영 대기(실측 8초) + OCR 1~3초 + 확인·저장 몇 초 |
| **앱 카메라 + 뒷면 스캔 + 필드 보정 + 중복 확인까지 포함(평소 실사용)** | **45~90초** | 위에 뒷면 스캔 반복 + 사용자가 값 고치는 시간 + 가끔 뜨는 중복/주소확인 대화상자 |

**300장(150×2기기) 총 소요 계산**:

| 시나리오 | 300장 총합 |
|---|---|
| 갤러리 프로토콜(하한) | 300 × 10초 = **50분** ~ 300 × 20초 = **100분(1.7시간)** |
| 앱 카메라 직접 촬영(중간) | 300 × 20~35초 = **100~175분(1.7~2.9시간)** |
| 평소처럼 꼼꼼히(상한) | 300 × 45~90초 = **225~450분(3.8~7.5시간)** |

📌 **폭이 매우 크다.** "먼저 재고 나서 정하라"는 이 프로젝트 원칙대로,
**첫 10~15장을 실제로 등록해 시간을 재고**(스톱워치나 그냥 시계로 충분),
그 페이스로 나머지를 외삽하는 것을 권장한다 — 특히 갤러리 프로토콜을
쓰면 자동촬영 대기(8초/장, 유일한 실측치)가 통째로 없어지므로 **시간
문제의 상당 부분이 촬영 변수 제거와 같은 선택으로 함께 풀린다.**

**⚠️ 표본을 줄이라고 강요하지 않는다 — 선택지를 나란히 둔다:**

| 선택지 | 얻는 것 | 대가 |
|---|---|---|
| **150장 그대로** | 통계적으로 더 믿을 만한 차이 검출(특히 몇 %p 수준의 미묘한 차이도 잡을 가능성) | 위 표대로 최대 몇 시간 |
| **표본을 줄인다(예: 50장×2=100건)** | 시간이 대략 1/3로 줄어든다 | 뚜렷한 차이(예: 20%p 이상)는 여전히 보이지만, 미묘한 차이는 표본이 작아 우연(잡음)과 구분이 안 될 수 있다 |
| **갤러리 프로토콜 채택**(표본 크기와 별개로 항상 적용 가능) | 어느 표본 크기든 시간이 크게 줄고, 촬영 변수도 제거됨(0절) | 실사용(카메라로 직접 찍는 상황)과는 다른 조건이라는 것을 보고서에 명시해야 함 |

### 1-9. 무엇을 비교로 기록하나 — 표 양식은 4절

정답지 없이도 "일치율"은 잴 수 있고, 정답지가 있어야 "어느 쪽이 맞았는지"
(정확도)까지 잴 수 있다.

⚠️ **기존 기준선과 형태가 다르다** — 91장 76.9%(정답 대조 정확도), 95건
OS 32.3%/행안부 67.7%(주소 매칭률)는 전부 **"정답과 비교한 정확도"**다.
이번 실험의 1차 산출물은 **"아이폰 값과 안드로이드 값이 같은가"**라는
**일치율**이라 잣대가 다르다. **직접 비교 가능한 정확도까지 얻으려면**
150장짜리 정답지가 따로 필요하다(1~2분/장 → 150~450분, **이 계획과는
별도의 큰 작업**으로 취급해야 한다 — 하려면 그렇게 결정하고 시간을 따로
잡을 것).

## 2. 아침에 사용자가 그대로 따라 할 순서

⚠️ 아래는 **"갤러리 프로토콜(0절 권장안)"을 택했을 때** 기준이다. 각자
카메라로 직접 찍기로 하면 3단계(사전 촬영·전달)를 건너뛰고 바로 등록하되,
0절의 차선책(거치대·조명 통일)을 따른다.

### 0단계 — 계획 확정 (사용자가 고를 것, 5분)

1. **표본 크기**를 정한다(150 그대로 / 줄이기 — 1-8 표 참고).
2. **촬영 방식**을 정한다(갤러리 프로토콜 권장 / 각자 카메라 직접).
3. **정답지(그라운드트루스) 채점까지 할지** 정한다(안 하면 "일치율"까지,
   하면 150장×1~2분의 별도 작업이 붙는다 — 이번엔 생략을 권장, 필요하면
   나중에 표본을 추려 따로).

### 1단계 — 폴드 쪽 계정 준비 (약 5~10분, 사용자 직접 조작)

1-7절 순서대로 로그아웃 → 비교용 계정으로 로그인 → **"현재 계정 데이터로
교체"** 선택 → 폴드 0장 확인.

### 2단계 — 아이폰 쪽 초기화 (약 5분)

1. 지금 계정 이메일 확인(설정 화면 상단).
2. **표 A(시작 전)** 기록: 명함 수, `설정 → OCR 통계` 초기화 버튼으로
   집계 리셋(`ocr_stats_view.dart`), (선택) `aiUsage` 스냅샷.
3. 명함 지갑 → 선택 모드 → 전체 선택 → 삭제 → 확인(**"선택한 명함과
   기록이 기기와 서버에서 모두 삭제됩니다. 되돌릴 수 없습니다."**) →
   0장 확인.

### 3단계 — (갤러리 프로토콜을 택했다면) 150장 사전 촬영·전달 (본 작업 앞단)

1. 아무 기기로나(또는 스캐너로) 150장을 한 번씩 촬영한다. **같은 순서를
   기억해 둔다**(나중에 짝짓기 기준, 1-3절).
2. AirDrop(아이폰↔폴드는 직접 안 되므로 카카오톡 "나에게 보내기"·구글
   포토 공유·이메일 등)으로 **같은 원본 파일들을 두 기기 사진 앱에
   모두 넣는다.**
3. 양쪽 사진 앱에 150장씩 동일하게 들어갔는지 확인한다.

### 4단계 — 150장 등록 (본 작업, 두 기기 병행 또는 순차)

- 두 기기 모두 **"갤러리에서 선택"**만 쓴다(앱 카메라 버튼 안 씀).
- **자동 인식 결과를 손으로 고치지 않고 그대로 저장한다**(1-3절 —
  이름·회사가 완전히 비어 저장이 막히는 카드만 최소 보완, 기록에 표시).
- 같은 순서로 등록한다(순번 짝짓기용).
- 첫 10~15장을 등록한 시점에 걸린 시간을 재서 전체 페이스를 가늠한다
  (1-8절).

### 5단계 — 등록 직후 측정 (약 15분, 양쪽 기기 각각)

1. **사진 백업 숫자 갱신** — 재시작 전/후 비교(3절 참고, 표 B).
2. **OCR 통계** — 설정 → OCR 통계 화면 캡처(표 C, 기기별로 따로).
3. **표 A(등록 후)** — 명함 수·`aiUsage` 스냅샷.
4. **서버 사진 업로드 확인** — Storage `users/<uid>/cards/` 개수(표 D).
5. **플랫폼 비교 원장 만들기** — `tool/_firebase_admin.py`로 양쪽 계정의
   `contacts`를 복호화해 뽑고, 순번(또는 전화번호)으로 짝지어 13개 필드를
   나란히 놓는다(표 E, 4절 — 실제 채운 결과물은 저장소 밖에 보관, 1-3절
   경고 참고).

### 6단계 — 폴드 원상 복구 (약 5분)

1-7절 5~7단계: 로그아웃 → 원래 계정 재로그인 → **"현재 계정 데이터로
교체"** → 기존 103장 복귀 확인.

## 6. 요약 보고

### ① 촬영 변수를 제거할 수 있나 — 갤러리 불러오기가 되나

**된다.** `_performGalleryScan`(`add_card_modal_view.dart:917~968`)이
갤러리에서 사진을 골라 인식하는 정식 기능이고, 카메라 촬영과 같은 인식·
저장 경로를 공유한다. **같은 사진 파일 하나를 두 기기에 넣고 둘 다
갤러리에서 불러오면, 촬영 조건(조명·각도·손떨림·카메라 화질)이 통째로
사라지고 순수하게 OCR 소프트웨어 층(과 그 폴백인 OS 지오코더)만 비교하게
된다.** 이것을 1순위 권고안으로 삼았다.

### ② 300장이 몇 시간짜리인가

**실측치는 "자동촬영 대기 8초/장" 하나뿐이고 나머지는 계산(추정)이다.**
갤러리 프로토콜(①을 채택)이면 **50~100분(약 1~1.7시간)**, 앱 카메라로
직접 찍으면 **100~175분(약 1.7~2.9시간)**, 뒷면 스캔·꼼꼼한 보정까지
평소처럼 하면 **225~450분(약 3.8~7.5시간)**으로 추정된다. 폭이 매우
크므로 **첫 10~15장을 실제로 재서 페이스를 확인한 뒤 나머지를 가늠할
것**을 권장한다. 다행히 **①(갤러리 프로토콜)을 고르면 촬영 변수 제거와
시간 단축이 같은 선택으로 동시에 해결된다.**

### ③ 사용자가 골라야 할 것

```
1. 표본 크기        150장 그대로(권장, 미묘한 차이까지 검출 가능) / 축소(예 50장,
                    시간 1/3로 줄지만 뚜렷한 차이만 검출)
2. 촬영 방식        갤러리 프로토콜(권장 — 촬영 변수 제거 + 시간 단축) /
                    각자 카메라 직접(실사용에 가깝지만 촬영 잡음이 섞임 —
                    거치대·조명 통일로 최대한 완화)
3. 정답지(그라운드트루스) 채점 여부   안 함(권장 — "일치율"까지만, 오늘 안에 끝남) /
                    함(150장×1~2분=150~450분의 별도 작업, 76.9%와 직접
                    비교 가능한 정확도까지 나오지만 시간이 크게 늘어남)
4. 폴드 처리        비교용 임시 계정 전환(권장, 1-7절 — 기존 103장 안전) /
                    기존 계정에 섞어 태그(비권장 — 집계가 지저분해짐)
```

## 📌 덧붙인 측정 항목 — 「지역조차 못 뽑는 명함」 수 (2026-08-27 PM 추가, 추가 534)

**등록하는 김에 세는 것이라 따로 시간이 안 든다.**

좌표를 못 얻은 명함은 지역별로 묶여 화면에 남는다(`contactsByRegionWithoutGeo`).
그런데 **주소에서 시/도·시군구조차 못 뽑으면 묶지 않고 빠진다**
(`radar_view_model.dart:388` — 의도적이다: *"「지역 미상」 묶음을 만들면 그
자리가 무엇을 뜻하는지 이용자가 알 수 없다"*).

🚨 **이 구멍이 비어 보이는 것은 표본 때문일 수 있다.** 2026-08-21 실측에서는
좌표 없는 30건이 **전부** 지역을 뽑을 수 있었다 — 즉 **0건이었을 뿐이다.**

📌 **F-15 와 같은 자리다**(CLAUDE.md 4절: *"표본이 없으면 안 나온다"*).
같은 주소 명함이 둘 이상 실제로 있어야 묶음이 그려지고 그래야 안 닫힌 것이
보였던 것처럼, 이 구멍도 **해당 명함이 실제로 있어야** 보인다.

### 세는 법

```
① 150장 등록을 마친 뒤 「주변」 탭을 연다
② 화면에 보이는 수를 센다
     거리순으로 뜬 것        = 좌표를 얻은 명함
     지역별 묶음에 있는 것    = 좌표는 없지만 지역은 뽑힌 명함
③ 등록한 총수(150) - ①의 둘을 더한 값 = 어디에도 안 보이는 명함
```

| 값 | 뜻 | 다음에 할 것 |
|---|---|---|
| **0건** | 구멍이 진짜 비어 있다 | P1-25 의 이 부분은 닫는다 |
| **1건 이상** | 실물이 있다 | 다시 연다 — 「지역 미상」 묶음을 만들지, 명함 상세 안내로 갈지 판단 |

⚠️ **아이폰·안드로이드 양쪽에서 각각 센다.** 주소 처리 층(행안부 API 실패 시
OS 지오코더 폴백)이 플랫폼별로 갈리는 자리라, **한쪽에서만 빠질 수 있다.**
