# 명함 필드 추가 스펙 — 직통·팩스·웹사이트 (2026-08-14, 스펙만)

테스터 피드백(통합본 기능개선 계열)과 명함 실측에서 **직통 전화·팩스·웹사이트**가
명함에 흔히 있는데 저장할 자리가 없다는 점이 드러났다. 이 문서는 **코드 착수 전
스펙**이다 — 무엇을·어디까지·어떤 게이트에 걸리는지 정리해 사용자·PM 판단을 받는다.

⚠️ **이 스펙은 코드를 바꾸지 않는다.** 아래 §4의 두 항목(백업·방침)은 사용자
결정 게이트라, 승인 전에는 구현하지 않는다.

---

## 1. 무엇을 추가하나 — 필드 3개

| 필드 | 타입 | 명함에서 | 비고 |
|---|---|---|---|
| `directPhone` (직통) | `String?` | "직통", "DID", "Direct" 라벨의 유선번호 | 대표번호(사무실)와 다른 개인 유선 |
| `fax` (팩스) | `String?` | "FAX", "팩스", "F." 라벨 | 지금은 파서가 팩스를 **걷어내 버린다**(사무실 오분류 방지용) — 저장 자리가 생기면 살릴 수 있다 |
| `website` (웹사이트) | `String?` | `www.` / `http(s)://` | 회사 URL. 이메일 도메인과 구분 |

**이름 확정 필요(사용자 결정 1)**: `directPhone`/`fax`/`website`로 갈지, 한글
키(`직통`)로 갈지. 기존 필드가 영문 카멜(`officePhone`)이라 영문 카멜을 권장.

**범위 결정 필요(사용자 결정 2)**: 3개 다 넣을지, 우선순위를 둘지. 실측 빈도로는
**웹사이트 > 팩스 > 직통** 순으로 흔했다(웹사이트는 거의 모든 회사 명함에 있음).

---

## 2. 손대야 하는 곳 (코드)

| 계층 | 파일 | 변경 |
|---|---|---|
| 모델 | `lib/data/models/contact_model.dart` | 필드 3개 선언 + `_toJson`(toJson/toBackupджon 공용) + `fromJson`(기본 null) + `copyWith` |
| 입력 | `lib/presentation/features/wallet/views/add_card_modal_view.dart` | 등록·수정 폼에 입력칸 3개(전화 계열 아래에 배치) |
| 표시 | 명함 상세 화면 | 값이 있을 때만 행 표시. **목록엔 넣지 않는다**(클러터 방지, 기존 관례) |
| 파서 | `lib/core/services/ocr_scanner_service.dart` | 팩스/웹사이트/직통 추출 — §3 |
| 내 명함 | 내 프로필·QR/디지털 명함 | 내 프로필에도 같은 필드를 줄지 결정 필요(사용자 결정 3). 주면 QR/vCard 생성도 반영 |

**마이그레이션**: `fromJson`이 없는 키를 null로 기본하므로 **기존 데이터 무손실**.
레거시 암호문은 다음 저장 때 자동 재암호화(기존 구조 그대로).

## 3. 파서(OCR) 처리 — R-04와 연결

지금 파서는 세 값을 이렇게 다룬다:
- **팩스**: `_looksLikeFaxLine`으로 감지해 **버린다**(사무실 전화 오분류를 막으려고).
  → `fax` 필드가 생기면 버리는 대신 담는다. **채점기에 `팩스` 칸을 추가**해
  정확도를 잰다.
- **웹사이트**: 지금은 leftover로 흘러 회사명 자리를 노릴 수 있다. URL 패턴
  (`www.` / `https?://`)으로 뽑아 `website`에 담고 다른 칸 후보에서 제외.
  이메일 도메인(`@… .com`)과 구분해야 한다.
- **직통**: 라벨(`직통`/`DID`/`Direct`)이 있을 때만. 없으면 사무실과 구분 불가라
  손대지 않는다(값이 없는 게 틀린 값보다 낫다 — 추가 183 원칙).

⚠️ **측정 전제**: 이 파서 변경은 **재생 채점기로 검증 가능**하다(백업·방침과 무관한
순수 텍스트 처리). 단 채점기·정답지에 `팩스`·`웹사이트` 칸을 추가해야 잰다 —
지금 정답지 17장에는 이 칸이 없으니 **정답지 보강이 선행**된다.

## 4. ⚠️ 사용자 결정 게이트 (승인 전 구현 금지)

### 게이트 A — 백업/저장구조 변경 = **전체 테스트 대상**

필드가 `toBackupJson()` → Firestore로 흘러간다. 저장·복원·마이그레이션 경로가
바뀌므로, CLAUDE.md의 "저장·복원·마이그레이션 변경은 **전체 테스트(실기기)**"에
해당한다. 구현 후 **배포 전 실기기 전체 테스트**로 다기기 동기화·복원을 확인해야
한다(P1-39 결정적 병합 경로 포함).

- 결정: 새 필드를 **서버 백업에 포함**할지(권장 — 안 하면 기기 변경 시 소실),
  포함하면 전체 테스트 슬롯을 언제 잡을지.

### 게이트 B — 개인정보처리방침 개정 = **정책 게이트**

`docs/legal/privacy-policy.html`이 수집 항목을 **열거**한다:
- **105행(내 프로필)**: "이름, 직함, 회사명, 전화번호, 이메일, 주소, 프로필 사진,
  생일" — 내 프로필에 팩스/웹사이트/직통을 주면 이 목록에 추가해야 한다.
- **112행(명함/인맥 정보)**: "상대방의 이름, 회사, 직함, 전화번호, 이메일, 주소,
  명함 사진, 태그, 관심사, 메모, 소통 내용" — 인맥에 세 필드를 더하면 여기에
  **"팩스, 웹사이트, 직통전화"**를 추가해야 한다.

방침과 구현이 어긋나면 그 자체가 법적 리스크다(BYOK 불일치로 이미 겪음, CLAUDE.md
4절). **방침 개정은 승인·검토 게이트**라 코드와 함께 올려 사용자 확인을 받는다.
게시는 `firebase deploy --only hosting`(별도 배포 게이트).

## 5. 권장 진행 순서

1. **사용자 결정 3건**(필드 이름·범위·내 프로필 포함 여부) 확정.
2. **파서 추출**(팩스/웹사이트)만 먼저 — 채점기·정답지에 칸 추가 후 재생 검증.
   백업·방침에 안 걸리는 순수 파싱이라 이 세션 자동 커밋 범위 안.
3. **모델·입력·표시** + **백업 포함** — 게이트 A(전체 테스트) 잡아서.
4. **방침 개정** — 게이트 B, 코드와 함께 사용자 확인 후 게시.

즉 **2번(파서)까지는 지금 진행 가능**하고, 3·4번은 사용자 승인·슬롯이 필요하다.
