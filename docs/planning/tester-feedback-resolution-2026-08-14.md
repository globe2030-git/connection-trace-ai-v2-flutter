## 오류 (E) — 14건 중 12건 종결

### E-01 · 자동 촬영이 빈 공간을 찍음 🟡 부분

- **증상**: 명함이 아닌 빈 벽·책상·모서리가 자동 촬영된다.
- **원인**: 자동 촬영 조건이 **"화면이 흔들리지 않으면"** 하나뿐이었다. 역설적으로
  아무것도 없는 면이 가장 안정적이라 더 잘 찍혔다.
- **조치**: 안정 조건에 **"가이드 안에 볼 것이 있는가"**를 더했다 — 밝기 표준편차
  (민무늬 면 차단)와 지배톤 비율(반반으로 갈린 모서리 차단). 계산을
  `core/utils/frame_contrast.dart`로 빼 7가지 장면을 테스트로 고정.
- **남은 것**: 각이 진 빈 곳은 밝기로 못 가른다(실측: 명함 톤 0.653 vs 책상 0.611,
  차이 0.04). **문서 경계 검출**(R-02)이 필요하다. → R-02와 한 덩어리.
- 근거: 추가 208·209·210.

### E-02 · 뒷면 스캔 버튼 무반응 ✅ 종결 (고칠 것 없었음)

### E-03 · 앞·뒷면 결과 덮어씀 ✅ 종결

- **증상**: 뒷면을 스캔하면 앞면 인식 결과가 지워진다.
- **조치**: `ScanConflict` 도입 — 한 명함을 앞면+뒷면으로 다루고, 서로 다른 값이
  들어오면 덮어쓰지 않고 감지·초기화한다. 근거: 추가 190.

### E-04 · OCR 문자 오독 (`길`→`킬`) ⬜ 남음

- **증상**: 인식된 글자 자체가 틀린다(`길`을 `킬`로).
- **성격**: ⚠️ **파싱 규칙으로는 고칠 수 없다.** ML Kit **인식 단계**의 문제다.
  `02-2000-0000`→`022-…` 같은 **형식** 오류는 이미 잡았지만(추가 197), 글자 오독은
  다른 층이다. **R-03(한글·영문 다중 OCR 패스)**이 유일한 길. 근거: 추가 207.

### E-05 · 필드 매핑 오류 ✅ 종결 (대폭 개선)

이번 통합본에서 가장 크게 개선된 항목. 사용자 진단이 출발점이었다 — *"OCR 추출은
정확히 하는데 분리하는 과정에서 잘못되는구나."* 실제로 이름 미검출 17장 중 16장은
원문에 이름이 있었다.

- **원인 1 — 자리를 뺏기면 끝**: 이름 후보 검사가 줄 순회가 끝난 뒤에만 돌아,
  슬로건 조각이 먼저 자리를 차지했다가 지워지면 진짜 이름을 다시 볼 기회가 없었다.
  → **"넣고 → 빈자리 재검증"** 구조로 전환(추가 199).
- **원인 2 — 이름 후보가 선착순**: OCR이 잘못 읽은 슬로건 끝자락이 먼저 이름이 되고
  진짜 이름은 회사 칸으로 밀렸다. → 이름 후보를 **강·약 두 갈래**로 나눠 강이
  있으면 약은 쓰지 않는다. 틀린 이름 14장이 정답으로 교정(추가 200).
- **원인 3 — 한 줄로 뭉친 명함**: 전화·이메일을 뽑은 뒤 `continue`해서 주소·회사·
  이름 검사를 아예 건너뛰었다. → 연락처를 걷어낸 나머지를 **같은 루프에 다시**
  넣는다(추가 201).
- **개선 측정(103장)**: 이름 82→**100**, 주소 76→**85**, 휴대폰 97→**100**.
  회사는 89~93 사이에서 **틀린 값(사람 이름)이 빠지고 정답이 채워지는** 방향으로
  이동 — 채움 장수가 아니라 정확도로 읽어야 한다.
- 근거: 추가 199·200·201·202.

### E-07 · 프로필 사진 미리보기가 안 바뀜 ✅ 종결 (실기기 확인)

- **증상**: 갤러리에서 사진을 골라도 미리보기가 그대로. **껐다 켜면 정상.**
- **원인**: `FileImage`의 **캐시 키가 파일 경로**다. 프로필 사진은 매번 같은
  파일명(`my_profile_avatar.jpg`)으로 덮어써서, 내용이 바뀌어도 캐시가 옛 픽셀을
  돌려줬다. `setState`가 소용없던 이유.
- **조치**: `evictImageFileCache(path)` — 덮어쓴 직후 그 경로를 캐시에서 비운다.
  같은 함정이 **SNS 로그인 시 프로필 내려받기**에도 있어 함께 고쳤다.
- **검증**: 캐시에서 실제로 빠지는지 보는 테스트(`test/image_file_cache_test.dart`),
  **사용자 실기기 확인 완료**("미리보기도 잘 나와"). 근거: 추가 206.

### E-08 · 직업과 무관한 AI 태그 ✅ 종결 (실기기 확인)

- **증상**: 회계사 명함을 등록했는데 태그에 `AI`, `IT`가 자동으로 들어갔다.
- **원인**: 명함 등록 화면 태그 입력칸 **기본값이 `'AI, IT'`로 하드코딩**돼 있었다.
  신규 등록이면 업종과 무관하게 무조건 박혔다 — 데모용 값이 남은 것.
  "가짜 데이터를 만들지 않는다"(CLAUDE.md 4절)에 정면으로 걸리는 결함.
- **조치**: 기본값을 빈 값으로. 회귀 방지로 **소스를 훑는 자동 테스트**
  (`test/no_seeded_form_defaults_test.dart`) 추가.
- **기존 데이터 정리**: 관리자가 눌러 실행하는 일회성 정리(태그가 정확히 `AI`+`IT`
  둘뿐인 명함만). 실기기 실행 결과 **등록 14명 중 13건**이 대상이었다.
  근거: 추가 204.

### E-09 · 카카오톡 실행 실패 ✅ 종결 (사용자 실기기 확인)

- **조치**: `kakaotalk://launch`(동작 확인됨)를 먼저 시도하고, 실패하면 옛

## 2026-08-17 점검 — **코드에서 확인한 것과 확인 못 한 것**

사용자 지시: *"테스터 6.7 처리 계획이 모두 완료되었는지"*. **PM이 직접 했다.**

⚠️ **이 문서의 상당 부분을 PM이 썼다. 자기 일을 자기가 검사한 것**이라,
**기억을 근거로 쓰지 않고 코드에서 실제로 찾아 확인**했다. 확인 못 한 것은
아래에 그대로 남겼다.

### ① ⚠️ 전제가 깨졌다 — E-01 · E-06 · F-03

이 문서는 *"자르기가 넷을 한 번에 닫는다"*고 적어 두었다. **그 자르기를 2026-08-17에
안 쓰기로 했다**(추가 277).

```
세 번 재서   기존 가이드 74 / 76 / 65
             B′        67 / 71 / 71     ← 2:1, "낫다는 증거가 없다"
결론         기본값 꺼짐 (PR #266)
```

**코드로 확인한 것**

| | |
|---|---|
| `cardRectDetectionEnabled` | **`false`** (`card_rect_detector.dart:91`) |
| `kUseDocScannerCaptureByDefault` | **`false`** (`doc_scanner_capture_service.dart:69`) |
| 손으로 자르는 UI | ⚠️ **없다.** `cropRect`·`ImageCropper` 어디에도 없음 |

→ **E-01·E-06·F-03은 "닫힐 예정"이 아니라 "다시 열림"이다.**

### ② ⚠️ 검출기를 판정용으로 쓰는 길은 **이미 코드에 있다** — 그러나 근거가 없다

**E-01의 남은 것**은 이 문서가 *"각이 진 빈 곳은 밝기로 못 가른다(명함 톤 0.653 vs
책상 0.611, 차이 0.04) — 문서 경계 검출이 필요하다"*고 적어 둔 부분이다.

⚠️ **PM이 처음 여기에 *"검출기를 자르기 말고 판정용으로 써 보자"*고 적었다가
지웠다. 이미 만들어져 있었다.**

```dart
// camera_scan_modal_view.dart:546
final rectOk = !_requiresCardRect || _hasRecentCardRect;
if (avgDiff < _stabilityDiffThreshold && hasContent && rectOk) { … 자동 촬영 … }
```

`_requiresCardRect`(:252)가 자동 촬영에 **"최근에 사각형이 잡혔을 것"**을 요구한다.
사용자가 처음 말한 *"빈 벽도 찍힌다"*를 막으려고 만든 것이고, **자르기와 별개로
이미 그 일을 하고 있다.** 새로 만들 것이 아니다.

#### ⚠️ 그런데 6초 유예가 보호를 지운다

```dart
static const _cardRectGrace = Duration(seconds: 6);   // :244
```

검출을 **한 번도 못 하면 6초 뒤 조건이 저절로 풀린다.** 안 그러면 검출이 안 되는
기기에서 자동 촬영이 **영영 안 되기** 때문이다. 즉 **정작 못 잡는 상황에서는
보호가 조용히 사라진다.**

⚠️ 그 유예에는 더 나쁜 성질이 있다 — **네이티브 등록을 빠뜨려도 6초 뒤 조건이
풀려 "잘 도는 것처럼" 보인다.**

#### ⚠️ 실물이 제안과 어긋난다

아이폰에서 사용자가 실제로 본 화면:

```
검출 채널OK · 후보없음 · 조건해제
검출 채널OK · 후보없음 · 조건적용
```

**채널은 살아 있는데 후보가 없었다.** 아이폰(Vision)이 명함을 못 찾은 것이다.
못 찾으면 판정에도 못 쓰고 6초 뒤 유예로 넘어간다. 안드로이드(OpenCV)는 낫다.

#### 📌 그래서 이렇게만 적는다

> **판정용으로 쓰는 길은 이미 코드에 있다**(`_requiresCardRect`). 다만
> **아이폰에서 후보가 안 잡히는 것이 실물로 확인됐고**, 6초 유예 때문에 못
> 잡으면 보호가 사라진다. **닫혔다고 적으려면 "검출 성공률"을 먼저 재야 하고,
> 그 숫자는 아직 없다.**

⚠️ **우리가 잰 것은 "자른 결과의 인식률"이지 "검출 성공률"이 아니다. 서로 다른
숫자다.** 이걸 안 적으면 나중에 *"판정용은 된다고 했잖나"*가 된다.

**재는 법**: 빈 벽·손·책상을 비춘 상태와 명함을 넣은 상태에서 **후보가 잡히는
비율**을 센다. 화면에 진단이 이미 뜬다(`검출 채널OK · 후보N개`). 실기기 30초면
대략 나온다. ⚠️ **아이폰·안드로이드를 따로** 재야 한다 — 엔진이 다르다.
