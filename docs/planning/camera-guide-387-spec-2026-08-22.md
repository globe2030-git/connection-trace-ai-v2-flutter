## 0. 착수 전에 실물부터 열었다

이 저장소는 낡은 기록을 보고 **이미 있는 기능을 다시 만들 뻔한** 전례가 있다
(F-02·F-06·F-12, CLAUDE.md 4-2). 바로 앞 배정에서도 같은 일이 있었다 — 진단
화면은 이미 구현돼 있었다.

그래서 387도 코드를 먼저 열었다. **결과가 브리프와 다르다.**

### 추가 387이 말한 방향과, 지금 실물

| 387의 방향 | 실물 |
|---|---|
| 자르기 기준을 가이드가 아니라 **검출된 테두리로** | ✅ **이미 그렇다.** `cardRectCropEnabled`가 **기본 켬**이고(2026-08-17 사용자 확정), 자르기는 `_cropByDetectedQuad`가 한다 |
| 가이드를 **꽉 채우지 않아도 되게** | ✅ **이미 그렇다.** B′일 때 바깥 크롭선(`kGuideCropMargin` 상자)을 **아예 안 그리고**, 흰 상자는 검출에 반응하지 않는 **"이쯤 두세요" 고정 안내**로만 남는다 |
| 가이드를 **크게** | ❌ **안 됐다.** 이것만 남았다 |

즉 **남은 것은 "크기" 하나**다. 브리프가 말한 "설계 변경"의 대부분은 추가
293·277 후속에서 이미 끝나 있었다.

### ⚠️ 코드에 낡은 주석이 하나 있다

`card_rect_detector.dart:98`의 요약표가 아직 이렇게 적혀 있다.

```
cardRectCropEnabled  자르기를 B′로  → 기본 꺼짐(추가 277에서 안 쓰기로 함)
```

**틀렸다.** 같은 파일 106~122행의 본문이 *"✅ 사용자 확정 (2026-08-17) — 켠다"*
이고 실제 값도 `ValueNotifier<bool>(true)`다. 요약표만 안 고쳐졌다.
**이 줄만 보고 판단하면 "자르기는 꺼져 있다"고 읽는다.** 이번 작업에서 함께
고친다.

## 1. 문제는 크기가 아닐 수 있다

추가 383에서 네 번 재고 얻은 결론은 이랬다.

```
가이드를 키운다 → 명함을 더 가까이 대야 한다 → 초점이 안 맞는다
가이드를 줄인다 → 초점은 잡힌다 → "맞추기 불편하다"
```

그런데 **자르기가 이미 검출 기준이면, 가이드를 채울 이유가 없다.** 대충 안쪽에
두기만 하면 파란 테두리가 명함을 찾아 그 자리로 자른다.

그래도 사용자는 *"맞추기 불편"*이라고 했다. 왜인가.

> **흰 상자가 "여기 맞추세요"로 읽히기 때문이다.**

네 변이 다 그려진 직사각형은 **채우라는 신호**다. 실제 뜻은 *"이 안쪽 어딘가에
두세요"*인데, 생김새가 다른 말을 하고 있다. 383의 사용자 평가 두 줄이 이걸
가리킨다 — *"초점은 잡히는데 가이드가 작아졌다"*, *"맞추기 불편"*.

📌 그러므로 이번 작업의 1순위는 **가이드를 키우는 것이 아니라, 가이드가 무엇을
뜻하는지 생김새로 바꾸는 것**이다. 크기는 그다음이다.

⚠️ **이 해석은 아직 안 쟀다.** 사용자에게 확인해야 할 가설이다.

## 2. 안 셋

### ㉮ 모서리 표식 (권장)

네 변을 지우고 **네 귀퉁이 갈고리(⌐ ¬ ∟ ⌐)만** 남긴다. 크기는 지금보다 키운다.

```
지금        ┌─────────┐        네 변 → "채우세요"
           │         │
           └─────────┘

㉮          ┌       ┐          귀퉁이만 → "이 안쪽에 두세요"

           └       ┘
```

- **얻는 것**: 채우라는 신호가 사라진다. 크기를 키워도 "가까이 대야 한다"는
  압박이 줄어든다.
- **대가**: 카메라 앱의 관습(QR·문서 스캔)과 같은 모양이라 학습 비용은 낮지만,
  **이미 익숙해진 사용자에게는 바뀐 화면**이다.
- **크기**: 짧은 변 비율을 iOS 0.50 → **0.62**, Android 0.65 → **0.72**로,
  상한 `kGuideMaxShortEdgeDp` 267 → **300**. ⚠️ 이 숫자들은 **고른 값이지 잰
  값이 아니다.** 383이 65%에서 아이폰 초점이 흐렸다고 쟀으므로, ㉮가 "채우지
  않아도 된다"를 실제로 전달하는지 확인한 뒤에만 이 크기로 간다.

### ㉯ 크기만 키우기

지금 모양 그대로 비율만 올린다.

- **얻는 것**: 변경이 가장 작다.
- **대가**: 383이 이미 재서 **초점이 나빠진다고 확인한 길**이다. 채우라는 신호가
  그대로라 사용자가 더 가까이 댄다. **권장하지 않는다.**

### ㉰ 가이드를 아예 없애기

검출 테두리만 남긴다.

- **얻는 것**: 헷갈릴 상자가 없다.
- **대가**: **검출이 실패하면 아무 안내가 없다.** 아래 3절의 폴백이 그대로
  드러난다. 그리고 처음 쓰는 사람이 "어디에 둬야 하지"를 모른다.
  **기각한다.**

## 3. ⚠️ 가장 위험한 곳 — 검출이 실패할 때

가이드를 키우면 **폴백이 나빠진다.** 이것이 8/17에 가이드를 줄인 이유였다.

```
검출 성공 → 파란 테두리로 자름 → 가이드 크기와 무관
검출 실패 → 고정 가이드로 자름 → 가이드가 크면 배경이 잔뜩 들어간다
```

### 얼마나 자주 실패하나 — **부분적으로만 쟀다**

| 재 본 것 | 결과 | 어디까지 믿을 수 있나 |
|---|---|---|
| 정지 사진 8장(추가 386) | **4 / 8** | ⚠️ 전부 **같은 무늬 배경**. 갤러리 사진 경로 |
| 실기기 라이브 프리뷰 | 사용자 확인 *"잘 잡혀"* | 횟수를 안 셌다 |

**이 둘이 크게 다르다.** 라이브 프리뷰는 초당 여러 장을 보고 그중 하나만
맞으면 되므로 정지 사진보다 유리하다. 그런데 **라이브 실패율을 숫자로 센 적이
없다.**

📌 **가이드를 키우기 전에 이 숫자가 필요하다.** 실패가 드물면 폴백이 나빠져도
감수할 만하고, 잦으면 가이드를 키우는 것 자체가 위험하다.

### 폴백 설계 — 크기를 갈라 둔다

가이드를 키우더라도 **폴백 크롭은 지금 크기를 쓴다.**

```
화면에 보이는 가이드     커진 것 (㉮)
검출 실패 시 자르는 자리  지금 크기 (kGuideCropMargin 적용된 안쪽 상자)
```

- **근거**: 사용자가 안내를 보고 두는 자리는 넉넉해도 되지만, **자동으로 잘리는
  자리는 좁을수록 배경이 덜 들어간다.** 지금 값은 8/17에 그 이유로 정해진 값이라
  그대로 쓸 근거가 있다.
- ⚠️ **대가**: 명함을 가이드 가장자리에 가깝게 두고 검출이 실패하면 **명함이
  잘려 나간다.** 그래서 폴백으로 갈 때는 화면에 알려야 한다(아래).

### 폴백이 일어났음을 사용자에게 알린다

지금은 **release에서 아무 표시가 없다**(`_lastCropSummary`는 `kReleaseMode`
에서 안 뜬다). 검출 크롭과 가이드 폴백의 결과가 눈에 띄게 다른데 구분이 없다.

확인 화면에 한 줄 — 예: *"명함 테두리를 못 찾아 안내선 기준으로 잘랐어요.
다시 찍으면 더 정확해요."* 문구는 검토 대상이다.

## 4. 무엇을 먼저 재야 하나

⚠️ **이 문서의 어떤 숫자도 아직 잰 것이 아니다.** 순서는 이렇다.

```
1. 라이브 프리뷰 검출 실패율      기기에서 N회 촬영, 폴백으로 간 횟수
                                 → 가이드를 키워도 되는지가 여기서 갈린다
2. ㉮가 "채우지 않아도 된다"를 전달하는가
                                 → 모서리 표식만 먼저 적용해 사용자 평가
3. 크기 조정                     1·2가 통과한 뒤에만
4. 크롭 해상도 vs 인식률          멀리 찍으면 크롭이 저해상도가 된다
                                 (예전 측정 1,208~2,353px). 아직 안 쟀다
```

📌 4번은 `card_rect_detector.dart`가 **이미 "아직 안 잰 것"으로 적어 둔** 항목
이다. 가이드를 키우면 사용자가 더 멀리서 찍게 되므로 **이 위험이 커진다.**
387과 같이 재야 한다.
