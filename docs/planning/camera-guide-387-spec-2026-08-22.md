# 촬영 가이드 개편(추가 387) — 설계

작성 2026-08-22. **발주 전 검토용**이다. 구현은 이 문서를 검토한 뒤 정한다.

## 0. 착수 전에 실물부터 열었다

이 저장소는 낡은 기록을 보고 **이미 있는 기능을 다시 만들 뻔한** 전례가 있다
(F-02·F-06·F-12, CLAUDE.md 4-2). 바로 앞 배정에서도 같은 일이 있었다 — 진단
화면은 이미 구현돼 있었다.

그래서 387도 코드를 먼저 열었다. **결과가 브리프와 다르다.**

### 추가 387이 말한 방향과, 지금 실물

| 387의 방향 | 실물 |
|---|---|
| 자르기 기준을 가이드가 아니라 **검출된 테두리로** | ✅ **이미 그렇다.** `cardRectCropEnabled`가 **기본 켬**이고(2026-08-17 사용자 확정), 자르기는 `_cropByDetectedQuad`가 한다 |
| 가이드를 **꽉 채우지 않아도 되게** | ✅ **이미 그렇다.** B′일 때 바깥 크롭선(`kGuideCropMargin` 상자)을 **아예 안 그리고**, 흰 상자는 검출에 반응하지 않는 **"이쯤 두세요" 고정 안내**로만 남는다 |
| 가이드를 **크게** | ✅ **추가 383에서 끝났다.** 플랫폼으로 갈라(iOS 50% · Android 65% · 상한 267dp) 실기기 확인까지 받았다 — *"확인했어 좋아 / 초점도 크기도"* |

즉 **387이 말한 방향은 세 갈래 다 이미 처리됐다.** 대부분은 추가 293·277
후속에서, 크기는 추가 383에서.

그러면 387에 무엇이 남는가 — 1절에서 가른다.

### ⚠️ 코드에 낡은 주석이 하나 있다

`card_rect_detector.dart:98`의 요약표가 아직 이렇게 적혀 있다.

```
cardRectCropEnabled  자르기를 B′로  → 기본 꺼짐(추가 277에서 안 쓰기로 함)
```

**틀렸다.** 같은 파일 106~122행의 본문이 *"✅ 사용자 확정 (2026-08-17) — 켠다"*
이고 실제 값도 `ValueNotifier<bool>(true)`다. 요약표만 안 고쳐졌다.
**이 줄만 보고 판단하면 "자르기는 꺼져 있다"고 읽는다.** 이번 작업에서 함께
고친다.

## 1. "맞추기 불편"은 둘이 겹친 말이었다 — 그중 하나는 이미 풀렸다

⚠️ **초안에서 이 절을 잘못 썼다.** "문제가 크기가 아닐 수 있다"고 적고 가이드를
키우는 안을 냈는데, 사용자 지적으로 바로잡는다.

> **"가이드가 작고, 맞춰야 할 것 같은 것 — 2개가 겹쳐진 이야기였어."**

### 크기 쪽은 추가 383이 이미 풀었다

383은 네 번 재고 **플랫폼으로 갈랐고, 실기기 확인까지 끝냈다.**

```
iOS       50%   아이폰 16 Pro 201dp   (원래 166보다 큼 · 초점 확보)
Android   65%   폴드 커버 267dp
상한      267dp
```

사용자 최종 확인: **"확인했어 좋아 / 초점도 크기도."** 즉 **크기와 초점 둘 다
합격 판정이 난 값**이다.

⛔ **그러므로 크기를 다시 건드리지 않는다.** 초안이 제안했던 상향
(iOS 0.62 · Android 0.72 · 상한 300dp)은 **철회한다.** 실기기로 확인된 값을
안 잰 숫자로 되돌리는 것이고, 383이 *"좋다고 확인된 값을 하나도 안 건드려도
됐다"*고 적은 성과를 무르는 일이다.

📌 383의 결론에서 크기는 **화면 모양이 아니라 카메라 하드웨어**에 붙은 문제였다.
그래서 플랫폼으로 갈랐다. 이 축은 그대로 둔다.

### 남은 것은 "맞춰야 할 것 같은" 하나

자르기는 이미 검출 테두리 기준이라 **가이드를 채울 이유가 없다.** 그런데도
채워야 할 것처럼 느껴진다.

> 네 변이 다 그려진 직사각형은 **채우라는 신호**다. 실제 뜻은 *"이 안쪽 어딘가에
> 두세요"*인데, 생김새가 다른 말을 하고 있다.

**387에서 다룰 것은 이것 하나다.**

## 2. 안 — 크기는 그대로, 생김새만

### ㉮ 모서리 표식 (권장, 그리고 사실상 유일한 안)

네 변을 지우고 **네 귀퉁이 갈고리만** 남긴다. **크기·비율은 383 값 그대로.**

```
지금        ┌─────────┐        네 변 → "채우세요"
           │         │
           └─────────┘

㉮          ┌       ┐          귀퉁이만 → "이 안쪽에 두세요"

           └       ┘
```

- **얻는 것**: 채우라는 신호가 사라진다. **크기를 안 바꾸고** 압박만 던다.
- **대가**: 이미 익숙해진 사용자에게는 바뀐 화면이다. 다만 QR·문서 스캔의
  관습과 같은 모양이라 학습 비용은 낮다.
- ⚠️ **이 안이 실제로 "안 채워도 된다"를 전달하는지는 안 쟀다.** 사용자 확인
  대상이다.

### ㉯ 크기 조정 — ⛔ 기각

383이 **실기기로 확인까지 끝낸 값**이다. 되돌릴 근거가 없다.

### ㉰ 가이드를 아예 없애기 — ⛔ 기각

검출이 실패하면 아무 안내가 없고, 처음 쓰는 사람이 어디에 둘지 모른다.

## 3. ⚠️ 가장 위험한 곳 — 검출이 실패할 때

가이드 **크기는 안 바꾸므로 폴백이 나빠지지 않는다.** 초안은 키우는 것을
전제로 이 절을 썼는데, 그 전제가 사라졌다.

다만 **폴백 자체는 그대로 남는 문제**라 적어 둔다.

```
검출 성공 → 파란 테두리로 자름 → 가이드 크기와 무관
검출 실패 → 고정 가이드로 자름 → 가이드가 크면 배경이 잔뜩 들어간다
```

### 얼마나 자주 실패하나 — **부분적으로만 쟀다**

| 재 본 것 | 결과 | 어디까지 믿을 수 있나 |
|---|---|---|
| 정지 사진 8장(추가 386) | **4 / 8** | ⚠️ 전부 **같은 무늬 배경**. 갤러리 사진 경로 |
| 실기기 라이브 프리뷰 | 사용자 확인 *"잘 잡혀"* | 횟수를 안 셌다 |

**이 둘이 크게 다르다.** 라이브 프리뷰는 초당 여러 장을 보고 그중 하나만
맞으면 되므로 정지 사진보다 유리하다. 그런데 **라이브 실패율을 숫자로 센 적이
없다.**

📌 크기를 안 바꾸므로 이 숫자가 **387의 관문은 아니다.** 그래도 알아야 할
숫자다 — 폴백이 잦으면 사용자는 "왜 어떤 건 깔끔하고 어떤 건 배경이 들어오지"를
겪게 된다. 아래 안내 문구가 그때 필요하다.

### 폴백 크롭 — 손대지 않는다

크기를 안 바꾸므로 폴백 크롭도 지금 그대로다. 8/17에 정해진 값을 유지한다.

### 폴백이 일어났음을 사용자에게 알린다

지금은 **release에서 아무 표시가 없다**(`_lastCropSummary`는 `kReleaseMode`
에서 안 뜬다). 검출 크롭과 가이드 폴백의 결과가 눈에 띄게 다른데 구분이 없다.

확인 화면에 한 줄 — 예: *"명함 테두리를 못 찾아 안내선 기준으로 잘랐어요.
다시 찍으면 더 정확해요."* 문구는 검토 대상이다.

## 4. 무엇을 먼저 재야 하나

⚠️ **이 문서의 어떤 숫자도 아직 잰 것이 아니다.** 순서는 이렇다.

```
1. ㉮가 "안 채워도 된다"를 전달하는가   모서리 표식을 적용해 사용자 평가
                                        → 387의 성패가 여기 하나에 달렸다
2. 라이브 프리뷰 검출 실패율            폴백 안내 문구가 얼마나 자주 뜨는지
                                        (387의 관문은 아니지만 알아야 한다)
3. 크롭 해상도 vs 인식률                아직 안 쟀다 — 387과 무관하게 남은 숙제
```

📌 3번은 `card_rect_detector.dart`가 **이미 "아직 안 잰 것"으로 적어 둔** 항목
이다. 크기를 안 바꾸므로 387이 이 위험을 키우지는 않는다. 별도로 재야 한다.

## 6. 이 문서가 답하지 않는 것

- **문구 확정** — 폴백 안내 문구는 사용자 검토 대상
- **모서리 표식의 정확한 형태·굵기** — 디자인 판단
- **아이폰/안드로이드 차이** — iOS는 Vision, Android는 OpenCV라 검출 실패율이
  다를 수 있다. 4절 2번(라이브 실패율) 측정을 **기기별로** 해야 한다
