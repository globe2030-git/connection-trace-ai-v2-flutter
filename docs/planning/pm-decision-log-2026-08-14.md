## D18. F-07 접근법 승인 + 병합 순서 (서버 변경·배포 게이트)
PR분할 조사 결과 대화 포인트 다양성은 **서버(functions/index.ts) 변경 필수**
(재생성 시 동일 페이로드→동일 프롬프트, generationConfig에 temperature/seed 없음).
승인 접근법: **previousPoints 제외(서버 프롬프트가 "다른 각도로" 지시) + temperature/
topP 추가**. **이유(기술 판단=PM 영역)**: 진짜 다양성은 프롬프트가 이전 포인트를
알아야 나오고, 클라 단독으론 서버가 새 필드를 안 읽어 무효. 병합 순서: index.ts를
관리자팀도 건드리나 **영역이 다름**(F-07=buildPrompt/generateBriefing vs 관리자팀=
grantBonusCredits) → 관리자팀 admin PR 먼저, F-07 PR 나중(rebase)으로 직렬화해
충돌 회피. **사용자 게이트**: 다양성 효과는 배포 후에만 확인되고 배포는 사용자
결정 → 구현·병합 완료 후 배포를 사용자에게 올린다. 지금 코드·커밋은 진행(자율 권한).

## D19. 전체 테스트 = 각 팀 종료 후 배치 (사용자 진행)
사용자 지시: **전체 테스트(실기기 전항목)는 각 팀 업무 종료 후 배치로 진행,
사용자가 직접**. **이유**: 사용자 지시 + CLAUDE.md "전체 테스트는 배포 직전 한
번 몰아서" 원칙. **함의**: 저장·복원·백업·필드추가 등 전체-테스트 대상 변경도
지금 개발·부분테스트까지는 진행하고 전체 테스트만 종료 배치로 미룬다(즉 지금
막지 않음). PM은 **"전체 테스트 필요 항목" 목록을 누적**해 종료 시점에 사용자
체크리스트로 제공한다. 현재 누적: F-02(주소 없이 저장 — 저장 경로), (예정)필드추가
(백업 구조), F-07(서버 변경 — 배포 후 동작 확인).

## D20. F-02 개선 — 빈 주소 저장 시 1회 확인 (사용자 실기기 피드백)
사용자가 F-02 실기기 눈확인 중 "주소 없이 묻지 않고 바로 등록된다, 뒷면에
주소가 있을 수 있다"고 지적 → **침묵 저장 대신 1회 확인 다이얼로그** 추가로
개선. **이유**: 명함 뒷면에 주소가 있을 수 있어, 조용히 저장하면 뒷면 스캔을
놓친 채 등록됨. 기존 중복 전화번호 확인 패턴 재사용(일관성). "주소 필수 해제"는
유지하되 빈 주소 저장 시 확인만 추가. 기능개선팀에 라우팅, 이 개선+재확인 전까진
커밋 보류. → 실기기 눈확인이 코드 리뷰로 안 잡히는 UX 결함을 잡은 사례.

## D21. 명함인식팀 → 필드추가(직통·팩스·웹사이트) (사용자 결정)
사용자가 명함인식팀 방향을 필드추가로 확정. **이유**: 매핑은 측정-블록(D16),
필드추가는 목표⑤ 항목이고 스펙(5466b18) 준비됨. 게이트 처리: **전체 테스트는
종료 배치로 미룸(D19)이라 지금 코드 안 막힘**, **방침 개정(새 필드 서버 백업 →

## D23. 병합 위임 명확화 — 사용자 승인 피로 해소
사용자가 "각 팀 허용 요청에 계속 답하느라 못 쉰다"고 함. **원인**: 팀들이
규약대로 커밋·병합 승인을 각자 사용자 창에 직접 물어, 같은 사람이 승인 폭주에
시달림. **조치**: (1) PM이 밀린 PR을 직접 병합(#146 F-02·#148 F-12·#149 관리자
보안) — 병합은 사용자가 PM에 위임한 권한. (2) 전 팀에 "병합은 PM에게, 사용자에게
직접 묻지 말 것" 확립. (3) 사용자에게 가는 것을 **배포·제품/정책 3종으로 한정하고
PM이 배치로** 올림: ① 서버 배포 1건(관리자+F-07) ② 과금 파라미터/U5 ③ 필드추가
방침 초안. **이유**: PM의 존재 이유가 조율 부담 흡수인데 반대로 사용자를 부품처럼
승인기로 만들고 있었음.
