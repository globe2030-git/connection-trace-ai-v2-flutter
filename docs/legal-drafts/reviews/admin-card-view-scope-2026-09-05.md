## 0. 먼저 — 이 폴더가 배포 대상이 아닌지 확인했습니다 (2026-09-05 실측)

2026-09-01에 법무 검토 메모 3건이 인터넷에 공개돼 있던 사고(추가 650)가 있었으므로,
**메모를 쓰기 전에** 확인했습니다. **확인한 방법을 그대로 적습니다.**

### (가) 배포 대상 디렉터리를 `firebase.json` 에서 직접 읽었습니다

```
$ python3 -c "import json; d=json.load(open('firebase.json'));
              [print(h.get('target'),'->',h['public'],'| ignore:',h.get('ignore')) for h in d['hosting']]"

legal -> docs/legal | ignore: ['**/.*', '**/node_modules/**', 'reviews/**', '**/*.md']
admin -> docs/admin | ignore: ['**/.*', '**/node_modules/**', 'README.md']
site  -> docs/site  | ignore: ['**/.*', '**/node_modules/**', 'README.md']
```

**`docs/legal-drafts` 는 세 타깃 중 어느 것의 `public` 도 아닙니다.** 따라서 이 폴더는
`firebase deploy --only hosting` 으로 나가지 않습니다.

⭐ **이중 방어도 살아 있습니다** — `legal` 타깃의 `ignore` 에 `reviews/**` 와
`**/*.md` 가 들어 있어(추가 650의 조치), 누군가 실수로 `docs/legal/` 안에
`.md` 를 떨어뜨려도 배포에 실리지 않습니다.

### (나) `tool/build_site.sh` 는 **존재하지 않습니다**

```
$ ls tool/build_site.sh
tool/build_site.sh 없음        ← 정적 사이트를 조립하는 별도 스크립트가 없습니다
```

`tool/` 에 있는 것은 `build_app.sh`(앱 빌드)뿐이고, 문서 배포는 `firebase.json` 이
직접 디렉터리를 가리킵니다. **즉 배포 대상을 정하는 곳이 `firebase.json` 한 군데뿐**이며,
그것을 위 (가)에서 확인했습니다.

### (다) 종전 노출이 실제로 닫혔는지 라이브로 찍어 봤습니다

추가 650은 *"병합만으로는 안 닫힌다 — 다음 `firebase deploy --only hosting` 때
사라진다"* 고 적어 두었으므로, **닫혔는지는 코드가 아니라 실물이 답합니다.**

```
$ curl -s -o /dev/null -w "%{http_code}"  (2026-09-05 실측)

/reviews/account-switch-30day-deletion-2026-08-27.md   404   ✅ 닫혔습니다
/reviews/app-name-trademark-similarity-2026-08-28.md   404   ✅ 닫혔습니다
/privacy-policy                                        200   (게시본 — 정상)
/robots.txt                                            404   ⚠️ 아직 없습니다
```

**노출은 닫혔습니다.** 다만 `robots.txt` 는 여전히 없습니다 — 지금은 나갈 파일이
없어 실해가 없지만, **「링크가 없다」가 「비공개」가 아니라는 추가 650의 교훈**이
그대로 남아 있는 자리입니다(이 메모의 판단 사항은 아니며, 참고로만 적습니다).

### (라) 게시본이 저장소와 같은지도 확인했습니다

```
라이브 https://connection-sense.web.app/privacy-policy

### ① C안이 관리자 열람 범위를 넓힌다

#### ①-1. 사실 (실측)

```
지금      관리자 조회 한 번  =  그 uid 의 명함              users/{uid}/contacts
C안 뒤     관리자 조회 한 번  =  그 사람의 모든 계정 명함     people/{personId}/contacts
```

- `data-schema.md` §7(194~208행): 명함·`cardSources`·`deletedContacts`·`commLogs` 가
  **통째로** `people/{personId}` 아래로 옮겨갑니다.
- C안 설계 §2-4(345~360행): `knownKeysFor(uid)` 가 `people.uids` 를 읽어
  **여러 계정의 키를 한 번에 모읍니다.** *"여기가 가장 위험한 한 줄이다 — `uids` 에
  남의 uid 를 넣는 순간 그 사람의 명함이 열린다."*
- 관리자 설계 §3-5(184행): 서버가 키를 얻는 길이
  `users/{uid}.personId → people/{personId}.uids → 각 encryptionKeyB64`.

⚠️ **아직 구현 전입니다.** C안 스펙 §7의 1단계(경로 함수)조차 미착수입니다.
**「곧 그렇게 된다」이지 「지금 그렇다」가 아닙니다.**

⭐ **그리고 C안 설계는 이미 옳은 방향을 골라 두었습니다** — §2-3-2(233행):
*"조회 기록에는 `personId` 를 남긴다 — uid 를 남기면 같은 사람의 계정이 여럿일 때

> **시행 전에 이 방침을 개정해 고지하고 필요한 동의를 받습니다.**"*

#### ②-4. 어긋나는가

| 물음 | 답 | 확신 |
|---|---|---|
| 조회 화면이 **사진**을 보여 주면 549행과 어긋나는가 | 🚨 **어긋납니다.** 549행은 *"이 세 가지 외의 목적으로 이용하지 않습니다"* 라고 **닫는 문장**이고, 「문의 응대를 위한 취급자 열람」은 셋 중 어디에도 없습니다 | **높음** |

⭐ **549행의 마지막 문장이 결정적입니다.**

> *"향후 그러한 이용이 필요해지면 **시행 전에 이 방침을 개정해 고지하고** 필요한
> 동의를 받습니다."*

**방침 스스로가 「새 목적이 생기면 먼저 개정한다」고 약속했습니다.** 그러므로
법 해석을 다투기 전에 **방침 자신의 문언이 순서를 정해 둔 것**입니다:
🚨 **사진을 조회 범위에 넣으려면 방침 개정이 먼저입니다.**

⚠️ **「동의를 받습니다」까지 적혀 있는 것에 주의하십시오.** 문언대로면 새 목적에
**동의**가 필요해 보입니다. 그러나 **명함 주인은 우리 이용자가 아니어서 동의를 받을
상대가 없고**, 이용자 본인의 CS 문의 응대는 §15①4호(계약의 이행)로 볼 여지가
큽니다. **그래서 「동의」가 아니라 「목적 추가 고지」로 가는 것이 맞다고 봅니다만,
이 지점은 판단이 갈릴 수 있어 변호사 확인이 필요합니다**(8절에 올려 둡니다).

> 삭제**하실 수도 있습니다. 기기에 저장된 데이터이므로, **앱을 삭제하시면 그 시점에
> 함께 삭제**됩니다. **이전 계정으로 서버에 백업된 명함은 이 절차로 삭제되지
> 않으며**, 그 계정으로 로그인하시면 복원됩니다."*

**함께 걸린 곳:**

| 위치 | 문언 |
|---|---|
| 초안 **727행** | *"**데이터 암호화 키** — 회원 탈퇴 시 즉시 파기 **(계정 전환 시에는 아래 「계정을 바꾸어 로그인하신 경우」 참조)**"* |
| 초안 **1166행** | *"계정을 바꾸어 로그인하신 경우 이전 계정의 기기 내 데이터는 4번에서 정한 기간이 지난 뒤 **복구·재생할 수 없는 방법으로 삭제**합니다."* |
| 초안 **1145행** | 13번 권리 표 — *"이전 계정 데이터 즉시 삭제 / 설정 탭 → 계정 → 이전 계정 데이터 → 지금 삭제"* |

#### ③-4. 어긋나는가

##### (가) §21 파기 의무와는 **어긋나지 않습니다** — 2026-08-27 메모와 **일치**합니다

**모순 여부를 먼저 확인했습니다**(이 저장소의 원칙 — 조용히 뒤집지 않습니다).
2026-08-27 메모의 결론:

```
⓪  삭제 대상은 「이 기기에 남은 이전 계정의 로컬 데이터」로 좁게 읽는다  ✅ 유지
1   30일은 「파기 유예」가 아니라 「보유 기간」으로 구성한다              ✅ 유지
    → 5일 기준(표준지침 §10①)의 시계는 30일이 지난 뒤에 돈다
3   §21③ 분리 보관 의무는 적용되지 않는다 — 접근 차단의 근거는 §29다     ✅ 유지
```

**뒤집지 않습니다.** 서버에 남는 A 계정의 명함은 **A 계정의 데이터로서 계속
필요**하므로 §21①의 *"불필요하게 되었을 때"* 에 해당하지 않습니다. **관리자가
그것을 볼 수 있다는 사실은 §21 의 문제가 아니라 §29·§28 의 문제입니다.**

##### (나) 🚨 그러나 **739행의 한 문장이 위태롭습니다**

> *"**이 기간에는 어느 계정에서도 조회·이용되지 않고, 회사 서버로 전송되지도
> 않습니다.**"*

| 물음 | 답 |
|---|---|
| 문언 자체가 거짓인가 | ❌ **아닙니다.** 이 문장의 주어는 **「이 기기에 보관된」 이전 계정 명함·사진**이고, 실물이 그렇습니다(`runDue`·`purgeNow` 는 서버를 안 건드리고, 전환 시 서버 쓰기는 새 계정 것만) |
| 그러면 무엇이 문제인가 | ⚠️ **읽는 사람이 「아무도 안 본다」로 읽습니다.** 같은 문단 마지막 문장이 *"서버에 백업된 명함은 이 절차로 삭제되지 않는다"* 라고 말하고 있어, **한 문단 안에서 「안 보인다」와 「남아 있다」가 섞입니다** |
| 관리자 조회가 생기면 | 🚨 **그 서버분을 취급자가 봅니다.** 문단 전체가 「이 데이터는 아무도 못 본다」로 읽히는 상태에서 그것이 사실이 아니게 됩니다 |

##### (다) 🚨 **실제로 빠진 것 하나 — 암호화 키**

**727행이 「아래 문단 참조」로 보내는데, 그 문단(739행)에 「키」라는 말이 한 번도
안 나옵니다**(`grep` 으로 확인). **참조는 걸려 있고 답이 없습니다.**

실물은 이렇습니다:

```
기기의 키 enc_key_v1_<uid>            30일 뒤 지웁니다   (deleteLocalKey — 245행)
서버의 키 users/{uid}.encryptionKeyB64  🚨 남습니다      (파기 코드 없음)
```

📌 **추가 676이 *"암호화 키 행을 빠뜨리지 않았다"* 고 적었는데, 실제로는
**참조 구절만 걸고 문단에는 설명이 없습니다.** 이것은 「센 것이 틀린」 유형이
아니라 **「걸어 놓고 안 채운」** 자리입니다.

##### (라) 정리

| 물음 | 답 | 확신 |
|---|---|---|
| 비대칭이 §21 위반인가 | ❌ **아닙니다** | **높음** |
| 739행이 지금 거짓인가 | ❌ 아닙니다(문언 기준) | **중간~높음** |
| 관리자 조회가 생기면 오독을 일으키는가 | ⚠️ **일으킵니다** | **중간~높음** |
| 727행의 참조가 비어 있는가 | 🚨 **비어 있습니다** | **높음**(실측) |

### ④ 조회 기록에 「어느 계정 키로 열렸는지」를 남길 것인가

#### ④-1. 사실 (실측)

```
암호화키 설계 §5-3    "명함 id → 이 명함을 연 키의 uid    기기 로컬에만 (서버에 안 보낸다)"
관리자 설계 §3-5:334  조회 기록 — "어느 키로 : 성공한 uid  ← 그 명함이 어느 계정 것이었나가
                                                          여기서 드러난다"
C안 설계 §2-3-2:233   "⚠️ 조회 기록에는 personId 를 남긴다 — uid 를 남기면 흩어진다"
```

⚠️ **부딪히는 것은 「설계 대 설계」가 아닙니다.** C안 설계는 이미 **㉢(personId만)**
쪽을 적어 두었고, 관리자 설계 §3-5 가 **㉡(키 uid까지)** 쪽을 적었습니다.
**두 문서가 서로 다른 답을 적어 놓은 상태**입니다 — 이것 자체가 이 저장소가
경고한 *"두 문서가 서로 달랐다"*(추가 675) 유형입니다.

**그리고 기존 감사 기록의 스키마를 확인했습니다**(`firestore.rules:297~313`):

```
isValidAdminAuditEntry(d)
  d.keys().hasOnly(['actorUid','actorEmail','action','target','summary','at'])
  action in ['billing.save','testers.add','testers.remove','appUpdate.save',
             'notice.create','notice.toggle','notice.delete',
             'inquiry.reply','inquiry.markAnswered']       ← 9개 고정 목록
  at == request.time
```

🚨 **필드 집합이 `hasOnly` 로 닫혀 있고, 만료 시각 필드가 없습니다.**
`at` 을 Firestore TTL 필드로 지정하면 **`at` 이 지나는 즉시**(=쓰자마자) 지워집니다.
**지금 스키마로는 「N년 뒤 자동 삭제」를 걸 수 없습니다.**

⭐ **그리고 좋은 선례가 이미 있습니다** — `docs/admin/admin.js:763~791`
`grantSupportCredits` 가 **사유 입력을 필수**로 하고(*"지급 사유 (필수)"*,
비면 거부), 그 사유가 감사 기록에 들어갑니다.

#### ④-2. 관련 법령·조문 — **조회 기록은 법이 요구합니다**

| 조문 | 문언(확인) |
|---|---|
| **보호법 §29** | *"개인정보가 분실·도난·유출·위조·변조 또는 훼손되지 아니하도록 내부 관리계획 수립, **접속기록 보관** 등 대통령령으로 정하는 바에 따라 … 조치를 하여야 한다"* |
| **시행령 §30①5호** | *"개인정보 침해사고 발생에 대응하기 위한 접속기록의 보관 및 위조·변조 방지를 위한 조치로서, **개인정보처리시스템에 접속한 자의 접속일시, 처리내역 등** 접속기록의 저장·점검 및 이의 확인·감독"* |
| **고시 §8①**(제2025-9호) | *"접속기록을 **1년 이상** 보관·관리하여야 한다. 다만 ① 5만명 이상의 정보주체에 관한 개인정보를 처리하는 시스템 ② **고유식별정보 또는 민감정보**를 처리하는 시스템 ③ 기간통신사업자 … 는 **2년 이상**"* |
| **고시 §8②** | 접속기록 등을 점검(2025-10-31 개정으로 주기를 내부관리계획으로 정할 수 있게 완화) |
| **고시 §8③** | 접속기록이 **위·변조·도난·분실되지 않도록** 안전하게 보관 |
| **접속기록의 구성** | 감독기관 해설서 기준 — **① 식별자(계정) ② 접속일시 ③ 접속지 정보 ④ 🚨 처리한 정보주체 정보 ⑤ 수행업무** |

⭐ **④번(처리한 정보주체 정보)이 이번 질문의 답을 절반 줍니다.**

> **「누구의 개인정보를 처리했는지」는 법이 요구하는 접속기록 항목입니다.**
> 그러므로 **㉠(아무것도 안 남긴다)은 선택지가 아닙니다.**

#### ④-3. 🚨 §5-3 과 조회 기록은 **사실 부딪히지 않습니다** — 다른 것을 말합니다

이 항의 핵심입니다. **두 값을 갈라 보아야 합니다.**

```
㉮ 「이 명함이 어느 계정(키) 것이었나」
   = 명함 ↔ 계정 대응표.  전수(全數)로 쌓입니다
   §5-3 이 서버에 안 쌓겠다고 한 것이 바로 이것입니다

㉯ 「관리자가 무엇을 보았나」
   = 열람한 건에 대해서만 남습니다
   법(고시 §8)이 요구하는 것이 이것입니다
```

⭐ **㉯는 ㉮ 없이 만들 수 있습니다.**

```
접속기록에 남길 「처리한 정보주체 정보」 = personId + 열람한 명함 id
→ 고시 §8 의 요구를 충족합니다
→ 🚨 「어느 키로 열렸나」를 따로 적지 않아도, 무엇을 봤는지는 완전히 특정됩니다
```

⚠️ **그리고 C안 ㉯(명함을 `people/{personId}/contacts` 로 옮김)를 이미
채택하셨으므로, 명함 경로에 uid 가 없습니다.** 즉 **경로를 그대로 적기만 하면
자연히 ㉢이 됩니다.** 설계가 이미 그 방향입니다.

📌 **반대로 C안 갈래 ㉮(읽을 때 합치기)를 골랐다면** 경로가
`users/{uid}/contacts/{id}` 라 **명함 id 를 남기는 순간 uid 가 딸려왔을 것**입니다.
⭐ **다른 이유(커서·rules 호출 한도)로 고른 결정이 여기서 개인정보 쪽으로도
유리하게 작용합니다.**

#### ④-4. 후보 셋에 대한 답

| | 후보 | 법적 평가 | 권고 |
|---|---|---|---|
| ㉠ | 조회 기록에 키 uid 를 **안 남긴다** | ⚠️ **부족합니다.** 「키 uid 를 안 남긴다」만으로는 부족한 게 아니라, **어느 정보주체 것인지를 아예 안 남기면** 고시 §8·시행령 §30①5호를 못 채웁니다. **문언이 모호합니다** | ❌ 이 표현대로는 안 됩니다 |
| ㉡ | 남기되 **§5-3 의 판단을 다시 본다** | ⚠️ **권하지 않습니다.** §5-3 이 막는 것(㉮ 전수 대응표)과 조회 기록이 필요한 것(㉯ 열람 건)은 **다른 자료**입니다. 조회 기록 때문에 §5-3 을 뒤집을 필요가 없습니다 | ❌ |
| ㉢ | **personId 만 남기고 uid 는 안 남긴다** | ✅ **법적으로 충분하고 §5-3 과도 충돌하지 않습니다** | ⭐ **권고** |

##### 🚨 다만 ㉢을 그대로 쓰면 부족합니다 — **한 가지를 더해야 합니다**

**personId 「만」 남기면 「어느 명함을 봤는지」가 안 남습니다.** 사고가 났을 때
*"이 명함이 열렸나"* 에 답할 수 없고, 정보주체(명함 주인)가 §35(열람 요구)로
물어와도 답할 수 없습니다.

⭐ **권고안: ㉢＋ — personId · 열람한 명함 id · 열람 건수를 남기고, 「성공한 키의 uid」는 남기지 않는다**

```
누가      관리자 uid · 이메일          (adminAuditLogs 스키마와 같은 모양)
언제      서버 시각                    (고시 §8 「접속일시」)
어디서    접속지 정보(IP)              🚨 지금 adminAuditLogs 에 없습니다 — 고시가 요구합니다
누구 것    personId                     (고시 §8 「처리한 정보주체 정보」)
무엇을    열람한 명함 id 목록 · 건수    (고시 §8 「수행업무」)
사진도?   사진을 열었으면 그 사실       ②-5(가)를 따르면 처음에는 항상 「아니오」
왜        🚨 **사유 — 필수**            grantSupportCredits 와 같은 방식
언제까지  expireAt                     🚨 TTL 용 필드. 지금 스키마에 없습니다
```

🚨 **「성공한 키의 uid」는 남기지 않습니다.** 남겨도 얻는 것이 없습니다 —
명함 id 로 이미 특정되고, 그 명함이 어느 계정 것이었는지는 **필요할 때
`people.uids` 와 대조해 다시 알 수 있습니다.** 반면 남기면 **§5-3 이 막으려던
대응표가 조회한 만큼 서버에 쌓입니다.**

##### ⚠️ 「사유 필수」에 대한 의견

관리자 설계 §3-5(351행)가 *"필수로 하면 기록의 값이 오르고 응대는 느려진다"* 로
열어 두었는데, **필수로 하시기를 권합니다.**

```
1  v2.6/v2.7 이 이미 그렇게 약속했습니다 — 게시본 652행 / 초안 764행:
   "문의 응대 등 정당한 목적이 있는 경우에 한해, **열람 사유와 열람자를
    기록으로 남긴 뒤** 열람합니다"
   ⚠️ 그 문장은 4-1 보존분(거래기록)에 대한 것이라 명함 열람에 바로 걸리지는
      않습니다. 다만 **같은 방침 안에서 명함만 사유 없이 여는 것은 설명하기
      어렵습니다**
2  이미 같은 패턴이 돌고 있습니다 — grantSupportCredits(사유 필수)
3  느려지는 대가는 **관리자가 둘**이라 작습니다
```

#### ④-5. 🚨 조회 기록의 보관 기간 — **2년을 권합니다**

| 요건(고시 §8①) | 이 서비스 | 판단 |
|---|---|---|
| 원칙 | — | **1년 이상** |
| ① 5만명 이상의 정보주체 | ⬜ **확인 못 했습니다** — Firestore 실물을 조회하지 않았습니다 | 🚨 아래 참고 |
| ② 고유식별정보 또는 민감정보 | ❌ **해당 없습니다** — 방침 585·587행이 *"일절 처리하지 않습니다"* · *"얼굴을 인식·추출하지 않습니다"* 로 명시(실측) | 미해당 |
| ③ 기간통신사업자 | ❌ 해당 없음 | 미해당 |

🚨 **①에 대한 의견 — 「정보주체」는 이용자만이 아닙니다.**

```
이용자 수    지금은 테스터 규모 — 5만명에 한참 못 미칩니다
정보주체 수  🚨 **명함 주인까지 셉니다.** 이 앱이 저장하는 개인정보의 정보주체는
             압도적으로 명함 주인입니다
             (2026-08-28 실측 기록: 폴드 103건 · 아이폰 195건 — **한 기기에서**)
```

⚠️ **저는 「5만명을 넘는다」고 말하지 않습니다 — 안 쟀습니다.** 다만 **이용자
250명이 각 200장씩만 등록해도 5만명입니다**(이것은 **계산**입니다, 실측이 아닙니다).
**출시하면 넘어갈 개연성이 큽니다.**

⭐ **그래서 2년을 권하는 진짜 이유는 이것입니다.**

> **넘어간 뒤에 기간을 늘리면, 그 전에 쌓인 기록은 이미 1년으로 지워져 있습니다.**
> **접속기록은 소급해서 만들 수 없습니다.**

**동시에 상한도 정해야 합니다** — 접속기록도 개인정보이고(관리자의 것 + 정보주체
식별자 포함), 목적이 다한 뒤 무한 보관하면 §21① 방향에서 문제가 됩니다.

```

```

##### ⚠️ 구현상 걸림돌 하나 (실측)

`adminAuditLogs` 는 필드가 `hasOnly` 로 6개에 닫혀 있고 **만료 시각 필드가
없습니다.** `at` 을 TTL 필드로 지정하면 **쓰자마자 지워집니다.**

```
권고: 명함 조회 기록은 **별도 컬렉션**(예: cardViewAudits)으로 만들고
      expireAt(= at + 2년) 필드를 두어 Firestore TTL 을 겁니다
      → 기존 adminAuditLogs 스키마를 안 건드립니다
      → 조회 기록만 별도 보관 기간을 갖게 됩니다
```

📌 **이것은 법적 판단이 아니라 실무 지적입니다**(확신: 실측 근거 있음, 설계는
개발 판단).

#### ④-6. 제안 문안

**[문안 F] §15 「취급자의 열람」의 (C-2) 부분에 이미 포함** — 재확인용

```html
<li>이 기록은 「개인정보의 안전성 확보조치 기준」에 따라 <b>2년간</b> 보관한 뒤
파기하며, 회사는 이 기록을 정기적으로 점검합니다. 기록에는 <b>열람한 취급자,
열람 일시, 열람한 대상, 열람 사유</b>가 남으며, <b>이 기록은 열람이 정당했는지를
확인하기 위한 목적으로만</b> 이용합니다.</li>
```

⚠️ **방침의 4번(보유 기간) 표에는 넣지 않기를 권합니다.** 접속기록은
**취급자에 관한 기록**이지 이용자의 개인정보 항목이 아니어서, 4번 표에 섞으면
*"내 개인정보가 2년 보관된다"* 로 읽힙니다. **15번에 두는 것이 시행령 §31①3호
(안전성 확보 조치에 관한 사항)의 자리와도 맞습니다**(확신: 중간).

#### ④-7. 확신의 정도

- **조회 기록이 법으로 요구된다** — **높습니다.** §29 · 시행령 §30①5호 · 고시 §8 전부 명시적입니다.
- **㉠(아무것도 안 남김)이 안 된다** — **높습니다.**
- **㉢＋ 가 §5-3 과 충돌하지 않는다** — **높습니다.** 두 자료의 성격이 다릅니다.
- **「키 uid 를 안 남겨도 법을 충족한다」** — **중간~높습니다.** 고시가 요구하는 것은
  *"처리한 정보주체 정보"* 이지 *"어느 키로 열었나"* 가 아닙니다. 다만 **감독기관이
  더 상세한 기록을 요구할 가능성을 배제하지 못합니다.**
- **보관 기간 2년** — **중간입니다.** 🚨 **법이 정하는 것은 1년이고, 2년은 「5만명
  요건에 걸릴 개연성」에 근거한 권고입니다.** 1년으로 정하셔도 **지금은 위법이 아닙니다.**
- **접속지 정보(IP)를 남겨야 한다** — **중간~높습니다.** 해설서의 5요소에 있으나
  고시 본문의 문언은 *"접속일시, 처리내역 등"* 입니다.
