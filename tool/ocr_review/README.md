# 명함 인식 검수 도구

실물 명함과 인식 결과를 나란히 놓고 **정답을 남기는** 로컬 도구다.
`index.html`을 브라우저로 열면 된다. 설치할 것도, 띄울 서버도 없다.

```bash
open tool/ocr_review/index.html
```

## 왜 필요한가

인식 규칙을 고칠 때마다 "좋아졌나"를 재야 하는데, **정답지가 없으면 잴 수 있는
것이 채움률뿐이다.** 실제로 2026-08-14에 그 함정에 빠졌다 — "오분류 0장"이라고
적어 둔 수치가 사실은 값의 **모양만** 본 것이라, 빈 값은 전부 "정상"으로 세고
있었다(backlog 추가 198).

정답지가 있으면 **정확도**로 잴 수 있다. 그게 이 도구의 목적이다.

## 버튼이 무슨 뜻인가 — **단계로 묶어 뒀다**

이름만으로는 어느 것이 시작이고 어느 것이 끝인지 알기 어렵다는 지적을 받아
(2026-08-18) 툴바를 셋으로 묶었다. **각 버튼에 마우스를 올리면 설명이 뜬다.**

| 묶음 | 버튼 | 무엇을 |
|---|---|---|
| **① 열기** | 인식 결과 열기 | 앱에서 뽑은 `scan_result.tsv` — **여기서 시작한다** |
| | 명함 사진 열기 | 원본 사진 폴더(건너뛰어도 된다) |
| **② 이어하기** | 지난 정답지 | 저번에 저장한 `ocr_truth.tsv`를 불러와 이어 채운다 |
| | 중간 저장분 | 하다 만 작업(`…progress.json`)을 되살린다 |
| **볼 것 고르기** | 칸·범위 선택 | 특정 칸만, 또는 아직 안 본 장만 보기 |
| | 정확도 보기 | 지금까지의 정답으로 칸별 정확도 계산 |
| **③ 저장** | 중간 저장 | **작업 상태**를 남긴다(.json) |
| | **정답지 저장** | **결과물**을 내보낸다(`ocr_truth.tsv`) |

### ⚠️ 파일이 두 가지다 — 이름이 비슷한데 쓰임이 다르다

| | 무엇인가 | 언제 쓰나 |
|---|---|---|
| **정답지** `ocr_truth.tsv` | **결과물.** 각 칸의 정답 | 인식률을 재는 **자**가 된다. 다음 검수 때 **② 지난 정답지**로 불러온다 |
| **중간 저장** `…progress.json` | **작업 상태.** 어디까지 봤는지·무엇을 ✓ 했는지 | **하다 말고 덮을 때.** 다른 컴퓨터로 옮길 때도 이것 |

📌 한 장 볼 때마다 브라우저에도 자동으로 남지만 **브라우저를 지우면 같이
사라진다.** 오래 걸리는 작업이면 **중간 저장**을 한 번씩 눌러 둔다.

## 쓰는 순서

1. 앱 관리자 화면 → **명함 일괄 스캔** → TSV 저장
   (`원문` 칸이 있어야 한다. 없으면 앱이 낡은 빌드다)
2. 기기에서 TSV와 이미지를 꺼낸다

   ```bash
   ADB=~/Library/Android/sdk/platform-tools/adb
   PKG=com.connectiontrace.connection_trace_ai_flutter
   $ADB exec-out run-as $PKG cat app_flutter/card_samples/scan_result.tsv > scan_result.tsv
   ```

3. `index.html`을 열고 **TSV 불러오기** → **이미지 폴더** 선택
4. 한 장씩 확인한다
   - 왼쪽: 실물 이미지 (⟲ ⟳ 회전, `원본 크기`로 확대 — 눕혀 찍힌 명함이 있다)
   - 오른쪽: 인식 원문 + 칸별 `추출값 / 정답`
   - **회색 추출값을 누르면** 그대로 정답이 된다
   - **원문 줄을 누르면** 방금 고른 정답 칸에 들어간다 (타이핑을 줄이는 게 핵심)
   - **앞으로 넘어가면(확인 완료·다음 / 다음 → / →) 그 장은 `확인함(Y)`으로
     기록된다.** 채점기는 Y로 표시된 장만 세므로, 검수한 장은 반드시 앞으로
     넘어가며 지나가야 한다. 뒤로 가기(←)는 재확인이라 Y를 건드리지 않는다
   - <kbd>Ctrl</kbd>+<kbd>Enter</kbd> = 확인 완료·다음
5. **정답지 내보내기** → `ocr_truth.tsv`

## 정답지 작성 규칙 (칸마다 이렇게 적는다)

**원칙: "OCR이 어떻게 읽었나"가 아니라 "명함에 뭐라고 적혀 있나".** 정답지가
이 규칙을 안 지키면 파서가 맞아도 채점이 틀리게 나온다 — 실제로 첫 채점에서
끝 쉼표·괄호·라벨 때문에 정확도가 89%로 눌렸다가, 규칙대로 고치니 94%가
됐다(backlog 추가 212).

| 칸 | 규칙 |
|---|---|
| 전화·휴대폰·사무실 | `010-1234-5678` — 라벨(M/T/F)·국가번호(`+82`) 빼고 하이픈만 |
| 이메일 | **명함 실물 기준**. OCR이 `,kr`로 읽었어도 `.kr`, 공백 없이 |
| 주소 | 끝 쉼표 빼기 (`…135,` → `…135`) |
| 우편번호 | 숫자만 (`(08511)` → `08511`) |
| 직함 | 이름 빼고 직함·부서만 |
| 회사 | 명함에 인쇄된 대표 표기 하나 |

## ⚠️ 진행 상황 저장

Chrome은 `file://`에서 자동 저장(localStorage)을 막는다. 그런 브라우저에서는
화면 위에 **경고가 뜬다** — 그때는 중간중간 **진행 저장**을 눌러
`ocr_review_progress.json`으로 남기고, 다음에 **진행 불러오기**로 이어서 한다.

Safari는 대개 자동 저장이 된다. 어느 쪽이든 검수가 끝나면 정답지를 내보내 둘 것.

## 정답지가 생기면 — 채점하기

정답지를 내보낸 뒤 이렇게 돌리면 **필드별 정확도**가 나온다.

```bash
TSV=~/card-ocr-data/scan_result.tsv \
TRUTH=~/card-ocr-data/ocr_truth.tsv \
flutter test test/ocr_accuracy_score_test.dart
```

출력 예:

```
검수 완료 42장 / 정답지 103장

=== 필드별 정확도 ===
이름    일치38 틀림2 미검출2 오검출0 둘다빔0 → 90%
회사    일치31 틀림5 미검출4 오검출1 둘다빔1 → 76%
...
전체 정확도: 84% (301 / 358)

=== 틀린 것 57건 ===
  틀림  card_56.png [회사] "크림하우스주)" ≠ "크림하우스(주)"
  ...
```

- **확인함(Y)으로 표시한 명함만** 센다 — 안 본 것을 정답으로 쓰면 그게 다시 추측이다
- 원문(rawLines)을 **지금 파서에 다시 먹여** 채점하므로, 규칙을 고칠 때마다 바로
  다시 돌리면 된다. 기기가 필요 없다
- ⚠️ **진짜 숫자는 이 채점기 쪽이다.** 검수 도구 화면의 집계는 TSV에 저장된
  **옛 추출값**을 비교하지만, 채점기는 **원문을 지금 파서에 다시 먹인다.** 그래서
  둘이 다르다(첫 채점 때 도구 이름 65% vs 채점기 94%). 도구 집계는 참고용이고,
  파서 개선 효과는 채점기로 본다
- 전부 검수하지 않아도 된다. **20~30장만 해도** 어느 칸이 약한지 드러난다

## 비어 있는 칸을 어떻게 적을 것인가

**명함에 그 값이 없으면 정답 칸을 비운 채로 둔다.** 집계에서 "둘 다 빔"으로
세고 **분모에서 뺀다** — 없는 것을 못 찾았다고 점수를 깎으면 안 되기 때문이다.

실제로 표본의 `card_134`(삼성SDI)는 전화·이메일·주소가 명함에 아예 없다.
처음 결함 목록은 이걸 "미검출"로 적어 두어서, 없는 문제를 쫓을 뻔했다.

| 집계 항목 | 뜻 |
|---|---|
| 일치 | 추출값 = 정답 |
| 틀림 | 둘 다 값이 있는데 다름 |
| **미검출** | 명함에는 있는데 인식이 못 찾음 |
| **오검출** | 명함에 없는데 값이 들어감 |
| 둘 다 빔 | 명함에 없고 인식도 안 함 → **분모에서 제외** |

정확도 = 일치 ÷ (일치 + 틀림 + 미검출 + 오검출)

## `vision_measure.swift` — 기기 없이 줄·낱말을 뽑는 자 (추가 405·409)

파서를 고칠 때 명함별 대조가 필요한데, 기기로 재려면 빌드→설치→스캔에 수십 분이
든다. 이 도구는 **맥에서 즉시** 앱과 **같은 형식**의 줄을 만들어 파서 테스트에
바로 먹인다.

```bash
swiftc -O tool/ocr_review/vision_measure.swift -o /tmp/vision_measure
/tmp/vision_measure 명함1.jpg 명함2.jpg > measure_vision_v2.tsv
```

### ⚠️ 이 자의 숫자는 실적이 아니다

**Vision은 ML Kit이 아니다.** 2026-08-22에 이 자로 84%를 봤는데 **기기에서 실제로
재니 75%**였다 — 줄 나눔이 달라 경로와 결과가 갈린다. 방향을 보는 자로만 쓰고,
**판정은 기기 측정으로** 한다.

### 형식 v3 — 다섯 칸, 낱말에 너비가 붙는다 (앱의 `ocr_measure_dump.dart`와 같다)

```
사진이름 \t 줄칸 \t 경로 \t 뽑은이름 \t 토큰칸
토큰칸:  글자 · 높이 · 위 · 왼 · **너비**(v3부터)
```

⚠️ 가로 값(왼·너비)은 **가로세로 비를 곱해** 세로와 같은 자로 맞춰 찍는다.
그래야 "틈이 글자 높이의 몇 배인가"를 바로 견줄 수 있다.

3·4번 칸은 앱만 채울 수 있어 **비워 둔다**(파서를 태운 뒤 그 자리에 넣는다).
높이·좌표는 **이미지 높이 대비 비율 × 1000**이라 사진 크기가 달라도 견줄 수 있다.

📌 **토큰 칸이 왜 생겼나**: 줄 높이는 좌우로 나란한 줄을 **한 행으로 합친 뒤의
값**이고, 그때 높이를 **가장 큰 것으로** 잡는다. "홍길동 ㈜회사이름"처럼 나란하면
**회사까지 이름만큼 커 보인다.**

⭐ **실측(Vision, 40장)**: 낱말이 둘 이상인 줄 276개 중 **106개(38%)**에서 낱말
높이가 **1.2배 이상 갈렸고**, 그런 줄이 있는 명함이 **40장 중 34장**이었다.
합친 줄 높이는 이 차이를 통째로 지운다.

⚠️ 위 38%는 **Vision으로 잰 값**이다. 앱이 쓰는 ML Kit 수치는 기기 측정에서 나온다.

### ⚠️ 결과 파일은 제3자 개인정보다

이름·전화·이메일·주소가 그대로 담긴다. `connection-sense-assets/명함데이터/`
(폴더 700) 규칙을 따르고 **저장소 안에 두지 않는다.**

## `score_measure.py` — 측정본을 정답지와 대조해 채점한다 (추가 405·409)

```bash
python3 tool/ocr_review/score_measure.py <측정.tsv> <정답지.tsv>
```

사진 이름과 정답지 순번이 이어지지 않으므로(찍은 순서 ≠ 등록 순서) **이메일·
전화번호로 내용을 맞춘다.**

### ⚠️ 여기서 세 번 틀렸다 — 같은 함정을 피하려면

| 함정 | 무엇이 잘못됐나 | 어떻게 세야 하나 |
|---|---|---|
| 정답 이름에 영문이 붙어 있다 | `홍길동 Gildong Hong`을 파서 출력과 그대로 견줘 **맞은 것을 틀렸다고** 셌다(84%를 66%로 보고) | 양쪽 다 **한글만** 남겨 견준다 |
| `채점제외`를 명함 단위로 읽었다 | 25장을 통째로 버려 표본이 70장으로 줄었다 | **칸 단위**다(`휴대폰`·`이름`…). 이름 채점에서 빠지는 건 **5장뿐** |
| 한글만 남긴 결과가 비면 "빈 값" | 파서가 **영문 이름**을 낸 것까지 "안 채웠다"로 셌다 | 빈 값은 **파서가 정말 아무것도 안 낸 것**만 |

📌 셋 다 **숫자가 그럴듯해서** 안 드러났다. 채점기를 고칠 때는 **이미 아는
측정본으로 알려진 값이 재현되는지** 먼저 확인한다.

### 기준선 (2026-08-22 기기 측정 · #445 이전)

```
채점 91장   맞음 70 · 틀림 18 · 빈 값 3   →  76.9%
(정답 이름이 임의값인 5장과 정답지에서 못 찾은 4장은 뺐다)
```

### ⚠️ 거칠게 재면 **방향이 뒤집힌다** (2026-08-23 실측)

마지막 절은 두 가지로 잰다. **아무거나 가장 큰 것**을 집는 것과, **이름처럼
생긴 후보 안에서** 가장 큰 것을 집는 것이다. Vision 93장으로 재 보니:

```
아무거나 큰 것       행 15%  ·  낱말 10%   ← 낱말이 더 나쁘다
이름처럼 생긴 것만   행 24%  ·  낱말 50%   ← 낱말이 두 배 낫다
```

📌 **거친 자로만 봤으면 "낱말 높이는 쓸모없다"고 접었을 것이다.** 명함에서 가장
큰 글자는 대개 **회사 로고**라, 후보를 안 좁히면 크기 신호가 실제보다 약해
보인다. 그래서 둘 다 찍는다.

⚠️ 위 수치는 **Vision**으로 잰 것이고, 앱은 ML Kit을 쓴다. 방향만 본다.

### ⚠️ 마지막 절은 규칙이 아니다

"가장 큰 행 vs 가장 큰 낱말"은 **그렇게 골랐다면 어땠을지를 세어 보는 것**이지
파서를 그렇게 바꾸는 것이 아니다. 실제 파서는 규칙을 먼저 보고 **확신이 없을
때만** 크기를 쓰므로, 그 숫자를 파서 정확도로 읽으면 안 된다.

## 사진 한 장으로 파서를 재현하는 법 (2026-08-29, 추가 590)

**기기에 깔지 않고** 명함 사진 하나로 *"파서가 무엇을 고르는지"*를 그 자리에서
본다. 2026-08-29에 이 경로로 **20분 만에** 주소 결함의 원인을 짚었다 — 예전
방식(빌드→설치→스캔)이면 수십 분이 든다.

```bash
# 1. 사진을 700 폴더에 둔다 (제3자 개인정보다)
mkdir -p ../connection-sense-assets/명함데이터/재현_YYYY-MM-DD
chmod 700 ../connection-sense-assets/명함데이터/재현_YYYY-MM-DD

# 2. 맥 Vision 으로 읽는다
swiftc -O tool/ocr_review/vision_measure.swift -o /tmp/vision_measure
/tmp/vision_measure card.jpg > lines.tsv

# 3. 줄만 뽑는다 (2번째 칸, 줄 사이는 \x01, 줄 안은 \x02)
python3 -c "
import io
row=io.open('lines.tsv',encoding='utf-8').read().rstrip().split('\t')
print('\n'.join(p.split('\x02')[0] for p in row[1].split('\x01') if p))
```

### ⭐ 어느 칸이 맞고 어느 칸이 틀린지로 원인을 좁힌다

2026-08-29에 실제로 쓴 판별법이다. globe2030님이 *"직함과 부서 빼고 모두
잘못"* → *"휴대폰까지 정상"* 이라고 좁혀 주셨을 때, 그 대비가 답을 가리켰다.

```
키워드·숫자 모양으로 찾는 칸    직함·부서·전화·이메일
   → 줄이 엉켜도 걸린다

줄을 골라 쓰는 칸              이름·회사·주소
   → 줄 나눔이 어긋나면 틀린다
```

| 무엇이 틀렸나 | 어디를 보나 |
|---|---|
| **줄로 고르는 칸만** 틀렸다 | **배치** — 줄 나눔·후보 선택 규칙 |
| **패턴으로 찾는 칸도** 틀렸다 | **오독** — 글자 자체가 잘못 읽혔다 |
| **한 칸만** 틀렸다 | 그 칸의 규칙 |

📌 그날 주소 결함이 정확히 첫 줄이었다 — 회사 이름 줄
(`FC서울프로축구단 | GS칼텍스서울Kixx배구단`)이 **「프로」의 `로`, 「축구단」의
`구`**에 걸려 주소로 잡혔고, **진짜 주소 줄이 바로 아래 있었는데도** 먼저 걸린
쪽이 이겼다.
